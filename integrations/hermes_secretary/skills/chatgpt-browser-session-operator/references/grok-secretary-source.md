# ChatGPT browser session operator

These are heuristics, not iron rules. Judge each session on what it actually shows, try sensible variations, and append what you learn to Lessons learned.

Applies only to ChatGPT in browsers. The Codex desktop app has its own watcher rules.

## Ground rules
- Paste text from the clipboard; never speed-type, because fast typing can trigger automation throttling.
- Read the chat before acting. Write a prompt tailored to where it stopped rather than a bare "resume" whenever you can.
- Don't force it. Repeated continue prompts get a session throttled harder. Space retries out.
- Pro mode is limited to about 200 turns per account per week; Extra High is unlimited. Spend Pro turns deliberately.
- Before acting, check whether the human (or a browser-control plugin) is driving that window right now; if so, leave it.
- When prompting an Extra High session, always explicitly ask it to run a full census/bootstrap (read the repo, PRs, CI, handoffs and current state) before answering or acting; otherwise it may give a shallow, lazy answer.
- Don't send a message to a session that's still running, especially in Pro mode; wait for the turn to finish. Extra High sessions can sometimes accept mid-turn steering when it's genuinely needed.
- Keep learning: record each new bug and the workaround that fixed it, so the playbook improves over time.

## Triage by symptom
1. **"Connection interrupted. Waiting for the complete answer"**: the session is usually stuck. Press the stop button (white circle with a black square), wait until it turns back into the normal send button (white or blue circle with the audio-bars icon), then paste a resume prompt and send.
2. **Red dot / "Error in message stream" / "Streaming failed"** (usually harmless): escalate in steps, one per turn, spacing them out. (a) Paste a resume prompt; it usually picks back up. (b) If that fails, switch to Extra High, ask it to census, rebase and checkpoint, then switch back to Pro next turn to continue. (c) If it keeps failing, the session is likely context-bloated: while it can still respond, ask it to checkpoint and write a detailed handoff, then copy-paste that handoff into a new Pro session (step 9).
3. **"Thinking failed" in Pro mode**: switch the model picker to Extra High for one turn and ask it to rebase, resolve conflicts, checkpoint and write a short status. After that turn finishes, switch back to Pro and ask it to continue from the checkpoint.
4. **Blue dot**: the session is probably asking for permission. Open it and click **Always allow** so it won't ask again that session.
5. **"Could not load this ChatGPT conversation" / "cannot load this conversation right now"**: (a) hard refresh the chat (Cmd+Shift+R on macOS). (b) If still failing, click the "Clear Cache" extension once (grey toolbar icon, tooltip "Clear Cache"; its position varies per browser, so locate it by capture or in the puzzle-piece menu), wait for it to turn green (about 30 s), then reload. It clears the whole site's cache, so one click per profile covers every failing chat. (c) If it still won't load, start a new recovery session for each such chat (step 9); don't keep retrying. **When many chats won't load, test with one new session** (Chris, Oct 21, 2026). Some chats never recover from could-not-load, which is a ChatGPT bug, so relaunching as a new session is often the only fix. If many of a profile's chats fail after the hard refresh and Clear Cache, start ONE new recovery Pro chat (step 9) for the most important dead chat. If that new chat loads and starts running, the account isn't throttled: relaunch the other dead chats as new recovery sessions too, one at a time. If the new chat itself can't load or start (the Oct 20 pattern), or chats say "You've hit your limit", it's an account-level throttle: stop, make no more new chats, leave the profile alone for about an hour, then Clear Cache and hard refresh again.
6. **"Message delivery timed out" with a Retry button**: click Retry once and verify it streams.
7. **Stopped, waiting on CI, an independent reviewer, or bounded workers**: leave it and come back in about 30 minutes, then start a new turn asking it to resume its project.
8. **Stopped and directionless**: ask it to rebase, work out what's still needed to finish its project, pick the next step, and keep working.
9. **Too long, too old, or repeatedly fails to restart**: start a new Pro-mode session in the same project, asking it to recover the old session, giving it the old chat's full URL and conversation id (new sessions can read the previous session's working memory and processes, plus GitHub, Slack and handoffs) and continue its project.
10. **Pro mode lost tool/write access**: switch the session to Extra High. Ask it to save its work, finish what it can this turn, checkpoint, and write a detailed handoff. Collect the handoff (zip, .md, or plain text) and paste or upload it into a new Pro-mode session to continue with tools.

## Silent stalls
- Some chats show no blue dot, no red error and no spinner, yet have quietly stopped (blank tail, no loading icon) and need servicing. On a regular round, open each project chat without a spinner and read its tail rather than trusting the sidebar indicators; treat a blank or unexplained stop as a stall and handle it per the triage above.

## Keeping each Pro account busy
- Target full throttle: about 7-11 chats running at once per account (see "Target state is full throttle" below; the old 4-5 projects guidance is superseded).
- To fill an open slot when you don't know what to launch: ask an Extra High session (usually the strongest advisor) or ChatGPT Dot (a lighter second opinion) which previously orphaned project is most worth restarting. Confirm no other session is already working on it.
- Write the census, masterplan and handoff in a Pro-mode session, not Extra High: Pro does the deepest census and works out the best next steps itself. That Pro session (or a fresh Pro session given its handoff) then drives the project.

- When a session decides on its own that it needs a fresh chat (e.g. its write tools were blocked) and writes a checkpoint plus a "continue from this exact point" handoff: copy that handoff verbatim (use the message's copy button, never retype hashes), open a new Pro chat in the same project, paste and send it, confirm it's working, then archive the old chat.

## Naming for continuity
- When a new chat takes over a project (recovery, handoff, relaunch), rename it to the old chat's name plus the next number (Chris, Oct 21, 2026): "Resume Portfolio Terminal" becomes "Resume Portfolio Terminal 2", and "Resume Fabric Implementation 2" becomes "... 3". That way the highest number is always the newest chat for that project. Keep the old chat until the new one confirms it has recovered the project and is actually working, then archive the old one (same or a later run).
- **Write-tool blocked chats get a handoff into a new session** (Chris, Oct 21, 2026). When a chat reports that "OpenAI's safety checks blocked" a connector action (e.g. marking a PR Ready for review), or keeps failing write actions while reads work, that chat is probably write-tool blocked and won't recover. Don't keep nudging it. Switch its pill to Extra High and send one short message asking it to save a checkpoint and write a complete handoff for a new session. Then start a new Pro chat in the same project. Paste the handoff into it, plus the old chat's URL and conversation ID, and upload any attachments the old chat relied on that aren't already on GitHub. Name it with the next number (rule above). Archive the old chat once the new one confirms it has recovered the project and is working. If the blocked action is a one-click human step that Chris has approved (e.g. marking a PR ready), I can do that step through my own GitHub connection as well.
- **Click inactive "running" sessions to reconnect them; Stop and resume on "Connection interrupted"** (Chris, Oct 21, 2026). A chat that should be running can sit disconnected in a background tab, showing no live stream until it's clicked open. On every pass, open such chats (in a fresh tab or by switching to the tab that holds them) so they reconnect and the stream carries on. If the chat shows the grey banner "Connection interrupted. Waiting for the complete answer" (often under a tool step like "Opened Studio Direct", with the black Stop button still showing), press Stop, wait until it has fully stopped (the send arrow is back and no spinner), then send the short continue prompt ("Please continue with [project]. Pick up from your latest checkpoint and carry on with the next most important work."). Don't send while the Stop button is still showing.
- **Independent reviews go through the Subagent Fabric** (Chris, Oct 21, 2026). The normal way for a session to get an independent review is to use the Subagent Fabric to spawn a reviewer subagent. If a session stalls waiting on a review or a bridge reviewer, the one sentence of context in the continue prompt can say: "Use the Subagent Fabric to spawn a subagent for the independent review." Only offer Chris a native or local reviewer when the Fabric launches themselves are failing. Avoid vague names like "Resume pro mode" or "Recover session"; if you find one, open it, work out its project, and rename it.

## Archiving
- Archive throwaway helper chats (e.g. the Extra High launcher chat) once they've served their purpose.
- Archive superseded or dead chats only after their recovery chat is running independently and has recovered all the data.

## Multilogin freeze (happens 2-3 times a day)
Usually caused by many Pro sessions sharing the ChatGPT browser-control plugin. Fix: force-quit all the Multilogin profile browsers, force-quit Multilogin, relaunch Multilogin, and reopen each profile.

## Helping a session past obstacles
- Ask a support agent for help via Slack.
- Start an Extra-High session in a native Chrome business profile for bounded fixes (keep Pro for long runs on the personal Pro accounts).
- Launch a Codex or Claude app session to fix the blocker for it.
- Material blocker a web session can't do itself (authenticated logins, local machine access, etc.): ask it to write a handoff for execution on local Codex (usually best for logins/local work), or to use the subagent fabric.
- You may help log in to services so sessions can use them, using saved browser/password-manager logins. Never type or store an OS admin/sudo or password-manager unlock password; if one is needed, ask the human to do just that step.

## Orientation
Each browser window shows its account and profile name at the top left of the sidebar (a profile badge plus the ChatGPT account name). Confirm which account you're in before acting. Windows may be spread across several monitors: navigate them where they sit rather than consolidating, and capture a specific window by id when it's covered by others.

## Lessons learned (append as you go)
- Foreground clicks steal keyboard focus; if the human is typing, a stray keystroke can land in a chat composer. **Chris (Oct 21, 2026): "u can do work even if im working too"**, so don't wait for him to step away. Before each click or paste, wait for a short gap of about 3-5 s with no input, then re-check which window is focused before pasting. Only hold off on a chat he is visibly working in.
- Background (non-focusing) clicks don't open ChatGPT's model picker; switching modes needs a real foreground click.
- A "debugging this browser" banner means a browser-control plugin may be driving the window; windows can change chats under you, so re-capture right before acting.
- Capture a covered window by its window id instead of moving it.
- A chat that won't load ("Could not load this ChatGPT conversation") can't hand itself off. The recovery Pro chat has to rebuild state from the old session's working memory and any processes it left running, cross-checked against GitHub (PRs, branches, CI, checkpoint comments), Slack and handoff files, so give it the old chat's title, full URL and conversation id. Keep the old chat until the new one confirms it has recovered everything.
- **A new chat that won't load confirms throttling** (Oct 20, 2026). If even a brand-new chat goes straight to "Could not load this ChatGPT conversation", the account is throttled. Context limits and single-chat bugs still let you open a new session. Don't create more replacements: wait about an hour, then Clear Cache and hard refresh. The flip side (Chris, Oct 21): if the single test chat does load and run, the account is fine, so go ahead and relaunch the other stuck chats as new sessions. Treat it as a sign we pushed too many Pro turns, so go easier on that account afterward.
- **Throttle timing (working theory, Oct 20, 2026).** Reports say ChatGPT web runs on a hidden rolling window of about 5 hours that starts with the first session. Hit its token cap and the account goes to could-not-load until the window resets. Note when you first see the block, check once an hour (Clear Cache plus a hard refresh), and expect it back within about 5 hours. It can clear much sooner: Y7's throttle on Oct 20 cleared after about 50 minutes, so the hourly check matters. Spread Pro turns evenly across the window instead of bursting.
- **Peekaboo v4 clicking on ChatGPT web content** (Oct 20, 2026). Background clicks fail on web content ("no pressable accessibility element"), and `click --at x,y --window-id W --foreground` refuses because peekaboo can't see the focused window. What works: `peekaboo window focus --app PID:x --window-id W`, then `peekaboo click --at GX,GY --global --foreground --input-strategy synthOnly` with global screen coordinates (window origin plus the point scaled by window width / capture width). Paste with `peekaboo press cmd+v --foreground` and send with `peekaboo press return --foreground`.
- **Cmd can stay latched after a synthetic Cmd chord** (Oct 20, 2026). After `press cmd+a`/`cmd+v` with no Return afterwards, the next sidebar clicks acted as Cmd-clicks and quietly opened background tabs. After any modifier chord, release it with `osascript -e 'tell application "System Events" to key up command'`, and close any stray tabs you created.
- **Your own synthetic input resets HID idle.** Record the time of your last click/keypress and only treat the Mac as busy when idle time is clearly shorter than the time since your own last input.
- **The sidebar reorders as chats start running** (running chats jump to the top of the project list). Re-capture right before every sidebar click; a stale position opens the wrong chat.
- **"Error in message stream" can hide a pending permission card** (Oct 20, 2026, KRIS KE and Y7). After pasting the continue prompt, a Studio Direct card (Write File / Start Terminal Process) surfaced right away below the message; the turn only ran after Always allow. Always re-capture and scroll to the bottom after sending a nudge.
- **Throttle signature: the running chat keeps streaming in its own tab, but every fresh load of another chat says "Could not load"** (ModernLuxe, 5:27 AM PT Oct 20). When testing loadability, never navigate the tab that holds a running chat away; if the account is throttled you lose the live view and can't get it back.
- **Sessions can hit third-party sign-in cards** (e.g. "Sign in to tencent.com" with WeChat/QQ/email options, "Take over to sign in" / "Not now"). Don't click Not now; that's a login only Chris can do unless a saved browser login covers it, so report it.
- **Peekaboo bridge error "Bridge operation receipt does not match operation facts"** (Oct 20, 2026, 5:41 AM PT). `window list`, `see`, `click` and `press` all failed through the remote bridge host. Adding `--no-remote` to every peekaboo command fixed it. Also, CopyToBox only reads files under the user's home folder (e.g. `~/gwcap/`), not `/tmp`, so save downscaled captures there.
- **A blue dot can just mean an unread finished turn**, not a card (KRIS KE "Redesign BioCatalyst User First", Oct 20). Read the tail: if the turn ended waiting on something that has since cleared (e.g. "after Studio recovers" while Studio Direct now works in other chats), nudge it with the continue prompt and tell it the wait is over.
- **A chat can be running with no sidebar spinner** (Y7 "Continue Prophet Implementation", Oct 20, 6:13 AM PT): the sidebar showed nothing, but the composer had the black stop button and the tail said "Preparing preview...". Check the composer button before treating a no-indicator chat as a silent stall; a stop button means leave it.
- **Clear Cache asks for confirmation** (Oct 20, 2026, ModernLuxe). Clicking the grey recycle-arrows icon opens a popup, "Clear cache for the active tab from the last day?", with a green Clear button. Nothing is cleared until you click Clear; the icon turns green while it works. Re-capture after the first click so you don't mistake the popup for a finished clear.
- **Clear Cache plus hard refresh can lift a throttle that a hard refresh alone doesn't** (ModernLuxe, Oct 20). First block about 5:27 AM PT; a plain hard refresh at 6:50 still said could-not-load; Clear Cache at about 6:53, then a hard refresh at 7:08, and every chat loaded again (about 1 h 40 min after the first block). Wait ~15 minutes after the clear before re-testing.
- **To reach a permission card below the fold, click the round down-arrow button just above the composer** (it jumps the chat to the bottom). Synthetic `peekaboo scroll` often doesn't move ChatGPT's chat pane, especially on windows with negative global y (the top monitors).
- **A "Connection interrupted" chat may reconnect on its own.** On Y7 (Oct 20, 7:04 AM PT) the banner vanished and the stop button stayed after one click near it; the turn was still running. Re-capture after pressing stop and only send the continue prompt if the composer shows the normal send button.
- **When a session asks for a real human decision** (e.g. "approve this worktree disposition and publication route"), don't approve it yourself in the nudge; Auto-review blocks that send. Leave the chat and report the exact ask to Chris.
- **A pending permission card can also hide the sidebar spinner** (ModernLuxe "Installer Recovery Check", Oct 20, 7:30 AM PT). The chat showed no indicator at all and the composer showed the send button, but jumping to the bottom revealed a GitHub Update Issue Comment card. Treat "no spinner + send button" as "open it and jump to the bottom", not as "finished".
- **"That approval request is no longer active. Please retry the action..." ends the turn** (ModernLuxe "Upgrade Sector Central Design", Oct 20). A card that waited too long expires and the session stops. Nudge it with the continue prompt, naming the exact action it was doing and asking it to retry.
- **Switching Pro to Extra High in the current UI** (Oct 20, 2026): click the "Pro ⌄" pill in the composer. A popup opens with a "Pro ›" header over a thinking-effort slider; Pro is the rightmost notch and Extra High is the next notch to the left (the label above the slider changes to "Extra High"). The "Pro ›" header itself opens the model list (GPT-6 / GPT-5.6 Sol), not the effort, so don't use it. Press Escape to close, then paste the prompt; the composer pill then reads "Extra High".
- **Chat timestamps in the Multilogin profiles read about 2 hours ahead of Pacific** (e.g. "Today 9:26 AM" for a 7:26 AM PT send), because the profiles run in a Central-time browser timezone. Convert before judging how long ago a nudge was.
- **A running chat opened fresh can show "Connection interrupted. Waiting for the complete answer" while its sidebar spinner keeps going** (KRIS KE "BioCatalyst R10 Correction Admission", 7:20 AM PT Oct 20). Superseded Oct 21, 2026 (Chris): the banner means the stream is broken even if the spinner keeps going, so press Stop, wait for it to fully stop, then send the short continue prompt.
- **A long-waiting hidden permission card can flip to "Error in message stream" the moment you approve it** (Y7 "Recover MedTech Session", 8:12 AM PT Oct 20). The sidebar showed no indicator; jumping to the bottom revealed a GitHub Update Pull Request card, Always allow started a spinner, then seconds later the sidebar showed a red dot and the tail said Error in message stream. Send the continue prompt, tell the session which approved action may not have gone through so it can redo it, and jump to the bottom again because a fresh card (here Studio Direct Start Terminal Process) often follows.
- **After an Extra High rebase turn finishes, the composer stays on Extra High.** Before the follow-up continue prompt, click the "Extra High ⌄" pill, drag or click the slider to its rightmost notch (header reads "Pro"), press Escape, and confirm the pill reads "Pro" before pasting.
- **"Always allow" doesn't carry over to the next turn** (Y7 "Recover MedTech Session", Oct 20). The same GitHub Update Pull Request card it got Always allow for at 8:12 AM PT was back, hidden and unanswered, by 8:41 after the follow-up nudge. Expect repeat cards for the same tool after each new turn, and check running chats with a quiet sidebar for a waiting card every run.
- **Open other chats in a fresh tab, not the live one** (Oct 20, 2026, 9:12 AM PT, ModernLuxe). Clicking a sidebar chat in the tab that shows a running chat navigates that live view away, and if the account has just been throttled the new chat says "Could not load" (browser Back brought the live view back that time). Instead press Cmd+T, paste `https://chatgpt.com/`, Return, then click the chat in that tab's sidebar; close the helper tab with Cmd+W when done. A fresh tab's sidebar often shows no spinners for chats running in other tabs, so judge those from the composer button. (`peekaboo click` has no `--modifiers` option, so Cmd-click isn't available.)
- **Two accounts can throttle at the same moment** (Oct 20, 2026, ~9:12 AM PT). ModernLuxe/ChatGPT1 and KRIS KE/ChatGPT2 both went to could-not-load on every fresh load (two chats each) while their running chats kept streaming in their own tabs, and Y7/ChatGPT3 loaded fine. ModernLuxe's second throttle of the day came about 2 hours after its first cleared. Treat each per profile: test with one new session first (step 5); if that fails too, retry Clear Cache plus hard refresh about an hour later.
- **Colored labels in the tab strip are collapsed tab groups, not tabs** (ModernLuxe, Oct 20, 2026, 9:40 AM PT). A label like "Installer Recover" turned out to be a group holding unrelated tabs, so a running chat named in a sidebar is not necessarily open in any tab. Keyboard tab switching (Cmd+9, Ctrl+Tab) jumps across hidden group members and lands on unrelated pages. Click a specific visible tab instead, and put the window back on the tab it started on before leaving.

- **The confirmation popup for Clear Cache doesn't appear in every profile** (Oct 20, 2026, 10:16 AM PT, KRIS KE). One click on the grey icon turned it green straight away with no "Clear" prompt, while ModernLuxe still asked. Re-capture after the click: green icon means clearing has started, a popup means you still need to click Clear.
- **A blue dot on a running chat can hide a brand-new tool card** (Y7 "Recover MedTech Session", 10:13 AM PT Oct 20). An hour earlier the same blue dot was just unread progress; this time a hidden "Allow ChatGPT to use Firecrawl?" card was holding the turn. Open every blue-dot chat each run and check the bottom, even if it was harmless last time.

Once the page reloaded, the failed Pro message (sent 8:11) was gone from the transcript, the pill had fallen back to Extra High, and the failed text was back in the composer as a draft. A ModernLuxe chat said "Could not load" on its first fresh-tab open, but one Cmd+Shift+R (wait ~20 s, it shows a spinner first) loaded it, so that account was fine. The traffic lights had gone grey and the composer stayed empty. Run `peekaboo window focus` again right before the composer click, and capture to confirm the pasted text is in the composer before pressing Return.

## The continue prompt (short and plain)
**Changed Oct 20, 2026 (Chris).** The old long "marathon" prompt (time targets like "aim for 60-100+ minutes", step-by-step rules on how to handle blockers and waits, "turns are scarce") looked like steering/manipulation to ChatGPT. Sessions that got it often went straight to "Thinking failed" (seen on ModernLuxe "Upgrade Sector Central Design", nudged 7:35 AM PT), and it likely feeds the throttling. Never send that style again.

Send a short, natural nudge of 1-3 sentences, the way a person would. Adapt it from the chat tail:

> Please continue with [project name]. Pick up from your latest checkpoint and carry on with the next most important work.

Optionally add ONE plain sentence of real context, only if it applies, for example: "Your last turn stopped because the approval for X expired, so please retry it." / "The CI run you were waiting on has finished." / "The Tencent sign-in is still unavailable, so work around it."

Don't include: time or duration targets, words like "marathon" or "don't stop", lists of how to handle blockers/waits, claims about scarce turns, or long capability lists. A bare one-word "resume" is still too thin; the short sentence above is the default.

When the session reports a big blocker, act on it like Chris would: help with logins (saved logins only, never the Mac admin or Passwords unlock password), hand work to local Codex or the subagent fabric, approve cards, fix the environment. Then tell the session briefly that it's cleared. Message Chris only if no tool you have can do it.

## Pacing, census and cleanup (owner guidance, Oct 22 2026)
- **Pace like a casual real user, not a power user.** Throttling, freezes and error rates go up with robotic usage. Let chats cool off for about 30 minutes between nudges, rotate across every chat that needs continuing (often more than the 5 visible ones), and don't re-continue the same chat over and over.
- **Is it actually finished?** Before reviving a chat, decide whether it has officially completed its job (final closeout, merged PR, handoff done) or genuinely still needs reviving.
- **Hidden permission waits.** A chat that looks empty or idle may be waiting on a permission card with no blue dot. Sessions ask for permission on almost every plugin. Open and check each chat, and accept the card (scroll down if it's under the message box). Approve every card, including ones tagged "Suspicious Instruction" (Chris, Oct 22, 10:12 AM: OpenAI's checks are too broad and flag his custom plugins). Open the dropdown next to Allow and pick "Allow <tool> for this conversation" (or Always allow) so it won't ask again; Allow once only if nothing broader exists. Never park a chat waiting on Chris for a card or blocker; work the blocker ladder yourself.
- **Project folder.** If the project folder in the sidebar is collapsed, expand it, then press "See more" to reveal the hidden chats.
- **Extra High vs Pro.** Extra High keeps full write-tool access (Pro sometimes loses it) and can run more perpetually, but each turn caps at about 20 minutes, so it needs frequent new turns, and it's weaker than Pro.
- **Periodic tab and cache cleanup.** When most sessions on a profile are on a break (none mid-turn driving the browser, no "started debugging this browser" banner) and the owner isn't using that window:
  1. Close the extra tabs the sessions opened, keeping one ChatGPT tab.
  2. Run the cache-cleaner extension on that tab: Active Tab Only on, Time Span 1 Week, everything checked except Cookies (App Cache, Cache, Cache Storage, File Systems, IndexedDB, Local Storage, Service Workers, WebSQL).
  3. Press clean. It takes about a minute and reloads the page itself, and the green icon goes grey when it's done.
  4. Hard refresh (Cmd+Shift+R).
  This clears the accumulated site storage that makes ChatGPT buggy and likely triggers Multilogin failures. Never clear cookies, and never close a tab a running session or the owner is using.
- **Platform-blocked Pro chat: switch it in place first.** When a Pro chat says the platform blocked a tool call (even a read-only preflight), switch that same chat to Extra High and paste something like: "Extra High mode is now on for you to continue with full tool access. Let me know if you want Pro mode in the future, and we'll checkpoint and hand off to a new session to continue in Pro." Only do the checkpoint and handoff to a numbered Pro chat when the work later needs Pro.
- **"You've reached the maximum length for this conversation."** This is mostly an Extra High limit (Pro usually has none). The chat still accepts messages, so ask it to save a checkpoint and write a detailed handoff for a new session. Then start a new numbered chat in the same project with the handoff pasted in, and archive the old chat once the successor is working.
- **Bloated or laggy Pro chat.** Switch it to Extra High, ask for a checkpoint and a detailed handoff, then start a new numbered Pro chat from the handoff.
- **Completely unusable chat** (won't load or accept input). Start a new numbered chat asking it to recover and resume the broken session, and include the old session's conversation ID and URL in the prompt.
- **"Connection interrupted" that won't revive points to a throttle.** Some interrupted chats only come back after another prompt, and it can take a while to tell whether they will. If one doesn't recover, or a refresh then shows "Could not load this ChatGPT conversation", treat it as a likely account-level throttle. Stop re-prompting the old chat and recover it with a numbered new chat (see the next lesson: new chats still work on a throttled account).
- **New chats work even on a throttled account (supersedes the one-new-chat throttle test).** When an account is throttled, its existing chats show "Could not load" and stay dead, but new Pro or Extra High chats still start and can do real work. So a new chat loading proves nothing about throttling. To recover a dead chat, start a numbered recovery chat in the same project that resumes it (old conversation ID and URL in the prompt). Do this one at a time and spread across runs at the casual pace, rather than waiting an hour before making new chats. Archive the old chat once the successor is working.
