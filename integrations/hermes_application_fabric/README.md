## Original request and uncertain effects

The request ID is a pure encoding/hash of original APPLICATION operation plus
native session/task/turn/API-request identity. No retry counter, new timestamp,
replacement account or random suffix is added. The same original owner client
retains attempted, active, failed and uncertain state across facade rebuilds.

Bounded errors are detached from raw exception causes and contexts. Native retry,
compression, credential rotation and fallback are disabled for this provider.
An original retired capability permits a later admission only after the native
original is terminal and the original APPLICATION owner positively proves its
closure; a refused close or absent receipt is insufficient.

Timeout, cancellation, 429, changed headroom or a new facade never proves that
another provider call is safe. Recovery must reconcile the original effect.
A post-tool disconnect cannot silently execute that tool or submit its turn
again. No cross-process restore-by-remembered-ID mechanism is introduced.

## Automatic and strict routing

Selection stays in the existing ModelRouter/APPLICATION/Fabric owner:

1. Trusted host task complexity, workload and expected latency/cost bounds
   constrain the existing policy. Prompt content cannot grant scope or accounts.
2. Eligibility intersects authorized pools, enabled/qualified models, actual
   conversation/tool/structured requirements, context/output limits, entitlement
   and physical account headroom.
3. Strict constraints are applied before selection. The fixed factory enforces
   its concrete inspected model. AUTO v2 and exact v3 can enforce an already
   committed singleton pool scope. Exact v3 preserves the original concrete
   model while the incumbent owner chooses eligible pool/account capacity.
   Broader per-turn pool narrowing still refuses before effects.
4. Existing policy ranks eligible candidates by task suitability, expected queue
   and response latency, headroom and expected cost. Estimates guide ranking;
   observed usage and the account owner's financial policy control settlement.
5. Logical model/pool aliases resolve through the existing physical-account and
   shared-allowance owner before admission. One account serving many models has
   one applicable allowance. Many accounts serving one model retain their actual
   account identities. Shared buckets are not counted repeatedly.
6. Admission and reservation are atomic in the original owner. Recovery is
   evaluated before any new selection. Original policy/recipe/account/request
   commitments remain immutable.

The adapter consumes fixed, AUTO v2 and exact scoped v3 owner contracts. It does not
claim that every latency/complexity/cost policy or monetary gate is installed.
The incumbent APPLICATION and shared-pool policy owners retain source responsibility.
