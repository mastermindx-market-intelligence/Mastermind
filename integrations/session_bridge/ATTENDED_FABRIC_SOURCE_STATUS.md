# Authenticated finite Fabric launch: source boundary

This source extends the existing Runtime, Supervisor and Fabric owners. It is
uninstalled and does not provide a production Backend or enable an execution
profile. Ordinary admitted shell Fabric and the previously accepted active Stop
return remain available independently.

The current Control path projects an actually validated Runtime launch pin to
the bridge's kernel-authenticated Control peer. The projection excludes the
private lease token. A concrete original owner must require the resulting
in-process command again at its existing O_EXCL reservation boundary. Missing
status is not authority, an uncertain effect blocks START, and recovery cannot
reconstruct a new command. Profile, attendance and physical-route checks remain
the concrete owner's obligations.

`fabric_attended_claude.py` compiles one bounded supported-Claude invocation
using the existing permission compiler. It binds the exact model, input schema,
closed tools/settings/environment and stdin prompt. It neither creates files
nor loads credentials, starts a provider or issues admission. The finite canary
validator accepts an exact MiniMax/Claude assigned realm only with the original
run/Job/worker/profile/physical/home binding and all unrelated-secret denials;
it does not produce a canary or relax the legacy validator.

WorkerRecoveryBinding V2 retains one real remote LaunchSpec and remote process
output paths. Only the retained prompt is Control-local. Its closed input-root
and source-workspace context participates in the original Runtime pin. The
Supervisor checks the exact durable Job/Attempt coordinates before opening the
private prompt, then verifies original-pin identity before transport/adoption.
Adapter-direct recovery checks that pin before its own prompt read. Recovery
uses status only; changed self-consistent public context cannot authorize a
replacement launch. V1 remains the default with its existing contract shape.

The proposed `fabric.attended.claude.bounded.v1` profile is disabled and retained
only in `proposals/attended_claude_profile.json`; it is absent from the installed
default registry. The exact native-return policy, version and digest from the
protected #1344 landing `8ba9838b` are preserved. Qualification and a separately
versioned registry release are required before this proposal can be selected.
The attended adapter permits only the Claude Code surface and requires a finite
READ grant with Fabric process-group cleanup; generic or missing profiles do
not grant this surface.

The real remaining integration is a concrete Backend over the incumbent
`remote_sub` controller, authenticated remote preparation of the pinned clone
and run inputs, execution of the bounded descriptor at that same owner's
process boundary, full post-exec START evidence, retained collection and actual
assignment revocation. The current early receipt is PRE_EXEC_HANDSHAKE and must
not be relabeled as full START. The original controller must continue heartbeat
and collection after returning START. Installation, actual host/realm/isolation
qualification and the exact-parent live task are separate, still-open proofs.

The old #633 Auth0 registration remains EFFECT_UNKNOWN. Current V3 READ+SUBMIT
authentication is a separate ingress; no Auth0 support request or replacement
registration is required to implement this source path. A queued request is
not foreground attendance, and GUI Runtime adoption is not a substitute for
the live authenticated originating operation.

## Finite lifetime and original-parent binding

A guarded START establishes attendance at launch; it does not authorize
unattended continuation. The current profile retains `interactive_only:true`
and `unattended_background_allowed:false`. If the request is the only qualified
attendance source, it must remain live through planner execution, canonical
sealed-plan admission, the paid child's START and collection. The handler may
await the existing service finisher outside transition locks. It must not
create another queue, finisher or lease owner. The finite upstream candidate's
300-second ceiling is also capped by principal expiry and the actual caller's
earlier deadline/disconnect; it is not a promise of that much connected time.

On originating-operation loss, request cancellation of the exact original
paid child through Runtime. Its existing finisher must retain cancellation,
collection and assignment-revocation ownership. Containment can continue after
attendance ends, but business execution cannot silently become unattended.
Closing only the local socket does not prove remote cancellation or cleanup.
The current Backend/cancellation/revocation prerequisites remain open.

The mixed execution-owner composition now keeps the original Codex planner
Supervisor and selects the paid Supervisor only for an exact pinned Worker.
It performs one canonical claim, refuses every already-claimed replay, retains
the original ActiveRun for finishing, and partitions restart before process
probes or mutations. The factory keeps the operator prompt source on the
original planner. Its existing disabled arm and dedicated-canary refusal remain.

For an attended Attempt, the composition observes the actual originating
`ForegroundOperation.wait_closed()` across START and collection. Loss requests
Runtime cancellation using the original Attempt ID and fence generation in one
transaction. A terminal Attempt wins without mutation; a successor refuses.
Caller cancellation keeps the original launch/collector draining instead of
dropping its response or manufacturing cleanup. On restart, missing original
attendance allows only the incumbent cancellation/recovery path. These are
source consumer semantics, not proof that a remote host can cancel or revoke an
assignment. Synthetic origin-signal tests do not establish authenticated ingress.

The native fresh-admission observer cannot be replayed for an existing root.
Later-request reentry needs canonical same-root provenance binding the original
authenticated principal and actual native-parent target to the current request.
An operation key, root ID, or caller-supplied Desktop UUID is insufficient;
authentication of the OAuth subject/client does not authenticate a GUI writer.
If that provenance is absent, a later caller cannot backfill it as authority.
The native writer owns qualification of that origin producer and any explicit
reentry binder. The bounded native-return no-child profile remains unchanged.

## Same-call cycle continuation

The installed-factory candidate now reserves the service's existing serial
cycle for the actual request task before the canonical sink can commit. The
fresh-admission observer still runs at the sink; it creates no asyncio owner or
caller-supplied root binding. The request-local exclusion is checked inside the
existing cycle lock, so a background tick cannot adopt the newly committed root
or advance it under a different foreground context.

For a fresh summon with explicitly configured attended Work placements, the
handler now drives the ordinary CooCycle: planner, sealed plan admission, Work,
required independent review, and aggregation. It awaits only the existing
Job/Attempt finisher outside transition locks. Each step rechecks the actual
foreground operation and retains the existing service, autonomy, policy and
host gates. A repeated transition, no action, finite cutoff or unresolved
finisher stops progression; there is no polling or separate retry scheduler.
The existing native-return no-child profile is explicitly excluded.

Caller cancellation closes attendance immediately while the original physical
transition drains. The original request slot is not released while that action
can still cross START. Collection remains with the existing finisher; exact
Runtime compare-and-cancel prevents cancellation of a successor Attempt.

The original immutable QUEUED admission receipt is retained. A separate
`foreground_completion` reports the current call's outcome. Whole-root success
requires `Runtime.validated_role_completion` for the exact aggregation Attempt;
completed Work/repair envelopes and their canonical digests are returned with
it. An oversized result is explicitly `RESULT_TOO_LARGE`, with retained result
identities rather than truncated content represented as successful delivery.
Result inclusion is not the original Codex parent's review or acceptance.
Duplicates and legacy queued requests do not acquire a fresh execution scope.

The real-source fixture runs the canonical plan, Work, independent review and
aggregation with inert role finishers. It does not attest a provider or host.
The current active registry remains unchanged and the attended adapter remains
unimplemented for production admission. A host-qualified preparation, START,
collection and assignment-revocation producer, the existing provider-policy
and C1 boundaries, protected release/installation, and an actual same-Desktop
paid return remain required. This finite same-call source does not establish
durable GUI enrollment, later-request reentry or idle Wake.

## Existing remote gateway composition

The optional remote target uses the incumbent MH1 mTLS gateway and its fixed
Unix connection to `FabricBridgeBroker`. It does not use the ordinary
`ExecutiveWorkerBroker` launch lifecycle. The validated Control command remains
in the original request; only the remote bridge's actual authenticated Unix
peer can construct the in-process authority consumed by `Backend.start_owned`.
The original Fabric reservation, lease, controller, retained result and
assignment owner remain responsible for every execution effect.

The same root-installed Fabric composition file accepts an explicit V2 schema
with unchanged physical `bindings` and a `remote_transports` list. Each transport
names its exact host, worker and physical binding digest, private IP/port,
existing CA/client-certificate/key paths, server certificate fingerprint and
finite timeout. TLS material is not copied into Runtime, the launch request or
receipts. Its protected file identities and the approved composition file are
rechecked before and after requests. An existing V1 file selects the original
local Unix client. Neither route falls back to the other on failure.

The gateway must explicitly select `broker_target: attended-fabric`, the actual
`expected_broker_peer_uid`, and its fixed protected Fabric socket. It preserves
the exact seven Fabric operations and forwards assignment sealing to the
original Fabric owner instead of the Worker Broker's separate seal handler.
Its startup metadata check is not a Backend-readiness check: Fabric has no
global `status {}` operation, and startup must not invent an Attempt to probe.
Actual calls authenticate the fixed Unix peer before sending their payload.
Existing Worker Broker documents, startup probing and sealing stay unchanged.

The loader selects the existing Linux installer namespace `/etc/mastermind-executive`
and `/run` on Linux; macOS retains its existing defaults. It never searches the
other platform namespace after refusal. The transport preserves EFFECT_UNKNOWN
if its pinned trust source changes after a modifying request has been sent.

These are installed-input contracts, not enrolled values. No endpoint,
certificate, worker generation, credential realm, binary/canary/isolation
attestation or selected profile is supplied by this source change. The finite
profile and `fabric_bridge_armed` remain disabled. The real Backend composition,
post-exec START, collection and assignment revocation must qualify before an
existing installation owner selects these inputs and before a live native
same-parent acceptance can be claimed.
