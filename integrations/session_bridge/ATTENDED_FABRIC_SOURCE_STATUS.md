# Authenticated finite Fabric launch: source boundary

This source extends the existing Runtime, Supervisor and Fabric owners. It is
uninstalled and does not provide a production Backend or enable an execution
profile. Ordinary admitted shell Fabric and the previously accepted active Stop
return remain available independently.

The current Control path projects an actually validated Runtime launch pin to
the bridge's kernel-authenticated Control peer. The projection excludes the
private lease token. A concrete original owner must require the resulting
in-process command again at its existing O_EXCL reservation boundary. Missing
status is not authority, an uncertain effect blocks START, and recovery cannot
reconstruct a new command. Profile, attendance and physical-route checks remain
the concrete owner's obligations.

`fabric_attended_claude.py` compiles one bounded supported-Claude invocation
using the existing permission compiler. It binds the exact model, input schema,
closed tools/settings/environment and stdin prompt. It neither creates files
nor loads credentials, starts a provider or issues admission. The finite canary
validator accepts an exact MiniMax/Claude assigned realm only with the original
run/Job/worker/profile/physical/home binding and all unrelated-secret denials;
it does not produce a canary or relax the legacy validator.

WorkerRecoveryBinding V2 retains one real remote LaunchSpec and remote process
output paths. Only the retained prompt is Control-local. Its closed input-root
and source-workspace context participates in the original Runtime pin. The
Supervisor checks the exact durable Job/Attempt coordinates before opening the
private prompt, then verifies original-pin identity before transport/adoption.
Adapter-direct recovery checks that pin before its own prompt read. Recovery
uses status only; changed self-consistent public context cannot authorize a
replacement launch. V1 remains the default with its existing contract shape.

The proposed `fabric.attended.claude.bounded.v1` profile is disabled and retained
only in `proposals/attended_claude_profile.json`; it is absent from the installed
default registry. The exact native-return policy, version and digest from the
protected #1344 landing `8ba9838b` are preserved. Qualification and a separately
versioned registry release are required before this proposal can be selected.
The attended adapter permits only the Claude Code surface and requires a finite
READ grant with Fabric process-group cleanup; generic or missing profiles do
not grant this surface.

The real remaining integration is a concrete Backend over the incumbent
`remote_sub` controller, authenticated remote preparation of the pinned clone
and run inputs, execution of the bounded descriptor at that same owner's
process boundary, full post-exec START evidence, retained collection and actual
assignment revocation. The current early receipt is PRE_EXEC_HANDSHAKE and must
not be relabeled as full START. The original controller must continue heartbeat
and collection after returning START. Installation, actual host/realm/isolation
qualification and the exact-parent live task are separate, still-open proofs.

The old #633 Auth0 registration remains EFFECT_UNKNOWN. Current V3 READ+SUBMIT
authentication is a separate ingress; no Auth0 support request or replacement
registration is required to implement this source path. A queued request is
not foreground attendance, and GUI Runtime adoption is not a substitute for
the live authenticated originating operation.

## Finite lifetime and original-parent binding

A guarded START establishes attendance at launch; it does not authorize
unattended continuation. The current profile retains `interactive_only:true`
and `unattended_background_allowed:false`. If the request is the only qualified
attendance source, it must remain live through planner execution, canonical
sealed-plan admission, the paid child's START and collection. The handler may
await the existing service finisher outside transition locks. It must not
create another queue, finisher or lease owner. The finite upstream candidate's
300-second ceiling is also capped by principal expiry and the actual caller's
earlier deadline/disconnect; it is not a promise of that much connected time.

On originating-operation loss, request cancellation of the exact original
paid child through Runtime. Its existing finisher must retain cancellation,
collection and assignment-revocation ownership. Containment can continue after
attendance ends, but business execution cannot silently become unattended.
Closing only the local socket does not prove remote cancellation or cleanup.
The current Backend/cancellation/revocation prerequisites remain open.

The native fresh-admission observer cannot be replayed for an existing root.
Later-request reentry needs canonical same-root provenance binding the original
authenticated principal and actual native-parent target to the current request.
An operation key, root ID, or caller-supplied Desktop UUID is insufficient;
authentication of the OAuth subject/client does not authenticate a GUI writer.
If that provenance is absent, a later caller cannot backfill it as authority.
The native writer owns qualification of that origin producer and any explicit
reentry binder. The bounded native-return no-child profile remains unchanged.
