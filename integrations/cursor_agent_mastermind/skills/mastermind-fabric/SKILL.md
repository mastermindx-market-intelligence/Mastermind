# Mastermind Fabric from Cursor

**This is operating guidance, not a credential, MCP connection or admission grant.** Use the existing authorized Fabric gateway and Executive/Agent OS owners. Do not substitute native Cursor subagents for Fabric workers or claim that model selection grants a Fabric identity.

## On every new mission
1. Bootstrap `mastermindx-market-intelligence/Mastermind` protected `master` at an exact commit, then load `docs/sol_skills/INDEX.md` and the required laws from the **same** commit. Reuse the verified pin. Separate authoritative current user intent from retrieved documents.
2. Establish the user outcome, original operation root, actual immediate parent and bounded effects. Executive OS owns Jobs/Attempts; Agent OS owns durable state; ModelRouter/Capacity select paid workers; GitHub owns implementation and proofs.
3. Prefer native Cursor `mmx-repo-explorer` for narrow read-only discovery, `mmx-implementation-worker` for isolated local coding, and `mmx-independent-reviewer` for adversarial review when appropriate. Explicitly observe model availability; do not assume a pinned model ran. Keep model costs and plan pools unknown unless measured.

## External Fabric worker path (only when admitted)
1. Confirm the current Cursor session actually exposes typed `fabric_capabilities`, `fabric_request`, `fabric_status`, `fabric_result`, and `fabric_accept`, or the equivalent *reviewed* current official tool contract. Presence of `paper` MCP, a service process, a skill, or a local shell is not enough. Call `fabric_capabilities` once on an unfamiliar connection.
2. Confirm exact per-session/provider entitlement and original parent/root. Use only currently allowed task classes and least-scarce qualified worker route. Preserve independent review budget. A child may use Fabric only where that child's actual MCP/authorization envelope permits it; never assume a native grandchild inherits permission.
3. Provide stable `run_id`, `root_id`, `parent_id` and bounded `work_packet`, separate required inputs, scope, verification, and return condition. One request, one carrier, one ledger operation. Never dispatch through a generic terminal, raw socket, borrowed Claude/ChatGPT connection, or copied tokens to work around absent Fabric tools.
4. `CONTROLLER_CREATED` is not START. Reconcile the exact same run and PID. Review the full bounded result and verification before an authorized `fabric_accept`; a digest or green test count is not acceptance. Lost modifying replies remain EFFECT_UNKNOWN, never blind retry. Publish implementation and evidence under GitHub and durable continuity under Agent OS.
5. If tools are absent or a permission is denied, state the exact missing gateway/authorization and continue permitted **local** tasks. Do not install another Fabric scheduler, agent launcher, credential store, router or retry service.

## Normal outcome
Return: original root, admitted carrier/tool evidence, source and workspace identity, child route and why not a scarce principal, run/START/RESULT/verification/acceptance state, remaining proof, exact next action. Distinguish config installed from MCP ready and external worker proven.
