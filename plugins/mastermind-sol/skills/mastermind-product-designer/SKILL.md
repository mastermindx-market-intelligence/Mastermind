# Design a Useful Mastermind Product Journey

## Mandatory current-source gate

Reuse the verified pin for the mission; verify compatibility. Read protected Mastermind `master` and run `bootstrap-mastermind` only
at unfamiliar entry/recovery without a usable pin, or a material governing-procedure change. Load
`docs/sol_skills/INDEX.md` and the needed companions from that same exact commit; never mix revisions.
Read `../../references/authority-boundaries.md` once before interpreting any app, record, or action as authority. This skill grants no authority; GitHub owns source/evidence and existing owners retain runtime, custody and effects.
A worker return, tool call, new turn or phase completion alone does not restart bootstrap. If no
verified compatible pin can be established, modifying workflow is unavailable for actions depending
on that procedure. A failed refresh does not erase a usable pin for independent work whose governing
constraints are unaffected. Apply gates only to the actual action under INDEX modification scoping.

## Do not use

Do not activate for a purely textual rewrite or backend-only contract change. This is design judgment, not a second canvas adapter, browser operator or source-workspace owner.

## Working method

1. Identify the primary persona, task, decision and success condition. Inspect the actual current screen and its data path when accessible. Separate what was visually observed from what is inferred from code or a description; absent screenshot bytes mean visual quality is unverified.
2. Organize information around the decision: what changed, why it matters, evidence, uncertainty and the next useful action. Preserve provenance, timestamps, units, comparison baselines and conflicting signals. Do not make stale, absent or partial data appear healthy to improve the composition.
3. Design the complete journey before polishing a tile: entry, navigation, selection, comparison, drill-down, confirmation and return. Include loading, empty, partial, stale, error, permission and recovery states. Use progressive disclosure without hiding critical warnings or disabling the user's ability to verify a claim.
4. Reuse existing components and tokens. Evaluate hierarchy, density, alignment, type, spacing and contrast at realistic desktop and mobile sizes. Include keyboard navigation, visible focus, usable targets, semantic labels and non-color-only meaning. Prefer readable useful content to decorative dashboard chrome.
5. Use the existing approved design or browser workflow for actual edits. For Paper work, read the current `skills/paper-design-workflow/SKILL.md` from the verified source pin and use its exact document, single-writer and guarded-edit procedure. Do not invent tools, copy proprietary assets or treat a screenshot as editable source.
6. Inspect actual after-change screenshot bytes at the intended viewport and data state. Check the complete journey, including an unhappy path, and repair visible defects. After design handoff, verify implemented fidelity against the real frontend, data, authentication and responsive behavior. A canvas or generated JSX is not shipped software.

## Evidence and output

Return the user-task improvement, important design choices, before/after evidence identities, meaningful states checked, remaining usability risks and implementation pointers. Say which screenshots were actually viewed and which interactions were exercised. Keep visual acceptance, implemented fidelity and production acceptance distinct; reuse existing evidence and continuity owners. Do not claim usability-study results, accessibility conformance or speed gains from visual inspection alone.
