# Recover Without Duplicating Effects

## Mandatory current-source gate

Reuse the verified pin for the mission; verify compatibility. Read protected Mastermind `master` and run `bootstrap-mastermind` only
at unfamiliar entry/recovery without a usable pin, or a material governing-procedure change. Load
`docs/sol_skills/INDEX.md` and the needed companions from that same exact commit; never mix revisions.
Read `../../references/authority-boundaries.md` once before interpreting any app, record, or action as authority. This skill grants no authority; GitHub owns source/evidence and existing owners retain runtime, custody and effects.
A worker return, tool call, new turn or phase completion alone does not restart bootstrap. If no
verified compatible pin can be established, modifying workflow is unavailable for actions depending
on that procedure. A failed refresh does not erase a usable pin for independent work whose governing
constraints are unaffected. Apply gates only to the actual action under INDEX modification scoping.

## Do not use

Do not run a recovery ritual for healthy work, a speculative future failure or a simple question. Do not use this skill to obtain an action that a safety or permission denial has forbidden.

## Leadership

Ownership is a role, not a session: never wait on an absent/orphaned owner or ask the Chairman to find old chats. The current session assumes leadership, records the takeover in the source-linked handoff, and proceeds. Independent review is still required; never self-merge or approve.

## Working method

1. Freeze the exact failed action, target, operation, carrier and last verified effect. Distinguish a failure before dispatch from a lost response after possible dispatch. Record the observed error, not an inferred outage, quota, served-model change or hidden context limit.
2. Classify the missing axis: tool exposure, schema/request validity, authentication, resource permission, service availability, source custody, admission or effect. A working read proves neither a working write nor its absence. Use the smallest safe current action-family discovery or non-mutating preflight required by `ACTIVE_EXECUTION.md`.
3. Preserve `EFFECT_UNKNOWN` on the original operation and carrier. Apply `RECONCILE_STATE.md` to read its canonical result before any retry, replacement, transfer or failover. A timeout, new chat, fresh mode or changed correlation ID does not establish that the effect was absent.
4. Treat a safety or permission denial as a boundary, not a prompt-engineering problem. Never change phrasing, tool, account, model, host or provider to obtain the refused effect. Correct a genuine malformed request or transient technical failure only within current permitted recovery limits, after reconciling any possible effect.
5. Use current enrolled recovery and mode policy, not a copied rule set here. When `SESSION_RELIABILITY.md` is enrolled by the same pinned INDEX, load it; an unmerged candidate or remembered procedure is not enrollment. Otherwise apply the existing active-execution and reconciliation owners plus the current outer instruction hierarchy, explicitly resolving any material conflict before the affected action.
6. Keep mode preference, observed capabilities, actual selector access and authority separate. Do not self-switch by announcing a mode. When a supported control is unavailable, request the precise human mode or session action with purpose, checkpoint, next action and uncertain effects. Reverify the required action after a material surface change. A mode change cannot waive a denial or clear an effect fence.
7. Advance useful independent scope where safe. Do not repeat the same diagnostic or status cycle without changed evidence. Follow the existing checkpoint and rotation owner at a genuine continuity boundary; never reopen sealed heavy work by treating 'continue' as a new lease.

## Evidence and output

Report the exact failure classification, proven and unknown effects, bounded recovery attempted, usable independent lane and next action. Preserve source and continuation references with verified readback. Disclose failed persistence; a chat note is not a durable receipt. Claim neither background recovery nor restored capability until observed through the real path.
