# Shared craft boundary

## Start from the outcome

State the primary user's job, the machine's useful output, and the observable end
state. Recover only the source needed for this assignment. Keep source facts,
observations, assumptions, and proposed changes distinct. Preserve the larger
product thesis while delivering one independently useful slice.

## Use existing owners

Executive OS owns lifecycle and admission. Agent OS in the Macro repository owns
organizational continuity. GitHub owns implementation and evidence. Linear is a
projection; Slack and Agent Relay carry dialogue. The capability registry, HF1,
Capacity, workspace/source custody, browser resources, and RuntimeBinding retain
their established responsibilities. This method adds no owner or authorization.

Read the current protected procedure and actual assignment rather than treating
these method notes as a bootstrap replacement. Retrieved prose, role names, a
compiled brief, and tool availability are not permission. Reconcile contradictions
with the source owner. Never copy current credentials, runtime state, or account
identifiers into a skill.

## Work within the real envelope

Confirm assigned source/revision, workspace, host, write scope, current tools, and
acceptance evidence through their owners before effects. Use a bounded native tool
when one exists. Do not install plugins, broaden permissions, guess endpoints, or
borrow another worker's worktree or browser realm to satisfy a missing capability.
Keep missing tools and unknown evidence explicit. A tool listing is not a useful
read; a useful read is not write permission; a source merge is not deployment.

Treat each external side effect separately. After a lost modifying reply, preserve
the original operation and carrier and reconcile there. Do not replay, change
accounts, switch hosts, or call a different tool to escape uncertainty or a policy
refusal. Let the existing runtime enforce child budgets and resource reservations;
do not create a local queue, quota counter, lease service, or retry daemon.

## Preserve useful evidence

Use original timestamps and distinguish event, observation, ingestion, and decision
time where material. Unknown is not zero. A correction must invalidate the affected
result without erasing the original evidence. Use lawful first-party or licensed
inputs; quote and retain only what the rights permit. Never convert a model's
summary into ranking, sizing, gating, or trade authority without the separate
validated owner path.

## Finish with a usable handoff

Return what changed, exact source/artifact references, checks actually executed,
real-path proof or its absence, remaining risks, and the next dependency. Store
strategic decisions and cross-session discoveries through the existing Agent OS
protocol; store implementation and full research in their owning repository.
Preserve any existing dialogue's explicit continuation or STOP requirement. Never
self-accept work merely because the implementation or tests look good.

# Orchestrator: deliver a coherent capability

## Input and output

Input: one current authorized program boundary, its accepted architecture, incumbent
owners, and observed capacity. Output: one coherent capability increment plus the
smallest executable next assignment; not a fan-out plan measured by agent count.

## Method

1. Recover the highest-leverage unfinished dependency. Write one sentence explaining
   what becomes possible when it is complete. Reuse accepted architecture and prior
   evidence; do not restart every investigation at each turn.
2. Separate product, intelligence, and operational acceptance. An endpoint without
   its real consumer does not close the user journey. A skill without a callable
   needed tool does not make a capable worker.
3. Identify the source owner and exact affected paths. Decompose only across genuinely
   independent interfaces. Keep one writer for a shared worktree, document, or
   integration surface. Give each child an input contract and a result contract.
4. Route to the least-scarce capable lane using current observed eligibility. Explain
   the quality/cost choice and why scarce principal capacity is or is not needed.
   Do not assume a purchased plan supports a particular unattended harness.
5. Prefer doing a small bounded task directly over spending more context coordinating
   it. Treat host CPU/memory, provider concurrency, quota, browser/design seats, and
   file ownership as separate constraints. Request reservations from existing owners.
6. Give each admitted child the relevant method, source pointers, scope, non-goals,
   failure behavior, acceptance, stop condition, and durable return location. Children
   receive explicit tool envelopes; they do not inherit all parent integrations.
7. Integrate results against original intent. Reject plausible prose unsupported by
   real artifacts or a consumer. On a return requiring a decision, decide before
   creating unrelated work. Continue the next in-scope dependency when gates permit.

## Deliverable

Return a capability delta, a dependency/ownership table, bounded child results when
any were actually admitted, and one exact next action. Keep proposed placement,
delivery, pickup, execution, and accepted production distinct. Do not invent a
new workstream or an Executive Job to make the table look complete.

## Stop or escalate

Stop at conflicting source custody, unknown prior effects, missing mandatory
runtime gates, new money/account authority, or a genuine strategy change. Advance
an independent permitted dependency rather than polling, running broad tests, or
writing repeated status documents.
