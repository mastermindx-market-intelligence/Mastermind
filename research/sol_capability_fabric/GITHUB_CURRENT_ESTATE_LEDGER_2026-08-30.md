## 4. Pagination, attempt and absence law

Current wrappers make some intentionally bounded calls:

- commit workflow runs: pull-request-triggered runs, first page;
- workflow run jobs: latest attempt, first page;
- workflow run artifacts: first page;
- several search functions: caller-selected top-N rather than proof of universe completeness.

Therefore:

1. `not returned` is not automatically `does not exist`;
2. current-head proof must identify the trigger, run ID and attempt;
3. cancelled or superseded runs remain non-green;
4. missing later-page jobs/artifacts makes the packet `PARTIAL` or `UNKNOWN` when material;
5. a GH2 gatherer must either traverse accepted bounded pagination or emit explicit truncation and
   continuation evidence.

## 5. Exact-head and effect semantics

### Read-side preconditions

A release candidate is identified by all of:

```text
repository
base ref and protected/default SHA
candidate branch and immutable head SHA
merge base / ahead_by / behind_by
expected changed paths and actual changed paths
stable operation key and exact carrier evidence
current writer evidence
required checks and exact run/attempt states
review submissions and unresolved threads
current source-law revisions
required production proof and capability claim
```

Branch name alone is never an immutable artifact. A green run on an older head never transfers to a
new head. Disjoint default-branch movement may be acceptable only when the assessment proves current
source compatibility and the actual GitHub merge context remains valid.

### Modifying-side semantics

Every modifying family preserves:

```text
NOT_APPLIED | APPLIED | EFFECT_UNKNOWN
```

- `NOT_APPLIED`: canonical evidence proves the effect did not occur;
- `APPLIED`: GitHub canonical state/read-back proves the exact intended effect;
- `EFFECT_UNKNOWN`: the request may have crossed the effect boundary and canonical read-back is
  unavailable or inconclusive.

`EFFECT_UNKNOWN` keeps the same carrier, blocks retry and blocks failover. Reconciliation reads the
canonical PR/ref/run state; it never resubmits.

## 6. Runner and host boundary

The connected GitHub surface can expose workflow/job/log evidence, but it does not currently provide a
closed exact runner inventory. SCF-RUN1 must join only approved facts from GitHub runner metadata and
accepted host/service owners.

Model-visible output may contain:

```text
runner_ref
scope
redacted name metadata
OS / architecture
online / offline
busy
labels / group
runner version
observation time
current job or host reference
source freshness
```

It must never contain registration tokens, credentials, private keys, raw environment, raw argv,
private network coordinates or a generic host command.

Queue diagnosis must distinguish `VALID_WAIT`, `NO_ELIGIBLE_RUNNER`, `ALL_ELIGIBLE_BUSY`,
`RUNNER_OFFLINE`, `LABEL_MISMATCH`, `RUNNER_GROUP_MISMATCH`, `CONCURRENCY_LIMIT`,
`ENVIRONMENT_GATE`, `UPSTREAM_JOB_PENDING` and `GITHUB_STATE_UNKNOWN`. Queue age alone is not a
failure proof.

## 7. Rights, secrets and public metadata

Safe connected evidence normally includes repository/branch/commit/PR/check/run/job identifiers,
public review content and approved log/artifact excerpts. GH2/RUN1 must still redact or refuse:

- access tokens, installation tokens and registration tokens;
- secret, credential, private-key or authorization values;
- raw environment variables;
- private runner addresses and raw host argv;
- connector-internal credential routing;
- arbitrary URLs supplied by the model.

The model never chooses a credential, installation, account or technical principal. Runtime app
identity and scopes are server-owned evidence.

## 8. Current conclusion

The current estate is materially stronger than a greenfield system: exact source reads, PR/review
operations, expected-head merge and workflow evidence are already native. The missing capability is
not a super-MCP. It is a small owner-preserving semantic layer:

```text
current native GitHub facts
-> pure operation/collision/release assessment
-> evidence packet
-> separately prepared owner-specific action
-> one native effect
-> canonical read reconciliation
```

GH1 therefore starts with the pure assessment engine. GH2 later composes live reads and guarded native
actions. RUN1 separately owns runner explanation. Administration remains isolated and assessment-only
unless an explicit A3 wave authorizes one closed family.
