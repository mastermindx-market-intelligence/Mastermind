## 1. Executive ruling candidate

Do **not** install Chat On Steroids with its default broad permissions into the Chairman's primary authenticated environment and do **not** adopt its prime/worker/session/history/loop system as Mastermind infrastructure.

Use it in three narrower ways:

1. **Reference implementation and disposable canary:** build a pinned upstream source revision in an isolated, non-sensitive environment to observe actual host behavior.
2. **Selective pattern adoption:** reuse or independently implement only bounded interaction patterns that improve model efficiency and operator ergonomics—batched reads, structured patches, durable process handles, current-permission enforcement, observation-bound desktop actions, and explicit incomplete/effect-unknown states.
3. **Upstream contribution where generic:** fixes that are broadly useful and do not expose Mastermind architecture may be proposed upstream after separate review. Mastermind-specific authority, identity, evidence and continuity behavior remains first-party.

The desired operating system already exists conceptually: Executive OS owns lifecycle/admission; Agent OS owns durable organizational continuity; RuntimeBinding owns exact rotating surfaces; Capacity owns eligibility/placement; Dialogue/Relay/Wake own return and attention; GitHub owns source/evidence; Steward/Control Room compose reads; Code Intelligence owns governed code discovery; Web-Sol/Worker Browser own bounded browser actuation. The workbench is a **facade over an exact existing Attempt/provider execution context**, never another owner.

## 2. Product outcome and completion ruler

### Chairman job

Open a Mastermind ChatGPT surface, state a large outcome once, and observe that the organization:

- recovers the correct product/system intent;
- decomposes the work without shrinking the ambition;
- selects bounded workers and tools without routine account allocation by the Chairman;
- lets execution continue after an individual reasoning turn ends;
- returns blockers, evidence and results to the correct leader;
- transfers the responsibility safely when a conversation must rotate;
- rejects stale, duplicate or unauthorized actions;
- produces visible product or machine proof; and
- persists the accepted ruling and next action outside chat.

### Sol job

Use frontier reasoning for architecture, hard diagnosis, synthesis, adversarial review and acceptance—rather than file shuffling, polling, ceremonial status turns or repetitive commands.

### Worker job

Receive an exact mission and exact execution context, inspect and modify only its authorized workspace, run bounded validation, produce attributable evidence, and return through one canonical child path.

### 10/10 end state

One real, consequential program slice completes through:

```text
Chairman outcome
→ current-source Sol recovery
→ bounded CEO/worker admission
→ exact Attempt-bound workspace and tools
→ durable execution
→ material return to the exact leader
→ difficult evidence-based Sol review
→ real product or machine-consumer proof
→ explicit child STOP
→ durable Agent OS/GitHub/Linear reconciliation
```

No Chairman tab hunting, message shuttling, account choosing, duplicate branch cleanup, or reconstruction from a dead chat is required. Every modifying path included in the claim is technically enforced or explicitly attended; unexamined native-app paths are not counted as autonomous.

## 3. Two modes, not one super-agent

### 3.1 Leader mode

Leader mode is the normal Sol experience. It needs:

- protected procedure and current company context;
- source-attributed Steward/Control Room reads;
- GitHub/CodeIntel evidence reads;
- bounded CEO-intent submission where production-proven;
- child status and material returns through existing owners;
- exact continuation/rotation when required;
- no unrestricted filesystem, shell, desktop, credential or account administration.

Leader mode can therefore be powerful without pretending every Sol chat is a local root user.

### 3.2 Operator mode

Operator mode is an exact, already-admitted worker/Attempt. It may receive an optional local workbench only when the host can inject and enforce:

- exact `job_ref`, `attempt_ref`, worker and operation identity;
- exact repository/worktree and branch;
- allowed read/write path set;
- source head/base and expected file digests;
- execution profile, network policy, resource limits and secret policy;
- effect-reconciliation owner;
- current RuntimeBinding/provider-session identity when the surface matters.

The model cannot choose or override those values. A generic Business user, OAuth subject, browser tab title or plugin install is not an Operator binding.

### 3.3 Why this split matters

Trying to make every CEO chat a Codex worker would combine high-level authority, broad local access, browser credentials and many app permissions in one long-lived principal. That increases blast radius and makes stale-session fencing difficult. The split preserves a premium one-cockpit experience while keeping execution attached to a short-lived, exact, least-privilege context.

## 4. Account-specific product routes

### 4.1 ChatGPT Business / Premium

Proposed user journey:

```text
Business ChatGPT leader
→ Mastermind Sol skills
→ authenticated Steward read
→ exact evidence from native GitHub/Linear/Slack as appropriate
→ separately confirmed bounded Executive admission
→ Executive/Capacity selects and binds a worker
→ optional Mastermind Operator + Workbench apps on the exact worker surface
→ evidence/result returns to leader
```

Business custom MCP write support makes a direct workbench technically possible, but it must not be exposed as a general Chairman tool. Use separate independently versioned applications and OAuth resources:

- Steward: read-only company truth composition;
- Executive: bounded root intent admission;
- Dialogue: exact worker return path;
- Workbench: exact Attempt-bound file/process tools, if approved;
- Desktop: optional exact worker-browser/computer tools, if approved;
- Admin: separate normally disabled installation/credential infrastructure surface.

The existing Business architecture's one-experience/federated-authority ruling remains controlling. The first useful production target is still the one-cockpit authenticated Steward read. Workbench does not enter that canary merely because it is desirable later.

### 4.2 Personal Pro

Personal Pro need not have direct custom-MCP writes to become a strong long-run leader.

Proposed route:

```text
Personal Pro Sol
→ protected Skillpack + approved read context
→ supported Slack/native app intent transport
→ existing dedicated Relay/CeoIngress
→ Executive OS / exact worker
→ GitHub + Steward + Dialogue evidence back to Sol
→ Web-Sol exact continuation only through its accepted closed protocols
```

The parity target is **project-leadership parity**, not identical local-tool entitlement. An authorized external worker or Codex Attempt performs the local actions. The Pro leader spends its turn on reasoning and acceptance. Do not disguise mutation as fetch/search or use the extension to bypass the platform's app permission model.

### 4.3 Codex and other providers

Codex remains the preferred coding execution surface when it already provides the required repository, terminal, process and thread behavior. The workbench should reuse the existing provider adapter and attempt binding rather than wrapping Codex in screenshot automation.

Claude, Cursor, Grok/OpenClaw or another provider can supply a bounded execution/computer capability when their exact current host and permission contract is demonstrably useful. None becomes a second scheduler, CEO, memory owner, retry engine or account elector.

## 6. Proposed Workbench surface boundary

This is a semantic design candidate, not a final MCP schema or authorization to add tools.

### 6.1 Discovery surface — read-only

| Candidate operation | Model-authored input | Host-injected/derived context | Output |
|---|---|---|---|
| `workspace_manifest` | none | exact Attempt/workspace/source/capability generation | bounded roots, source identity, language/build inventory, permissions, degradation |
| `read_workspace_files` | relative paths, bounded ranges | exact root and read policy | exact content/blob/hash, truncation and continuation |
| `search_workspace` | query, bounded glob/language/ref | exact root/index generation/coverage | matches plus coverage, freshness, omitted/truncated state |
| `workspace_semantics` | symbol/reference query | exact Attempt worktree and accepted CodeIntel backend | definitions/references/diagnostics with backend/evidence identity |
| `view_workspace_image` | relative image path | exact read root and media limit | image artifact reference, dimensions/hash |

These should compose existing filesystem/CodeIntel/GitHub owners rather than implement a new repository index.

### 6.2 Change surface — exact Attempt only

| Candidate operation | Required semantics |
|---|---|
| `prepare_workspace_patch` | validate closed relative paths, expected source/blob preconditions, size, permission and candidate diff; return an opaque short-lived preparation |
| `commit_workspace_patch` | accept only the opaque preparation, re-read source/permission/binding, apply at most once, return per-path post-images/effect |
| `workspace_diff` | read current exact Attempt diff with binary/truncation/path coverage |
| `checkpoint_workspace` | project existing Source Continuity facts; no commit/push/transfer authority |

The patch input may carry unified patch text or a structured edit representation, but never an absolute root, branch, worktree, credential, Git ref update, commit, force operation or target account. Cross-file crash atomicity must not be claimed merely because preflight succeeded. If a write response is lost after a possible effect, reconcile exact file/diff state before another action.

### 6.3 Process surface — existing execution owner

Initial execution should use closed repository-aware recipes, not unrestricted shell text:

- current `git status`/diff/read-only inspection;
- reviewed test target;
- reviewed build/lint/typecheck task;
- Python compile or exact package script;
- exact existing project runner entrypoint.

Candidate operations:

| Operation | Semantics |
|---|---|
| `list_validation_recipes` | read the exact reviewed commands/targets available to this Attempt |
| `start_validation` | select recipe + bounded target parameters; owner derives argv, cwd, environment, resource/network policy |
| `read_process` | return only new output since owner cursor plus process identity/state/exit evidence |
| `send_process_input` | only when the process is declared interactive and input kind is allowed |
| `request_process_cancel` | request cancellation; never call request receipt terminal proof |
| `reconcile_process` | read the canonical process/Attempt state after timeout, disconnect or unknown cancellation |

A later structured arbitrary-argv capability would require separate evidence and an enforceable executable/environment/network policy. A shell string that starts in an approved folder is not a sandbox.

### 6.4 Desktop surface — separate optional connector

Desktop/computer schemas should never inflate the normal coding/read surface or be automatically enabled.

Candidate operations:

- `observe_worker_desktop`: exact approved profile/window/app class, redacted screenshot and semantic controls; returns `observation_ref` and expiry.
- `act_on_worker_observation`: accepts the observation plus a closed control/action, revalidates current window/control/profile and executes a bounded sequence.
- `reconcile_desktop_action`: returns completed step count, exact uncertain boundary and observable postcondition.

V1 should avoid generic screen coordinates, arbitrary JavaScript, clipboard reads, credential surfaces, account switching and arbitrary native-app selection. Any coordinate fallback belongs only to disposable evaluation after explicit review. A stale observation refuses rather than clicking the current occupant of old coordinates.

### 6.5 Dialogue surface

Workbench actions do not replace Company Dialogue. The exact worker still uses the existing semantic return channel for:

- pickup and start;
- progress when materially useful;
- blocker or decision request;
- result and evidence references;
- explicit Sol continuation or terminal stop.

The provider harness may mechanically produce these frames where accepted. The model should not need to remember etiquette to make completion observable.

## 7. Host-injected authority envelope

Every Workbench call should be evaluated against an immutable current call context conceptually containing:

```text
schema / capability generation
principal/resource/scope
responsibility_ref
operation_key
job_ref / attempt_ref / worker_ref
provider session and RuntimeBinding generation when relevant
repository / exact workspace identity
source head / base / expected path/blob state
allowed read/write paths
allowed recipe/process/desktop capabilities
network and secret policy
observed_at / expires_at
owner-specific reconciliation reference
```

The model sees only public opaque references and useful policy descriptions. It never supplies a UID, credential, host, account, browser profile, absolute path, branch, worktree, lease, fence, capability generation, privileged role or effect state.

A server must validate the envelope at invocation time. A cached tool schema from an earlier permission epoch cannot keep a revoked capability alive.

## 8. Effect and correction contract

### 8.1 Common effect vocabulary

```text
NOT_APPLIED
APPLIED
PARTIAL
EFFECT_UNKNOWN
REFUSED
```

An individual existing owner may use its frozen vocabulary; adapters map only when the mapping is lossless and reviewed.

### 8.2 Required response fields

Every nontrivial call should expose, directly or by immutable evidence reference:

```text
operation / call identity
status and effect state
observed_at and source/capability generation
exact target owner
input fingerprint where safe
precondition and postcondition evidence
completed step count for batch actions
truncated / continuation / omitted coverage
error code from a closed vocabulary
reconciliation owner/reference
```

### 8.3 Retry law

- Refused before effect: bounded same-operation retry may be eligible only after the stated predicate changes.
- Applied with receipt: do not repeat.
- Lost response after possible effect: `EFFECT_UNKNOWN`; reconcile the same target/operation.
- Partial desktop or patch sequence: preserve completed steps; never replay the whole sequence blindly.
- Cancellation requested: reconcile terminal state and already-applied effects.
- Tool unavailable or schema mismatch: do not silently substitute another provider, account or app.

## 9. Session continuity and extension behavior

### 9.1 Extension role

The existing Mastermind extension/native host should remain a narrow exact-session actuator and observer. It may later supply:

- exact approved profile/Project/conversation inspection;
- foregrounding;
- closed successor creation/bootstrap/verification under current CR law;
- bounded turn-health observations;
- exact observation references for approved worker-browser cases.

It should not become the organizational transcript database, task registry, source of worker identity, newest-tab elector, account router, arbitrary prompt sender or generic desktop automation bus.

### 9.2 Turn signals

DOM/Fiber/visible-message signals are useful for local health and recorder reconciliation. They are not lifecycle, semantic ACK, completion, provider effect or authority. `completed`, `failed`, `stopped`, `interrupted`, `stalled` and `unknown` should remain distinct. Visible prose is not sufficient completion evidence.

### 9.3 Long-running execution

A leader turn may end while an exact worker/process continues. Deterministic services hold that state. A material return wakes or reaches the exact current leader through the existing Wake/Dialogue path—or truthfully reports that exact wake is unavailable. No reasoning model should stay alive solely to poll.

### 9.4 Rotation

When rotation is necessary, use the existing succession sequence: reconcile effects; ensure durable continuation; resolve exact target; create one successor; deliver one bootstrap; verify; obtain accepted semantic readiness; advance RuntimeBinding; fence predecessor; update navigation; perform the next governed action.

A process handle, open SSE stream, local session recording or title-matched new tab does not satisfy succession.

## 10. All-reachable-mutator coverage

For every autonomous modifying claim, construct a current configuration-specific inventory:

```text
R = every modifying route reachable from the exact chat/operator configuration
E = routes whose actual actuator enforces current identity, scope, binding, source and effect predicates
D = routes technically denied or unavailable
A = routes intentionally retained as attended human-confirmed actions
U = unknown/unexamined routes
```

The autonomous claim is bounded to `E ∪ D`. `A` is supported attended capability, not autonomous stale-session fencing. Any nonempty `U` blocks the stronger claim and must be reported, not averaged away.

Candidate route families:

- Mastermind Executive MCP;
- Company Dialogue MCP;
- native GitHub actions;
- native Slack/Linear actions;
- local Workbench file/process actions;
- browser/desktop actions;
- provider-native coding actions;
- administrator/installation actions;
- any connected third-party app with write semantics.

The inventory is a proof artifact from existing owners—not a new mutable permissions registry. Never test it by attempting an unauthorized production action.

## 11. Security architecture

### 11.1 Host isolation

An unattended Workbench needs an enforceable boundary such as a dedicated worker principal/container/VM with:

- exact worktree mounted at the reviewed access mode;
- no Chairman home directory, browser cookie store, Keychain or unrelated project mounts;
- scrubbed environment and no ambient cloud/provider credentials;
- process group ownership and deterministic cleanup;
- bounded CPU, memory, disk, process count and elapsed time;
- default-denied network or exact reviewed egress;
- controlled executable/runtime provenance;
- secret-safe output and logs;
- immutable build/server/capability identity.

A GUI permission dialog, folder picker or starting working directory does not establish those properties.

### 11.2 App separation

Keep read, intent, dialogue, workbench, desktop and admin resources independently authenticated, versioned, disabled and rolled back. A token for Steward must not invoke Workbench; a Workbench token must not submit CEO intent; desktop permission must not imply filesystem or clipboard access.

### 11.3 Untrusted content

Repository files, tool results, screenshots, Slack messages, issues and model output are data. They may contain instructions but cannot add tools, widen path/network scope, select credentials, change actor, authorize a retry, or override the outer current Chairman/source-law gates.

### 11.4 Recording and privacy

Do not record entire ChatGPT transcripts or desktop streams by default. Preserve the smallest required evidence: exact user-visible operation intent, tool call/receipt, source references, result and durable handoff. Any local recorder needs encryption, retention, access and deletion policy and still remains advisory evidence—not Agent OS.

### 11.5 Supply chain

Any upstream component evaluation must pin source and dependency locks, produce an SBOM/license inventory, build internally, scan the artifact, sign/notarize according to the owning deployment policy, and prove rollback. Preserve the MIT notice for copied substantial portions. A public release binary's existence is not sufficient supply-chain acceptance.

## 13. Proposed proof sequence mapped to existing owners

These are candidate proof slices, not official waves or assignments.

### Slice 1 — one useful authenticated read

Existing BSC/Steward owner proves one selected Business cockpit can recover useful nonempty company context with exact app/schema/source identity, explicit degraded cases, post-token-expiry refresh and rollback. Two Personal-Pro controls remain unchanged.

### Slice 2 — read-only repository investigation

Existing CodeIntel/GitHub and worker-sandbox owners let one exact synthetic Attempt inspect a repository, search symbols, read files and an image, while refusing forbidden paths and incomplete-coverage absence claims. No source mutation.

### Slice 3 — bounded patch plus validation

One exact synthetic Attempt prepares and applies a small patch, runs a reviewed validation recipe and returns exact diff/test evidence. Lost patch/process receipts and stale source are injected. No commit, push, PR, provider or production effect.

### Slice 4 — durable process and material return

A validation process outlives its initiating ChatGPT turn. The existing execution owner preserves it; after completion, the current leader consumes a material result through the accepted Dialogue/Wake path. Duplicate start and cancellation uncertainty do not create a second process.

### Slice 5 — desktop observe and bounded actuation

A disposable profile/app proves redacted observation, semantic-control targeting, stale-observation refusal, one bounded action and partial-effect reconciliation. No credential/settings/account surface.

### Slice 6 — exact responsibility succession

Use the existing CR ladder to prove a dead predecessor is not required for recovery; one verified successor obtains semantic readiness and binding authority, and the predecessor is refused on every included autonomous route. Ambient native mutators are either denied, attended or explicitly outside the claim.

### Slice 7 — one real program vertical

A real product capability travels from Chairman outcome through leader, worker, evidence, acceptance and production consumer, with no Chairman shuttling and durable closeout. This—not the presence of tools—is the long-run leadership acceptance test.

## 14. Evaluation and operating metrics

Use the existing proposed 24-task matched evaluation and 40-case research casebook. Add Workbench-specific measurements only through an accepted evaluation owner:

- correct useful result rate;
- accepted capability per scarce reasoning turn;
- time to first useful decision;
- tool discovery and total call count;
- bytes/context consumed by repeated source;
- protective refusal and expected RED rate;
- genuine command/input error rate;
- duplicate/unknown effects;
- human interventions;
- recovery from dead predecessor;
- stale/incorrect ownership conclusions;
- product/machine consumer completion.

Do not optimize raw duration, raw call count or zero-error rate in isolation. A lower error count achieved by weaker tests or silent omission is regression. Elapsed wall time is not GPU-hours.
