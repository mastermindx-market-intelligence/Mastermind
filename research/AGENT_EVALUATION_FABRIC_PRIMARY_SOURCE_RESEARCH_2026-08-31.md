## 1. Research question and ruling

The program needs to determine which external evaluation components accelerate Mastermind without duplicating its lifecycle, identity, memory, routing, evidence, or organizational-learning owners.

The ruling is:

1. Build the Mastermind scenario/run/validity/scorer/evidence-reference contracts first with the Python standard library.
2. Reuse the existing OHF laboratory and PR #162 as the first exact fresh-session runner.
3. Evaluate Inspect AI as a subordinate orchestration/log/scorer adapter only after one native real run exists.
4. Evaluate Promptfoo as a locked-down adversarial generator/executor using synthetic or explicitly public-safe inputs.
5. Hold Langfuse out of V1 until experiment volume and reviewer workflow prove that a service is worth its retention, access-control, migration, and operating burden.
6. Keep all analysis projections rebuildable from immutable Mastermind receipts.

This is not a rejection of mature frameworks. It is a refusal to let a framework’s convenient identity, retry, logging, control, dataset, experiment, or score semantics become company authority by accident.

### 3.3 Sandbox and provider-side capability risk

Inspect’s agent-bridge documentation states that several capabilities execute outside the sandbox at the model provider:

```text
web_search
web_fetch
code_execution
remote MCP servers
```

The sandbox bridge withholds these by default unless explicitly granted, which is useful. However, a Mastermind adapter must independently attest the granted capability profile and reject any unexpected provider-side feature. A container egress deny rule is not sufficient if the model provider executes a tool remotely.

The documentation also states that the in-process `agent_bridge()` already runs with host network/filesystem access and has no sandbox boundary to defend. It must not be described as isolated. Fresh high-risk Mastermind tasks should use a true sandbox/process boundary or be invalid.

Remote media references can also trigger dereferencing outside the sandbox; the bridge requires inline data URIs for sandboxed requests. The adapter must therefore bind media/input handling, not merely text tools.

Primary source:

- <https://inspect.aisi.org.uk/agent-bridge.html#granted-capabilities>

### 3.4 Checkpoint and retry semantics

Inspect checkpoint recovery can restore agent state, selected sandbox filesystem paths, events, and internal store data into a fresh sandbox and continue at a turn boundary. Checkpoint triggers wait for a turn boundary and do not interrupt in-flight tools.

Those semantics are valuable for some long-running evaluations but invalidate task classes whose purpose is to test a genuinely fresh constitutional/cold start. For those scenarios:

```text
checkpoint = forbidden
resume = forbidden
retry-as-continuation = forbidden
```

A crash creates an invalid run. A later rerun receives a new Mastermind run identity after effect/cleanup reconciliation.

The adapter must also set checkpoint failure behavior explicitly. Defaults that tolerate checkpoint failures or retain incomplete state are not acceptable when cleanup and exact configuration are validity requirements.

Primary source:

- <https://inspect.aisi.org.uk/checkpointing.html>

### 3.5 Log semantics and privacy

Inspect writes a log for each evaluated task. Current documentation describes `.eval` as the default compact format, with APIs for reading headers/samples and exporting data. It also supports post-evaluation score/tag/metadata editing with provenance and history.

Important implications:

- The mutable/current view of an Inspect log cannot be Mastermind’s immutable run receipt.
- Mastermind must record the exact original and accepted scorer-pass references separately.
- Inspect log format/version upgrades cannot reinterpret historical Mastermind evidence.
- Raw logs can contain sample input/output, events, traces, model usage and media.
- By default, Inspect logs raw model API request/response data for the first few calls and all error calls; sensitive scenarios must set explicit logging policy.
- Image/media retention must be disabled or bounded when the scenario does not require it.
- A successful Inspect log status is necessary evidence, not sufficient Mastermind validity.

Primary source:

- <https://inspect.aisi.org.uk/eval-logs.html>

### 3.6 Control channel and intervention

Inspect can expose operational controls for active evals and can support human intervention. These are evaluation-process controls only. They cannot become:

- Executive Job cancellation;
- production worker/session authority;
- a Mastermind continuation carrier;
- a policy approval surface;
- an acceptance decision.

The adapter should disable the control channel by default and add it only for a reviewed operational need. Intervention must be recorded as a configuration change and generally makes a run incomparable with autonomous arms unless predeclared.

### 3.7 Inspect decision

**Decision:** adopt later as a subordinate optional adapter after EVAL-R0 and one OHF real run.

**Use for:** batch orchestration, framework-native tasks, sandboxes, agents, log extraction, scorer execution, concurrency and analysis helpers.

**Do not use for:** Mastermind run identity, Executive lifecycle, source authority, capability truth, acceptance, routing, policy promotion, canonical storage, or fresh-session semantics without independent proof.

**Falsifier:** reject the adapter if it cannot prevent/attest provider-side capability widening, bind exact model/tool/environment/procedure identity, export privacy-safe evidence, and preserve Mastermind validity without invasive duplication.


Sharing uploads an evaluation/report snapshot that can include prompts, variables, outputs, traces, metadata, provider configuration fields, media/blob references and scan artifacts. Sharing must be disabled and absent from the V1 capability profile.

Primary sources:

- <https://langfuse.com/docs/api-and-data-platform/features/experiments-api>
- <https://langfuse.com/docs/compatibility>
- <https://langfuse.com/changelog/2026-08-17-langfuse-v4>

Langfuse V4 is generally available in August 2026. Its Experiments API exposes experiment and item data for analysis, and its current platform uses an observations-first model with OpenTelemetry-based SDKs. Cloud legacy paths have a November 16, 2026 cutover; self-hosted deployments control migration but still carry server/SDK/API compatibility requirements.

This is a capable current product, but it is evolving at exactly the point Mastermind would be designing its own canonical contract. V1 must not tie evidence truth to that migration surface.

### 5.2 Service and retention burden

Self-hosting Langfuse adds a service topology that includes durable databases/ClickHouse and potentially object storage, cache, backup, access, deletion and migration operations.

Official retention documentation states that self-hosted data is stored indefinitely by default without a retention policy. Project-level data retention is an Enterprise feature. Deleted traces can leave dataset references pointing to non-existent traces. Server-side data masking, advanced audit logs and project-level RBAC are also listed as Enterprise features.

Primary sources:

- <https://langfuse.com/docs/administration/data-retention>
- <https://langfuse.com/self-hosting/license-key>
- <https://langfuse.com/self-hosting/security/data-masking>

These are not objections to Langfuse’s quality. They are direct costs and privacy obligations that require a measured product benefit.

### 5.3 Licensing

Langfuse states that code outside `/ee` is MIT licensed and core self-host features are available in the OSS edition, while advanced security/retention/audit features require Enterprise licensing.

Primary sources:

- <https://langfuse.com/handbook/chapters/open-source>
- <https://langfuse.com/pricing-self-host>

### 5.4 Langfuse decision

**Decision:** hold out of V1.

**Reconsider only when:**

- Mastermind has enough valid runs that local artifact/DuckDB analysis produces measurable reviewer friction;
- a dedicated evidence UI materially improves a Chairman/Sol/platform-owner job;
- private retention, backup, deletion, audit and role access are solved;
- exact v4 server/SDK/API compatibility is pinned;
- all data is a rebuildable projection from Mastermind receipts;
- the service cannot become a second experiment/policy truth plane.

## 6. DuckDB and Parquet

Mastermind already declares DuckDB in its project dependencies and uses PyArrow. A derived local analysis layer can therefore avoid a new service in early waves.

Decision:

- immutable JSON receipts remain canonical;
- Parquet partitions are derived projections;
- DuckDB runs deterministic paired/aggregate queries over those projections;
- projection manifests bind source receipt digests and analysis version;
- projections may be deleted/rebuilt;
- no table becomes the only copy of a run, scorer pass, or owner decision.

This is the lowest-operational-cost route to comparison matrices, invalid/degraded counts, paired deltas, uncertainty inputs and quality/resource frontiers.

## 7. Architecture option comparison

### Option A — Inspect-centric execution and identity

**Advantages:** fastest access to mature task/dataset/agent/scorer/log/UI/concurrency primitives.

**Rejected as initial core because:** Inspect retry/checkpoint/control/log identities could leak into Mastermind lifecycle and acceptance; provider-side capabilities need independent attestation; logs are editable/current views; privacy configuration is nontrivial.

### Option B — fully bespoke Mastermind evaluation platform

**Advantages:** exact company semantics.

**Rejected because:** it would recreate orchestration, sandboxes, agent bridges, concurrency, viewers and generic scorer machinery that mature frameworks already provide.

### Option C — thin Mastermind canonical core plus pluggable runners

**Selected.**

Mastermind owns:

- closed scenario/experiment/run/scorer/evidence-reference contracts;
- canonical bytes/digests and create-only identity;
- validity and invalid/degraded semantics;
- privacy and no-authority law;
- owner handoff.

OHF owns:

- the first exact fresh App Server runner.

Inspect may own later:

- generic evaluation orchestration and native log/scorer execution.

Promptfoo may own later:

- adversarial payload generation/execution.

DuckDB/Parquet may own later:

- rebuildable comparative analysis.

Outcome Learning owns:

- organizational expectation/outcome studies and policy promotion.

This composition minimizes new code while preventing framework convenience from becoming company authority.

## 10. Final research conclusion

The strongest rollout is not “install an evaluation platform.” It is to create the minimum Mastermind-specific evidence constitution that frameworks cannot supply, prove it with the already-owned OHF substrate, and add mature framework components only where measured value exceeds new semantic and operational cost.

This preserves speed, auditability, vendor neutrality, privacy, and organizational authority simultaneously.
