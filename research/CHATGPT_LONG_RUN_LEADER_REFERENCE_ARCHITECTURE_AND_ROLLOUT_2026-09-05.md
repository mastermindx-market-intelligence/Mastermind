## 1. Product thesis

The product is not “ChatGPT with a terminal.” It is a governed organization in which a scarce frontier-reasoning session can lead consequential work without becoming the scheduler, shell daemon, task database, or sole memory of that work.

The primary user job is:

> Chris states a difficult company outcome once. The correct Sol responsibility reconstructs current truth, resolves the problem at the required level, delegates bounded execution, receives real evidence, rejects inadequate work, and advances the company without Chris hunting tabs, carrying messages, or rebuilding context.

The machine job is:

> Preserve exact identity, authority, source, effect, execution, evidence, continuation, and correction truth while replaceable reasoning sessions perform high-value cognition over existing canonical owners.

The moat is not the plugin or the model. It is the accumulated correction-safe graph of Mastermind responsibilities, decisions, discoveries, evidence, product architecture, implementation, outcomes, and observed operating behavior, combined with a workflow that lets frontier models use it reliably.

### 1.1 The 10/10 end-state

A complete system demonstrates all of the following on one real approved program:

1. A fresh authorized leader recovers the full product outcome and current company state without relying on prior chat memory.
2. It sees only source-attributed, freshness-aware facts and explicit unknowns.
3. It can use task-relevant code, data, documents, images, and product surfaces without unrestricted exposure to the Chairman's machine.
4. It produces a coherent architecture or decision before implementation convenience narrows the outcome.
5. It admits or delegates one bounded mission through the existing authority and lifecycle owners.
6. The worker executes in an isolated exact context, survives the leader turn, and returns attributable evidence.
7. A material return reaches the exact responsible leader or a truthful continuation path without model-driven polling.
8. The leader adversarially reviews the result against the original user and machine outcome, not only green tests.
9. The result is proven through the real producer, real consumer, actual deployment or browser/machine path where required.
10. Durable records let a later fresh session recover what became true, what remains false, and the exact next action.
11. Context exhaustion or session failure can cause one reconciled succession, with no duplicate effect and no stale predecessor regaining governed write authority.
12. The Chairman can inspect status, evidence, blockers, and next actions in one coherent cockpit without that cockpit owning any underlying truth.
13. The system scales to multiple accounts and many parked responsibilities without account sharing, limit evasion, title-based session election, blind failover, or hundreds of continuously generating tabs.
14. Every claimed autonomous modifying route is either technically enforced at its existing owner or explicitly excluded from the autonomy claim.

Anything less is a useful partial capability, not “autonomous long-run ChatGPT leadership.”

## 2. Architectural ruling candidate: one experience, federated authority, replaceable cognition

The coherent user experience should compose existing systems rather than replace them:

```text
Chairman
  |
  v
Mastermind Sol experience
  |-- current protected procedure
  |-- source-attributed company/context reads
  |-- bounded decision and intent workflows
  |-- evidence and review workflows
  |-- exact surface/continuation workflows
  |
  +--> Executive OS ---------------- Job / Attempt / Worker / Event / admission
  +--> Agent OS -------------------- responsibility / decision / discovery / handoff
  +--> RuntimeBinding -------------- current exact reasoning or execution target
  +--> Capacity -------------------- eligible account/model/provider placement
  +--> Wake / Company Dialogue ----- attention, delivery, semantic returns
  +--> GitHub ---------------------- implementation and immutable evidence
  +--> Code Intelligence ----------- global discovery and exact-worktree semantics
  +--> Worker provider/runtime ----- isolated execution and durable process state
  +--> Web-Sol / computer provider - narrow surface actuation
  +--> Linear / Slack -------------- selected projection and transport
```

The reasoning session is a replaceable office occupant. The responsibility, lifecycle, evidence, and organizational state live elsewhere.

### 2.1 Hard no-rebuild boundaries

Do not create:

- a ChatGPT session database;
- a plugin task queue;
- a “prime/worker” company lifecycle parallel to Executive OS;
- another transcript memory store;
- a second responsibility or workstream graph;
- another RuntimeBinding or Capacity registry;
- a browser-tab election service;
- another retry/effect ledger;
- a plugin-owned process registry;
- a second company-wide code index or code-truth database;
- a generic super-MCP that mixes company reads, filesystem/shell, browser control, Executive admission, GitHub release, Slack, Linear, credentials, and administration;
- a model-driven always-on polling supervisor;
- an OpenClaw or Chat On Steroids authority plane;
- a new ranking signal that can originate company priority or privileged action.

A local adapter may keep ephemeral transport handles necessary to talk to an existing owner. It must not become canonical state merely because the provider lacks an ergonomic protocol.

## 3. Personas and responsibility shapes

### 3.1 Chairman cockpit

Needs a high-density answer to:

- What outcome is each major program pursuing?
- What is actually running, returned, blocked, parked, or terminal?
- Who or which exact responsibility owes the next judgment?
- What evidence makes the claim true?
- What is stale, unknown, contradictory, or inaccessible?
- What can be done now, and what requires Chairman/admin confirmation?

The cockpit may render and navigate. It does not own lifecycle, priority, authority, or completion.

### 3.2 Meta-CEO Sol

Owns portfolio orientation, cross-program contradiction resolution, executive architecture, bounded resource allocation inside approved rules, major acceptance, and Chairman communication. It should receive compact program returns, not every worker transcript or repository file.

### 3.3 Program CEO / Project Sol

Owns one coherent program or bounded workstream, preserves its full thesis, resolves dependencies, commissions bounded verticals, consumes returns, and updates durable records. It is the normal long-run leader unit.

### 3.4 Integrator and Auditor Sol

The Integrator resolves independently developed plans or returns into one coherent architecture. The Auditor independently checks outcome, authority, evidence, negative states, duplication, and real-path completion. Neither gains merge/release authority merely from its role name.

### 3.5 Bounded worker

Executes a concrete mission in an exact repository/workspace/provider context. It does not reconstruct the whole company, select its own authority, silently widen scope, self-approve, or create successor work.

### 3.6 Deterministic sidecar

Performs cheap condition detection, state projection, batching, process I/O, and event transport. It does not reason about company strategy or create operations. It wakes reasoning only on a material event under the existing Wake/RuntimeBinding law.

## 4. Account and surface architecture

### 4.1 Personal Pro leader route

Personal Pro remains a first-class reasoning surface even without arbitrary custom MCP writes:

```text
Personal Pro Chat
  -> protected bootstrap and current procedure
  -> approved native/read app evidence and Mastermind read projections
  -> bounded Chairman/Sol decision
  -> supported dedicated relay or confirmed owner-specific action
  -> Executive OS / Company Dialogue / worker runtime
  -> evidence return
  -> exact leader continuation or durable succession
```

Personal Pro should not receive a disguised write endpoint labeled as a read tool. A supported Slack or native app action is still only that app's action; it is not automatically Executive admission or exact child authority.

### 4.2 Business leader route

Business provides the strongest coherent plugin/app experience:

```text
Business Chat
  -> exact reviewed Mastermind Sol plugin generation
  -> authenticated Steward app for company reads
  -> separately authenticated Executive app for root CEO intent
  -> native GitHub / Linear / Slack where useful and separately authorized
  -> Company Dialogue / worker runtime / evidence
```

The accepted architecture remains one experience with independently versioned authority surfaces. Read, root admission, exact-child dialogue, surface presence, GitHub actions, and administration should remain separable by app generation, scope, confirmation, and rollback.

### 4.3 Codex and other worker surfaces

Codex/App Server, Claude Code, Cursor, or another approved provider are execution surfaces. They may retain provider thread or process continuity, but Executive OS remains the company lifecycle owner. Provider-native state is evidence and an actuator coordinate, not another company Job or responsibility.

### 4.4 OpenClaw or generic computer-use providers

Use only as a bounded actuator where it supplies a capability the existing provider lacks and its host/session isolation is actually proven. It may observe or manipulate an approved disposable surface. It must not become:

- the Meta-CEO;
- the session registry;
- the account selector;
- the durable memory store;
- the retry authority;
- a silent fallback when another mutator is uncertain;
- a credential broker;
- a multi-tenant isolation assumption unsupported by its actual gateway.

### 4.5 Chat On Steroids disposition

Recommended production disposition: **selective pattern/code adoption under existing owners, not wholesale installation as the company control plane**.

Potentially useful components or patterns:

- small read/patch/exec/continue tool semantics;
- capability-surface separation;
- batched reads and bounded outputs;
- process output deltas;
- recent-observation binding for desktop actions;
- invocation-time permission rechecks;
- explicit incomplete and unknown states;
- local recording as disposable debugging evidence where approved.

Components that conflict with Mastermind ownership if adopted as authorities:

- prime/worker registry;
- independent session lifecycle;
- automatic compaction as canonical succession;
- local conversation database as organizational memory;
- free-running model loop as company policy;
- browser DOM/Fiber signals as semantic ACK or execution truth;
- broad shell and desktop privileges under the interactive user's account.

Any source reuse requires an immutable upstream pin, license preservation, dependency/SBOM review, threat analysis, tests, and an owner-specific adapter. An upstream update is a new candidate generation, not an automatic production update.

## 5. Context architecture: progressive disclosure over existing truth

A leader should not load the entire company or repository by default. The experience should compose four tiers without creating a new canonical context store.

### Tier 1 — constitutional envelope

- current Chairman instruction;
- protected repository and Skillpack identity;
- canonical owner map;
- authority/effect/correction laws;
- current reasoning route and proven tool limitations.

### Tier 2 — responsibility hot state

- exact `responsibility_ref`;
- user and machine outcome;
- accepted decisions and explicit rejected alternatives;
- organizational wave state;
- current Job/Attempt/Worker and effect state where available;
- exact RuntimeBinding and attention state where available;
- source disagreements and freshness;
- one next lawful action.

### Tier 3 — program evidence bundle

- governing architecture and plans;
- relevant PRs/branches/checks/reviews;
- open reciprocal dialogue;
- dependencies and collisions;
- production proof and capability ledger;
- bounded raw evidence references.

### Tier 4 — exact raw evidence

- selected source files and diffs;
- logs and artifacts;
- test output;
- browser or machine proof;
- external primary sources.

The leader asks for Tier 4 only where it discriminates a decision. Immutable content can be cached by exact digest at the serving owner; runtime state cannot become fresh merely by being copied into a new wrapper.

### 5.1 Candidate leader context view

This is a conceptual projection, not a new wire schema or store:

```text
responsibility_ref
user_outcome
machine_outcome
accepted_decision_refs[]
rejected_alternatives[]
capability_ledger[]
current_job_attempt_worker
current_effect_state
current_binding_generation
attention_and_dialogue_edge
source_refs_and_freshness[]
material_disagreements[]
active_collisions[]
evidence_refs[]
next_lawful_action
modification_allowed_and_reasons
```

Every field is derived from an existing owner or remains unknown. Model-generated synthesis is labeled as synthesis and cannot overwrite owner facts.

### 5.2 Checkpoint content

Before a session retires, delegates, or reaches material context pressure, preserve:

- the original outcome and current success ruler;
- decisions made and why rejected alternatives remain rejected;
- exact evidence supporting material claims;
- current source and operation identities;
- open effects or ambiguous boundaries;
- current worker/dialogue obligations;
- unresolved risks and falsifiers;
- one exact continuation action.

Do not export hidden chain-of-thought. Do not depend on the dying session to write the only recoverable checkpoint.

## 6. Reasoning architecture and Pro-mode utilization

The company should consume scarce Pro turns on cognition that changes the quality of the outcome:

- long-horizon scientific or market research synthesis;
- cross-system architecture;
- hard debugging where multiple explanations must be discriminated;
- adversarial product, security, or acceptance judgment.

Routine ACK, START, status, routing, polling, message transport, foregrounding, simple tests, and mechanical edits remain deterministic or non-Pro/worker work under current law.

### 6.1 How to use a large daily allowance without wasting it

Scale by creating enough high-quality, non-colliding responsibilities, not by padding individual turns:

1. Select current company problems from existing strategic/Agent OS owners.
2. Define one substantial observable decision or architecture result per reasoning responsibility.
3. Supply a complete Pro-mode receipt when the current law admits it.
4. Bound dependencies, exact sources, non-goals, and stop conditions.
5. Run independent first passes where diversity is valuable.
6. Use one Integrator and one Auditor rather than repeated undirected “continue” turns.
7. Park dependency-gated responsibilities without active generation.
8. Route implementation to bounded workers.
9. Wake the leader only for decisions, results, material source movement, or exceptions.
10. Retire or rotate the chat after durable closeout rather than keeping an empty turn alive.

The number of available messages is a capacity input, not a target. A daily plan that creates hundreds of shallow turns while review, source ownership, host capacity, or human confirmation is saturated is false utilization.

### 6.2 Candidate selection ruler

The existing priority, Capacity, and routing owners should favor tasks that meet all of:

- strategically material outcome;
- meaningful unresolved uncertainty;
- frontier reasoning changes the expected decision quality;
- enough current evidence is accessible;
- no active collision or effect uncertainty;
- an actionable downstream consumer exists;
- completion can be tested;
- durable continuation is available.

A model may recommend candidates. It cannot originate company priority, capacity, or authority by scoring them.

## 7. Worker execution architecture

### 7.1 Complete journey

```text
leader freezes one observable mission
-> existing admission/placement owner resolves operation and receiver
-> worker receives exact scope, source, authority, non-goals and proof contract
-> worker materializes an isolated exact worktree/runtime
-> worker establishes path/semantic collision and effect truth
-> separate START precedes first effect
-> commands/subtasks survive leader inactivity under existing provider/Attempt ownership
-> worker creates immutable evidence
-> worker returns result/blocker/decision request through exact dialogue
-> exact leader consumes and adjudicates
-> worker receives CONTINUE or terminal STOP
-> source writer and watcher obligations close explicitly
```

### 7.2 Bounded subagents

A provider may expose subagents or parallel workers. They are child execution mechanisms inside the one admitted operation and assigned envelope, not independent company Jobs unless Executive OS deliberately creates them.

The parent worker must retain:

- fixed maximum concurrency and depth;
- exact task partition;
- shared source ownership rules;
- no two writers on the same path/effect;
- attributable outputs;
- aggregate resource budget;
- cancellation and cleanup receipts;
- no self-created successor program.

### 7.3 Long-running process handles

A continuing command handle must be bound to:

- Job/Attempt/Worker or the accepted provider execution identity;
- exact workspace and command policy;
- start time and process identity;
- output cursor and truncation behavior;
- current running/terminal/unknown state;
- cancellation request and actual termination separately;
- cleanup and survivor census where required.

A provider reconnect may recover the handle. It must not launch a replacement solely because the first handle is temporarily unavailable.

## 8. Local files, shell, images, and desktop control

### 8.1 Separate capability classes

```text
R0 file/image observation
R0 code discovery and semantic reads
W1 bounded patch within exact worktree
W1 reviewed build/test command families
W2 broader local command or desktop action
A3 host, credential, service, connector, or policy administration
```

Do not fold all classes into one “computer” permission.

### 8.2 Filesystem rules

A file adapter should enforce exact approved roots, symlink/realpath containment, file type and size limits, binary handling, no credential or browser-profile roots, and current permission checks on each call. A root allowlist is not a shell sandbox.

### 8.3 Shell rules

Unattended shell execution requires an actual process/container/user boundary, not only a starting directory. The admitted command family, network behavior, environment, credentials, child process rules, CPU/memory/disk/time limits, and cleanup contract must be explicit.

Where arbitrary shell is necessary for a human-attended coding worker, the autonomy claim must be correspondingly narrow. Do not claim that the model is technically unable to escape merely because procedure forbids it.

### 8.4 Image and browser proof

A worker may inspect screenshots or renderings needed for product proof. Evidence must bind the screenshot to the exact deployment, route, viewport, account-safe fixture, timestamp, and asserted condition. Screenshots of secret-bearing settings, tokens, cookies, Keychain, authenticated admin pages, or unrelated windows are excluded.

### 8.5 Desktop actions

Every consequential desktop action should bind to a recent observation, exact approved application/window/profile, expected precondition, and closed action. If the target changes, refuse. A multi-step action reports completed steps and the exact uncertain boundary; it never replays the batch blindly.

Clipboard read/write should be independently permissioned and normally disabled. The clipboard is not a credential transport.

## 9. Browser and ChatGPT session architecture

### 9.1 Web-Sol remains the narrow exact-session actuator

The live-seat surface should expose only reviewed high-level actions. Generic click, type, arbitrary JavaScript, transcript export, account selection, newest-tab selection, and caller-selected navigation remain outside the governed Web-Sol surface.

Low-level browser automation may exist in a disposable worker testing environment. It is not a back door into persistent Chairman seats.

### 9.2 Derived session-health experience

The cockpit may project, from existing owner evidence:

```text
HEALTHY
SUSPECTED_PRESSURE
ROTATION_REQUIRED
AUTH_REQUIRED
TRANSIENT_FAILURE
SURFACE_UNUSABLE
UNKNOWN
```

These are user-facing interpretations of existing facts, not a new canonical session lifecycle. Slow generation, one error, a spinner, or model prose cannot prove context exhaustion.

### 9.3 Exact rotation

The accepted sequence remains:

1. resolve exact predecessor responsibility and RuntimeBinding;
2. establish a closed rotation reason;
3. reconcile all modifying effects;
4. ensure durable continuation exists independently of the predecessor;
5. resolve the exact account/profile/Project and current generation;
6. create one successor candidate;
7. deliver one deterministic continuation bootstrap;
8. verify same approved profile/Project and a different exact conversation;
9. establish semantic readiness through the accepted dialogue/ACK owner;
10. advance RuntimeBinding generation and fence the predecessor;
11. update navigation without rolling authority backward if navigation fails;
12. perform the next governed action.

A lost create or submit response becomes effect-unknown and blocks another candidate. Visible model output is not semantic readiness. A stale predecessor that later responds does not regain the Mastermind binding.

### 9.4 Exact wake

A material event may resume the current exact provider task only when an accepted exact-native wake/resume path can address the verified current binding. Otherwise the event remains durable and the system reports `WAKE_UNAVAILABLE` or equivalent. It must not pick another tab, session, account, or newest conversation.

A durable MCP task, open connection, browser notification, or Slack delivery does not prove exact ChatGPT reasoning wake.

## 10. Authority coverage architecture

### 10.1 Why endpoint fencing is insufficient by itself

One chat may have several modifying avenues:

- Mastermind Executive MCP;
- native GitHub;
- native Slack;
- native Linear;
- generic filesystem or shell;
- desktop/browser computer use;
- another custom MCP app;
- Codex/Claude provider control;
- host/service administration.

A RuntimeBinding check at one endpoint cannot logically deny an action through another independently authorized endpoint.

### 10.2 Authority coverage view

For one claimed autonomous capability, derive a read-only evidence view:

```text
capability_claim
principal_and_surface_class
reachable_mutators[]
for each mutator:
  exact actuator owner
  actual grant/scope
  confirmation behavior
  current binding/context enforcement
  source/TOCTOU enforcement
  idempotency/effect reconciliation
  stale-generation behavior
  disposition = ENFORCED | DENIED | ATTENDED_ONLY | UNKNOWN
uncovered_paths[]
claim_supported = false when any required path is UNKNOWN or ATTENDED_ONLY
source_refs[]
```

This is an audit composition, not a new permission registry. The facts remain with their existing provider, app, RuntimeBinding, and action owners.

### 10.3 Approval is additive, not authority

A provider or ChatGPT approval prompt may prevent an unattended action in a particular interaction. It does not establish the Mastermind identity, scope, current source, effect reconciliation, or durable continuation. Conversely, a provider grant does not eliminate native confirmation requirements.

### 10.4 Staged posture

- Company-state and research leaders: read-only by actual app/provider grants where possible.
- Root CEO admission: one narrow Executive path, separately confirmed and idempotent.
- Existing-child dialogue: exact bound Company Dialogue path.
- GitHub review/release: owner-specific prepared/confirmed actions and exact-head evidence.
- Broad native writes or shell: human-attended until technical enforcement and stale-actor behavior are proven.
- Administration: isolated normally disabled principal/app generation.

### 10.5 Minimum autonomy falsifier

Use two synthetic chats sharing one authenticated human principal, one synthetic responsibility, one generation transition, and every enabled mutator. Prove:

- the current generation can perform only the claimed permitted action;
- the old generation is refused by every route included in the claim;
- paths not covered are clearly labeled and remain attended/unavailable;
- an unrelated sibling's legitimate capability is not revoked;
- no unknown result is retried;
- no second authority service is introduced.

## 12. Material return architecture

A material return is an event the existing owners can project when it changes the responsible leader's decision set:

- worker `RESULT`;
- `BLOCKED` requiring a ruling;
- `DECISION_REQUEST`;
- exact-head CI/security or review result that changes release eligibility;
- effect reconciliation;
- source-law movement that makes a plan materially stale;
- external dependency satisfied or failed;
- capacity restored for a ready responsibility;
- session health crossing a reviewed rotation boundary.

Unchanged status, ordinary progress, repeated no-match polls, and expected waiting do not wake a frontier model.

### 12.1 Candidate material return view

Conceptual projection only:

```text
responsibility_ref
operation_key
return_kind
canonical_owner
source_event_refs[]
observed_at
new_decision_required
current_effect_state
exact_target_binding_or_unknown
recommended_read_set[]
required_reply_kind
expiry_or_freshness
```

The recommendation cannot send a reply. The exact responsible reasoning session must reread current sources and apply normal procedure.

### 12.2 Return consumption

A return is not complete because Slack delivered it. Completion requires the current responsible parent to consume it and emit one explicit continuation or terminal edge where the dialogue contract requires one.

## 13. Tool discovery and schema economy

### 13.1 Progressive tool discovery

The model should initially see only the plugin workflows and task-relevant app families. Discover or load:

1. Steward/context reads;
2. evidence/CodeIntel reads;
3. exact owner action preparation;
4. low-level worker workbench only for the bound worker mission;
5. administration only during a separately authorized ceremony.

Do not require every chat to discover desktop automation, admin, release, local shell, and all market tools.

### 13.2 Output economy

Responses should be:

- bounded by bytes after final encoding;
- schema-valid and strict JSON where structured;
- explicit about truncation and coverage;
- paginated with owner-authored opaque continuations;
- content-addressed where immutable;
- able to reference large evidence artifacts rather than repeating them;
- designed so blocker, effect, correction, source, and stop fields cannot disappear silently.

### 13.3 Compatibility

A published app generation has one static tool census and digest. Breaking schema changes create a new reviewed generation. The server must not silently expose a different shape under an approved ChatGPT snapshot.

Optional protocols such as MCP Tasks are used only after actual client/server negotiation. Old experimental and current extension shapes cannot be mixed.

## 14. Security architecture

### 14.1 Threat classes

- prompt injection in repository, Slack, Linear, GitHub, web pages, files, images, tool results, and Agent OS records;
- stale or malicious plugin/package content;
- overbroad provider OAuth grants;
- approval settings mistaken for technical restrictions;
- stale session retaining another write path;
- shell or desktop escape from a cosmetic allowlist;
- secrets exposed through settings, clipboard, screen, argv, environment, logs, recordings, or tool output;
- symlink/path traversal;
- session/title/account misidentification;
- lost responses and duplicate effects;
- second worker/source writer collision;
- third-party dependency or update compromise;
- recorded transcripts becoming an unofficial truth store;
- output truncation hiding a blocker or effect state;
- model self-attestation of mode, identity, or completion.

### 14.2 Required controls

- current same-commit procedure loading;
- retrieved text treated as data;
- least-privilege resource-specific OAuth and host principals;
- exact audience, subject, scope, issuer, expiry, and client checks;
- exact source and binding checks at modification time;
- stable operation identity and canonical status reconciliation;
- sealed worktree/process boundaries;
- secret-free model-visible output;
- immutable package and app generations;
- no automatic third-party update;
- explicit confirmation and rollback for consequential changes;
- independent review for major source and production proofs;
- all-mutator coverage before strong autonomy claims;
- no account sharing or usage-policy evasion.

### 14.3 Session recordings

Local recordings may aid debugging only when expressly approved, bounded, access-controlled, retention-limited, and excluded from credentials and secret-bearing pages. They are not Agent OS, evidence authority, or a replacement for structured returns. Deleting a recording cannot erase canonical company history; retaining it cannot confer authority.

## 15. Observability and evaluation

### 15.1 What to measure

Per task and aggregate:

- user/machine outcome success;
- factual/source correctness;
- preserved original intent;
- proof completeness;
- unauthorized or duplicate effects;
- manual interventions;
- context-recovery failures;
- tool calls and discovery calls;
- response bytes and repeated immutable reads;
- source freshness failures;
- waiting time by category;
- time to first useful decision;
- accepted capabilities per scarce reasoning turn;
- worker execution and review latency;
- number and type of expected RED/protective refusals;
- product or machine-consumer completion;
- stale-session action coverage.

### 15.2 What not to claim

Do not infer:

- GPU-hours from elapsed browser time;
- hidden reasoning time;
- useful work from an open spinner;
- completion from token consumption;
- autonomy from a large number of tabs;
- reliability from zero visible errors;
- production proof from source tests;
- exact model/mode from model prose;
- context exhaustion from one provider error.

### 15.3 Benchmark design

Use paired, equivalent, isolated tasks with matched model/mode, permissions, source snapshot, time budget, and independent rubric. Prevent answer leakage between conditions. Include architecture, research, hard debugging, implementation review, interrupted recovery, and multi-source reconciliation. Report each task and disagreement, not only averages.

The forty-case companion file supplies adverse definitions. A separate machine-readable 24-task protocol on this PR specifies the evaluation design; it is also records-only and unexecuted.

## 19. Durable completion and learning

A rollout stage is not complete merely because source landed. Closeout records:

- before/after capability;
- exact source and deployment identities;
- tests/security/review evidence;
- real user or machine proof;
- negative proof and exclusions;
- unresolved effects and limitations;
- observed metrics;
- decisions and discoveries;
- one next action;
- explicit dialogue/watch termination.

Learning should answer:

- Did the leader reach better decisions?
- Did the system reduce Chris's routing/recovery burden?
- Did workers receive enough context without reconstructing the company?
- Did evidence quality improve?
- Did accepted capabilities per scarce turn improve?
- Which failure classes dominate?
- Did authority or source mistakes increase?
- Did any infrastructure become technically present but practically unused?

The next generation is justified by observed failure or value, not by a desire for more mechanisms.
