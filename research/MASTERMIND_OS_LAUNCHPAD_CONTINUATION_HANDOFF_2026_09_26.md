## Current client contract

The launch form receives owner-supplied project/profile choices and emits typed intent. The session component receives bounded messages and an opaque session identity. Neither constructs a URL, runtime identity, grant, shell command, or storage record.

Each launch, send and stop callback receives a completion handle correlated to that exact action. The host may invoke it only after reconciling an accepted or refused terminal outcome. Lost responses, thrown exceptions and unknown effects must leave the action pending. A busy prop or error string is display state and cannot release the duplicate guard. Completion for an old session must not mutate the current session. This is component behavior, not durable owner-side deduplication.

The UI-local operation controller is separately reviewed. Its injected port and pointer store are not production adapters. Before use, the actual owner must supply a synchronous, effect-free pointer preparation step; store-before-submit behavior; exact operation/kind/target receipt matching; authenticated read-only reconciliation; principal isolation; a monotonic generation; and exact-pointer clearing. The host must invalidate results on selection changes. A local abort is not proof of provider cancellation.

Do not persist prompt text or credentials in a pending-operation hint. An accepted launch must include a strictly decoded mission selection before this client can resolve it. A missing or malformed selection keeps the pointer for read-only reconciliation. Target invalidation suppresses rendering and may abort a local request, but retains the original-scope pending pointer; it cannot authorize a second dispatch. Producer reason text must not become a client reason merely because it matches a known label.
