# OS masterplan amendment — always-on company workspace

**Chairman direction: 2026-11-09.** This is an explicit product-experience amendment to the existing [OS completion masterplan](MASTERPLAN.md), not another programme, runtime plan, task store or transfer of live writers. Implementation remains unproven. The original runtime, continuity, release and accepted-outcome obligations stay in force.

## Amendment to §2 — The intended finished product

Mastermind OS must be a unified working environment for a company of persistent Hermes teammates. **Meta-CEO is one of those always-on teammates, with leadership responsibilities and a persistent chat identity—not a separate static office.** The Chairman must be able to address any permitted teammate directly, participate in group rooms, observe actual team-to-team communication and handoffs, and inspect the granular work and artifacts produced by the company.

The existing **Team** destination composes Overview, Conversations, Work, Routines, Artifacts and People. Existing Projects opens contextual AI-maintained plans, task/subtask dependencies and evidence. Existing Inbox owns the human's reserved decisions; Code retains the deep embedded T3 workbench; Settings retains enrolled profiles, models/pools, tools/skills and connections. These are views over existing owners, not independent control planes.

Required connections include persistent direct/group conversation, real collaboration messages, Kanban/work tracking, versioned AI-authored plans, GitHub issues/PRs, drafts and source artifacts, and permission-aware Google Docs/Notion/Paper links or native previews when their real connectors support them. No mandatory manual goal/plan form replaces the previously adopted AI-led intake direction.

## Amendment to Stage 3 / Stage 4 — Connected delivery proof

The required product trace is:

**Human → persistent Meta-CEO or project room → inferred/versioned plan → bounded task and actual teammate handoff → code or document artifact → result returned to the original room → original-parent acceptance.**

Prove direct teammate steering, group membership, real bot-to-bot collaboration, stable project/task/source references and recovery after interruption. Qualify at least one enrolled scheduled routine with the UI/browser closed. A browser dashboard that only polls, an animated office, fixture messages or an enabled-looking toggle does not prove an always-on company.

Every source preview/comment/edit must obey the source's actual permissions and revision. Adding a document link or joining a room grants no source access. No synthetic progress, invented messages, private reasoning exposure or duplicate work on reconnect is permitted.

## Amendment to §7 / §11 — Acceptance and truthful delivery

Acceptance requires the company workflow on authenticated web and macOS consumers, deliberate mobile use, keyboard/accessibility, intended themes/languages, and honest empty/loading/stale/offline/queued/refused/uncertain-effect behavior. Card movement does not independently complete a task or close a GitHub issue. Artifact returned, parent accepted, PR merged, product deployed and consumer verified are distinct.

**Current delivered outcome:** Paper redesign, individual screenshot verification of all twelve new boards, preserved-reference readback, source-linked donor assessment and implementation contract. **Not delivered by this amendment:** runtime implementation, deployment, live-team census, connector enrollment or live consumer proof. The broader OS programme remains open.
