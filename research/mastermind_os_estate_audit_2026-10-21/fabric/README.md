# Fabric work-packet and return contract

This directory contains an authored example and a completeness checklist for **bounded paid Subagent Fabric work beneath an Opus owner**. It does not create a worker, install a role, grant source access or change lifecycle state.

## Binding a proposed package to real execution

1. Select a ready dependency from `WORK_PACKAGES.json`. Its `WP-xx` is a document reference, never a Job/run/lease identifier.
2. Resolve current protected law, exact source/candidate revisions, real immediate parent and original root, permitted effects, source writer/lease, workspace and selected host/route through their existing owners.
3. Resolve task complexity and the least-scarce qualified worker. C0/C1 routine labor belongs in Fabric. Use C2 for difficult bounded labor with objective tests. Keep unresolved C3 judgment with Opus/Fable until it becomes bounded; their direct execution remains available when justified.
4. Set finite budget and expiry from the current grant, including reserved reviewer/repair allowance. Unknown quota is not zero or unlimited. A maximum child count is not free capacity.
5. Give the worker the complete task brief and only relevant source/methods. The included Craft example has `assignment_ref`, `workspace_ref` and `host_ref` null because it is **UNBOUND_AUTHORING**. Replace them only with actual issued references; compilation does not authenticate them.
6. Dispatch through the actual supported Fabric owner, using the tool's current schema. The audit-visible request supports `task_class` values `mechanical`, `fix_build`, `review`, `census`, `audit` and complexity values C0–C3; re-read changed capabilities, not an invented wrapper. Preserve actual `parent_id`, `root_id` and `run_id`.
7. Confirm admission and START separately. Consume the complete retained return, review and integrate it, then record actual original-parent consumption.

## Every complete leaf packet must contain

| Field | Requirement |
|---|---|
| Why and outcome | One bounded user or machine capability, its consumer and why it matters now |
| Source | Exact repository/commit/path, current original PR carrier and material evidence |
| Scope | Exact allowed write paths, existing writer custody, exclusions and permitted effect class |
| Input contract | Identity, event/observation time, completeness, null/unknown, freshness, corrections and source rights |
| Runtime binding | Real original root, immediate parent, assignment/run/grant, actual host/workspace/route |
| Budget | Finite work/elapsed allowance, expiry and review/repair reserve from the existing grant |
| Method | Deterministic validation and arithmetic; model judgment only where appropriate; relevant role method |
| Deliverables | Exact patch/artifact/evidence and a usable consumer result |
| Acceptance | Useful case, discriminating failure cases, independent reviewer and owning consumer |
| Stops | Ambiguous effect/authority/writer, source contradiction, invalidated dependency, exhausted budget, unbounded scope |
| Continuation | Existing canonical owner, one exact next action and original return recipient |

## Return shape

Use the existing result owner and native schema. The following checklist describes the content and creates no new transport:

```json
{
  "planning_reference": "WP-23",
  "actual_assignment_reference": "<issued reference>",
  "original_root": "<issued reference>",
  "immediate_parent": "<issued reference>",
  "state": "RESULT | BLOCKED | DECISION_REQUEST | FAILED | EFFECT_UNKNOWN",
  "outcome": "<consumer-visible result>",
  "source_revision": "<exact commit>",
  "artifact_references": ["<existing retained artifact or PR>"],
  "validation": ["<actual command or scenario and observed result>"],
  "review": "<independent actor, exact revision and disposition>",
  "effects": "<none, known committed effects, or unresolved effect>",
  "limitations": ["<material remaining gaps>"],
  "next_action": "<one concrete owner action>",
  "continuation_reference": "<existing Agent OS record>",
  "parent_consumption_reference": "<actual acknowledgment, or not yet consumed>"
}
```

The placeholder strings above must never be sent as issued identities. An author cannot independently approve its own consequential change. If a worker reports an unknown effect, preserve the original operation and reconcile; do not replace the root, credentials, tool or account to try again. For qualified pre-task quota rejection, use only the existing continuity owner and its actual lease-release/attempt ceiling. There is no generic mid-task replay.

## Example and limitations

`WP-23-handoff-selector.brief.json` is a complete backend authoring example using pinned Macro source. The compiled Markdown adds the installed backend/common Craft methods and records authoring hashes. It asks for a source fix and focused regression proof; it does not assume a semantic ordering rule before the Opus owner chooses one, authorize production records rewrites, or claim the isolated audit reproduction is a full compiler run.

The six `opus/*.brief.json` inputs and compiled Markdown are similarly authored domain instructions. Bind the actual domain assignment before use. Do not paste every domain method into every leaf task; preserve the small task context and one real consumer.
