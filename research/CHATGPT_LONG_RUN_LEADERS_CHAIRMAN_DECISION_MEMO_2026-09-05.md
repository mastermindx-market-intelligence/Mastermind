## Binding product rulings

### 1. Do not install Chat On Steroids defaults into a primary authenticated Chairman environment

Approve only pinned-source, disposable, non-sensitive pattern evaluation. Do not adopt its prime/worker/session registry, local transcript history, automatic compaction or goal loop as Mastermind lifecycle, memory, authority or continuation.

Selective adoption remains eligible for:

- batched reads and bounded continuations;
- structured patch ergonomics;
- durable process handles;
- separate Core/Desktop discovery surfaces;
- invocation-time permission enforcement;
- observation-bound desktop actions;
- explicit partial and effect-unknown results.

FS0 must reuse one already-installed suitable backend when proven or select one pinned backend. Do not build both OpenClaw and DesktopCommander adapters. Do not use `@latest`, vendor remote pairing, telemetry-default acceptance, unrestricted shell-as-sandbox claims, credential access or global configuration overwrite.

### 2. Preserve one experience with existing federated authority

No new Mastermind control plane is approved.

- Executive OS owns lifecycle and CEO admission.
- Agent OS owns durable organizational work.
- RuntimeBinding/Capacity/Wake own exact surface, placement and attention.
- GitHub owns source and immutable evidence.
- Steward/Control Room compose company reads.
- Code Intelligence owns governed global discovery and exact-worktree semantics.
- Company Dialogue owns bounded worker returns.
- Web-Sol and Worker Browser own exact browser/computer actuation.
- Existing local executor and Integration owners retain file/process/tunnel identity for FS0.

The proposed Workbench is a facade over an existing exact Attempt/provider or attended pilot context. It is not a lifecycle, process manager, permission registry, shell authority service or evidence database.

### 3. Separate leader and operator capability profiles

**Leader:** current procedure, company context, evidence, bounded root admission, child state, material returns, review and closeout. No default broad filesystem, shell, desktop, clipboard, credential, account or installation authority.

**Operator:** exact host-injected operation/Job/Attempt/worker/workspace/source/path/network/secret binding. May receive bounded file/process tools and, later, optional disposable desktop tools. The model cannot choose operation identity, privileged actor, host, root, source ref, account, profile, capability generation or effect state.

**FS0 attended pilot:** a deliberately narrow Web-CEO surface over one disposable allowlisted directory and bounded command policy. `ATTENDED_ONLY` is not autonomous fleet authority. A directory allowlist is not shell containment; command policy, environment, timeout, output boundary, process identity and reconciliation are separate controls.

### 4. Every mutator requires pre-effect identity and loss-safe reconciliation

Canonical `operation_key` is host-derived and never caller/model-selected. A non-authoritative client correlation value may not choose authority, owner, idempotency or reconciliation scope.

Every proposed modifying action must:

1. receive an owner-issued immutable action reference before effect;
2. bind that reference to the exact operation, Attempt/capability generation, target, payload digest, preconditions and expiry;
3. consume it at most once;
4. expose read-only reconciliation through the same pre-effect reference;
5. return the one canonical prior result or `EFFECT_UNKNOWN` after duplicate delivery;
6. block retry and provider/account/backend/carrier failover while effect remains unknown.

This applies to workspace patch, process launch, process input, cancellation and desktop action. A general process read is not sufficient to reconcile a launch whose response was lost before the caller learned `process_ref`.

The first independently useful **company-read** capability remains:

```text
→ current reviewed package/app generation
→ authenticated source-attributed Steward read
→ explicit degraded-state behavior
→ another successful read after access-token expiry/refresh
→ rollback/readback
→ two Personal-Pro controls unchanged
```

Protected PR #500 now provides U1 binding/enrollment **source tooling only**. Its truthful state is:

`SOURCE_PROTECTED / U1_BINDING_AND_ENROLLMENT_TOOLING / PRODUCTION_INERT`

Do not commission another U1 source-publication worker. Remaining gates are current-base resolution of the truthful partial Steward S1 carrier PR #463, immutable package/app generation, actual publication/import/install, endpoint and OAuth/resource/subject/client configuration, one useful cockpit read, post-expiry refresh, independent evidence acceptance and rollback/readback.

Future desktop/fleet/autonomous-write proof must not become an invented prerequisite for this bounded read-only step. Conversely, Steward completion does not prove FS0, local shell, exact wake or stale-session fencing.

### 6. Personal Pro receives leadership parity through governed delegation

Personal Pro does not need unsupported custom-MCP writes to lead difficult programs. Preserve the accepted route through protected source, approved reads, supported native action, dedicated Relay/CeoIngress, Executive OS, exact external workers, GitHub evidence, Dialogue returns and Web-Sol continuation.

Do not disguise mutation as read/fetch. The parity target is project leadership and acceptance, not identical direct-computer entitlement.

### 7. All autonomous-action claims must cover every reachable mutator

A stale chat refused at a Mastermind endpoint may still possess an independently authorized native GitHub, Slack, Linear, shell, provider or desktop path. Therefore classify every reachable route for the claimed configuration as:

- `ENFORCED`;
- `DENIED`;
- `ATTENDED_ONLY`, a supported human-confirmed route excluded from the autonomous claim; or
- `UNKNOWN`, which blocks the stronger claim.

App registration metadata, installation scope, access-token scope, repository selection, ChatGPT product action availability, approval behavior and organizational authority are separate evidence layers. Approval prompts are not technical permission revocation. Never prove this by attempting an unauthorized production action.

### 8. Long-running execution and exact ChatGPT wake remain different claims

A worker/process may continue after a reasoning turn. A client may reconnect to a result. Neither proves that the exact inactive ChatGPT leader can be awakened. Preserve durable execution in existing providers/Attempts and return through existing Dialogue/Wake. Exact ChatGPT continuation/rotation remains separately gated by semantic readiness and RuntimeBinding succession.

### 9. Spend Pro turns on frontier judgment, not polling or mechanical labor

Use the current protected Pro-mode exception law. High-value uses include cross-system architecture, hard diagnosis, adversarial judgment and long-horizon synthesis. Handoffs, ACK/START/STOP, polling, monitoring, routing, simple tests and mechanical edits remain non-Pro work.

Optimize accepted capabilities per scarce reasoning turn, recovery quality, intervention rate, duplicate/unknown effects and real consumer completion—not elapsed turn duration or a raw zero-error metric.
