# ChatGPT Pro capacity operating playbook

**Date:** 2026-09-05  
**Parent:** `chatgpt-pro-long-run-leaders-research-20260905-sol-001` / Mastermind PR #490  
**Status:** `RESEARCH_CANDIDATE / RECORDS_ONLY / NOT_CAPACITY_STATE / NOT_ROUTING_AUTHORITY`

This playbook answers the Chairman's capacity question: how to convert a large included ChatGPT Pro allowance across several authorized accounts into sustained, high-value company work without confusing message allowance with guaranteed compute, keeping models alive as polling daemons, sharing accounts, evading limits, or creating a second capacity/router/lifecycle system.

Current plan terms, account eligibility, model availability, limits, reset windows, concurrency, product policy, and actual usage remain current platform and existing Capacity-owner facts. Public documentation and user observations are hypotheses until the specific account/surface attests them. Nothing here authorizes an account migration, automated account hopping, usage-policy bypass, paid-credit purchase, or assignment to an unavailable session.

---

## 1. Capacity thesis

A large message allowance is valuable only when the organization has enough **decision-ready responsibilities** to consume it.

The wrong unit is:

```text
messages used
minutes a spinner remained active
tabs open
nominal account-hours
```

The right unit is:

```text
accepted user or machine capabilities
+ high-quality decisions that unblock them
+ durable research/architecture that prevents rebuild
+ defects and false claims caught before production
per scarce reasoning turn and per unit of Chairman attention
```

A Pro turn can be valuable without lasting 30 minutes. A 60-minute turn can be waste if it polls, rereads immutable material, repeats another session, or produces no actionable consumer.

### 1.1 Theoretical allowance math versus operational truth

For any account family, define:

```text
A = number of currently eligible authorized accounts
S_d = observed daily Sol-Pro allowance per account
A_w = observed weekly Astra-Pro allowance per account
D_d = any observed combined daily cap per account
C = actually supported concurrent active turns
T = measured median elapsed occupancy of an admitted task turn
```

A rough weekly message ceiling is bounded by current plan rules, for example:

```text
weekly_messages <= A * min(7 * D_d, 7 * S_d + A_w)
```

This is an allowance calculation, not a promise that every message will be accepted, run concurrently, take a particular duration, or produce equal value.

If approximately 600 turns per day each occupy 30 minutes of wall time, the resulting 300 aggregate task-hours require 12.5 concurrent active turns on average. At 60 minutes, 600 aggregate task-hours require 25 concurrent active turns. These are arithmetic implications of the assumptions—not observed provider concurrency or reserved GPU-hours.

A portfolio with only six concurrent active turns and 30-minute median occupancy can physically complete at most 288 such turns in 24 hours before failures, pauses, review, and human gates. Therefore the limiting factor may be concurrent serviceability, source ownership, review bandwidth, local host resources, or decision-ready work—not the nominal message cap.

## 2. Four classes of capacity

Do not aggregate all “available turns” into one fungible pool.

### C1 — frontier executive reasoning

Use for:

- product and systems architecture;
- long-horizon research synthesis;
- hard diagnosis;
- adversarial product/security/acceptance judgment;
- cross-system contradiction resolution.

This is where Pro mode may add value under the current complete exception receipt.

### C2 — ordinary included Chat reasoning

Use for:

- bounded current-state recovery;
- routine planning after architecture is frozen;
- straightforward evidence review;
- closeout and projection repair;
- well-scoped research that does not require frontier depth.

Current law makes this the default for Sol-class work.

### C3 — bounded engineering/research workers

Use Terra, CTO Sol, Opus, Grok, Fable, Codex, Cursor, or another current approved avenue according to task ambiguity, risk, surface, cost, and current availability. These workers execute concrete waves; they do not absorb Meta-CEO responsibility.

### C4 — deterministic always-on services

Use for:

- lifecycle and claims;
- source/state projection;
- timers and health;
- material-event detection;
- exact-carrier transport;
- process I/O;
- immutable evidence collection;
- bounded retries where current effect law permits them.

No reasoning model should consume turns merely to keep these functions alive.

## 3. What deserves a Pro turn

A candidate should pass all of the following before consuming frontier reasoning:

1. **Material outcome:** the answer changes a meaningful product, intelligence, risk, company, or release decision.
2. **Real uncertainty:** several plausible explanations or architectures exist.
3. **Frontier advantage:** deeper reasoning can materially improve correctness, coherence, or foresight.
4. **Evidence availability:** enough current source can be obtained to make progress.
5. **No active collision:** no sticky owner or uncertain effect makes another turn duplicative or unsafe.
6. **Actionable consumer:** the output will be accepted, implemented, reviewed, or used by a real owner.
7. **Falsifiability:** success and failure can be distinguished.
8. **Recoverability:** conclusions and next action can be persisted before the session disappears.
9. **Bounded role:** one session has one coherent responsibility rather than an unbounded company prompt.
10. **Current route receipt:** the current protected Pro-mode and worker-routing requirements are satisfied.

A candidate that fails these tests is parked, routed to non-Pro/worker capacity, or returned for missing evidence. The model must not create demand merely to consume allowance.

### 3.1 High-return Pro responsibility types

- competitor and primary-source research that changes product architecture;
- a full experience/intelligence architecture for an ambiguous major program;
- difficult multi-causal incident or defect analysis;
- cross-repository no-rebuild architecture;
- adversarial review of a consequential source or production candidate;
- integration of several independent specialist conclusions;
- scientific hypothesis and evaluation design;
- portfolio-level dependency and resource adjudication;
- high-stakes correction of false-green organizational state.

### 3.2 Pro-ineligible work under current law

- ACK, PICKUP_ACK, START, CONTINUE, STOP;
- status checks and routine progress summaries;
- watcher/polling turns;
- tab foregrounding;
- message relay;
- routine worker placement;
- mechanical edits/tests;
- simple reviews;
- waiting for CI or external dependencies;
- repeated “continue working” when no substantive new decision set exists.

A larger parent program does not make these substeps Pro-eligible.

## 4. Responsibility portfolio design

Scale through many **recoverable responsibilities**, not hundreds of live tabs.

### 4.1 Recommended logical portfolio

```text
one Meta-CEO responsibility
several Program CEO responsibilities
bounded Project Sol responsibilities
independent Integrator responsibilities where needed
independent Auditor responsibilities for consequential work
many worker Jobs/Attempts beneath the existing Executive lifecycle
parked responsibilities consuming no active turn
```

The exact number is determined by current evidence and Capacity, not this document. The Meta-CEO should not load every project's raw context.

### 4.2 Work-in-progress ceilings

The existing Capacity and program owners should establish measured ceilings for:

- active frontier reasoning turns per account;
- active responsibilities per Program CEO;
- concurrent source writers per repository/path family;
- open returns awaiting Sol;
- independent reviews awaiting capacity;
- local CPU/memory/disk-intensive worker processes;
- browser/managed-profile actuators;
- production/admin ceremonies;
- total active child depth and fanout.

Exceeding a ceiling causes backpressure and parking. It does not authorize moving a started operation to another account or converting work into an untracked browser tab.

### 4.3 Review is a first-class bottleneck

Every consequential build needs enough independent review and product acceptance capacity. Starting thirty builders with two qualified reviewers creates false utilization and an evidence backlog.

Track:

```text
builder-ready work
review-ready work
production-proof-ready work
returned decisions awaiting parent
```

Shift new capacity toward audit, integration, or evidence when those queues—not implementation—are limiting outcomes.

This is a conceptual balancing rule over existing owners, not a new queue implementation.

## 5. Daily operating cycle

### 5.1 Intake and current truth

At the start of an operating window:

1. Refresh current protected procedure.
2. Read the compact company/attention state from existing owners.
3. Consume every material worker return already awaiting Sol before minting replacement work.
4. Reconcile current source, collisions, unknown effects, account/surface readiness, and review bottlenecks.
5. Identify decision-ready responsibilities and park the rest.

### 5.2 Allocate cognition

Assign each responsibility to one class:

```text
frontier Pro reasoning
ordinary included Chat reasoning
bounded worker execution
independent review/audit
parked / waiting external dependency
```

Record why frontier reasoning is necessary. Do not infer exact model/mode from model prose.

### 5.3 Run deep work

A substantial reasoning session receives:

- one outcome and success ruler;
- exact source/evidence references;
- decisions and rejected alternatives;
- known unknowns and competing hypotheses;
- task-relevant tools and their limits;
- non-goals and current owners;
- expected downstream consumer;
- explicit stop, checkpoint, and return behavior.

The session frames hypotheses, retrieves discriminating evidence, decides, persists, and yields. It does not spin until a clock expires.

### 5.4 Integrate and audit

Where several independent turns address one problem:

1. preserve independent first-pass conclusions;
2. expose only material disagreements for cross-examination;
3. let one Integrator produce a coherent plan preserving dissent;
4. let one independent Auditor challenge outcome, evidence, authority, duplication, and execution scope;
5. Meta-CEO accepts, requests bounded repair, or rejects.

Repeated mutually anchoring “think harder” turns are less valuable than independent decomposition and audit.

### 5.5 Close or park

Every responsibility ends the window as:

- accepted/terminal with durable evidence and next state;
- returned for a bounded repair;
- explicitly parked with review condition;
- blocked on a named external/admin gate;
- effect-unknown and held for reconciliation;
- active on its exact continuing owner with one known next event.

A chat left open without a recoverable state is not a capacity asset.

## 6. Account and session allocation

### 6.1 Account neutrality before START

For ordinary capacity-selectable work, the existing Capacity/placement owner may choose any eligible authorized account before START. The responsibility and operation remain stable. The actual receiver identifies itself truthfully.

### 6.2 Stickiness after START

After START or any modifying effect, the concrete runtime remains sticky until current RuntimeBinding/Capacity/effect law explicitly reconciles it. Quota exhaustion, slowness, or apparent browser inactivity do not authorize pasting the operation into another account.

### 6.3 Exact-session work

Use exact-session-required binding when the provider conversation itself is the target: native continuation, effect reconciliation, local unpublished work, or an exact session canary. A Slack mention, account nickname, or newly created same-model chat is not a substitute.

### 6.4 Account controls

- no credential sharing outside the authorized user/workspace policy;
- no automated behavior designed to evade plan limits or enforcement;
- no presenting one person's account as another worker identity;
- no model-generated account choice treated as Capacity fact;
- no exposing account identifiers, cookies, tokens, or session storage to model-visible tools;
- no changing one account's provider/app grants without sibling-impact analysis and rollback;
- no claiming account parity until each account/surface generation is independently attested.

## 7. Turn continuation and session recycling

### 7.1 Checkpoint triggers

Checkpoint after:

- a material architecture decision;
- acceptance/rejection of a hypothesis;
- a worker handoff;
- a worker return and Sol ruling;
- source or production proof;
- a detected context-pressure boundary;
- before an exact session rotation;
- before yielding to a long external dependency.

### 7.2 Checkpoint contents

Preserve the outcome, accepted decisions, rejected alternatives, evidence, source/operation/binding identities, open effects, current dialogue, remaining risks, and exact next action. Do not store private chain-of-thought or duplicate full transcripts.

### 7.3 Recycling policy

A healthy session may continue when it still has coherent context and current authority. Rotate only through the existing closed classifier and succession law. Session age, number of messages, title, or a single provider error is not by itself a rotation mandate.

A parked responsibility may release its live Chat binding while retaining its durable Agent OS state. On reactivation, Capacity selects a lawful surface and the current procedure/context is reconstructed.

## 8. Material events versus polling

A reasoning turn should wake for:

- a worker result;
- a decision request;
- a blocker requiring judgment;
- source/review/CI movement that changes release eligibility;
- effect reconciliation;
- external dependency satisfaction/failure;
- a current session-health transition requiring judgment;
- a material new Chairman instruction.

It should not wake for:

- unchanged status;
- ordinary logs;
- repeated in-progress CI;
- an expected waiting period;
- low-value progress prose;
- a healthy process heartbeat;
- repeated absence of a Slack reply.

The deterministic layer coalesces events and supplies a recommended minimal read set. The reasoning session still fresh-reads its current authority and carrier before acting.

## 10. Economic allocation

Do not set permanent percentages before observing the portfolio. Use a rolling evidence-driven envelope with protected reserves.

A candidate initial principle is:

- reserve capacity for urgent incidents and Chairman questions;
- ensure independent review/audit capacity grows with builder capacity;
- prioritize programs with complete evidence and downstream consumers;
- shift idle frontier capacity to deep research, architecture audits, competitor work, and pre-mortems—not mechanical tasks;
- park work when a missing external source prevents useful reasoning;
- use ordinary included Chat for routine CEO cognition and cheaper workers for bounded execution;
- use metered routes only under their separate approved economic exception.

### 10.1 Opportunity-cost ruler

Before spending another Pro turn on a program, ask:

```text
What material uncertainty will this turn resolve?
What decision or capability will consume the answer?
Why is this better than independent review, worker execution, or waiting for evidence?
What other ready responsibility is displaced?
```

A turn without a concrete answer is not automatically forbidden, but it should be recognized as exploratory research and assigned an explicit stopping test.

## 11. Failure modes

- theoretical allowance treated as guaranteed availability;
- usage duration reported as compute-hours;
- Pro mode used for lifecycle messages;
- many sessions repeat the same archaeology;
- several sessions modify the same source or decision;
- workers exceed reviewer capacity;
- large fanout produces shallow, mutually anchored conclusions;
- sessions are left alive to poll;
- Capacity silently switches accounts after START;
- exact-session work lands in a new chat;
- quota exhaustion triggers blind failover;
- stale capacity observations authorize work;
- local CPU/memory saturation makes “parallelism” slower;
- tool/app permissions differ across accounts but are assumed equal;
- broad native actions remain available to stale sessions;
- lack of a real consumer means research accumulates without impact;
- context is lost because durable checkpointing was deferred;
- a metric rewards low visible error by weakening tests or hiding refusals.

## 12. Evaluation and promotion

Use the 24-task matched protocol and 40-case casebook on PR #490 after current owner review. Additionally, run a natural operating-window study that records:

- available versus admitted responsibilities;
- frontier versus ordinary versus worker turns;
- wait and review bottlenecks;
- exact accepted outcomes;
- manual Chairman interventions;
- collisions/duplicates/effect uncertainty;
- recovery and session-rotation events;
- account and host pressure;
- unused capacity and why it remained unused.

Unused capacity is not automatically waste. It may be correct backpressure when source, review, host, or authority gates are unavailable.

Promote a larger active portfolio only when:

- accepted outcome quality remains stable or improves;
- no safety/authority/collision degradation appears;
- review and evidence keep pace;
- Chairman burden falls;
- session recovery is reliable;
- actual provider/host concurrency supports it;
- downstream product throughput—not just messages—improves.

## 13. A concrete phased operating target

The numbers below are **evaluation envelopes, not provider limits or current assignments**.

### Phase A — prove the loop

- one Meta-CEO;
- two to four active Program/Project Sol responsibilities;
- a small number of bounded workers;
- one independent Auditor responsibility;
- exact material-return and closeout discipline;
- one real product/program canary.

### Phase B — prove multiplexing

- several related projects per Program CEO;
- parked responsibilities recover correctly;
- review and production-proof queues remain controlled;
- no increase in duplicate/wrong-owner effects;
- account/surface differences are attested.

### Phase C — scale to measured concurrency

Increase active reasoning and worker envelopes incrementally. At each step, compare accepted capabilities, manual interventions, collision rate, recovery, review latency, and host pressure with the prior stable step.

### Phase D — exploit surplus frontier capacity

Only after execution and review loops keep pace, route surplus eligible Pro capacity to:

- deep competitor studies;
- architecture red-team work;
- scientific hypothesis generation;
- failure pre-mortems;
- product experience alternatives;
- independent research replication;
- evidence quality audits;
- next-generation system design.

These outputs require a declared downstream owner or durable research acceptance process.

## 14. Capability delta and exact next action

Before this playbook, the research established that the nominal allowance could imply hundreds of aggregate task-hours but did not define how to admit, classify, multiplex, park, audit, and measure a high-volume responsibility portfolio under current Mastermind laws.

After this playbook, the capacity thesis is tied to current owners, deep-work eligibility, account/session stickiness, review constraints, deterministic event handling, dashboard requirements, failure modes, and staged evaluation. Runtime capacity and automation remain unchanged.

**Primary next action:** after the one-cockpit Steward read is accepted, freeze and run one bounded Phase-A operating canary: one Meta-CEO, two to four substantial responsibilities, bounded workers, one Auditor, exact returns/closeout, and one real product capability. Use the 24-task protocol for controlled workflow evidence and the real canary for operational evidence. Scale only from observed outcomes and bottlenecks.
