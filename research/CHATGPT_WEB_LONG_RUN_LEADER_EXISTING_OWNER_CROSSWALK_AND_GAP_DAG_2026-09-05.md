## 1. Executive conclusion

The long-run leader product is not one subsystem. It is the **composed user journey** across six existing owner groups:

```text
1. cognition and role topology
2. current company context and cockpit
3. bounded worker execution and code intelligence
4. material return and exact dialogue
5. context succession and stale-surface fencing
6. evaluation, learning and fleet scaling
```

Mastermind already has architecture or source for most of those groups. The principal deficit is that several links remain `BUILT_NOT_PROVEN`, `PARTIAL`, `DARK_OR_DISCONNECTED`, or `NOT_BUILT` as **real producer-to-consumer journeys**.

Therefore the governing strategy is:

> Finish the missing joins and proof ladders inside the existing owners. Do not create a “ChatGPT Automation OS,” “Session OS,” “Agent Swarm OS,” “Long-Run Task DB,” or another super-MCP merely because the user experience spans several systems.

The first independently useful outcome is still one authenticated, source-attributed Business Steward read through the real cockpit, including honest degraded states, post-expiry refresh, and rollback evidence. It does not need full autonomous write authority. The next valuable outcomes are one exact-bound worker workbench vertical, material return to the correct parent, and exact context succession. Fleet concurrency comes last, after evaluation.



Capacity increases active responsibilities/concurrency gradually, preserving reserve, backpressure, exact ownership and rollback. Expansion halts on safety, quality, host, review, or intervention regressions.

- Does this create a Job/task/worker/session/retry state outside Executive OS?
- Does it store decisions/handoffs outside Agent OS or implementation/evidence outside GitHub?

- Does it replace exact worker return with transcript scraping?
- Does it treat permission confirmation as a technical action restriction?
- Does it claim source/CI/import/authentication/QUEUED/visible text is execution or product completion?

- Does it convert an unknown effect into an automatic retry or failover?

A “yes” requires rejection or an explicit new architecture ruling. Most such proposals should be redirected to the existing owner.
