## Executive decision

Mastermind needs one premium place where the Chairman and authorized operators can answer, without Slack archaeology:

1. **What is happening?**
2. **What needs attention now?**
3. **What evidence makes that state true?**
4. **Who or what is currently bound to act?**
5. **What is the exact next safe action, and what will it change?**
6. **What changed since the last accepted view?**

The AI Operating Hub is an **`UMBRELLA_EXTENSION`** and the **derived operational experience and action surface** over the systems that already own truth. It extends the protected Project Workroom Fabric and existing Chairman Control Room; it does not replace either substrate. It is not another operating system and must never become a second Job lifecycle, workstream ledger, queue, identity graph, retry engine, Slack inbox, Git mirror, Linear database, or model-authored status authority.

## Product thesis and moat

The user value is not “all tools in one dashboard.” The value is **decision compression with exact receipts**: a live workstream can be understood, adjudicated, and safely advanced from one coherent view while every claim remains traceable to its canonical owner.

The machine value is a stable, typed operational context that lets Sol and bounded workers reason from the same identity, authority, freshness, evidence, and correction state instead of reconstructing the company from prose on every turn.

The durable moat is the combination of:

- exact cross-system identity and provenance;
- correction-safe operational history;
- explicit authority and action admission;
- outcome instrumentation showing which interventions actually unblock work;
- reusable workroom compositions that make complex AI organizations legible without flattening them into generic task lists.

## Experience architecture

### 1. Attention Inbox

A ranked-by-policy, **not LLM-ranked**, list of typed attention items:

- `DECISION_REQUIRED`
- `WORKER_AWAITING_SOL`
- `EFFECT_UNKNOWN`
- `SOURCE_MOVED`
- `PROOF_MISSING`
- `PROJECTION_CONFLICT`
- `CAPACITY_BLOCKED`
- `PRODUCTION_REGRESSION`

Each row shows consequence, canonical owner, freshness, workstream, operation, current actor/binding, exact requested action, and the evidence that admitted it. Model summaries may explain an item but cannot originate, suppress, prioritize, or close it.

### 2. Workstream Workroom

One real workstream page is the flagship composition. Above the fold:

- outcome / user job;
- capability state with sub-capability ledger;
- current operation and exact runtime binding;
- latest accepted milestone and proof;
- present blocker or decision;
- exact next action and owner;
- freshness/conflict banner.

Below the fold:

- architecture and no-rebuild boundaries;
- ordered wave map;
- GitHub implementation/evidence timeline;
- Agent OS decisions/discoveries/handoffs;
- Linear projection comparison;
- Slack delivery/receipt evidence;
- production proof and learning metrics.

### 3. Decision Desk

The decision view provides:

- the question and why it is now decision-ready;
- 2–4 closed options with consequences and reversibility;
- exact evidence and unresolved uncertainty;
- authority required;
- preflight diff: what the selected action will and will not change;
- stable operation key and replay behavior;
- immutable accepted/refused/unknown receipt.

### 4. Evidence and Proof Drawer

Every material claim opens to exact source identity, observed timestamp, source timestamp, digest/SHA/URL, parser/adapter version, correction lineage, and any conflicting claim. “Green,” “merged,” “delivered,” “queued,” “running,” “deployed,” and “accepted” remain separate concepts.

### 5. Action Composer

Only actions implemented by an existing canonical owner are exposed. The first supported action is a single CEO continuation boundary for one already-existing child operation:

- `CONTINUE`
- `REQUEST_REPAIR`
- `STOP`

The Hub performs deterministic preflight, submits through existing Executive/CEO admission when that path is production-proven, and reconciles the stable operation identity. Slack is a transport projection, never the mutation authority. If the canonical submission path is not proven or current state is stale, the control is disabled with the exact blocker rather than silently falling back.

## Projection and correction architecture

The Hub composes a read model from canonical adapters. A derived cache may exist for performance, but it is disposable, timestamped, provenance-bound, and never accepted as lifecycle or organizational truth.

Every field carries:

```text
value
canonical_owner
source_identity
observed_at
source_time
freshness_state
confidence (for model/advisory fields only)
correction_id / supersedes
```

Corrections invalidate affected derived views. Conflicting canonical/projection claims remain visible until the owning layer is repaired. The Hub never rewrites GitHub, Linear, Slack, Agent OS, or Executive state merely to make the screen internally consistent.

## Deterministic, statistical, and model-generated boundaries

**Deterministic only:** identity resolution, lifecycle state, freshness, capability vocabulary, permission, attention admission, action eligibility, idempotency, effect reconciliation, evidence digests, and correction lineage.

**Statistical/policy-derived:** future attention scoring may prioritize already-admitted items only after a replayable policy and measured calibration. It cannot suppress constitutional blockers.

**Model-generated:** summaries, option explanations, handoff drafts, and “what changed” narratives. They must cite structured source facts, label uncertainty, and carry zero lifecycle, ranking, merge, deployment, or trading authority.

## Action law and effect uncertainty

The action request uses a stable canonical fingerprint under a versioned contract such as `mastermind.ai_hub_action_intent.v1`. Conceptually:

1. fresh-read current canonical state;
2. verify user permission and required authority;
3. bind exact workstream, operation, runtime, carrier and source revisions;
4. display the deterministic preflight;
5. submit once through the existing canonical ingress;
6. reconcile by stable operation key;
7. return accepted, refused, conflict, or `EFFECT_UNKNOWN` receipt;
8. never blind-retry or fail over carriers.

Same key + same fingerprint is one operation and returns the original canonical receipt. Same key + changed payload is a conflict. A timeout is not proof of failure.

## Required failure states

The premium experience is defined as much by honest failure as by the happy path:

- no workstreams / no matching identity;
- partial source outage;
- permission denied;
- stale source beyond action budget;
- GitHub/Agent OS/Linear disagreement;
- Slack delivered but runtime unconsumed;
- worker awaiting Sol with no later edge;
- source moved after preflight;
- competing writer / overlapping PR;
- effect unknown after submit;
- accepted action not yet projected;
- implementation merged but production proof absent;
- model synthesis unavailable while deterministic facts remain usable;
- correction supersedes the fact currently on screen.

No failure state may collapse to an empty card, generic spinner, or false-green “healthy.”
