## 1. Chairman outcome and 10/10 completion ruler

### 1.1 User job

The Chairman can give a difficult, high-value outcome to a ChatGPT web Sol once and then observe a governed organization complete it without personally:

- locating the right browser tab or managed profile;
- re-explaining the product thesis after context rotation;
- copying messages between Sol, workers, reviewers, and integration owners;
- guessing whether a Slack post, PR, process, or model actually ran;
- deciding which numbered account should receive routine work;
- rescuing work that silently stalled behind an expired chat or missing watcher; or
- accepting a persuasive status summary in place of production evidence.

### 1.2 Intelligence job

The reasoning organization must preserve the original outcome, retrieve current canonical evidence efficiently, decompose ambiguity into bounded missions, use strong Pro reasoning only where it creates frontier value, supervise durable execution outside the reasoning turn, review returns adversarially, and hand responsibility across replaceable conversations without duplicating effects or authority.

### 1.3 Machine job

The deterministic system must preserve and expose:

```text
responsibility and authority
→ current exact surface and generation
→ current operation / Job / Attempt / Worker when one exists
→ source, permission and capability state
→ durable execution and material return
→ exact dialogue edge and continuation obligation
→ immutable implementation / proof evidence
→ safe context succession and predecessor fencing
→ accepted outcome and next action
```

The model supplies reasoning, synthesis, hypotheses, plans, reviews, and bounded decisions. Deterministic owners supply identity, authorization, canonical state, idempotency, effect truth, binding transitions, capacity, and durable records.

### 1.4 10/10 completion

The full product is complete only when a real approved program demonstrates all of the following through the actual production path:

1. A Chairman-facing Meta-CEO accepts the outcome and reconstructs current company state from canonical owners.
2. It selects or creates bounded Program CEO / Project Sol / Integrator / Auditor responsibilities without inventing authority or requiring routine Chairman account allocation.
3. The selected reasoning sessions receive compact, current, source-attributed context and verified capability limitations.
4. A difficult reasoning turn produces a high-quality architecture, diagnosis, research result, or adversarial judgment rather than merely consuming time.
5. Concrete work continues in a durable exact-bound worker/process after the leader turn ends.
6. Material worker returns reach the exact responsible Sol or truthfully report exact-session wake unavailable.
7. Every return receives a same-carrier `CONTINUE`, `REQUEST_REPAIR`, or terminal `STOP`; no watcher-enabled participant waits on silence.
8. The leader validates the result against the original user and machine jobs and rejects infrastructure-only or false-completion outcomes.
9. A context-expired or retired leader is succeeded exactly once; the successor recovers durable context and the predecessor cannot perform the claimed governed actions.
10. The result is visible to the real user or machine consumer, not only in source, CI, or Slack.
11. Durable Agent OS, GitHub, Executive, Linear, and transport projections agree at the precision promised or expose their disagreement explicitly.
12. Scaling across the approved account fleet improves accepted outcomes without unauthorized action, duplicate work, hidden account hopping, unsafe ambient native writes, or increased Chairman intervention.

Anything less is a bounded intermediate capability and must use the corresponding `PROVEN_LIVE`, `BUILT_NOT_PROVEN`, `PARTIAL`, `DARK_OR_DISCONNECTED`, `BROKEN`, `SPEC_ONLY`, `NOT_BUILT`, or `REJECTED_BY_DESIGN` state.

## 4. Runtime profiles: one experience, different authority envelopes

A major source of risk is treating every ChatGPT web session as a Codex-like worker merely because it has tools. The system needs explicit **role profiles** whose tool eligibility, write boundaries, return obligations, and proof expectations differ.

The profiles below are architecture candidates over existing owners. They are not app manifests or executable policy files.

### 4.1 `META_CEO`

**Primary job:** recover the Chairman's full intent, maintain company topology, assign bounded responsibilities, adjudicate cross-program conflicts, accept or reject consequential results, and report exceptions.

**Default cognition:** included Chat web / `NON_PRO_DEFAULT`.

**Pro exception:** only one of the protected long-horizon classes with a complete current receipt and at least the protected minimum duration. Handoff, monitoring, ACK, START, status, routing, and STOP turns remain non-Pro even when they support a large program.

**Eligible capabilities:**

- Steward / Control Room read and source disagreement inspection;
- GitHub/Linear/Slack native reads where current connected permissions and source law permit;
- current protected Skillpack acquisition;
- Executive root-intent preparation/submission only through the reviewed owner and only with current Chairman intent and complete action-time gates;
- bounded Program CEO / Project Sol / Integrator / Auditor responsibility design and routing;
- review/acceptance and durable closeout.

**Not eligible by default:** unrestricted shell, arbitrary filesystem edits, generic desktop control, worker-local credentials, branch ownership, app administration, direct existing-child continuation from a sibling role, or self-selection of another account/session.

### 4.2 `PROGRAM_CEO`

**Primary job:** maintain one major program's full thesis, dependency DAG, current child graph, proof ladder, and cross-wave consistency.

**Scope:** exactly one `responsibility_ref` / program or accepted workstream family. It does not inherit company-wide Meta-CEO authority merely because the model is strong.

**Eligible capabilities:** same read families as needed for its program; bounded child commission drafting; exact same-carrier continuation where it is the action-authoritative parent; GitHub review and product acceptance within its assigned envelope.

**Return contract:** claims, decisions, dissent, evidence references, unresolved effects, and one exact next action. Do not send the Meta-CEO every child transcript.

### 4.3 `PROJECT_SOL`

**Primary job:** own one bounded project, product capability, or architecture slice through a truthful return.

**Eligible capabilities:** task-relevant Steward/GitHub/CodeIntel reads; bounded research and design; exact worker handoff; review of its child outputs; no cross-program reprioritization.

**Use Pro mode when:** the project turn genuinely needs cross-system architecture, long-horizon frontier reasoning, hard debugging, or adversarial judgment under the complete protected receipt. Project importance alone is insufficient.

### 4.4 `INTEGRATOR_SOL`

**Primary job:** combine independently produced outputs, resolve contradictions, preserve material dissent, and produce one coherent integration candidate.

**Default authority:** read and recommend. It gains no release, merge, or child-command authority unless the exact responsibility explicitly grants that edge.

**Required inputs:** same frozen original intent; exact candidate identities; current protected law; dissent and negative evidence; owner-specific completion definitions.

**Required output:** selected architecture/result, rejected alternatives, conflicts resolved or preserved, integration risks, exact acceptance tests, and current source compatibility.

### 4.5 `AUDITOR_SOL`

**Primary job:** independently falsify a candidate against the original outcome, authority, security, correction, and production-proof contracts.

**Default capabilities:** read-only. It may create attention or a review finding through the accepted review path. It must not repair the source it is independently reviewing, select itself as a replacement worker, merge, release, or convert a review into lifecycle truth.

**Independence:** where practical use a different model/provider/account or at minimum a clean context and no access to the author's hidden reasoning. Independence is an evidence property, not a title.

### 4.6 `BOUNDED_WORKER`

**Primary job:** implement or prove one observable mission in an exact Attempt/worktree/provider context.

**Eligible capabilities:** the separately authorized worker workbench: exact repository/worktree read, bounded patching, command execution, test/build tools, artifact collection, and task-relevant browser/computer control where the current execution profile grants it.

**Required binding:** current Job/Attempt/Worker, exact source branch/worktree, capability profile, credential boundary, path ceiling, operation/carrier, and effect state. A role label or Slack mention is insufficient.

**Required lifecycle:** pickup ACK, read, continuation path, separate START, checkpoints, BLOCKED/DECISION_REQUEST/RESULT, and explicit parent CONTINUE or terminal STOP.

### 4.7 `MECHANICAL_WORKER`

**Primary job:** repetitive deterministic migration, fixtures, formatting, or exact artifact publication.

**Authority:** narrower than a bounded worker. No architecture choices, broad repository exploration, account/provider selection, or semantic widening. Unexpected ambiguity returns rather than being “helpfully” resolved.

## 7. Worker workbench: Codex-like hands without a second Codex lifecycle

The requested local files, shell, image, and computer-use capability belongs to an exact-bound worker execution profile. Chat On Steroids demonstrates useful interaction patterns; Mastermind must enforce them through existing worker, Attempt, worktree, credential, and browser owners.

### 7.1 Candidate semantic capabilities

The eventual worker-facing capability family may include concepts equivalent to:

```text
workspace_read
workspace_search
workspace_view_image
workspace_apply_patch
command_start
command_continue_or_input
command_status
artifact_collect
browser_observe
browser_action
```

These are semantic examples, not approved tool names. Existing CodeIntel, GitHub, provider adapters, browser workers, or native tools should implement the job where they already satisfy the contract.

### 7.2 Mandatory derivation

The worker/model must not choose:

- host or login account;
- root directory or arbitrary path;
- repository identity by free text;
- worktree, branch, Job, Attempt, Worker, lease, or fence;
- credential, environment, network policy, browser profile, or target account;
- command interpreter or arbitrary privileged executable when the execution profile is closed;
- retry, replacement worker, or another carrier after an uncertain effect.

The trusted execution owner derives those values from the current operation and capability profile.

### 7.3 Filesystem and shell separation

Approved filesystem roots do not sandbox a general shell. The shell and child processes must run inside the existing reviewed isolation boundary with:

- exact worktree/root and path preflight;
- symlink, mount, nested repository, and directory-replacement defenses;
- least-privilege user and scrubbed environment;
- explicit network policy;
- bounded resource/process group;
- no unrelated credentials;
- attributable process identity and output;
- deterministic cleanup or explicit residue.

When that isolation cannot be proven, unrestricted shell must remain unavailable for unattended use even if the file tools are read-only.

### 7.4 Durable process semantics

A long command or provider worker may outlive the initiating reasoning turn. Its handle must map to the canonical Attempt/provider process and support:

- immutable operation / Attempt / execution-profile binding;
- start receipt before output polling;
- bounded output deltas and artifact references;
- current status and terminal exit evidence;
- input only when the original operation permits it;
- cancellation requested versus cancellation confirmed;
- process-group and child cleanup evidence;
- no second launch on a lost response until the original is reconciled;
- ownership transfer only through the current continuation/Attempt law.

A handle is not proof the process is alive, the result is correct, or the exact Chat has been awakened.

### 7.5 Patch semantics

- Every patch is scoped to the current path ceiling and current file/blob preimage.
- Preflight does not prove cross-file crash atomicity.
- Partial application reports exact changed and unchanged paths plus effect uncertainty.
- An unexpected branch/head move blocks or reconciles; it does not justify reset, rebase, force, or a new PR.
- Generated artifacts, logs, caches, secrets, and runtime state stay outside source unless the commission explicitly owns a reviewed fixture.

### 7.6 Browser/computer semantics

- Observe before action and bind the action to the recent exact window/control state.
- Revalidate the target immediately before each consequential input.
- Refuse stale geometry, changed profile/account, authentication walls, secret-bearing settings, or ambiguous target identity.
- Report completed steps separately from the uncertain or refused step.
- Use disposable non-sensitive profiles for development and canaries.
- Browser access never confers Chairman identity, Job ownership, semantic ACK, RuntimeBinding authority, or permission to select another account.

## 9. Context succession and all-path fencing

### 9.1 Succession sequence

```text
rotation condition established for exact current binding
→ every modifying effect reconciled
→ durable continuation sufficient without the predecessor
→ exact profile/account/Project/predecessor resolved
→ exactly one successor created
→ exactly one deterministic bootstrap delivered
→ exact surface responsiveness verified
→ semantic readiness accepted through the existing owner
→ RuntimeBinding generation advances atomically
→ predecessor generation is fenced
→ navigation projection updates or degrades truthfully
→ successor performs the next governed action
```

A generic error, slow generation, or “Thinking failed” does not prove context exhaustion. A lost create or bootstrap receipt becomes effect-unknown and blocks a blind second attempt.

### 9.2 Reachable-mutator coverage

The predecessor is not technically fenced merely because one Mastermind endpoint rejects it. For each claimed autonomous modifying capability, inventory the mutating routes reachable from the actual chat/account/app/host configuration.

Candidate review relation:

```text
R = reachable modifying route families
E = routes whose actuators enforce current role/scope/binding/source/effect predicates
D = routes technically denied or unavailable to this surface
U = routes whose effective permission or enforcement is unknown

promotion requires R ⊆ E ∪ D and U = ∅ for the claimed capability
```

Route families include owner-mediated Mastermind actions, native GitHub/Slack/Linear apps, separate custom apps, shell credentials, browser/computer control, clipboard-based pathways, deployment/admin apps, and any provider-specific direct action surface.

This is a review and proof obligation over existing actuators, not permission to build another central permission database. An allowed native action may remain attended and outside the autonomous claim.

### 9.3 Required stale-predecessor tests

- old generation through each enabled Mastermind modifying action;
- old generation through every ambient native mutator in scope;
- late model output after cutover;
- stale cached tool schema after permission revocation;
- navigation failure after authority transfer;
- old watcher firing after terminal STOP;
- changed provider/profile/account identity;
- lost RuntimeBinding writer response and ABA race;
- sibling responsibility unaffected by the fence;
- current successor remains able to perform the explicitly allowed action.

No real unauthorized mutation is required. Start with hermetic/mock/provider-sandbox evidence and use disposable approved targets for the final bounded canary.

## 10. Cognition, capacity, and account-fleet policy

### 10.1 Reasoning economics

The account fleet is a capacity resource, not an excuse to spend Pro turns on low-value operations. Apply the protected distinction:

```text
COGNITION_ROUTE: CHAT_INCLUDED_DEFAULT
CHAT_REASONING_MODE: NON_PRO_DEFAULT
```

A Pro exception requires the complete current receipt:

```text
CHAT_REASONING_MODE: PRO_MODE_EXCEPTION
WHY_PRO_MODE: specific frontier advantage
WHY_NON_PRO_INSUFFICIENT: why the default cannot reliably meet the bar
PRO_MODE_TASK_CLASS: allowed closed class
EXPECTED_DURATION_MINUTES: 80..1440
STOP_CONDITION: observable completion or abort condition
```

Pro mode is not eligible for ACK, START, CONTINUE, STOP, routing, placement, polling, status, foregrounding, message relay, simple review, mechanical edits, or routine tests. Those actions should not consume the scarce reasoning budget even when the parent program is large.

### 10.2 High-value Pro mission classes

Use Pro for:

- full product/system/intelligence architecture with conflicting owner boundaries;
- deep competitor and primary-source synthesis where omissions materially change strategy;
- hard debugging with multiple plausible root causes and security/effect implications;
- adversarial judgment over a consequential PR, program, or production result;
- integration of independent Sol research where dissent and hidden contradictions matter;
- recovery of a materially ambiguous, cross-repository stalled program after current-state archaeology.

Do not use elapsed generation time as the optimization target. The useful unit is an accepted decision/capability and its avoided rework or Chairman intervention.

### 10.3 Account placement

- Capacity, not the Chairman, should choose ordinary concrete account/session placement when an accepted automated path exists.
- Before START, capacity-selectable work may be rebound only under the current no-effect/no-uncertainty rules.
- After START, the exact runtime is sticky until canonical reconciliation.
- Quota loss does not permit account hopping, resending, or a new carrier while an effect is unknown.
- Exact-session-required continuation remains exact; an account mention or new same-model chat cannot substitute.
- Personal-Pro and Business sessions can have different app/tool access while sharing the same logical role family. Capability parity is not identical permission.
- The fleet should keep reserve capacity for integration, audit, incident response, and context succession instead of saturating every session with generation.

### 10.4 Capacity observations

Record only observations supported by the current platform/account owner:

- account/workspace/model/surface eligibility;
- reset and remaining-usage facts when exposed lawfully;
- concurrent active/held/parked responsibilities;
- current exact binding and sticky operations;

## 12. Evaluation and promotion contract

### 12.1 Matched task set

Use 24 matched tasks, four from each class:

1. cross-system architecture;
2. primary-source / competitor research synthesis;
3. hard debugging with multiple plausible causes;
4. adversarial implementation or production review;
5. interrupted-context recovery;
6. multi-source state reconciliation.

Each task must have equivalent fixtures and the same original outcome, source snapshot, allowed model/mode, tool permissions, time/budget envelope, and independent grading rubric. Do not reuse a task after its answer leaked into the comparison context.

### 12.2 Baseline and candidate

- **Baseline:** current approved Chat workflow and tools.
- **Candidate:** improved context composition, task-relevant capability discovery, durable worker/process return, and accepted continuation mechanisms actually available for that task.

Do not compare a tool-rich candidate with a deliberately crippled baseline and call the difference model quality.

### 12.3 Required measurements

Per task:

```text
primary user-job completion
machine/intelligence-job completion
source/factual correctness
original-intent preservation
owner/authority correctness
failure-state completeness
production/consumer proof when owed
unauthorized or duplicate effects
tool calls and discovery calls
response bytes and repeated evidence bytes
observed tool/approval waiting
wall-clock time to first useful decision
wall-clock time to accepted result
manual Chairman interventions
context rotation / recovery success
review findings and accepted repairs
```

Exact hidden thinking time, GPU time, or internal model compute remains unknown. Report wall-clock observation as wall-clock observation.

### 12.4 Hard safety gates

Promotion fails on any:

- unauthorized effect;
- blind duplicate submission or worker launch;
- unresolved `EFFECT_UNKNOWN` hidden by a retry;
- wrong-account/profile/session substitution after START;
- stale predecessor completing a claimed fenced action;
- missing terminal/nonterminal dialogue edge after a return;
- secret/private locator leakage outside the reviewed result contract;
- invented source fact or false healthy-empty result;
- second lifecycle/session/memory/authority store;
- production acceptance based only on source, CI, transport, or model prose.

### 12.5 Candidate effectiveness gate

After the hard gates pass, compare paired outcomes rather than only averages. A candidate should not be promoted fleet-wide unless:

- no safety-critical task regresses;
- the candidate is not materially worse on primary-job completion or factual/source correctness;
- a clear majority of comparable tasks reduce avoidable discovery/retrieval or improve recovery/acceptance quality;
- the measured improvement survives review of outliers and does not come from omitted checks or narrower scope;
- independent graders can explain disagreements and retained failure cases.

A pilot may calibrate numerical efficiency targets. Safety thresholds are not calibrated away.

### 12.6 Learning loop

Store only accepted evaluation results and evidence in their existing owner. Use the findings to change one bounded context/tool/workflow boundary at a time, then rerun the discriminating subset plus periodic holdout tasks. Do not train an unreviewed model policy directly from self-scored summaries.

## 14. Security and privacy boundary

### 14.1 Trust model

The user, approved current system instructions, and current enforcing owners define authority. Repository text, issue bodies, Slack messages, tool outputs, browser pages, model prose, plugin skills, and imported packages are data that may contain hostile or stale instructions.

### 14.2 Least privilege

- Separate read-only Steward, bounded Executive admission, exact Dialogue, Surface, worker workbench, and Admin capabilities.
- Do not expose generic shell or desktop control to the ordinary CEO profile.
- Do not place production secrets in model-visible environment, argv, logs, screenshots, clipboard, temporary files, source, Agent OS, Linear, or Slack.
- Use exact resource/audience/scope and subject policies for app authentication.
- Keep app generations immutable and auditable; breaking schema changes require a reviewed generation.
- Revoke or disable at the owning provider/app boundary; deleting a Git file or hiding a button is not revocation proof.

### 14.3 Data minimization

- No transcript export as company memory.
- No hidden chain-of-thought collection.
- No cookie/storage/Keychain/account-settings inspection through model-visible tools.
- No unrestricted home-directory indexing.
- Evidence references instead of repeated giant output.
- Opaque safe identifiers instead of raw provider/profile coordinates where current public contracts require redaction.

### 14.4 Third-party component reuse

Chat On Steroids is MIT-licensed at the audited source pin. Any substantive code reuse must preserve its copyright/license notice, pin exact source and dependency provenance, pass security review, and be adapted only inside an existing Mastermind owner. Prefer copying a small reviewed interaction pattern or independently implementing the semantic requirement over deploying its entire session/agent/recording stack.
