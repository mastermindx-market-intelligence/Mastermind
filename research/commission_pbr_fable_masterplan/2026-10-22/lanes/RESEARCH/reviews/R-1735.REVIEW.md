## 4. Findings

**F1 — MINOR — `tests/test_decision_snapshot_real_capture.py:170` and `:253` — capture-derived size magnitudes in a public repo.**
The comments state `~10 KB-per-row real decision tail` and `The 1.3 MB decision tail`. The 1.3 MB figure is the
rounded byte count of a production capture file (exact value 1,298,253) and the 10 KB figure is its rounded mean row
size. A6 forbids copying a capture byte count into the diff; every *exact* count, digest, ticker, id and row value is
absent (verified, §3 A6), so the leak is a coarse magnitude only — but it is capture-derived and this repo is public.
Smallest fix: drop the two numerals ("a multi-megabyte real decision tail", "the large-per-row real decision tail");
no code or assertion changes.

**F2 — MINOR — `portfolio/decision_snapshot_contracts.py:82-83` — the stated constant invariant is off by the 2 list-framing bytes.**
The comment says the constant "must stay >= the largest single lawful row". Retention measures the *list* encoding
(`kept_bytes` starts at 2, `portfolio/decision_snapshot_sources.py:778`), so a row whose canonical size is exactly
`MAX_JSONL_TAIL_BYTES` — or `MAX_JSONL_TAIL_BYTES − 1` — fails its source closed as OVERSIZE. Probed: a 39-byte row
with `max_bytes=40` → OVERSIZE; with `max_bytes=42` → retained. The effective single-row ceiling is `max_bytes − 2`.
No live impact (largest observed canonical row 49,731 vs ceiling 65,534). Smallest fix: reword to "must stay greater
than the largest single lawful row plus the 2 bytes of list framing", or state the effective ceiling as
`MAX_JSONL_TAIL_BYTES − 2`.

**F3 — MINOR — `portfolio/decision_snapshot_sources.py:743-752` (and `portfolio/decision_snapshot_contracts.py:81-85`) — A3's worst-case sum is not enumerated.**
The arithmetic present is correct, but it covers only the two JSONL tails. `historical_memory` has four sources
(observed `source_ids`: `book.positions_ledger`, `book.decisions`, `book.fills`, `book.settlement_receipts`), so the
same section also carries a raw-object ledger row bounded only by `MAX_SOURCE_BYTES` = 8,388,608 and a settlement
manifest bounded by `MAX_MANIFEST_METADATA_BYTES` = 65,536; `book_truth` (four raw-object sources, same 8 MB bound)
gets no figure at all. "Leaving the other half of the snapshot budget to every other section" is literally true of
the tails but invites the reading that `historical_memory` ≤ half the ceiling, which its ledger row can violate.
The fail-closed residual sentence does cover the case, so no unsafe conclusion follows. Smallest fix: one sentence
naming the manifest (≤ 65,536) and the raw-object rows (≤ `MAX_SOURCE_BYTES` each) as the remaining
`historical_memory`/`book_truth` terms, and stating that their worst case exceeds 262,144 and therefore fails closed
at `portfolio/decision_snapshot_contracts.py:441`.

**F4 — MINOR — `portfolio/decision_snapshot_sources.py:1152-1170` — the fail-closed OVERSIZE receipt discards a row count it already knows.**
The branch leaves `rows_total`/`rows_returned`/`omitted_rows` at their `_base_receipt` zeros (`:429-431`) and merges
`omitted_rows=0` into the section, so a decision log blocked by the byte budget contributes 0 rows *and* 0 omissions
to coverage accounting; only the gap records the loss. That is consistent with the sibling read-OVERSIZE (`:1103-1119`)
and FUTURE_AT_CUTOFF (`:1127-1141`) branches — but those genuinely never parsed the bytes, whereas here
`tail["rows_total"]` and `tail["omitted_rows"]` are in hand. Smallest fix: set `receipt["rows_total"] =
tail["rows_total"]`, `receipt["omitted_rows"] = tail["omitted_rows"]`, and pass
`omitted_rows=tail["omitted_rows"]` to `_merge_into_section` (status/coverage/gap unchanged).

**F5 — MINOR — `scripts/portfolio_decision_snapshot.py:60-70`, `:125-126` — a largely-omitted tail still reads COMPLETE at the operator's default depth.**
The byte bound makes heavy omission normal: on the real capture `book.decisions` retains 9 of 90 rows (90 % omitted)
while its receipt reads `status=AVAILABLE`, `coverage_state=COMPLETE`. The counts are honest and reachable via
`show --section` (`section_page` returns `rows_total`/`omitted_rows`, `portfolio/decision_snapshot.py:647-658`), but
the CLI's compact manifest exposes only `state`, `coverage_state` and the five `summary` domain/source counters
(`portfolio/decision_snapshot_contracts.py:316-322`), so `status` and section-less `show` never reveal the omission.
Pre-existing shape (the 100-row cap did the same), materially amplified by this PR. Smallest fix: add
`rows_returned`/`omitted_rows` totals to the compact manifest summary, or document in the CLI module docstring that
`COMPLETE` means "available and fully counted", never "nothing dropped".

**F6 — MINOR — `tests/test_decision_snapshot_real_capture.py:218-262` — A5's "china seals non-COMPLETE" is met only in a weaker capture-level form, with a weak assertion.**
The constraint is real and honestly documented: `compose_snapshot` rejects any book but `autonomous`
(`portfolio/decision_snapshot.py:466-467`, literal `_BOOK_ID` at `:29`, dir at `:63-68`), so no china snapshot can be
sealed by any caller. The test therefore asserts on `sources.capture_all("china", …)` and its final coverage claim is
`coverage_states != {"COMPLETE"}` (`:261`), which passes if any single section is non-COMPLETE (observed
`{BLOCKED, COMPLETE, PARTIAL}`). Smallest fix: keep `capture_all` and assert the specific expectation — e.g. that at
least one section is `BLOCKED` and that the macro-dependent sections are the blocked ones — instead of the
set-inequality form; optionally note in the test docstring that the packet's "seals" wording is unreachable for china
by contract.

## 5. Observations (no severity; not required fixes)

- **O1** Retention breaks at the first row that does not fit (`portfolio/decision_snapshot_sources.py:783-787`), so it
  keeps a *contiguous* newest tail: probed `[small, huge, small]` → only the newest small row survives. A
  skip-and-continue greedy variant would retain more rows but would misrepresent a "tail". The docstring's
  "kept only while their cumulative size … stays within" (`:730-736`) matches the code.
