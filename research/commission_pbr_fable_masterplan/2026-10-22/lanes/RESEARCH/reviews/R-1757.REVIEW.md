### A3. Accessor semantics — MET (corrupt-input degradation characterized, F6/F7)
`effective_rows` (bot/decision_rows.py:186-255) attacked directly (scratch `a3_edge_cases.py`, all observed):
1. **Legacy file, no pointers**: fast path returns `list(rows)` unchanged, in order, no hashing (also asserted by `test_effective_rows_fast_path_hashes_nothing_and_copies`). Contract holds.
2. **Pointer to unknown id**: ignored; pointer row survives alongside its same-asof sibling → **two rows for that asof** (contract broken on tampered input only; the writer cannot produce it — `plan_decision_row` builds pointers only from the current effective same-day view). Downstream degradation is stale-extra-rows; settlement then fails safe on exactly-one. See F6.
3. **Pointer to a different asof**: ignored via the `asof` equality check (bot/decision_rows.py:233); same class as (2). Unit-tested (`test_effective_rows_cross_asof_pointer_is_ignored`).
4. **Cycle / self-pointer**: supersede targets must be strictly earlier (`candidate >= index` skipped, bot/decision_rows.py:231), so pointer cycles are unconstructible; `revise_target` maps strictly downward and `_slot`'s `seen` guard bounds the walk — no non-termination (verified with a constructed "2-cycle", which degenerates to a legitimate chain). Self-pointer ignored (tested).
5. **Duplicate byte-identical rows sharing one `row_id`**: one pointer supersedes **both** copies (identity-keyed, bot/decision_rows.py:220-239) — contract restored. Observed.
6. **Stored `row_id` ≠ content (tamper)**: `row_identity` trusts the stored id (bot/decision_rows.py:158-165) and never re-hashes content — supersession still resolves, but `row_id` is not tamper-evidence (F7). Observed.
7. **Revise of a revise**: chain resolves to the original slot (`test_effective_rows_revise_chain_resolves_to_the_original_slot`); observed order `["v3","next"]`.
8. **Asof row after a revise**: the asof-mode row sorts by its own index (end of file), exactly matching master's `kept + [entry]` — observed `[d12, d11-new]`, equal to master's rewritten order. Writer produces this via `supersedes=[revise-row id]`.

10. **`tail=`**: whole file is read and effectivized first, then sliced (bot/decision_rows.py:527-532; `test_read_effective_rows_tail_applies_after_the_whole_file_is_effectivized`) — the correct semantics for a late same-day revise owning an early slot.

### A9. Performance — acceptable; one quadratic class named (F8)
`effective_rows` fast path is O(n) with zero hashing when no row carries pointers (verified with 3,000 legacy rows). With pointers, only legacy rows whose `asof` occurs among superseding rows are hashed (bot/decision_rows.py:210-219) — sound, because cross-asof pointers are ignored. The `_slot` chain walk runs inside the sort key, so a degenerate single long revise chain costs O(chain) per comparison → worst case O(n²·log n); real chains are 2–3 rows (queued → executed → optional lesson refresh), so a few-thousand-row ledger stays linear in practice (F8). `load_decisions` still reads the whole file once per call, as on master; no reader added I/O.

## Findings

1. **F1 · MAJOR · `app/decision_availability.py:22,96-112,384-389`** — `_MAX_ROWS = 2_048` and `_MAX_BYTES = 16_000_000` are judged on the **raw** file inside `_read` before `effective_rows` is applied, and a breach marks the whole decisions source `invalid` (`source_too_many_rows`/`source_too_large`, data → None). The append-only ledger grows ~2–3 raw rows per effective trading day (queued + executed revise + optional lesson-refresh revise), so the invalid horizon shrinks from ~2,048 days to roughly ~680–1,020 days (inferred — no live ledgers on this host to measure; ratio is structural). Master's compacted file kept the cap years away; this design walks a PRODUCT availability surface into a hard `invalid` state while its effective view is still tiny. *Smallest fix:* for `decisions.jsonl` either apply the effective view before the row-count judgement, or raise/exempt the caps for this file; a sanctioned compaction operator is the longer-route alternative.
2. **F2 · MAJOR · `scripts/remove_positions.py:1-12,100-123`** — the module contract says "Erase named positions … AS IF THEY WERE NEVER BOUGHT" and "removes every trace of it from the trade history and holdings surfaces", listing `decisions.jsonl`; after this PR the scrubbed ticker demonstrably remains in the raw ledger bytes forever (superseded history retained by design; `_scrub_decisions`'s own docstring discloses it, but the module header still promises full erasure). An operator verifying erasure with `grep` will find the ticker and rightly consider the tool's promise broken. Operator-only, paper-only — severity per the brief. *Smallest fix:* amend the module docstring to scope the erasure claim to the effective view and state that superseded ledger history retains the ticker (pointing at the backup for byte-level removal), or add an explicit operator redaction mode outside the production append law.
3. **F3 · MINOR · `scripts/remove_positions.py:111-123`, `scripts/scrub_cn_tiny_trims.py:86-100`** — crash classes on degenerate rows, both observed: duplicate identical effective rows → `ValueError` from the revise guard (the second duplicate's identity is already superseded); a row missing `asof` → `KeyError: 'asof'`. Master scrubbed both silently. Loud failure, no corruption; operator-only. *Smallest fix:* skip a row whose identity is no longer in the freshly-read effective view, and guard `row.get("asof")` before revising.
4. **F4 · MINOR · `brain/decision_submission.py:227-249`** — malformed-line behavior delta in `_latest_holdings`: master scanned `reversed(lines)` (newest first) and could fill `prior_targets` from a clean newer record and `break` before ever reaching an older malformed line; HEAD's `[json.loads(line) for line in lines]` parses oldest-first and aborts the entire scan on the first malformed line anywhere, so on a corrupt ledger with an old bad line HEAD loses `prior_targets` master kept (enrichment only — rationale/prior-target weights; the account remains the position authority and the fallbacks degrade conservatively). The in-code claim "raises into the same handler" is true of the handler, not of the outcome. *Smallest fix:* keep per-line lenient parsing (skip bad lines) before `effective_rows`, restoring master's tolerant scan.
5. **F5 · MINOR · `tests/test_decision_rows_supersedes.py:594-616`** — the static guard is a name-based tripwire over 9 hardcoded dirs, not a proof. Evasion classes: (a) alias import (`from bot.decision_rows import write_rows as _seed; _seed(...)`); (b) any direct byte write on a decisions path — `write_text`/`write_bytes`/`open("w")`/`os.replace`/`shutil` are not scanned at all; (c) `getattr(dr, "write_rows")`; (d) repo-root `.py` files or any top-level dir outside `_GUARD_DIRS`. It does catch the realistic accident (calling the known names), which is its value. *Smallest fix:* additionally flag `write_text|write_bytes|open(…,"w")` within a few lines of a `decisions` token, and scan the whole repo (minus `vendor/`, `tests/`, `research/`, `docs/`).
6. **F6 · MINOR · `bot/decision_rows.py:178-239`** — on corrupt/tampered pointers (unknown id, cross-asof, self-pointer) the accessor ignores the pointer and leaves **two rows for one asof**, breaking the one-row-per-asof contract for that asof (observed). The writer cannot produce these states; degradation is stale-extra-rows and settlement fails safe (exactly-one conflict), so no unsafe path. *Smallest fix:* none required; optionally count ignored pointers in a debug counter so a corrupt file is observable.
7. **F7 · MINOR · `bot/decision_rows.py:158-165`** — `row_identity` trusts a stored, well-formed `row_id` without recomputing its content hash (observed: tampered content keeps the old identity and supersession still resolves). `row_id` is therefore an identity, not tamper-evidence; integrity rests on atomic append. *Smallest fix:* none required; document it, or verify the hash on strict reads if tamper-evidence is ever required.
8. **F8 · MINOR · `bot/decision_rows.py:241-254`** — `_slot`'s chain walk executes inside the sort key, giving a degenerate O(n²·log n) worst case on one long revise chain. Real chains are 2–3 rows, so a few-thousand-row ledger is fine, but the quadratic class is real. *Smallest fix:* memoize `_slot` results in a dict during the sort.
9. **F9 · MINOR · `brain/management_lifecycle.py:450-451`** — stale docstring: "settlement rewrites the row it advances in place" is now false (settlement appends a revise row; behavior over the effective view is unchanged, so `_newest_row` is unaffected). File is out of the PR's permitted scope; doc-only. *Smallest fix:* reword in a docs-only follow-up.
10. **F10 · MINOR · `app/web.py:1703` (and :1488)** — `/api/decisions` serializes full effective rows, so responses gain three additive fields (`supersedes`, `supersede_mode`, `row_id`). No logic change; the availability payload's `_decision` allowlist does not leak them. *Smallest fix:* none needed; note for PRODUCT consumers.
