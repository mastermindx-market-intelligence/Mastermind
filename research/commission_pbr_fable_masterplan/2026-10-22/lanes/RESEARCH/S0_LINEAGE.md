### Explicit disagreements (PR vs PR / spec)

1. **Rights vocabulary.** #673 `RIGHTS_CLASSES = {FIRST_PARTY_INTERNAL, MACRO_VENDORED}` (contracts `:56`); #1357 `{FIRST_PARTY_INTERNAL, LICENSED_INTERNAL, UNKNOWN, BLOCKED}` (`:37`). #1357 additionally **requires** qualified rights for `AVAILABLE` (`:196`). A #673-captured vendored-Macro receipt (`MACRO_VENDORED`) fails #1357 validation and vice versa (`LICENSED_INTERNAL` fails #673). The stores are therefore **not byte-compatible**: a snapshot written under one PR's contracts fails the other's `verify_snapshot` (fail-closed, but poisons mixed stores).
2. **Authority-class vocabulary.** #673 has 7 values incl. `RISK_STATE`, `MARKET_CONTEXT` (contracts `:58–65`); #1357 has 5 (`:36`).
3. **Clock-basis vocabulary.** #673 admits `CALLER_SUPPLIED` and `SOURCE_DECLARED` (contracts `:66–73`) and lets `AVAILABLE` rest on them; #1357 admits only `FILE_MTIME_FIRST_PARTY_STATE | DECLARED_SOURCE_FIELD | UNQUALIFIED_EXTERNAL_CLOCK | UNKNOWN` and requires one of the first two for `AVAILABLE` (`:38`, `:195`). #1357 is stricter; #673's `CALLER_SUPPLIED` path is a weaker clock the stricter law deliberately removes.
4. **Correction-status vocabulary.** #673 `{ORIGINAL, CORRECTED, SUPERSEDED}` (contracts `:74`); #1357 `{ORIGINAL, CORRECTED_GENERATION_AVAILABLE}` (`:256`).
5. **Seal-time cross-field laws.** #1357's validator additionally enforces summary⇔evidence consistency, generation-set⇔sources consistency, section⇔source/domain reference integrity, state⇔coverage agreement, and `snapshot_id` not preceding itself (contracts `:200–268`); #673's validator checks shapes and per-field vocabularies only (contracts `:222–428`). #673 compensates at capture (its composer derives consistent values structurally) but a hand-built or forged payload passes #673's seal where #1357's refuses.
6. **Future-known-at enforcement point.** #673: capture only; #1357: seal (see row 12). The spec's negative-proof list (§30.5 L2217 "no stale source cast as calm") is only fully guaranteed at seal.
7. **Predecessor referential integrity.** #1357 verifies correction predecessors exist at the same cutoff at persist time (`snapshot.py:190–196`); #673's `compose_snapshot` accepts caller-supplied prior ids unverified (its own `create_snapshot` derives them from the store, so the production path is safe by construction).
8. **Publication atomicity.** #673: direct `O_EXCL` create + fsync (snapshot `:303–341`). #1357: private temp inode + `fsync` + no-replace `link` + directory syncs, plus typed `SnapshotWriteUncertain` for durability-unknown outcomes (`:185–248`). #1357's is the stronger durability contract; #673's is simpler and equally create-once.
9. **HTTP surface.** Both define `GET /api/decision-snapshot`: #673 inline in `app/web.py:1668+` (dashboard family, no operator-auth gate of its own); #1357 as a dedicated router `app/decision_snapshot.py` mounted in `app/main.py:106–107`, gated on `app.auth.is_operator_authorized`, excluded from `app/response_cache.py` (`/api/decision-snapshot` deny entry), with a CSP-hardened static shell. Only one can ship; #1357's has the stronger auth posture.
10. **Compose/producer.** Only #673 has `create_snapshot` + a `compose` CLI subcommand and the whole capture engine; #1357's CLI is intentionally inspector-only and its store can only be fed by fixtures (runbook: "Only explicit callers of the library persistence function can publish records"). Under #1357 alone, the §30.4 "minimum real journey" (real artifacts → snapshot) cannot run.
11. **Coverage derivation detail.** #673: root COMPLETE iff all sections COMPLETE (`snapshot.py:437–442`); #1357 additionally requires no gaps for COMPLETE (`snapshot.py:139`) and counts `UNKNOWN` sections as partial domains. Cosmetic once laws in (5) are unified.

## C. Recommendation

## `continue-#673`

**Reasons.**
1. **It is the only branch that can perform S0's defining act.** §30.4's minimum real journey is "real current source artifacts → bounded snapshot composition → …". #673 has the capture engine (1,707 L + 1,982 L of tests), the `compose` writer and the CLI; #1357's capture was held/refused, so continuing #1357 means rebuilding exactly the largest, most review-sensitive component #673 already carries — rebuilding an existing system without evidence it is unusable.
2. **It is mechanically mergeable today**: `merge-tree` against current master is clean; its head tests pass (`83 passed`). #1357 carries three conflicts whose equivalent master already merged (#1599) — its calendar work should be dropped, not rebased.
3. **The valuable parts of #1357 are additive and portable**, not architectural alternatives: the seal-time cross-field laws, the future-known-at seal check, predecessor referential integrity, `SnapshotWriteUncertain`, the operator-gated router/UI with `response_cache` exclusion, and the research-context layer all layer onto #673's store (the two stores' public functions — `compose_snapshot/persist_snapshot/load_snapshot/list_snapshots/latest_snapshot/section_page/read_projection` — share names and signatures).
4. **Scope hygiene.** #673 touches no file owned by ECON/RESEARCH families; #1357 mixes in calendars, canaries and Fabric-dispatch work that belong to other waves.

**Required follow-ups when continuing #673** (input to L-S4): port #1357's seal-time laws and storage-durability improvements; resolve the single HTTP surface (one `GET /api/decision-snapshot` only — prefer #1357's operator-auth router posture); reconcile the vocabularies in §A disagreements 1–4 (pick one; snapshots written under the other's enums must be refused, and no mixed store may exist); implement the decision-row digest binding (§A row 17) — neither PR has it.

**Risks of `continue-#1357`.** Largest: no capture ⇒ no snapshot can ever exist ⇒ S0's acceptance journey is impossible until #673's engine is recreated; plus three redundant calendar conflicts to discard; plus re-review of a wider, multi-concern diff (canaries, browser fixtures, dispatch).

**Risks of `merge-path` (fresh branch taking files from each).** It re-reviews ~10k lines under a third PR while abandoning two existing drafted review threads, and buys nothing continue-#673 lacks: the file sets are not disjoint-composable anyway — the three shared filenames (`portfolio/decision_snapshot.py`, `_contracts.py`, `scripts/portfolio_decision_snapshot.py`) hold **divergent implementations** that must be reconciled line-by-line in either path. The delta merge-path would add (a fresh branch identity) is procedural, not technical.

**Risks of `continue-#673` (accepted).** Losing #1357's stricter seal laws until ported (forged/hand-built payloads seal more easily — mitigated by the L-S4 negative tasks); two UI surfaces temporarily defining the same route until the surface task lands; enum-vocabulary churn if #1357's receipts were ever persisted anywhere (none should exist — neither branch deployed; `(unverified)` no production compose has ever run).
