# Acceptance and evaluation design

**Purpose:** Make completion falsifiable without prescribing Fable's implementation. This is a traceability and experiment design companion to the existing acceptance and Agent Eval owners, not a second grader or lifecycle service. None of the scenarios below was executed as a product test by this research pack.

## 1. Preserve the original denominator

Full completion must account for the six criteria and all original proof obligations in `WS:CHAIRMAN-CONTROL-ROOM`'s Meta-CEO R2 acceptance contract; the original R2 stage exits; the 30 section-15 failure/rollback tests; ecosystem H1-H8; and the original Web/native product obligations. A result can satisfy several obligations, but an untested obligation cannot disappear because a broader test title sounds similar.

The original source and each field's meaning remain controlling. The ordinals below are only presentation order, not new canonical task IDs. [Machine-readable exact original text](evidence/original_r2_obligations.json) is retained to prevent accidental paraphrase drift. Existing sealed E1 experimental inputs and model/runner bindings must not be changed by this new delivery program.

## 5. Comparative harness experiment

The design should answer a product question: **Which admitted configuration best completes the original Chairman journey at acceptable quality, risk and total cost?** It is not a leaderboard for model brands.

### Comparison arms

Use the incumbent-compatible DSH route, the later Hermes route and, only where it can be qualified without duplicating control authority, the Rakazo product comparator. A smaller stable incumbent baseline should remain in the comparison. An unqualified arm is explicitly unavailable, not assigned a fabricated score.

Run two kinds of comparisons:
1. **Normalized context/capability:** same task information, tools, data, budget/accounting envelope and model where actually available. This helps isolate harness behavior.
2. **Realistic delivered configuration:** each candidate's lawful tools/context/operational environment. This measures the system the user would actually receive.

Record visible selected mode, configured model/provider and actual served identity separately; unknown served identity remains unknown. A candidate cannot win by silently obtaining broader tools, hidden paid usage or prohibited data.

### Cases

Use real Mastermind tasks with varied ambiguity, one ordinary worker question, intent correction, stale-source conflict, context recovery, unavailable-tool claim, permission denial, delayed result, review backlog and a plausible false completion. Include native research only on eligible arms and label incomparable capabilities rather than averaging them away.

Separate development cases, held-out qualification cases and a forward observation set. Randomize or counterbalance order where possible; avoid leaking expected answers between candidate runs. Freeze the relevant source/config/input identities before comparing, and record exclusions/missingness. Do not reuse the historical sealed E1 as though it were an editable generic benchmark.

### Grading

Deterministic checks own exact artifact/effect/identity assertions. Independent reviewers assess original-intent fit, useful judgment, evidence sufficiency and design quality with a concrete rubric. Human calibration is appropriate for subjective/product judgments. A model judge's confidence is not calibrated correctness. Reviewers should inspect outputs before reading the author's persuasive explanation when practical.

Run more than one trial where model variability matters and resources permit; choose the actual sample plan prospectively under the existing evaluation owner. Report denominators, exclusions and uncertainty, not a single impressive demonstration. A small clean sample cannot certify rare safety failures.

## 6. Metrics with explicit denominators

| Measure | Proposed definition | Caveat |
|---|---|---|
| Accepted useful outcomes | Independently accepted user-visible results, linked to original missions | Do not count PRs, tool calls or repeated result deliveries as separate outcomes |
| Avoidable Chairman interventions | Routine relay/re-explanation/placement/recovery requests that the accepted system should handle | Keep legitimate reserved decisions separate; annotate classification with evidence |
| Outcome/intervention relationship | Outcomes and avoidable interventions reported side by side; ratio only when denominator meaningful | Zero interventions is not a license to divide by zero or hide low outcome volume |
| Decision-resolution delay | Actual question creation to consumed ruling, including queue time | A sent answer is not consumed; unresolved items stay in denominator |
| Parent-return completion | Eligible terminal results whose original parents consumed the disposition | Distinguish failed, unknown, missing, reviewed and accepted |
| Recovery correctness | Original identity/effect preserved through qualified interruption | Measure failures and uncertainty, not just recovered process count |
| Foreground responsiveness | Actual ordinary question response and usefulness while children work | Report observed distribution and load, not a made-up universal SLO |
| Review/repair pressure | Pending decision/review age, repair cycles and rejected incomplete outputs | Reviewer throughput alone can reward rubber stamping |
| Total completion-cycle cost | Measured reasoning/tool/host usage plus included-pool consumption and review/repair | Unknown usage/cost is unknown; no hidden metered fallback |
| Context efficiency | Relevant source acquisition/reacquisition and reviewer burden per outcome | Fewer tokens are not success if outcome quality or safety drops |
| Idle discipline | No invented tasks or unnecessary reasoning when no useful admitted work exists | A quiet process alone does not prove no missed obligation |

Performance targets should be chosen after a real baseline and kept separate from hard authority/security requirements. Neither a benchmark nor a summary grants trading, financial sizing or production authority.

## 7. Real installed campaign

The original seven-day campaign is an evidence obligation, not a promise that this chat will run in the background. It starts only through the actual existing runtime/observation owner after installation and safe admission. Record its real start/end, interruptions, source/config changes, selected accounts, roles and workload coverage. Existing owners retain timers and wake; do not create a competing watchdog.

Observe normal work and busy periods, not only handpicked successful turns. Include realistic recoveries and a lawful administrative pause. Preserve original operations during host/provider loss. Keep review independence under load. Record any private security incidents in their authorized private channel, with only non-sensitive disposition in the public report.

At campaign close, review every original obligation and distinguish PASS, FAIL, untested, blocked and not-applicable only where the original acceptance owner permits that classification. These are report dispositions, not new runtime states. Scope any acceptance to the actual observed release and workload. Material failures lead to repair and affected requalification, not a cosmetic all-green summary.

## 8. Required evidence bundle for an accepted increment

A useful bundle has original-intent reference; exact source and installed identity where relevant; current actor/target/resource association; actual commands/tests or consumer actions; observed outputs and negative cases; retained artifact references; independent reviewer scope/disposition; original-parent consumption; remaining limitations; and a read-back durable handoff. Keep private payloads and secrets out of public artifacts.

An evidence bundle is a set of references through existing owners, not a second event ledger. One receipt may support several claims only when it truly tests them. A fixture result never changes into an installed result merely because the file was committed.

## 9. Research-pack validation versus product validation

The validator accompanying this pack checks document links, coverage counts, metadata identities and absence of obvious unfinished placeholders. It **does not** run the product, certify the donor security boundary, approve a PR, validate runtime health or complete any scenario above. Its pass is only a publication-quality check for the preparatory artifact.
