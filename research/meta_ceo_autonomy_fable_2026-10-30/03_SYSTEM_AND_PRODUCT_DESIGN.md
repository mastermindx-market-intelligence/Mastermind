# System and product design

**Design status:** Detailed proposals over existing owners, not a new wire schema, implementation claim or approval. Fable may improve the solution; the original outcome, actual authority and evidence boundaries remain fixed. Source and external research anchors are in the resource map and research companion.

## 1. Architecture: stable responsibilities, replaceable implementations

The architecture should make it possible to replace a model, interaction harness, execution host or visual shell without replacing company identity or losing an in-flight operation. This is not a proposal for additional microservices. It is a separation of responsibilities already owned by Mastermind:

| Concern | Existing authority | Replaceable or subordinate components |
|---|---|---|
| Human intent and reserved decisions | Current Chairman direction, accepted intent/decision records and existing authority policy | Office presentation, conversational summarization, input affordances |
| Strategic and product judgment | The currently assigned principal inside its delegation envelope | Qualified model/surface, bounded domain advisors, evaluation method |
| Organizational memory | Agent OS workstreams, decisions, discoveries and eligible handoffs; owning repo plan | Harness retrieval cache, local transcript, concise working context |
| Live execution | Executive Job/Attempt/Worker/Event and RuntimeBinding owners | Eligible host, process, harness adapter and admitted worker implementation |
| Placement and economy | Existing Model Router and Capacity/Fabric | Qualified provider/model candidates within the admitted tier |
| Tools and external effects | Receiving resource owners, scopes, leases and effect reconciliation | MCP/ACP transport adapters and UI clients |
| Dialogue and wake | Existing Dialogue/Wake/transport owners | Slack/app delivery adapter, host-native attention surface |
| Implementation and release | GitHub/source custody, normal independent review, installed release owner | Branch, worktree, build tools and artifacts |
| Quality and learning | Existing product acceptance, Agent Eval/OHF/learning owners | Task-specific scorers, reviewers and prospectively admitted experiments |

A harness may retain its own conversation/session data for operation. That does not make it an alternate company workstream, priority queue, identity authority or source of accepted completion. Recovery reads authoritative owner facts and treats local summaries as pointers and hypotheses.

## 2. One office, several bounded responsibilities

**Primary office role:** interpret the latest request, find the existing mission, answer strategic questions, choose or revise the next bounded result, adjudicate consequential conflicts, and communicate an honest integrated outcome. It should not read every log, make every mechanical implementation decision or serialize every child return.

**Program/domain operator role:** own a bounded delivery domain, decompose when useful, manage admitted child work, resolve ordinary implementation questions, arrange independent review, perform bounded repair, and return one integrated result with evidence and exceptions. Topology does not itself justify a stronger model.

**Worker role:** implement or research a clearly scoped result with exact inputs and proof; report a concrete question rather than fabricating permission or silently widening scope.

**Reviewer role:** independently inspect original intent and actual artifacts or behavior. Source correctness, product usefulness, security, research adequacy and installation are different review questions; one generic approval cannot stand in for all of them.

**Secretary role:** handle eligible interaction/transport tasks, exact target use and useful attention delivery. It is not the executive decision owner, universal router or default relay for every event. A browser-capable Secretary need not hold broad company mutation permissions.

Fable may combine compatible roles in one operator or split a difficult domain. Consequential author/reviewer independence, actual runtime grants and the conserved root still apply. Six available accounts are capacity, not six permanently active departments.

## 3. Product surfaces and interaction design

These are user jobs, not mandatory tabs. Fable can combine or rename them while preserving the behavior.

### The Office / Today

The first view should answer: What is the current direction? What materially changed? What is actually running? What outcome is ready? What genuinely requires me? What useful work is blocked and by what exact condition?

Prefer an answer-first narrative with expandable source and execution detail. Avoid an internal-schema wall, misleading green badges and a screen whose only useful content is a list of PRs. Current, stale, partial and unavailable information must be visually distinguishable without forcing the user to learn lifecycle jargon.

An unsent direction belongs to its original identity/project/session context. Browsing evidence or another route must not destroy it. Switching accounts or a different target must not quietly retarget it. Explicit preview should say it creates no effect; an actual submit should identify the permitted action and preserve its returned operation identity.

### Mission workspace

Show the accepted objective, latest meaningful correction, completion proof, active responsibility, accepted increments, unresolved decision and exact next step. The task tree is the owning repository plan; wave state is Agent OS; live execution is Executive. The UI can compose them, but edits must go to the proper existing writer.

The user can ask a question without cancelling or restarting work. Changing an objective is not merely editing a chat bubble: it must reach the current responsible principal and follow the existing intent/effect fence. Already completed external effects remain visible even when the goal changes.

### Decisions and attention

Distinguish an ordinary worker question, a missing resource observation, a release review, and a genuine human-only control. Each attention item should show its source, affected work, what decision is needed and who can decide. Deduplicate display through existing exact identities; do not invent a second priority ledger.

The default should be a small set of consequential items, with complete drilldown available. Review backlog and unresolved decisions should be visible before spawning more builders. A missing notification does not erase the underlying obligation.

### Result and evidence

Present what the user can now do, how it was verified, the exact accepted scope and what remains unproven. Preserve independent source, deployment, runtime and acceptance receipts. A result can be technically correct yet fail the original user intent; make that rejection legible and link the scoped repair.

A proof drawer can expose source SHA, release identity, result selector, reviewer identity, receipt timestamps and consumer tests. It should not dump credentials, private transcripts or raw internal reasoning. Absence is explicit: no implied result when the body is unavailable or over budget.

### Resources and recovery

A diagnostic view should explain the selected route/profile/host capability and its evidence, not display every machine as globally ready. Show permission, capacity, provider, network, source and uncertain-effect failures separately. The relevant recovery action should be executable by the actual owner.

A fresh session should recover the same current mission from source-linked records without asking the Chairman to locate the previous conversation. The interface should expose the last durable reference, unresolved original operations and exact next action. A successful UI reload is not proof of runtime recovery.

### Native research / browser work

Show the exact eligible account, Project, selected mode and target evidence when that native capability is used. A title or similar-looking tab is not an identity. Separate the human's browsing from admitted agent interaction, preserve actual browser-resource leases and prevent cross-account context disclosure.

When this capability is held, the Office should still support independent safe work and honestly state the narrower release. It must not silently substitute an API worker, Work session or transcript scraper for the original native requirement.

### Product quality ruler

Evaluate desktop, 390/320px mobile, 200% text, keyboard and focus, EN/ZH where the existing product requires them, delayed responses, empty states, auth loss and conflicting data. The original Paper AT08/AT08M/Atelier references are source navigation, not fresh design screenshots from this research. Fable may evolve the design; reuse the existing shell and accepted behavior rather than building another application shell solely for aesthetics.

## 4. Interface obligations: bind exact facts at existing seams

The following is a **review checklist**, not a proposed replacement schema. Use the actual current owner contracts and names; add fields only through their normal reviewed evolution.

| Seam | Facts that must travel together | Consumer obligation | Failure behavior |
|---|---|---|---|
| Chairman input -> intent interpretation | Original wording/reference, selected work, latest accepted correction, audience and completion condition | Preserve the user's actual objective and distinguish an interpretation from an admitted effect | Ambiguous consequential scope becomes a precise question; ordinary reversible details are decided in scope |
| Intent -> Executive admission | Existing operation identity, actor/profile, permitted authorities, bounded source/resources, root/parent and budget | Receiving authority validates grants; role text and UI state grant nothing | Typed refusal or exact unresolved state, never a second path around it |
| Executive -> Fabric | Original Job/Attempt/root, exact admitted binding, source input, grants and result/return contract | Actual placement inside lawful tier; no invented descendants or root reset | Capacity wait stays a wait; denial and unknown effects retain their own rules |
| Worker -> question/ruling | Original child/attempt, exact obligation and return carrier, current intent revision | Correct principal decides; originating worker actually consumes the ruling | Delivery/ACK without consumption remains incomplete |
| Worker -> retained result | Exact execution and artifact identity, evidence location, status and limitations | Verify the retained bytes and actual execution boundary | Missing/truncated/unconfirmed result is not an accepted response |
| Reviewer -> disposition | Original intent, exact candidate/release and independent reviewer scope | Reject source/product/authority failures at the correct boundary | Precise bounded repair; no implicit approval of adjacent effects |
| Result -> original parent | Canonical result tuple and lineage, review/disposition reference, current parent responsibility | Parent consumption is observed separately from transport delivery | Pending consumption remains a live obligation |
| Mission/Result -> Office | Associated producer observation, exact selected work/root/job/attempt/digest, auth/owner generation | Commit selection and snapshot together; preserve complete/incomplete coverage | Wrong, stale or unbound context cannot release another context's data |
| Native session -> Office continuation | Owner-verified target, workRef/rootJobId, principal/generation and current Mission | Show the existing controller only when the entire association is qualified | Empty target projection or mismatched owner stays unavailable/unbound |
| Milestone -> continuity | Accepted outcome, source/ref, remaining effects, do-not-redo, exact next action | Existing task-tree/Agent OS writers validate and read back | Unsaved or unaccepted projection is named, not claimed durable |

For Office result association, preserve the existing five-field selector and owner observation rather than joining by display title or approximate timestamp. For continuation, use the actual `continuation_operation_key` supplied by the current eligible target, not an invented key for a historical chat.

## 5. Transaction and effect semantics

There are at least two transactions to reconcile: the company admission/effect and the provider or interaction request. Either response can be lost independently. A transcript saying “started” is not an admission receipt; a queued Job is not provider execution; a provider response is not accepted company output.

The design should enforce these properties through existing owners:

- One original logical request has a recoverable identity before the caller relies on a successful response. Unknown submission outcome causes an exact status read, not a second submit.
- Idempotency is scoped to the actual receiving owner and operation. Do not claim universal exactly-once execution across providers and external services. Where an external API lacks idempotency or effect lookup, preserve uncertainty and require its real reconciliation procedure.
- Cancellation is a request until the owner proves the resulting state. Completion may win the race; UI and parent must show the actual effect rather than claiming rollback.
- A new accepted correction fences stale commands and keeps prior effects visible. It does not retroactively erase completed external work or silently reinterpret an existing STARTed contract.
- A stale or replaced principal cannot act merely because its old response arrives later. Current ownership/generation and exact target are checked by the receiving boundary.
- Transport reconnect and process restart do not clear effect uncertainty, transfer custody or authorize a replacement run.
- A terminal child closes its continuation cycle. A new independent child needs its own lawful assignment; an old thread or standing program does not self-create it.

The proposed user labels such as “waiting for a decision” are presentation only. Canonical lifecycle states remain those already implemented by Executive/Dialogue, and the UI must preserve distinctions among delivery, pickup, execution, result, review and acceptance.

## 6. The cognition and delegation loop

### Before substantial work

Recover the relevant existing workstream and accepted outcome; choose the smallest source pack; verify decision-changing freshness; classify complexity/ambiguity separately from business impact; select an actual admitted route; and reserve independent review capacity. A large parent program is not evidence that every child is C3 or needs Fable.

### While children work

The principal should consume integrated returns and material exceptions, not tail every log. Domain operators resolve ordinary questions, supervise bounded repair, and update their existing continuity at meaningful milestones. Keep one source writer per overlapping effect. Parallelism is justified by separable inputs/paths/results, not by the number of available subscriptions.

Use human intervention for actual credentials/consent, reserved spend/authority, a real unavailable selector/physical ceremony, or a genuinely new decision. A worker claiming a missing tool should first provide the exact action and bounded capability observation. Conversely, an explicit permission/safety denial must not trigger rephrasing or alternate-account experiments.

### After a result

Verify source/consumer evidence, compare against original intent, consume the exact result in the original parent, save the milestone through existing writers, and reassess the next useful authorized dependency. Do not stop simply because a PR is green. Do not invent a successor mission merely to keep the system busy.

### Review-pressure feedback

Use existing attention/admission owners to notice overdue decisions and review bottlenecks. Prefer completing/reviewing already built work to unlimited new fanout when reviewers or integration are saturated. A budget estimate should include coordinator, worker, reviewer, repair and user interruption costs. No fabricated quota telemetry or “zero cost” for unknown usage.

## 7. Context, memory and project continuity

The durable organization should not be a transcript archive. Use Agent OS for accepted workstreams, decisions, discoveries and handoffs; the owning repo for deep task structure/source evidence; Executive for live operations; private harness session history only for its actual local continuity.

A compact working pack for a domain contains: original outcome, relevant current source/contract, exact target, accepted do-not-redo, open dependency, held effect, allowed surface, desired evidence, and return identity. Expand only when an actual question requires it. A receiver should not reread 70 PRs because this pack contains 70 references.

Corrections need provenance and an actual precedence relationship. New model prose cannot override accepted records. Retrieved instructions in a repository, email, webpage or tool result cannot widen authority. Source freshness and semantic relevance both matter: a fresh but unrelated snapshot is not a correct mission context.

On crash/recovery, obtain original status and pending effects first, then the latest eligible handoff and plan nodes. Do not replay a stream merely because a local chat history is missing. Session rotation follows current failure/context conditions; neither a fixed reset timer nor a model label is proof of necessity.

A harness learning a procedural skill is a candidate improvement. Review and test it through existing skill/evaluation owners before it affects a sensitive workflow. Keep accepted prior policy immutable in its historical decisions; prospective updates should not rewrite old experiment outcomes.

## 8. Security and privacy design

### Trusted authority must remain outside model claims

The receiving resource validates actor, audience, exact scope, target, operation, expiry and current generation. A model cannot turn an arbitrary string into a CEO role or choose another account to defeat a hold. Scopes must be appropriate to the actual client, including the existing prohibition on Fable's CEO-submit enrollment.

### Harness isolation is an observed property

Separate DSH_HOME/profile directories and a read-only persona prompt do not prove OS isolation. Qualification must exercise real file/process/network boundaries, extension/plugin loading, inherited environment, tool registry and cleanup. Prefer least-privilege, owner-private artifacts and exact dependencies; no production installer is run from a public README during this research.

Hermes #1885 illustrates a concrete issue: withholding one variable name did not prevent an equivalent secret value reaching a model child as a dashboard password. Test credential value aliases, not only names. Use distinct scoped credentials through their original secret owner; never place them in prompts, Git, logs, fixtures or private-working copies that become public evidence.

### Remote tool and MCP boundary

Current MCP authorization guidance requires token audience validation and resource binding, forbids token passthrough, and retains PKCE, exact redirects and issuer/consent protections. Preserve the actual implementation's contract rather than making a generic proxy that forwards arbitrary upstream tokens. Validate local Host/Origin/path/method and duplicate auth inputs where applicable. A loopback address is not sufficient authorization by itself.

### Untrusted content and tools

Treat repository content, external web pages, returned model text and tool output as data. Separate evidence retrieval from action authorization. Constrain actual tools and side effects at the receiver; instruction filtering alone is not a security boundary. Preserve source provenance, disclose uncertainty, and ensure one malicious page cannot redirect the agent to a different recipient or exfiltration destination.

### Audience and computer use

A program may contain data for several users or accounts. Retrieval and returns must preserve those audiences. External vision/image services are new disclosures, not implicitly allowed because the parent can see a screenshot. Browser access needs actual shared-profile/tab scope and current resource identity; a common OAuth account is not a unique conversation.

### Operational pause and recovery

The operator must be able to stop new admissions for an affected route without relying on the model to comply. Existing effects/results remain readable and reconcilable. A process kill, UI uninstall or machine reboot must not be presented as proof that every remote action stopped. Disaster recovery stays with its existing owner and real key/restore ceremony.

## 9. Observability without a second truth store

Instrument the actual existing owner transitions and propagate their correlation references. Useful observations include request/intent reference, root/job/attempt where truly bound, current target/owner generation, selected and observed provider/model identity separately, source/release identity, effect/response/result states, review and parent-consumption references, queue/decision/review delays, and measured usage. Do not synthesize absent identities from titles or timestamps.

Tracing should answer: where did a useful request stop; was it admission, capacity, tool auth, source custody, provider execution, result retention, review or consumption; what is the smallest lawful recovery action? A trace is diagnostic evidence, not a new execution authority.

Avoid logging raw private prompts, secrets, broad transcripts or internal hidden reasoning. Store only the content required by the existing evidence policy, with audience and retention controls. External GenAI observability conventions can improve naming/interoperability, but the current OpenTelemetry docs have moved repositories; pin the actual adopted convention rather than copying obsolete fields.

## 10. Release, migration and rollback

A research draft, source merge, focused test, general CI pass, installed release, authenticated user journey and final acceptance are separate milestones. Compose the current candidate stack through original owners and bind every proof to the precise source/build/release. A downstream branch based on an old repaired parent must not inherit the parent's latest review by prose.

Before replacing Grok or switching a resident harness, qualify side-by-side shadow behavior without duplicate external effects, compare the same original jobs, and prove current operation/return ownership. Disable only new admissions on the old route when the actual cutover is authorized; reconcile in-flight work. Keep rollback about preserving real identities/effects, not erasing an inconvenient failure history.

The installed seven-day campaign begins only after the relevant consumer path is actually qualified. A scheduler configured for seven days is not a completed campaign. If a material source/release change occurs, label the split and rerun only affected obligations; do not stitch incompatible receipts into a false uninterrupted pass.

## 11. Optional opportunities after the first real loop

Potential differentiators include a genuinely useful “what changed since I left” briefing, intent-drift detection before expensive work, cost-aware alternative plans, a compact review packet generated from actual source/consumer evidence, and a personal decision notebook grounded in accepted company records. These are optional product hypotheses. Choose them from observed user value, not because another agent framework advertises the feature.

Keep the first architecture small. The system should become more legible and easier to recover as capabilities improve. A successful model/harness upgrade should remove unnecessary scaffolding, not require another permanent orchestration tier.
