## 2. Incident interpretation and truth boundary

The Chairman’s current observation is materially different from the familiar historical pattern:

- ordinary historical case: one long Web conversation dies or becomes unusable while fresh conversations remain healthy;
- 2026-09-12 observed case: several Pro-mode conversations became unreliable or failed in a correlated period while a higher-effort lane appeared materially healthier.

This record treats that as **direct local operating evidence of a possibly degraded lane**, not proof of provider intent, deliberate throttling, exact quota exhaustion, or a specific backend topology.

The existing Web-Sol law remains controlling:

> `Thinking failed != context exhausted`.

A single generic provider error, stalled spinner, missing cue or terminal generation failure may establish a bad or uncertain **surface**. It does not by itself prove context exhaustion, account quota exhaustion, model outage or provider-wide unavailability.

Likewise, several failures in the same period justify a stronger **routing precaution** only when their independence, scope and freshness are explicit. Provider-health inference must never silently turn browser error text into billing/quota truth.

## 5. Architecture — one persistent organism, disposable cognition leases

### 5.1 Durable responsibility plane — Agent OS

A logical Sol responsibility is identified by its current organizational responsibility/workstream and accepted handoff state, not by the URL/title of a ChatGPT conversation.

Agent OS must contain enough durable state that a totally dead predecessor is not required to summarize itself. Project chat history may accelerate recovery but remains advisory.

Minimum recoverable continuation:

```text
responsibility_ref / workstream
current governing decisions and source law
accepted completed capability boundaries
open decision or worker dialogue obligations
exact next observable capability action
known blockers and effect uncertainty
```

### 5.2 Durable execution plane — Executive OS

Provider/session liveness must never become the Job lifecycle owner. Worker execution can outlive the Web leader turn.

Executive OS continues to own:

```text
Job
Attempt
Worker
Event
claim
retry/reconciliation
canonical terminality
```

A leader conversation dying does not cancel a Job. A provider route becoming degraded does not authorize replay or replacement of a started modifying Attempt.

### 5.3 Cognition lease plane — RuntimeBinding

For one stable Sol responsibility:

```text
generation N   = current exact conversation/runtime lease
generation N+1 = exact verified successor lease
```

Succession preserves the logical responsibility and fences generation N. The old chat may become responsive later; it does not regain authority.

This is **succession**, not generic failover.

### 5.4 Provider evidence plane — existing Capacity / Provider Control

Provider Control receives content-free observations from accepted sources and emits the one canonical provider/resource health and availability view. It does not scrape transcripts, private backend calls, cookies, hidden request metadata or secret-bearing account state.

The Web-Sol browser adapter is a **sensor**, not the health owner.

### 5.5 Placement plane — existing claim + Model Router

For **new, unstarted, eligible work**:

```text
required task/capabilities
-> Model Router suitability
-> Capacity/provider evidence
-> existing atomic claim / placement
-> exact provider adapter
```

A degraded provider may be de-ranked or excluded under accepted deterministic policy. That placement choice creates no authority to migrate an in-flight modifying effect.

### 5.6 Attention plane — Wake / Agent Relay

Wake and Agent Relay return material results/decisions to the exact current leader responsibility. They do not become a scheduler or retry mechanism.

If the exact leader lease is stale, attention waits for or participates in the accepted RuntimeBinding succession path. It does not choose the newest browser tab.

## 6. Two different recovery mechanisms

### A. Session-local recovery: exact conversation succession

Use when the provider/product lane remains usable but the exact bound conversation cannot safely continue.

Sequence remains the protected context-rotation sequence:

```text
classify exact surface
-> reconcile predecessor modifying-effect boundary
-> establish durable continuation
-> resolve exact predecessor binding/profile/Project
-> create exactly one successor
-> deliver exactly one deterministic continuation bootstrap
-> verify exact successor
-> establish semantic readiness through accepted owner
-> RuntimeBinding generation N -> N+1
-> fence N
-> update navigation projection
-> successor COLD_STARTs and performs the next governed action
```

No blind duplicate create, bootstrap or RuntimeBinding swap after a lost response.

### B. Provider/lane recovery: capacity admission and placement

Use when several independent observations establish that a provider/product/mode/resource is materially degraded.

For work that has **not STARTed and has no effect**:

```text
provider health/cooling changes eligibility/rank
-> existing placement selects another eligible route
-> normal Job/Attempt/Worker ownership begins there
```

For started/effect-unknown work:

```text
NO automatic provider failover
-> preserve original carrier/runtime binding
-> reconcile effect through canonical owner
-> only after a truthful terminal/no-effect result may a new operation/placement be admitted
```

These mechanisms must not be collapsed. Creating another ChatGPT conversation does not solve a provider-wide outage; routing a started modifying operation to another provider is unsafe.

## 7. Web provider-health evidence model

### 7.1 Preserve existing health vocabulary

Do not invent another persistent breaker-state machine. The existing Provider Control vocabulary already supports:

```text
health.state = available | degraded | unavailable | unknown
cooling.active = true | false | unknown
cooling.kind includes provider
freshness and evidence source
last_outcome / typed error class
```

The future ChatGPT-Web resource must enter a **versioned successor** to the current provider-capacity contract, as already required by Q0. Do not patch `mastermind.provider_capacity.v1` in place.

The exact version/name remains owned by the Q0/Provider Control schema evolution; this integration record freezes semantics, not a parallel schema implementation.

### 7.2 Health scopes stay separate

Every observation and derived state must preserve its scope:

```text
SURFACE      exact conversation fingerprint / generation
REALM        opaque managed profile/account realm
MODE         verified selected reasoning mode only after #480 evidence
PRODUCT      ChatGPT Web product lane
PROVIDER     OpenAI provider family only when evidence supports that aggregation
```

A surface failure cannot silently become provider failure. A Pro-mode observation cannot become `MODE=PRO` merely because a user said “Pro” unless the accepted product evidence binds that exact surface/turn to that mode. Until #480 closes that evidence gap, mode-specific routing remains manual/advisory and machine state stays `UNKNOWN` at that dimension.

### 7.3 Closed content-free signal classes

The browser/provider health bridge may consume only accepted normalized signals such as:

```text
TURN_OR_SURFACE_SUCCESS
GENERATION_CUE_ACTIVE
GENERATION_TERMINAL_FAILURE_CUE
PROVIDER_ERROR_CUE
AUTH_REQUIRED
SURFACE_UNUSABLE
TRANSPORT_UNAVAILABLE
USAGE_LIMIT_EVIDENCE          # only from supported source; not inferred from generic failure
UNKNOWN
```

No raw provider error prose, prompt, response, transcript, DOM dump, title, cookie, token, billing identifier, private endpoint response or account PII enters Provider Control.

### 7.4 Correlation law

Correlated degradation must be derived from **fresh independent observations**, not a single error multiplied by multiple projections.

At minimum:

- duplicate tabs of one exact conversation count as one surface identity;
- repeated samples of one unchanged terminal error do not become independent failures;
- freshness is bounded and explicit;
- inventory coverage and probe coverage remain separate;
- a provider-wide `unavailable` claim requires evidence broader than one exact conversation;
- a mode-specific claim requires verified mode identity;
- missing evidence yields `unknown`, not healthy;
- a natural successful current turn is positive evidence but does not erase an unresolved effect on another operation.

The Q0/Provider Control implementation owner may tune numeric thresholds from observed data. The sensor must not hard-code product-wide policy.

### 7.5 No synthetic retry storm

Web-Sol must **not** manufacture provider traffic merely to make health green. In particular:

- no automatic submit loop;
- no “open five chats and see which works”;
- no cross-account quota evasion;
- no background prompt canary solely to repair missing telemetry;
- no synthetic success that overwrites an unresolved failed/unknown production effect.

For ChatGPT Web, recovery evidence comes from normal eligible work, a separately approved harmless proof, or supported provider/account evidence. For existing CLI/API workers, current provider-attempt telemetry may continue to supply health evidence through its canonical owner.

## 8. Deterministic placement policy

A future accepted Web resource participates in placement through existing Capacity policy.

### New/unstarted work

- `available`: eligible normally.
- `degraded`: eligible only when suitability/quality/economic policy says it remains the best safe route; rank below equivalent healthy capacity by default.
- `unavailable`: exclude from new placement until accepted fresh evidence changes state.
- `unknown`: never pretend it is spare/free capacity; policy may use it only when the operation explicitly permits unknown evidence and no stronger route exists.
- `cooling.active=true`: exclude for the cooling scope/horizon.

### Started work

Health affects **attention and expected latency**, not authority. Started modifying work remains bound until canonical effect/lifecycle reconciliation.

### Frontier cognition versus worker labor

Current routing law remains controlling: scarce/high-effort Chat cognition should perform architecture, hard diagnosis, synthesis, adversarial judgment and acceptance. Handoffs, polling, routing, repetitive tests and mechanical edits should run on cheaper/less-scarce eligible workers.

A provider incident strengthens this rule: do not consume the healthiest remaining frontier lane doing work that can safely run through Codex/Cursor/Claude/Grok/operator lanes.
