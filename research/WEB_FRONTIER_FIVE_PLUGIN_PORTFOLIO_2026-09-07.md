Date: 2026-09-07

It is not an accepted architecture freeze, implementation commission, runtime admission, worker assignment, installation, release, or production claim.

Source operation: web-frontier-five-plugin-research-20260907-sol-001.
Source carrier: sol/web-frontier-plugin-portfolio-20260907; exactly this research path.
Organizational context: WS:CHAIRMAN-CONTROL-ROOM / MAS-198, with federated Context Index, CodeIntel, Workbench, Runtime/Capacity/Dialogue, evaluation, browser and release owners preserved. This proposal creates no new workstream or canonical owner.

## 1. Recommendation

Build five focused capability packages over existing Mastermind systems:

1. **Mission Intelligence:** recover the exact mission, current evidence, open uncertainty and permissible next actions.
2. **Workbench:** inspect authorized working source, run bounded reproducible experiments and make scoped branch changes.
3. **Specialist Mesh:** obtain independent expertise, consume useful returns, resolve disagreements and preserve responsibilities across conversations.
4. **Reality Lens:** inspect the real product journey and connect visible behavior to exact release, data and application evidence.
5. **Integration Radar:** identify change dependencies and collisions, request relevant combination proof and expose the next useful integration action.

The intended improvement is not a larger menu of tools. It is a complete loop from a consequential question to evidence, experiment, independent judgment, authorized execution and verified user or machine value. The potential company-specific advantage is a reusable linkage among intent, evidence, intervention, decision, change and user outcome. More records are not themselves the moat.

The immediate delivery priority is one useful mission-recovery and exact-evidence journey, followed by one investigative experiment and actual product observation. Read-only integration planning can advance independently. Multi-specialist scale must follow a proven reciprocal return/continuation loop, not precede it.

## 3. Alternatives considered

A generic terminal wrapper is insufficient because attended host tools already provide basic primitives; original value must come from exact project binding, reproducibility and effects. A generic browser wrapper is insufficient because screenshots and clicks do not establish user success or release/data correctness. A new vector memory store would duplicate Agent OS and Context Index. A new API-powered CEO would duplicate cognition cost and control ownership. Another Linear-like dashboard would add operating burden. A standalone AI reviewer is better treated as a bounded specialist role within a wider delivery loop.

Reject five independent mini-platforms. Reject one super-MCP holding every credential and arbitrary action. Prefer five separately scoped skill/MCP packages over federated existing owners. Share transport/result conventions and UI patterns, not privileged credentials or lifecycle authority.

## 4. Shared architecture and contracts

A web role selects a purpose-specific skill and small tool surface. Existing authentication and resource owners resolve principal, project, current source, RuntimeBinding and grants. Reads return exact evidence with omissions and uncertainties. Execution uses the existing executor and lifecycle. The frontier model remains responsible for relevance, hypotheses, synthesis, decomposition and adjudication.

Common result concepts are projections of existing owner facts: source/evidence references; observed-at and validity basis; committed baseline separate from working bytes; coverage/omissions; deterministic observations separate from model inferences; current owner-native operation references; effect evidence; and bounded drilldown positions. Do not create a universal replacement receipt, graph database, identity registry or status store.

Caller expected hashes are stale-source assertions, not source-selection or authority grants. Missing, empty, stale, partial and unavailable are distinct. Negative search cannot establish global absence when coverage is incomplete. Corrected evidence must identify affected conclusions while preserving historical provenance.

Extend existing capability projections to distinguish installed package, exposed schema, authenticated caller, authorized resource, successful operation and useful end-to-end result. A ping, app listing or green source test establishes only its stated boundary. Keep results useful without optional UI; decisive evidence and uncertainty belong in model-readable structured output. UI-only metadata is not a secret store.

Reads, writes and computation must be separate tool contracts. Asking for a plan cannot silently submit a job. A process timeout or cancellation request never establishes that no effect occurred. Preserve the existing NOT_APPLIED / APPLIED / EFFECT_UNKNOWN vocabulary and original reconciliation identity. Expired execution authority does not erase durable effect knowledge or independently authorized historical receipt reads.

Use existing identity providers and resource policies. Resource/audience, subject, client and project must be checked at the proper boundary; OAuth login is not blanket filesystem or Executive authority. No token passthrough, prompt-based permission, credential export or automatic scope widening. Retrieved text and specialist returns remain data, not Chairman instructions.

## 5. Mission Intelligence

### Mission, value and user journey

A fresh CEO or specialist should know the outcome, current evidence, unresolved disagreements and useful next investigation without reconstructing the company. This is not a summary of the previous conversation. It is a mission-aware composition of current canonical sources.

For a request to continue Control Room work, recover the existing responsibility, accepted user outcome, current source and release distinctions, active change carriers and evidence gaps. When Agent OS and a PR disagree, show the discrepancy and relevant observation epochs. Do not restart the project or select the newest-looking sentence as truth. The model chooses the most valuable uncertainty to resolve and drills into exact evidence.

### Candidate tools

- `brief_mission(responsibility_ref, prior_brief_ref?, detail?)`: compact outcome, current owner-derived state, source vector, obligations, uncertainty and drilldown references. Read-only.
- `search(question, scope_refs, evidence_classes?)`: relevant evidence with coverage and freshness; relevance is not authority.
- `fetch(evidence_ref, range?)`: original bounded evidence at the exact returned revision.
- `mission_delta(responsibility_ref, prior_brief_ref)`: changed facts and invalidated assumptions, or an explicit need for full reconstruction.
- `assess_claim(claim, evidence_refs)`: structured support/contradiction/missing-evidence slots; any semantic judgment is an explicitly labelled model inference, not a deterministic truth verdict.

Avoid duplicate aliases where an existing owner already supplies the job. Brief references are evidence projections/artifacts, not a new responsibility identity or memory store.

### Composition and method

Extend Context Index and the CEO boot-packet/read owner. Use the accepted CodeIntel facade when qualified; until then, lawful direct source reads remain useful with explicit semantic-index limitations. Deterministic code resolves scope, revisions, coverage and changes. The frontier model decides relevance, asks discriminating questions and synthesizes. Progressive disclosure should preserve material dissent and uncertainty, not compress them away.

Keep source event time, observation time and recorded-at time separate where available. A missing Executive read means runtime evidence unavailable, not an empty queue. Market specialists must preserve point-in-time data and descriptive/forecast/trade-authority boundaries.

### Useful slices and proof

**M1:** one real mission brief plus exact evidence drilldown, its short recovery skill, tests and fresh-web canary. Acceptance: correct objective, carrier and next useful read without Chairman relay.

**M2:** material source deltas and correction invalidation. Acceptance: a relevant correction changes the conclusion basis; unrelated source movement does not force redundant archaeology.

**M3:** accepted CodeIntel and one non-code evidence family. Acceptance: a real cross-source question is answered with exact evidence while a wrong-worktree reference is refused.

Stop modifications on ambiguous responsibility or missing authority. Do not block independent lawful reads merely because another source is unavailable. Measure recovery effort, time to first correct useful action, wrong-source conclusions, omitted blockers and repeated work.

## 6. Workbench

### Mission, value and user journey

Give web frontier reasoning an experimental and source-editing loop. Sol should be able to inspect exact source, test a migration or correction hypothesis, compare outputs and produce a narrow reviewable change without a COO handoff for every small uncertainty. Research, statistics and data-quality specialists should use the same governed execution/evidence substrate rather than hidden notebooks and data copies.

### Candidate tools

- `inspect_workspace(project_or_attempt_ref)`: host-derived baseline, working observation and actual allowed capabilities.
- Existing `read_project_file`: preserve its selected-project, relative-path, range and expected-hash contract.
- `execute_project_command(workspace_ref, command_spec, operation_ref)`: explicitly admitted execution through the existing process owner; result and cleanup/effect evidence.
- `run_experiment(experiment_spec_ref, input_refs, operation_ref)`: existing executor/evaluation composition with reproducible outputs.
- `apply_project_patch(workspace_ref, expected_hashes, patch, operation_ref)`: one assigned writable scope, verified readback, no default-branch mutation.
- `read_execution(attempt_ref, range?)`: current result and historical effect evidence; no automatic retry.

### Composition and method

Extend the maintained `integrations/workbench_read_mcp` source owner and existing executor. The current read component is not a shell grant. Separate attended direct command capability from sealed automated recipes; do not call a three-recipe validator a complete terminal. Conversely, a selected working directory is not a sandbox.

Exploratory code needs an explicitly granted isolated execution environment with enforced filesystem, network, process and resource limits. No ambient home directory, unrelated browser profile, root credentials or production data access. If the native environment cannot enforce the promised restriction, narrow or refuse the action. Do not create another supervisor or silently route an uncertain mutation to Desktop Commander.

Freeze confirmatory experiment inputs and methods before the run: hypothesis, data/source references, environment/dependencies, relevant randomness, bounded resource use, expected observations and a disconfirming result. Label exploratory versus confirmatory work. Deterministic execution collects evidence; the frontier model designs experiments and interprets limitations. Corrections generate linked new results, not silent replacement of history.

### Useful slices and proof

**W1:** complete the existing read owner's remaining qualification and one approved installation. Prove fresh-web reads, stale-hash refusal and revocation; do not restart its completed source-authoring child.

**W2:** one real investigative experiment using the existing executor, with exact inputs and cleanup evidence. Acceptance: the model revises a material assumption when falsified. Exit zero alone fails.

**W3:** one expected-hash patch and real test on an assigned branch. Prove a useful bounded fix, correct diff and no other workspace modification.

**W4:** add domain profiles only for demonstrated needs; use Agent Evaluation for assignment/scoring/artifact retention rather than another experiment authority.

On timeout, report running, terminated or unknown accurately. Cancellation requested, descendants stopped and side effects reconciled are distinct. Measure questions resolved, evidence latency, reproducibility, unnecessary handoffs and containment failures.

## 7. Specialist Mesh

### Mission, value and user journey

The CEO obtains genuinely different expertise, resolves contradictions and preserves responsibilities across conversations without Chris selecting routine accounts or relaying messages. The product is accountable specialist work, not tab count.

For a complex capability, give product, data-integrity and adversarial specialists the same frozen outcome but different mandates. Collect independent first passes, use one bounded cross-examination on a material disagreement, integrate while preserving dissent, and independently review. For a small task, use one worker and reviewer rather than mandatory councils.

### Candidate tools

- `plan_specialists(mission_ref, questions, constraints, budget_ref)`: advisory decomposition and least-scarce avenues; no starts.
- `request_specialist(approved_commission_ref, operation_ref)`: existing Executive admission receipt; QUEUED is not dispatch or START.
- `read_specialist_return(child_turn_ref)`: conclusions, evidence, contrary observations, uncertainty, outputs and requested decisions.
- `respond_to_child(current_turn_ref, decision, continuation_or_stop)`: same-carrier current-parent operation through existing Dialogue/lifecycle owners.
- `checkpoint_responsibility(responsibility_ref, continuation, evidence_refs)`: existing durable organizational continuation, not a new transcript store.

Existing endpoint names should be retained when they already provide these capabilities. Role labels and self-identification do not grant authority.

### Composition and method

Reuse Executive OS, SessionTargetRegistry/RuntimeBinding, Capacity, Dialogue/Agent Relay/Wake and Agent OS. Keep always-on state and attention deterministic. Preserve useful reasoning summaries and evidence, not private chain-of-thought or whole provider transcripts. Majority agreement is not correctness; select independent methods/evidence and discriminating tests.

An admitted job or persistent MCP request does not prove the ability to start another ChatGPT web reasoning turn. Qualify the exact supported continuation adapter. Codex hooks, visible model output and open tabs are not web semantic ACK/START. An unavailable parent leaves an honest pending obligation, not a second parent or automatic paid fallback.

Succession preserves responsibility, reconciles uncertain effects, advances the existing binding generation and fences the predecessor. Late replies and renamed/revived old chats cannot regain authority.

### Useful slices and proof

**S1:** through current Runtime/Dialogue owners, prove one exact web parent-child exchange from bounded commission to evidence return, parent decision and explicit closure. Preserve #491 and associated source ownership.

**S2:** two independent read-only mandates and one synthesis. Prove a planted substantive disagreement is preserved and resolved through evidence, not answer concatenation.

**S3:** one supported conversation succession with checkpoint, generation fencing and a useful post-transfer action; lost ACK must not duplicate an effect.

**S4:** product, statistical, architecture, data-quality and adversarial skill profiles; no separate authority systems.

Admission must enforce current child/depth/resource budgets. Start with one child as a rollout scope, not a claim about provider limits. Measure unconsumed returns, Chairman relay actions, parent response latency, duplicate effects and outcome quality per specialist turn. Fable remains scarce; route bounded implementation to the least-scarce capable worker.

## 8. Reality Lens

### Mission, value and user journey

The model sees the actual user journey and connects visible behavior to release, data and application evidence. Reject technically present but unusable, misleading, disconnected or unproven features.

For Control Room, inspect the approved current application, follow a meaningful decision, observe desktop/narrow-screen states and verify the result. A successful backend response with a failed user journey remains a failure. For data specialists, trace a displayed claim to its source and correction behavior.

### Candidate tools

- `observe_surface(target_ref, release_expectation, scope)`: image/semantic snapshot, exact release, loading/error conditions and coverage.
- `inspect_journey(journey_spec_ref, target_ref, test_identity_ref)`: explicit execution with step observations, expected/actual behavior and unvisited states.
- `correlate_observation(observation_ref, trace_refs)`: existing logs/metrics/data with stated correlation limits; timestamps alone do not prove causality.
- `compare_experience(observation_refs, rubric_ref)`: comparable change evidence, preserved exceptions and missing comparability.
- `read_proof(proof_ref)`: bounded evidence and optional visual inspection, not final acceptance.

### Composition and method

Reuse worker-browser, telemetry and release owners. Playwright provides traces with actions, snapshots, screenshots and network/console evidence; do not build another trace store. Original value is the link between journey, intent, release, data and acceptance.

Use image and semantic evidence together. Screenshots alone cannot prove backend truth; DOM evidence alone cannot prove visual usability. Deterministic capture/assertions support frontier visual and product judgment.

Keep workload/application browsing separate from the restricted Web-Sol ChatGPT control surface. This plugin does not widen Web-Sol into arbitrary click/type/transcript access. Use approved application origins and identities. Host screen/provider-session capabilities require separate qualification.

Prefer seeded non-sensitive identities. Redact and authorize both artifact creation and subsequent access. Mark live, stale, sampled and synthetic data. Missing telemetry means not observed when coverage is incomplete, not did not occur. Preserve clock/release skew and corrected input states.

### Useful slices and proof

**R1:** one read-only approved product observation with visual/semantic/exact-release evidence, consumed by an existing canary owner. A fresh specialist must find a seeded usability or truthfulness issue.

**R2:** one reversible seeded journey with producer, consumer, UI and required telemetry. Test normal, empty and one failure state; name untested states.

**R3:** comparable release/correction observations that surface a real regression without treating every visual change as a functional defect.

**R4:** approved production outcome instrumentation through the existing analytics owner. Instrumentation presence is not improved user success.

Stop on wrong target/release, missing grant, sensitive-content risk or uncertain business-side effect. Do not repeat a mutation to obtain a prettier trace. Measure journey success, meaningful coverage, pre-acceptance defects, false alarms and escaped failures.

## 9. Integration Radar

### Mission, value and user journey

Given the active change estate, identify independence, collisions, dependencies, required combination proof, valid existing evidence and the next useful integration action. Advisory only: no new scheduler, queue or merge authority.

Two PRs can modify different files yet change a shared producer/consumer contract. Radar should expose that relation, request the right bounded combined test through the existing executor and preserve unrelated accepted evidence. It must not churn every author's branch because protected master moved.

### Candidate tools

- `map_change_estate(scope_ref)`: exact heads/bases, evidence coverage, holds and owner references; no rebase or allocation.
- `explain_change_relation(change_refs)`: textual, symbol, contract, migration, release and ownership relations with evidence/uncertainty.
- `plan_integration(snapshot_ref, mission_constraints)`: advisory partial order, independent sets, cycles, missing evidence and proposed tests.
- `request_integration_check(plan_ref, change_refs, operation_ref)`: explicit existing-executor admission for a combined test.
- `assess_delivery_evidence(capability_ref, evidence_refs)`: separate source, review, CI, deployment, product and learning states; no automatic final acceptance.

### Composition and method

Extend current integration-planning, GitHub release assessment and Operation Assurance owners. Do not start a competing Integration Planner assignment.

First, derive an exact deterministic map from changed paths, heads, holds and validated owner references. Second, add accepted CodeIntel and explicit APIs/events/data schemas/migrations/configuration to identify semantic relations. Model-proposed relations remain hypotheses until verified or adjudicated. Incomplete graph coverage cannot establish independence.

Third, request high-value combination tests in isolated integration source, never another worker's writable branch. Pairwise passes do not prove a larger combination; bound the search rather than enumerate every subset. Where native GitHub merge queues are available and configured, consume their merge-group proof rather than reimplementing their queue.

Keep authority tree distinct from dependency graph. Dependencies do not transfer ownership. Evidence reuse depends on exact applicability under existing release policy: a path-disjoint documentation change need not invalidate semantic review; a relevant schema, policy, environment or data change may. The model cannot waive current-head/base gates.

### Useful slices and proof

**I1:** useful read-only plan for an actual bounded PR cohort with drilldown and omissions; identify a real next review or prerequisite without manual graph reconstruction.

**I2:** one accepted semantic relation family and a changed-file-disjoint contract conflict, distinguished from a speculative model flag.

**I3:** one isolated combined-change run through existing CI/executor, catching a combination defect and preserving source-writer branches.

**I4:** closeout evidence projected through existing Control Room/Agent OS owners. CI-green-but-unproven product work must remain unaccepted.

On partial pagination, stale heads, missing repositories, unknown coverage or rate limits, return partial/unavailable rather than green independence. Preserve unknown effects of previous integration requests. Measure missed collisions, false edges, unnecessary rebases/re-reviews, integration wait and time to a useful decision.

## 10. Connected operating example

This is illustrative, not a new Control Room commission.

Mission Intelligence recovers the existing decision-first outcome and maintained carriers. Reality Lens reveals how the current approved journey behaves. Sol asks product and runtime specialists different questions about one material gap. Their disagreement about empty versus unavailable state is preserved. Workbench tests that distinction using a bounded fixture and the real selected consumer. Sol commissions the existing source owner only after the relevant gates. Integration Radar checks producer/consumer dependencies and the combined proof needed. After authorized release, Reality Lens repeats the exact journey. Sol adjudicates against the original user job and records the outcome with its current owners.

The same pattern serves data research, architecture validation, statistical falsification, narrow implementation and adversarial review. Research context never becomes trade authority by implication.

## 11. Packaging and current platform feasibility

Current OpenAI docs describe plugins as skills, MCP connections and optional UI. Tool-only operation is valid. Package a small relevant skill/tool surface for each role; installation selects an experience, while server-side policy determines authority.

The developer-mode guide currently includes Pro and read/write tools; the Help Center FAQ still describes Pro read/fetch only. Do not infer actual tool support solely from either plan prose. Qualify the real account, host, app generation, schema, authentication and confirmation behavior.

Current packaging docs describe `.codex-plugin/plugin.json`, skills, registered MCP mappings and local/workspace distribution. Some authoring/installation and hook behavior is explicitly desktop/Work/Codex-specific. Do not assume those features automatically exist in the web consumer.

Use existing Python/MCP/auth compositions where maintained, and optional MCP Apps UI only where it adds visual value. Model-readable conclusions and evidence must not be hidden in UI-only metadata. Use the accepted private transport, including supported Secure MCP Tunnel where appropriate; never expose an Executive control socket or privileged shell directly to the internet. Test web behavior independently of local MCP Inspector or Codex success.

## 12. Delivery sequence, evaluation and stop criteria

Deliver M1 and the maintained Workbench read proof first. Reality read observation and Radar read planning can proceed independently through their own source owners. Then add one experiment and one journey proof. Complete the existing single parent-child loop before specialist fanout and succession. Scale concurrency only when it is the bottleneck rather than integration/review debt.

Do not require the entire #490 repair, whole CodeIntel program or a new common-schema project before unrelated useful slices. Conversely, never skip the particular resource/authority gate required by an action.

Use the existing Agent Evaluation Fabric. Compare current-tool baseline against skill-only, structured-read and full-capability variants on representative frozen tasks. Counterbalance order, use fresh contexts, preserve exact source/model/surface/resource conditions and keep held-out tasks. Report uncertainty and failures rather than a single cherry-picked demonstration.

Primary measures: accepted end-to-end capability increments per bounded CEO/specialist effort; elapsed critical-path time; evidence/tool/context overhead; Chairman interventions; escaped defects; wrong-source conclusions; and duplicate/unauthorized effects. No speedup has been measured here. A proposed 30–50% orientation/tool-overhead reduction may be a pilot hypothesis, not a forecast or acceptance fact.

Required fault cases include unavailable Executive reads, stale tool schemas, incomplete source coverage, working/indexed-source disagreement, superseded decisions, adversarial retrieved instructions, lost execution replies, expired grants with retained historical effects, incomplete cancellation, competing specialist edits, stale-binding late returns, unsupported web wake, screenshots with incorrect data, missing telemetry, disjoint-file shared-contract conflicts, pairwise versus group interaction, and unfamiliar accounts without their own canary.

Refuse unauthorized effects in every case. Preserve partial evidence rather than inventing a global green result. Reshape a plugin into skills over existing tools when its new server does not improve held-out outcomes. Reduce specialist fanout when coordination cost exceeds additional judgment. Remove unused aliases and dashboards.
