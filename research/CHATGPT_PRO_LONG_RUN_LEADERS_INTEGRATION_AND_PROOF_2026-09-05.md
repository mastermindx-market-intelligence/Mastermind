## 1. Result of the deeper investigation

The missing product is not a larger collection of plugins. It is a dependable route from a substantial reasoning turn to an observable result, with preserved intent, exact ownership, safe execution, independent evidence, and recoverable continuation.

Three conclusions materially sharpen the initial assessment:

1. Much of the requested interface architecture already exists in the **Sol Capability Fabric, Business Sol Surface Convergence, Code Intelligence Fabric, Executive boot packet, Company Dialogue, and Web-Sol succession** programs. A second workbench/control framework would repeat those owners rather than finish the journey.
2. A Mastermind RuntimeBinding fence does **not, by itself, prove that a retired chat cannot write through an independently authorized native GitHub, Slack, or Linear connection**. End-to-end autonomous claims require coverage of every reachable modifying path. This is a design inference requiring a falsifier, not a demonstrated exploit or an assertion that a current production incident occurred.
3. Plugin packaging, approval behavior, asynchronous tool protocols, and exact chat continuation are separate compatibility problems. A package can be present but unavailable on web; a read-approval preference can still permit a confirmed write; a durable tool handle can survive a disconnect without waking a dormant Pro conversation.

The practical recommendation is **one coherent experience, existing federated authorities, and smaller proof-complete verticals**. Give Pro sessions better evidence and bounded execution before giving them wider privileges.

## 5. New finding: fencing must cover all reachable mutating paths

### 5.1 The counterexample

Consider this possible configuration:

1. Chat A owns binding generation N.
2. Mastermind advances the responsibility to Chat B at N+1 and refuses A at CeoIngress.
3. A still has a separate native GitHub connection with repository-write permission.
4. A calls that native app directly rather than the fenced Mastermind endpoint.

Unless the native action path has an independent enforcing restriction, the RuntimeBinding refusal at CeoIngress does not logically imply a GitHub refusal. The same reasoning applies to generic Slack/Linear writes, shell credentials, desktop automation, and alternative MCP endpoints.

This is **an architectural falsifier, not an executed attack**. No real credential was inspected and no unauthorized action was attempted. Current instructions already prohibit stale actors from acting, but procedural prohibition and technical prevention are different assurance claims.

### 5.2 A precise coverage condition

For an autonomous modifying capability, inventory its reachable mutators R under the actual account/app/process configuration. Let E be the paths whose actuators enforce the required current scope, permission, identity, source and effect predicates, and D the paths technically denied for that configuration. The claim requires `R` to be covered by `E union D`; any unexamined reachable path remains an explicit gap.

This is a review criterion over existing owners, not a new runtime permission engine, registry, database, or lifecycle. A read-only result may honestly state that action coverage has not been established.

### 5.3 Approval timing is not action restriction

OpenAI distinguishes available action controls and provider grants from when ChatGPT asks approval. In particular, **Allow read actions** permits reads without asking and requests confirmation for changes; it is not evidence that write capability has been removed. Changing an app permission does not itself revoke the provider connection. Business and Enterprise/Edu also have different available access controls. Verify the actual surface rather than assuming per-chat or per-role isolation. [O1, O2]

### 5.4 Recommended staged posture

Keep research leaders read-only where actual action/provider restrictions can enforce that posture. Route autonomous modifications through narrow existing owner-mediated actuators. Keep broad native writes attended and separately authorized when they are necessary and cannot be mechanically fenced. A human-approved native action remains a legitimate supported action, but it must not be used as evidence that every old session is technically unable to act.

Never revoke a shared connector or change workspace permissions casually: the change can disrupt active siblings. Any such migration needs its own current identity, ownership, confirmation and rollback gates.

Minimum proof: two synthetic chats sharing a principal; one exact child; a binding transition; old-generation attempts through every enabled modifying route; controlled current-generation success; and verification that an unrelated sibling's allowed work is preserved. No production release can be justified by testing only the custom MCP path and ignoring ambient native apps.

## 7. The long-run leader's actual working contract

A good long-horizon turn needs a rich but bounded problem, not artificial delay. The following is a proposed mission-template refinement for existing skills and commissions:

```text
Original user outcome and primary persona
Machine/intelligence outcome
One observable deliverable for this turn
Current source and evidence references
Relevant accepted decisions and explicitly rejected alternatives
Known unknowns and competing explanations
Scope, non-goals and existing path/authority owners
Tools actually available and their permission boundaries
What can be done independently versus what requires a returned worker result
Evidence that would discriminate success from persuasive prose
Current operation/carrier and unresolved effect state
Stop, blocked-return and durable continuation conditions
```

The reasoning loop should be: frame hypotheses; retrieve the smallest discriminating evidence; resolve material uncertainty; specify or review one useful vertical; persist the decision; and return the next action or explicit blocker. A turn may be long because the reasoning is hard. It must not be padded with polls, repetitive reviews, cosmetic re-grounding, or unrelated improvements.

Before handing off or approaching a context boundary, preserve conclusions, evidence references, alternative explanations, rejected approaches, remaining risks and exact next actions. Do not store hidden chain-of-thought or duplicate whole transcripts. A dead predecessor must not be a single point of failure for recovery.

Proposals are model-generated. Identity, permission, idempotency, effect reconciliation, binding transfer and budget enforcement remain deterministic at their current owners. Model or effort mode requires actual host evidence; prose cannot attest it.

## 8. Execution and observation should be more efficient, not less strict

### 8.1 Optimize the expensive boundaries

Measure the real cost of discovery, tool round trips, repeated evidence, bootstrap, and recovery. Then prefer:

- immutable-source batching and content-addressed reuse;
- exact-symbol or bounded diff reads through the CodeIntel/GitHub owners;
- progressive discovery of one task-relevant tool family;
- bounded output with explicit coverage and evidence references;
- deltas from an existing result/output cursor where its owner supports them;
- coalesced material-return events instead of model-driven status polling;
- producer-plus-consumer vertical proofs rather than repeated infrastructure-only reviews.

No claimed latency or token reduction has been measured here. A schema-size budget is a future measured contract, not a guessed universal threshold. Respect frozen client snapshots: a smaller representation that breaks a reviewed schema is not an optimization.

### 8.2 Preserve the distinction between files, shell and desktop

Approved filesystem roots do not sandbox a general shell or desktop controller. A production workbench needs the existing worker/process isolation boundary, least-privilege credentials and network rules. Command handles must be bound to the actual authorized execution context. Current permission revocation must affect calls even when the chat retains an old schema.

A requested cancellation is not proof that a process stopped, and a timeout is not proof of no effect. Partial patches, completed desktop steps, long-lived commands and surviving child processes require attributable receipts and owner reconciliation. Do not add a parallel process/task database or silently launch a replacement worker.

### 8.3 Do not optimize away useful failures

Chat On Steroids' own historical error-rate report distinguishes expected validation failures, shell quoting/glob errors, a missing path, an option-shaped regex and a rejected stale patch. The lesson is classification, not importing its corpus as our performance benchmark. Its estimated improvement was a projection on observed inputs, not a universal live reliability claim. [C1]

Our measurement should retain at least: expected test RED, protective refusal, input/operand mistake, permission/authentication problem, source/schema drift, transient transport, unknown effect, product defect, and successful result. A raw zero-error target would reward weaker tests and quieter failures.

## 9. MCP asynchronous work: negotiate, do not assume

Current MCP Tasks documentation describes a negotiated extension with durable handles, status retrieval, mid-flight input and cooperative cancellation. It is distinct from the older experimental task protocol. The documentation establishes a protocol option, not that the current ChatGPT client supports it. [P1, P2]

For Mastermind, a task-shaped response must remain a projection of existing Executive/provider execution and evidence, with authenticated access to its owner. If the exact client does not negotiate the supported generation, do not emit incompatible results or retrofit another task store. Use only an already reviewed compatible owner contract.

Keep three claims separate:

```text
The underlying operation can continue.
The client can reconnect and retrieve its result.
The exact inactive ChatGPT reasoning session can be awakened.
```

The first two do not prove the third. A protocol handle does not reserve Pro quota, create native subagents, or keep a model reasoning. A timer, open SSE stream or successful Slack post does not close the exact-session wake proof gap. Unsupported wake remains explicitly unavailable/attended until the existing Wake/Web-Sol owners prove a lawful path.

## 10. Evaluation that measures useful work

This is a proposed preregistration, not a new evaluation service or a completed benchmark.

Use 24 matched tasks: four each in architecture, research synthesis, hard diagnosis, implementation review, interrupted-context recovery, and multi-source reconciliation. Use equivalent isolated fixtures, not a repeated task whose answer has already been leaked to the comparison. Balance order and retain the same allowed model/mode, permissions, source snapshot, outcome rubric and budget wherever the comparison requires them.

Compare the current workflow against the improved context/tool/continuation arrangement. Independent grading should inspect user/machine completion, factual/source correctness, omitted failure states, unauthorized effects, duplicate actions, preservation of original intent, and recovery quality. Report per-task outcomes and disagreements, not only an average.

Directly measure tool calls, discovery calls, response bytes, duplicate retrieval, observed tool/approval waiting, time to a useful decision, human interventions, and accepted deliverables per scarce reasoning turn. Exact hidden compute or thinking time remains unknown. Report wall-clock task time as such, never GPU-hours. An apparent throughput increase with more scope mistakes or hidden refusals fails the comparison.

Do not increase concurrency just because daily message allowance remains. Capacity, provider concurrency, local CPU/memory, actual tool availability, branch ownership and review bandwidth all constrain useful throughput. Under an illustrative limit of six simultaneous turns and 30-minute average occupancy, at most 288 turns fit into a day before other losses; this is arithmetic under an assumption, not a provider limit. The existing Capacity owner holds unknown/exhausted capacity rather than silently moving a started operation between accounts.
