## 1. A single operating loop, with the user beside it

```text
Chairman intent and current accepted boundaries
  -> existing strategic cognition / agenda
  -> existing Executive admission and current responsibility
  -> existing Model Router / Capacity / capability qualification
  -> exact admitted provider/host execution
  -> actual output, artifacts and canonical return
  -> existing parent obligation and current-target Wake
  -> actual parent consumption, ruling and next permitted action
  -> evidence, accepted decisions and learning in their durable homes

The user's workspace reads each permitted part and can address the CEO or an
exact session through an accepted command seam. Reading and chatting do not
create a second owner of this loop. Closing the workspace does not close it.
```

There are three linked clocks, not one:

- **Work clock:** admission, execution, return, acceptance and continuation.
- **Conversation clock:** messages, visible plans, partial/completed content and tool observations.
- **Viewer clock:** selection, scrolling, unread state, connection and presentation.

A browser heartbeat advances only the viewer's connection evidence. A new sentence does not necessarily advance the work clock. A model stopping its output does not establish a terminal accepted program. These distinctions are displayed in context, not as dozens of mandatory badges beside every sentence.

## 4. Boundary-specific integration decisions

### Executive app and conversation API

The #599 document enumerates `executive_state`, `executive_inbox`, `executive_job`, `ceo_intent_status` and `submit_ceo_intent`. Rich history, generic message send, Workspace candidate-return callbacks and Workbench files are not synonyms for those operations. They need explicit finite resource/action contracts through their correct existing owners. Do not silently broaden a reviewed tool schema or create an omnipotent proxy because the UI has another tab.

The #599 installation/source owner remains untouched by this design. Its identity and accepted input/output/effect contract must be read at implementation admission. A newer protected/head version can satisfy the prerequisite only through its actual release/proof, not because the PR description says source-complete.

### Native content observation

The existing adapter is already the right place to join exact execution and provider content, but the inspected public projection strips the required content and waits for completion. The finite extension must therefore address source event ingestion, safe visible item content, spectator subscription and history, not merely add an HTTP facade around the same metadata.

It must preserve active helper audits, current-writer checks, effect handling and terminal consumption. The controller must not lose events to a second reader. A content observer cannot mark source progression, alter the provider session, or complete a Job. If the provider can replay only some content, that limit is part of the consumer contract.

### Portfolio chat and research products

The private Portfolio Research Advisor already owns its domain-specific conversation and policy. It may eventually be an authorized linked surface in the same navigation product. It remains an adviser with its own tool/data bounds; sharing a chat UI cannot turn it into the Master CEO or grant order sizing, execution or portfolio control. Its existing history store is not silently generalized into a company archive.

The same separation applies to Prophet, market intelligence, research vault and product dashboards: the workspace links to relevant accepted data/tools/artifacts under their owners. It does not bring every dataset into every agent prompt or manufacture trade authority from a helpful conversation.

### Workspace Agents

The optional adviser/reviewer profiles are not Fable's mandatory parent. Their useful output is a bounded candidate returned to the current responsible owner. A conversation_key maintains a provider conversation; a trigger idempotency key deduplicates one event. Neither should be reused as another Executive Job ID or accepted-result key.

Provider completion and candidate return can arrive in different orders. The UI preserves both. A missing accepted return is a visible integration gap, not a fabricated chat message. A callback requires authenticated operation/input/target/artifact correlation and cannot directly mark the parent's obligation resolved.

### Workspace context and tools

Tool discovery/capability packages, project file access, actual host availability and model eligibility are joined to the exact execution profile. An agent's marketing feature list is not its effective tools. The Context drawer shows the attested/allowed capability and remaining unknowns; raw credentials, full provider homes, process argv and unrelated personal tabs are not inventory material.

## 5. Shared read model and independent actions

The UI read context conceptually contains an authorized scope, source publication/epoch, a selected responsibility or exact session, item/history cursors, supported content classes, related work/artifact references, source coverage and action hints. These are projections of existing identifiers. No new opaque identity registry is needed to display them.

The action request is revalidated separately. It binds the principal, recipient intention, exact resolved target, admitted capability, relevant policy/preimage, stable operation and payload. A read hint is never permission. When a user changes panes, an in-progress draft remains attached to its intended recipient until deliberately changed.

Content/history, execution state, project files and message capability have separate access checks. Losing one optional source should degrade its pane rather than falsely erasing independently readable conversations. Conversely, readable messages do not prove a currently serviceable modifying target.

Record data provenance once at its owner and reuse references. Do not copy whole transcripts into Agent OS, a graph database, a model memory cache and a new frontend service to achieve consistency. Cross-source updates carry their own epochs; there is no global timestamp that makes them one transaction.

## 6. First useful vertical and ownership handoff

The highest-leverage implementation capability is **one exact supported conversation with actual visible content during execution, complete available history, inline related work, and the real supported communication path**. It tests the missing producer, the user experience and the existing action/continuity boundaries together. A smaller read-only release may be useful but remains explicitly below the interaction ceiling.

Sol owns this contract and the visual acceptance criteria. Once the architecture and primary journey are accepted and the existing-owner source gates are resolved, the Chairman has authorized Fable as an appropriate principal orchestrator for this cross-system build. The actual later commission must select a real receiver, allowed source paths and effect scope through current rules; this document does not dispatch one.

A Fable implementation packet should split disjoint work by capability: provider spectator/history seam; authenticated read/message integration; conversation-first frontend; route/context/Workbench integration; and independent security/behavior/browser review. One shared interface contract and source custody prevent each worker from inventing a new backend. Integration and the authentic golden path remain the principal's responsibility, not an unassigned final step.

Before admission, the plan must specify exact source-owned DTOs, provider version, intended installed authority, permitted fixture capture, privacy policy and production canary. Source that can be written safely without a live credential ceremony can proceed; the real interaction canary cannot bypass the ceremony. Do not hold unrelated source work behind a fictitious owner, and do not call a disconnected frontend complete.

## 7. Failure points to exercise across the suite

A complete first-path proof includes a nonterminal response observed before completion; a long paged history; a hidden/filtered content range; a slow spectator; a source disconnect; a changed binding while drafting; a revoked resource scope; a message reply lost after possible dispatch; an optional Workspace completed run with no candidate return; and a worker result arriving while all UI viewers are closed.

For each, record which owner is authoritative, what the user sees, whether any effect occurred and what exact continuation is allowed. A failed Workbench read is not a failed conversation. A failed chat content subscription is not proof the worker stopped. A successful app gateway health probe is not an authenticated Executive read. A source-level protocol test is not real provider support. A successful Figma interaction is not any of these runtime proofs.

## 8. Current scope and remaining uncertainty

Their source writers are not reassigned. No Workspace agent was published/triggered, no database created/migrated, no provider or host configured and no public endpoint exposed.
