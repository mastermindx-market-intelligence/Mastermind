This is the capability-level delivery program and acceptance DAG. It does not assign a worker, create an Executive Job, take source custody, install software or authorize another program's effects. The executor-specific TDD plan follows review of the written architecture and current-source reconciliation. Development tasks such as a reducer, fixture gallery or dependency installation are subwork, not individually advertised product releases.

## 1. Program outcome and ownership

Sol owns the product thesis, architecture reconciliation, decomposition, integration decisions, review against Chairman intent and final acceptance. Existing runtime, identity, transport, capacity, Workbench, installation and source owners keep their systems. The GUI cannot become their substitute because one dependency is delayed.

The complete outcome contains four capabilities: understand the live company; interact with exact operators; keep approved work advancing without the GUI or Chairman relaying messages; and use the same coherent experience on macOS and remote web with explicit security boundaries.

A role name is not proof a source writer is alive. Every future admitted work packet records its exact writer/session when available, safe continuation path, current effect state, return condition and next accountable action. If no receiver is placed, the projection says so. Sol does not ask Chris to choose routine numbered accounts.

Route future work through the current Skillpack and existing Capacity owners. Standard bounded frontend work should not consume principal capacity merely because the whole program is ambitious. Cross-owner integration and adversarial concurrency review require stronger expertise and genuinely independent review; they do not automatically require Fable for every PR.

## 5. LF-V1 — one authentic mission, end to end

**Mission:** Chris opens a specific current mission and understands its recorded work, parallel descendants, exact identities, next accountable role and implementation evidence without tab or Slack hunting.

**Why first:** It tests the difficult source-to-persona join and creates a useful product even before rich provider streams or intervention are ready.

**Input contract:** An authorized exact mission/root reference; owner-qualified plural records; existing organizational and evidence projections; source scope/coverage. Do not derive a root by matching a title. No assumed fleet-wide inventory.

**Output:** Graph and equivalent list, inspector, source/evidence drill-down, and exact navigation only where the current owner already proves it. Recorded lifecycle remains visibly distinct from provider activity.

**Subwork, in order:**

1. Reconcile the current plural reader and its real consumer seam with Runtime/Steward. Reuse valid source review; do not rebuild #508.
2. Materialize a redacted real-data reference composition and adversarial companions. Compare at least two materially different screen compositions before freezing the visual implementation rubric.
3. Build the smallest pure display adapter and one isolated UI bundle. Development fixtures are unmistakably synthetic.
4. Integrate through the existing compositor/server owner. Preserve Today, remote X1, cache and source validity behavior.
5. Exercise one authentic root with at least two recorded descendants, including unknown/partial evidence, through the intended installed read path.
6. Obtain independent functional/security review and live design review. Record actual user task success and all unverified fields.

**Non-goals:** All-account discovery, live provider execution certification from recorded RUNNING, arbitrary session adoption, new scheduler, messaging, remote writes, full Mac privileges or instruction editing.

**Acceptance:** A tester identifies the mission's known work and real uncertainties, selects an exact child, opens its evidence, and returns to the mission without source confusion. Empty scope is distinct from failed source. Graph/list agree. No new canonical mutation occurs. The parent/child rows come from real producer output, not a copied fixture.

**Stop/return:** Wrong or unavailable root source, contested source custody, required field not projected, unsupported schema or privacy conflict. Return the exact missing owner seam and preserve already-built disjoint work. Do not call the milestone shipped until the real journey passes.

## 6. LF-V2 — qualified current activity and semantic history

**Mission:** A person watches a mission evolve without manually refreshing several applications and without confusing transport activity with execution.

Consume current source-owned event/history and observation capabilities. The initial path may continue bounded cached fetches; low-latency updates require a reviewed inexpensive producer/composition extension. Never run the full Agent OS/GitHub gather per client event.

Use header-authenticated fetch streaming if SSE is introduced. Bound subscriptions, queued bytes and source work through existing owners. One tab opening cannot multiply all source gathers. An update heartbeat cannot renew stale source evidence.

Prove out-of-order replies, changed scope, duplicate source events, gaps, reconnect, sleep/wake, client revocation, slow consumer and unavailable history. Deterministic grouping preserves event class, causal references and original receipts. A history gap is visible and does not prevent current snapshot use where independently qualified.

C3 observations are integrated only to their actual installed ceiling. In its current contract, complete inventory and incomplete probes remain distinct, navigation stays unsupported, and remote X1 remains unchanged. No C3 source reimplementation belongs in this wave.

## 7. LF-V3 — one exact interaction

**Mission:** Chris addresses one verified operator and sees the actual result of one supported action, not just a submitted request.

Choose the smallest already-supported owner action at admission; a controlled message at an allowed turn boundary is a valid first candidate. The implementation plan records the exact provider/action scope. No whole-family action permission is inferred.

The preflight binds principal, source/target generation, payload and applicable obligation. The existing owner enforces semantic single-consumption where required, in addition to idempotent request keys. A message, including a request for status, is treated as an action that can spend tokens and invoke tools.

Acceptance includes success, refused preflight, moved target, revoked principal, two-client race, dispatch-reply loss, client restart and canonical receipt rehydration. A lost response is reconciled without duplicate dispatch. The UI never silently switches providers or sends a second message.

The current local CSRF nonce cannot authorize this action by itself. A production-ready existing authenticated action/admission seam is a hard dependency. Where absent, implement the smallest extension through that owner, not inside the GUI.

## 8. LF-V4 — autonomous continuation, not owner theater

**Mission:** A real approved mission advances after its child returns, even with the GUI closed and an unavailable previous reasoning session, without Chris routing the next message.

This milestone is co-delivered through existing Executive/Dialogue/Wake/Capacity/RuntimeBinding/recovery owners. Live only exposes the evidence and intervention points.

Required positive interval:

1. An approved parent commissions bounded child work through the canonical owner.
2. The child's result becomes a durable canonical return without relying solely on model etiquette.
3. The parent's exact current reasoning target consumes the obligation and issues the permitted semantic edge.
4. A next useful child is independently admitted within the original approved scope.
5. Final review and production evidence reach the correct durable records.

Required recovery interval: make the current parent reasoning target unavailable in an approved disposable test. Preserve the role and obligation; reconcile any pending effect; prove the accepted stale-authority fence; transfer to a qualified successor; continue once. A late old-owner response must not regain authority.

The source-custody proof must include actual stale-writer behavior, not only expiry of a database lease. Direct filesystem writes and independent provider tools require effective isolation/fencing at their real sinks. Missing fencing is an upstream capability defect; never hide it with an owner badge.

An indefinite demand that a dead session confirm its own release fails the recovery outcome. The recovery policy must expose finite next actions or an exact genuine external ceremony. It may not invent a bypass. Independent safe work continues while one uncertain effect is reconciled.

Closing Live, losing its stream or restarting the Mac app must not stop the organization. A terminal child must not terminate sibling watchers or be reused to originate its successor. No duplicate Job, semantic edge or provider effect is permitted in the exercised interval.

## 9. LF-V5 — fleet and capacity

**Mission:** Understand where work is running, why it was placed there and which enrolled resources can accept the next independent task.

Consume the existing capacity/physical-domain/host owners. Display compute saturation separately from provider entitlement, quota and account health. Use source-authored routing explanations. Requested model, selected control and served-model evidence are distinct.

Prove two qualified hosts, at least two provider/surface classes where authorized, one portable new task on the secondary host, and refusal of stale boot, wrong workspace, unauthorized realm or missing toolchain. WSL and its host must not double-count physical resources. Enrollment coverage is explicit; disconnected devices remain missing evidence, not deleted from a supposedly complete fleet.

Do not migrate an in-flight uncertain write to another host or copy authenticated browser profiles, live runtime databases or provider homes. Routine placement belongs to Capacity, not the Chairman.

## 10. LF-WEB and LF-MAC

### Remote browser viewer

After V1, a separate remote owner projection supplies exactly the allowed fields. Authentication, authorization and revocation are proven. Sensitive local paths, raw account/session locators, secret shapes and private host information remain excluded. An unknown or dropped local field is not silently coerced into an empty remote fact.

Remote read-only availability must not create provider action or terminal capability. A future remote interaction wave requires explicit source/action authorization and proof; it is not unlocked by setting a frontend flag.

### Native Mac viewer

Package the same UI through a reviewed Tauri shell. Validate the bundled-origin boundary, fixed-target read bridge, signed artifact, notarization, updater/rollback and supported OS/WebView matrix. Untrusted/remote content has no native IPC. No arbitrary HTTP, filesystem, shell or password bridge is admitted.

The current Chrome-paired validity profile does not qualify WKWebView. The initial Mac viewer remains read-only until its own client/action qualification is accepted. A successful app launch is not a working exact-session navigation journey.

A shell update or crash must not restart Executive services or alter their database. Browser and Mac views show consistent source-qualified facts, while accurately differing in supported capabilities.

## 11. LF-ACTIONS and LF-STUDIO

Broader intervention is delivered one action family at a time: inspect, message, interrupt, graceful stop, cancel, reconcile, and separately approved pause-admission/revoke controls. Each has exact targets, scope, effect classes and per-target receipts. Bulk failure is never summarized as atomic success.

Organization Studio contains three independent verticals:

- **Teams/roles:** review a proposed edit, write through the existing organizational/configuration owner, then display its canonical readback. No drag-to-reparent mutation in view mode.
- **Routines:** edit one existing scheduler definition and prove timezone, missed-run, overlap, idempotency and wake/return behavior. No second task scheduler.
- **Instruction evolution:** candidate version, evidence, diff, evaluation, reviewer, bounded rollout and rollback. Existing Attempts remain pinned; concurrent clones do not overwrite shared logs. No prose change expands authority or budget.

Artifact boards are safe views over approved artifacts. A model-created HTML artifact is not permitted to execute inside the privileged cockpit. Learning measures completed jobs, quality and cost, not number of tokens or dashboard pulses.

## 12. LF-FLEET — sustained proof and learning

Use an explicitly approved staged interval: a short integration canary first, then a proposed 24-hour interval, and a broader proposed 72-hour interval only after the shorter result is accepted. These are future proof targets, not work scheduled or performed by publishing this program.

Include authentic work, a child return during GUI absence, controlled parent/worker restart, delayed messages, a source outage, a capacity limit, a changed binding and one uncertain-action reconciliation. Preserve exact counts of actual admissions, effects, returns, consumption and final outcomes.

Measure time to find an exact session, time to understand a blocker, unresolved owner obligations, recovery latency, manual relay/account-selection events, false-currentness defects, duplicate effects, resource overhead and useful completed capabilities. Existing telemetry ownership is reused; no raw transcripts or secrets enter analytics.

Acceptance requires zero duplicate modifying effects in the tested cases, zero false-current/false-complete claims, and no routine Chairman message shuttling in the declared interval. A genuine external authentication/admin ceremony is disclosed separately rather than hidden. The interval's limited scope is recorded; it is not proof of every possible provider failure.

## 13. Handoff contract for each admitted implementation wave

Every actual operator handoff contains mission; why it matters; authority precedence; verified heads and capabilities; exact source/effect scope; non-goals; full user journey; time/null/correction semantics; deterministic versus advisory model method; failure behavior; implementation order; acceptance and production proof; stop condition; and continuation handoff.

The handoff must additionally distinguish source START from installation and provider effects, document actual receiver placement and source custody, and identify the exact response that brings work back to Sol. No worker-specific watch is claimed until a receiver exists. No plan creates an imaginary executing owner.

Independent review is against original intent as well as code. The reviewer must not be the author disguised by another account. A test can discriminate a failure without proving production behavior; both evidence classes are retained.
