## 5. Workspace Agent protocol delta

Official developer reference observed 2026-09-13:

```text
POST https://api.chatgpt.com/v1/workspace_agents/{id}/trigger
GET  https://api.chatgpt.com/v1/workspace_agents/{id}/runs/{run_id}
```

`id` is a published API-channel identifier. Trigger input accepts `input` and optional `conversation_key`; `Idempotency-Key` deduplicates the same event. The beta header `OpenAI-Beta: workspace_agent_runs=v1` returns an `agent_trigger_run_id` for status observation. The API does not retrieve the agent's answer. Provider `completed` is not company acceptance.

The Help Center still describes an older response without a body/run ID. Prefer the developer contract for implementation research, but qualify the actual published channel before depending on the beta. Neither page proves entitlement in these seats.

References: [trigger contract](https://developers.openai.com/workspace-agents/trigger-runs), [authentication](https://developers.openai.com/workspace-agents/authentication), [builder and controls](https://help.openai.com/en/articles/20001143).

### 5.1 Start as a supervisory client, not a fictional full worker adapter

The initial integration belongs at the existing Wake/attention and governed-app boundaries. Do not label it a complete OperatorHarnessAdapter or WorkerExecutionAdapter merely because HTTP triggering works. The inspected public contract does not establish the cancellation, streaming-result, process, or rich-session semantics those interfaces require. Unsupported operations remain unsupported.

Any new transport identifier or remote-target representation requires reviewed extension of the existing descriptor/binding owner and its real consumers. Do not insert a made-up local PID, invent a second session registry, or mark the transport implemented before its complete current-target and return path is qualified.

### 5.2 Bind the event, responsibility and provider observation separately

At admitted dispatch, the existing owner must bind the logical responsibility, exact current target/generation, approved agent configuration, event identity, payload digest and economic envelope. Store only permitted provider observations with those existing records.

Use responsibility-scoped conversation continuity, not a shared conversation for the entire organization. Deduplication identity is per event, not per whole project. A corrected or new event must not accidentally reuse an old event key. A changed payload under an existing key is a conflict. Keys must be opaque and must not disclose paths, credentials, people or confidential task content.

A provider `202` proves provider queue acceptance only. It does not prove execution, consumption of the current obligation, delegated authority, receipt of useful output, or a completed Job.

### 5.3 The missing return edge is the decisive integration

Because the trigger API does not deliver the answer, the agent must return a bounded candidate through an authenticated, purpose-limited tool over the existing result/attention owner. Reuse its accepted grammar rather than create a generic webhook state store.

The implementation freeze must identify the exact current ingress and prove all of these joins: authenticated calling principal, intended agent/channel/version, current responsibility/epoch, originating obligation, input/context digest, exact artifact references, disposition, and evidence limitations. Agent-authored IDs or prose alone cannot authenticate a run. Where run-specific attestation is unavailable, output remains an untrusted candidate; the receiving owner must validate it and must not synthesize a trusted Wake ACK or action-authoritative session.

The current five-tool Executive contract is not silently widened. #599 remains its original repair. Any additional bounded result action is a separately reviewed extension through the existing app/auth/result owners, with an explicit scope and compatible consumer.

Keep acknowledgment of attention, decision/ruling, candidate artifact, independent review, canonical result acceptance, and next-child admission distinct. A run can finish successfully while producing no acceptable artifact. A valid artifact can arrive before provider status is terminal; both states must remain visible.

### 5.4 Recovery and security

Unknown launch outcome holds the same event and carrier for canonical reconciliation. Provider idempotency helps but does not replace Executive effect ownership. Never automatically move an uncertain operation to another account, host or provider. A known pre-start refusal can be placed anew only through existing rules.

A suspended run is a wait, not free capacity or completion. A missing callback does not authorize redoing the work. Reject stale-target, duplicate, out-of-scope and corrected-input callbacks. Preserve the earlier evidence with supersession; do not erase history.

Use exact tool/role scopes and existing secret custody. Revalidate grants at every material write so a stopped responsibility cannot continue changing the company through a late tool call. Revoking tool authority does not prove the vendor stopped computing or billing. Do not promise cancellation or bounded provider lifetime without direct evidence.

Treat repository text, Slack, issues, web research and returned artifacts as data. Only current authorized intent and existing policy owners can confer authority. A research note that says 'launch workers' is not an instruction to do so.

## 6. Two initial agent definitions, not two guaranteed compute lanes

These are proposed builder profiles, not installed skills, published agents or assigned runtime seats. Start with one canary at a time until actual concurrency and accounting are known.

### Profile A: Program Continuity Adviser

Mission: read one current approved responsibility and its pending returns; identify the next useful in-scope action or exact decision/blocker, preserving original user intent.

Inputs: current Executive read projection; cited Agent OS context bundle; exact candidate artifacts; current instruction/profile revision. Missing inputs remain missing.

Method: recover the goal, accepted decisions and no-rebuild boundary; consume pending results before launching unrelated work; distinguish ready, waiting, unknown, failed and terminal; propose one next action with evidence and a stop condition. Avoid broad fresh research when an accepted plan already supplies the answer.

Output: a scoped continuity recommendation/candidate through the qualified return path. Initial tools are read-only plus the purpose-limited candidate-return action once it exists. No source editing, direct provider launch, credential changes, production deployment, merge or independent acceptance. A later reviewed grant may allow already-admitted continuation; this draft does not.

### Profile B: Independent Outcome Reviewer

Mission: evaluate an exact artifact against the original user journey and failure states, not against the builder's summary or test count.

Inputs: frozen acceptance contract, exact head/artifact, actual test and real-path evidence, known limitations and corrections. Use a separate review context from the author; separation alone is not proof of judgment quality.

Method: inspect important claims directly, trace producer to real consumer, challenge missing/null/stale/correction behavior, verify scope, and distinguish schema/source/CI from user-visible usefulness. Flag unsupported assumptions and insufficient proof.

Output: evidence-bound acceptability findings or a bounded repair request. Reviewer recommendations do not merge, deploy, grant authority, or self-accept the parent program. Source-write and provider-dispatch tools remain absent.

### Builder and activation procedure

The owner creates draft definitions, previews with bounded non-sensitive input, selects the actually available model/reasoning setting, connects only approved apps, and publishes an explicitly reviewed version. Prefer a restricted agent-owned service connection for unattended operation rather than borrowing personal credentials. Retain confirmation for risky actions; narrow routine actions require both provider-side controls and backend enforcement.

Workspace Agent access tokens require the admin permission and Workspace Agents scope; provision them directly into existing secret custody. Do not put token values in this document, a prompt, a PR, or Slack. Token scope is not a substitute for app-side authorization.
