# Session-owned reviews across ChatGPT Web, Codex, Claude and Fabric

**Status:** proposed cross-repository Chairman review-rule amendment (2026-11-03). A branch is not protected policy, installed native instructions, an edited ChatGPT Project setting, a reviewer START, or a GitHub ruleset change. Apply only after normal source adoption and actual consumer enrollment.

**Intent:** an assigned working session must be able to finish its review work without handing the source to a *different top-level ChatGPT conversation, account or outside human session*. A real subagent spawned and managed **inside the same parent session** can be a distinct *technical* reviewer. Ordinary work need not spawn any reviewer at all. This replaces the organizational habit of equating independence with a third-party session. It does not misstate GitHub's actual approval identity, weaken branch protection, or authorize self-merge.

## Decide the actual requirement before requesting a reviewer

1. Recover repository, PR, immutable head SHA, changed paths, current governing source, material risk, original outcome, active writers/reviews/holds and actual repository merge rules. The [risk-tiered policy](REVIEW_RISK_POLICY.md) determines any **additional** internal review requirement only after its accepted release. In-flight #2018 proposes zero independent assessments and zero additional non-author approvals for FAST and STANDARD. Until accepted, do not claim it is installed.
2. **FAST / ordinary STANDARD only AFTER the actual accepted source-and-host policy qualifies zero extra review:** the active session performs its own adversarial diff check, focused tests and required CI without a redundant external reviewer. **Before #2018 is protected and its qualifying consumer enrolled, preserve incumbent STANDARD's one independent technical assessment and real non-author formal approval; do not cite this proposed page as a bypass.** Record the head, checks and findings; this is `SELF_REVIEWED`, never proof of a distinct reviewer. A native subagent remains optional when the accepted tier permits.
3. **CRITICAL or an explicitly independent-review-sensitive assignment:** use distinct-context subagent(s) **within the current session** where actually available and permitted. The parent remains accountable, adjudicates findings and handles repair. A qualified native subagent review can count as an **independent technical perspective**, without a separate top-level Web/Claude/Codex chat. If accepted risk policy requires two distinct technical perspectives, record two genuinely separate reviewer child runs; an author's second pass is not a second independent actor.
4. **HOLD:** incomplete source, live conflicting reviewer, unreconciled effect, actual permission denial or mandatory native GitHub approval still holds that effect. Do not assert a review exemption or manufacture a reviewer. Continue other lawful implementation/tests/review analysis on nonconflicting work.

## Session-local review avenues (discover, do not assume)

| Assigned parent surface | Allowed review execution in that same session |
| --- | --- |
| **ChatGPT Web, ordinary session** | Perform a structured, attributable author/adversarial review directly in the session. For FAST/STANDARD this is sufficient under an accepted zero-external-review policy. Do not call it a distinct independent reviewer if no separate subagent actually ran. |
| **ChatGPT Web, Pro session with native subagent tools** | If native child/spawn controls are truly exposed and authorized **in this specific session**, spawn an isolated read-only reviewer child, consume its real terminal result here and decide repairs here. Pro mode or account labeling alone proves neither spawning support nor a child START. |
| **Codex native** | Use an actually available Codex native subagent/reviewer in a separate task/context, with exact source identity, bounded read-only remit, observed launch and return. Paid Fabric remains an optional distinct route when its own binding/admission is satisfied; native Codex review does **not** impersonate a Fabric result. |
| **Claude native** | Use an actually available Claude native review subagent, isolated task/context, read-only remit and observed result, returning to the same working session. Fabric is optional when separately admitted. |
| **Subagent Fabric** | The parent may request and consume a qualified reviewer worker under its **actual** original root, parent, grant, budget and collision controls. Do not invent Fabric identity or call QUEUED/CONTROLLER_CREATED a reviewer START. |
| **Other eligible native agent harnesses** | A true context-separated subagent can qualify when identity, source snapshot, read-only limits, launch, result and parent adjudication are verifiable. |

A **different reviewer task/context**, not a different human-facing session tab, is the independence unit for technical assurance. Subagent isolation must be real and observable; a second prompt in the builder's own context is SELF_REVIEWED. CRITICAL's two technical perspectives must show two distinct child executions with independently attributable methods/findings; use model/provider diversity when justified, and do not count two repeated prompts to the same agent as two perspectives. A child shares no automatic separate GitHub approval principal. Use least-scarce qualified capability; an external Dot/account is an option **only for genuinely new, permitted work with prior effects reconciled**. On `EFFECT_UNKNOWN`, ongoing review or explicit safety/permission refusal, preserve the **original** review carrier and HOLD; do not switch to Slack, provider, host or account. A new name is not a new effect.

## Receipt, adversarial protocol and limits

For a dedicated reviewer child, record `REVIEW_CHANNEL=session_native_subagent|fabric|external`, exact repository/PR/base/full head, changed paths and original acceptance; native parent and child identity when actually exposed; the real tool launch/START and returned result; distinct-context/read-only evidence; commands/tests actually executed; severity-ranked source-linked findings and negative cases; and parent disposition. If the child cannot be proved, record `INDEPENDENT_TECHNICAL_REVIEW_NOT_PROVEN` and continue permissible work. Do not put fake START, account, model or tool receipts in Markdown.

The child receives frozen code and adversarial questions, not a request to rubber-stamp its parent: inspect omitted paths, security/permission changes, concurrency, state/effect retry, test validity, backward compatibility, original product purpose and proof gaps. It must **not** push, edit the candidate, merge, deploy, change permissions or read production secrets while acting as reviewer. The parent repairs findings under original source custody, reruns affected tests and obtains fresh review only when actual changed source invalidates the previous coverage. No duplicate worker for an already-running/uncertain identical review.

**Formal GitHub approval is not technical review.** `APPROVED` requires an actual native submitted PR review by an eligible authenticated non-author at the right revision, if enforced by a current GitHub ruleset/CODEOWNERS or explicitly held release. A same-session child, author self-check, issue comment, model persona or second login does not create that GitHub event or another authenticated principal. Never self-approve, switch identity to impersonate independence, admin-bypass a hold, or merge outside the authorized protected path. If rulesets demand a distinct reviewer, identify that **specific GitHub enforcement dependency**, not a fictitious need to open another ChatGPT conversation. Source release, required CI, genuine acceptance and production proof remain separate.

## Finish-to-release ownership: a PR is an intermediate artifact

The **assigned session remains responsible for the original useful outcome**, not just opening a PR. This applies equally to Web, native Codex, Claude, Fabric parents, and handoff authors. Default path: retain the original authorized branch/PR -> finish the source and focused local qualification -> publish exact head -> read hosted CI and repair actual failures -> mark qualified Draft **Ready** where permitted -> obtain only the genuinely required review -> admit to the authorized existing protected merge controller/queue -> verify exact merged SHA -> verify actual installed/user-path behavior when that outcome owes it. **A draft, comment, reviewer request, CI observation, checkpoint or pending auto-merge is never "finished."** Do not report DONE or abandon the work because the first PR was created.

**No draft graveyard:** Draft means *specific unfinished qualification*, with a named failing test/incomplete capability or other real source hold and the next executable repair. CI merely **pending** is not a reason to remain Draft when the candidate is stable and reviewable. If source/tests are ready, progress through Ready and applicable protected release instead of writing another handoff. Do not open a second PR to escape a failed, behind, review-pending or blocked original. Reuse accepted immutable reviews when candidate-owned bytes/semantic dependencies did not change; refresh only required integration evidence. Do not manufacture rebases, noop commits, screenshots or documentation-only "progress" to refresh timestamps.

**Session-end decision:** first inspect the exact current PR/head/checks/reviews and required remaining consumer. If a safe in-scope action exists, **execute it in this turn**. After every successful repair/CI/review/save, reassess and do the next eligible release/consumer step; a phase boundary is not a stop. If a real external wait exists, set one owned existing CI/worker/merge observer with proven return where supported; meanwhile advance nonconflicting work. If all lanes are genuinely blocked, preserve the exact original PR/operation, held effect, missing gate, accountable reachable actor and next lawful action in the existing Agent OS handoff; do not claim merge/completion, create another queue or rely on a discontinued chat. A published draft is a recoverable work-in-progress **failure to finish**, not a success metric.

**No self-merge:** the source author cannot approve or merge their own protected change; an authorized independent release actor and real native checks remain required.

**Backlog reduction:** work **existing** live PRs before authoring new duplicates. Prioritize (a) green and release-eligible, (b) fixable failing CI, (c) needed review/Ready, (d) genuinely conflicted/obsolete, while preserving active writers, explicit holds, required review, finite host budgets and unrelated scope. Do not indiscriminately mark Ready/merge/relabel 900 PRs, auto-dismiss critical findings, or weaken true CI/security checks to improve a count. Track actual merged, closed-as-superseded, and production-accepted outcomes independently. Optimize completed user journeys per release, not PR creation.

Keep #2018 (STANDARD relief), #1968 (Web reviewer portability), #2003/#1977 (incumbent GitHub/Executive ingress) and Terminal #1251 (CI fast lane) on their original carriers. Coordinate overlapping changes by the source owner's normal PR review/integration, never a duplicate rewrite of in-flight effects.

Link this document from the same-pinned Skillpack INDEX, account/project bootstrap and native `AGENTS.md` / `CLAUDE.md` entrypoints in the three product repositories. For shared ChatGPT Web Projects, an authorized Project editor must update each **distinct Project's** saved instructions, preserve existing project-specific rules and prove fresh-chat loads. Account memory, project memory and historical chat claims are advisory; repository source cannot silently edit ChatGPT's server-side Memory or Project settings. For organization memory, persist an approved decision/handoff through the incumbent Macro Agent OS writer, not an extra memory database.

**Smoke test:** on a fresh Web session without native children, a STANDARD change is self-checked and no external-chat reviewer is requested; on a fresh Web Pro session with verified native spawn, a CRITICAL source subagent runs and returns locally; Codex and Claude each prove one isolated native review; Fabric preserves root/parent and START/return if chosen; actual GitHub non-author rule still rejects self-approval; pre-existing review, denied effect, changed head and HOLD remain fenced. Every test distinguishes source wording, installed instructions, actually available tools and observed behavior.
