## 3. Worker packets and routing economics

Before actual dispatch, recover the current lawful worker avenue/admission procedure at the then-
current protected pin. This design does not itself assign a worker. Select the least-scarce capable
eligible lane using current Router/Capacity evidence. No provider, account or host is selected by
this document, and no metered Codex/work fallback is assumed.

Every admitted packet states: objective; why it unlocks the consumer capability; exact inputs and
source revision; allowed paths; contracts it may not change; output/evidence requirements; tests;
independent review requirement; effect/permission gates; budget/repair envelope; stop/escalation
conditions; and canonical result/return path. A bounded worker owns investigate/build/test/repair
inside that envelope without needing a principal instruction for every edit.

Use principal time for native trust-boundary judgment, versioned root/ruling contracts and review
of decisive evidence. Delegate separable fixtures, compatible package changes or tests only when
admission and custody are actually available. Do not fan out seven workers by packet count. Reserve
review/repair descendants as well as active workers before claiming capacity.

The first H4 proof uses one reviewed implementation child and one truly read-only evidence child.
If both require independent review under actual policy, the proposed 11-slot graph is no longer
valid. Reduce the mission to an admissible truthful graph or obtain an explicit owner policy change;
do not override the budget or misclassify mandatory review.

## 4. Review barriers

**Design review:** verify each factual baseline against pinned code, accept/reject the selected
architecture and expose unresolved native/owner facts. The current package is a review candidate,
not an independent approval of its own design.

**Source review:** confirm closed schema migration, exact principal/role semantics, old-client
compatibility, authority ceilings, duplicate/unknown-effect handling and no duplicate control plane.
Changes to root admission, native enforcement or neutral dialogue need independent adversarial review.

**Integration review:** use actual owner interfaces and dependency-complete tests. Synthetic
generation fixtures prove only their exercised behavior. Missing dependencies are not a waived
integration gate and must not be hidden by weakening tests.

**Native acceptance:** prove package installation/selection, authentication, exact current profile,
observed tool/schema/resource generation and actual allowed/refused behavior. Claims stay bounded
to the qualified native/version/host surface.

## 5. Candidate and CI discipline

Reuse the operation's canonical workspace and one modifying carrier. Each semantic source change
is tested locally, reviewed in staged diff, committed and pushed to the existing candidate. A
changed head invalidates only evidence affected by the actual change, but hosted exact-head CI
must apply to the candidate being merged. No empty pushes, unchanged polling or admin bypass.

Publish incomplete work only as DRAFT/HOLD. Identify repository, PR, head, run IDs and owner of
observation. Pending CI blocks merge/release, not independent useful work. A terminal failure
requires bounded exact-log diagnosis and an in-scope repair, not automatic rerun. A status query
is not independent review, source release permission or proof of production behavior.

## 6. Installation, selection and rollback

The existing installation owner receives an exact accepted artifact and rollback reference. Verify
publication, installed bytes, selected plugin/profile, current settings and native behavior as
separate facts. Do not use the current host's unrelated successful read as proof that the new
COO route or rich profile is installed. Human-only enrollment/admin ceremonies remain gates and
should be requested only when their exact prepared artifact and preflight are ready.

Enable only the approved generation and mission. No all-account rollout follows automatically from
one canary. Preserve existing working lanes. If the new lane fails, fence its new effects through
the existing owner, reconcile active operations/resources and return selection to the exact prior
accepted generation where authorized. Never delete unresolved runtime state, reset source leases,
clear locks blindly or remove old evidence to make rollback appear complete.

## 7. Final acceptance and continuity

Review all seven original completion clauses individually. Do not substitute one successful native
read for the whole product. Required proof includes multi-owner context, supported-generation drift,
role-correct action/status, two governed child lanes with review/repair, CI continuation, reciprocal
dialogue and source-bound browser evidence with cleanup.

Persist material decisions/discoveries and the final handoff in existing Macro Agent OS through its
normal procedure; implementation/CI artifacts stay in GitHub and runtime facts stay in Executive.
Linear and Slack are projections/transport. No new authoritative completion registry is created.

At any real interruption, retain exact mission, source/candidate, current owner, pending effects,
active child/return obligations, verified evidence and next action. A new chat does not transfer
custody. A checkpoint is a save, not permission to stop while useful authorized work remains.
The current work product is a detailed design candidate; native program completion remains false.
