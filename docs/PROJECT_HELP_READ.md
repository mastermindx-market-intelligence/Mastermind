# Current project help through the existing owners

`executive_project_help({"work_ref": "WS:..."})` is an explicitly enrolled,
read-only COO operation. It joins the current project's adopted source plan
and original Executive root to the existing Session Bridge, Company, and
Capacity read owners. It does not create an agent, a task, a team, a grant,
or a placement decision.

The implementation keeps each fact with its owner:

| Fact | Existing source and boundary | Meaning in the help result |
| --- | --- | --- |
| Original project and root | Current installed COO mission, Workspace Mission v3, bounded Runtime, canonical project DATA | One explicitly enrolled original root, re-proved for this operation |
| Adopted plan | Workspace Plan v2, typed current adoption, immutable Git source, original plan parser | Exact repository, commit, path, content digest, and parsed contract digest |
| Company relationships | Independently authenticated Workspace `PaperclipWorkspace.read`, explicit project bindings, `company_context` | Visible company facts and reporting relationships; visibility is not project membership |
| Current session targets | Original installed Session Bridge target source and principal permissions | Existing addressable sessions under that original root; addressability is not permission to launch work |
| Capacity | Existing Workspace Capacity Fabric permission boundary and `ExistingCapacityFabricSource` | Bounded observed estate capacity and source/runtime evidence; task placement remains `NOT_EVALUATED` |

There is no second roster, task store, root registry, scheduler, OAuth owner,
or polling process. The returned sections can independently be unavailable.
An available empty target inventory means that the installed reader observed
no currently visible targets; it does not mean that every harness is absent.

## Explicit enrollment and compatible defaults

The catalogue is `coo.project_help.v1`. Its fixed tool set has schema digest
`0b7d9e4b7c336d0330665f40ebd8f2156997c3e42a0245c641dda625893a3e6e`.
The installed mission uses authority version 4: the existing version 2
mission fields plus the closed `project_help` scope. This is separate from
the version 3 memory-evaluation delegation. Existing mission versions and
catalogues retain their formats, digests, defaults, and grants.

| Source profile | Surface | Intended consumer |
| --- | --- | --- |
| `principal.hermes-native.executive-coo.project-help.v1` | `hermes-native-principal` | Explicit native Hermes consumer publication v6 |
| `principal.t3-api.executive-coo.project-help.v1` | `t3-api-principal` | Ordinary authenticated T3 API-principal MCP read |

Both profiles ship disabled. The grant is
`mastermind-executive-coo-project-help-v1`. The mission must explicitly grant
`read_project_help`; the native current-context operation also requires its
existing `read_current_agentos_context` action. These names do not enroll a
session or activate a service. The actual installed policy, mission,
principal binding, source custody, and authenticated connection must agree.

The public arguments contain only `work_ref`. They cannot supply or replace
the original root. The installed scope records an exact root and source-plan
tuple as selectors. The host proves those selectors against the current
owners at acquisition and again before delivery. A missing, ambiguous,
foreign, expired, or changed root/plan is unavailable, with no latest-root
heuristic or fallback to the AgentOS memory binding's `owner_root=None`.

The App requires both the original Executive principal and the independently
verified Workspace principal. Workspace credentials remain on the existing
paired-resource path and are never included in the result. No T3 native
origin is asserted by an API-principal read.

## Current facts without inventing execution readiness

The generic Mission and mandate semantics are unchanged. A current-DATA
project can have a truthful Mission v3 `PARTIAL` result because the existing
discovery producer has not supplied dispatch evidence. Its transport remains
`UNKNOWN`, historical, and non-actionable.

For this read only, the existing Workspace discovery acquisition can provide
a private qualification companion. It requires the actual current canonical
DATA card, the coherent `SAME` v2 owner receipt, one enrolled original root,
retained root metadata and creation-publication provenance, no degraded
missingness, and the producer's exact unobserved-dispatch case. It does not
infer freshness from the generic `PARTIAL` label or a diagnostic string.

The help result distinguishes `CURRENT_MISSION` from
`CURRENT_DATA_CARD_WITH_UNOBSERVED_DISPATCH`. It retains the original Mission
read state, transport state, diagnostics, and root-origin digest. The latter
qualification cannot open a generic mandate, admission, or execution gate.
`execution_authority` and `native_origin_attested` are always false.

Fresh acquisitions naturally have different observation timestamps and
connection identities. The currentness bracket compares the closed stable
owner facts while retaining the full original observation digests for
evidence. It does not freeze clocks, erase receipts, or require unrelated
global sources to become available.

The App obtains original help, reads Company and Capacity through the actual
Workspace owner, then obtains original help again. It compares the original
source/root/mission/target facts and rechecks the same grants and callback
owners before delivering the combined result. A late authority change
withholds the result. Company observations use the service's captured clock;
Capacity retains its original expiry and source-currentness checks.

Company `reportsTo` relationships are business organization facts. Explicit
`project_bindings` join a visible native project ID to a work reference;
display names never create a join. If the configured project is outside the
visible window, the bounded company roster can remain visible while the
project mapping and project work are unavailable. This is not inferred
project membership or execution lineage.

Capacity is estate-level observation. An existing account allowance,
protocol capability, or composed adapter cannot establish task-specific
placement eligibility. In particular, T3's recovery/observation composition
must not be promoted to new governed execution availability; the native
scope and descendant-quiescence fence remains in force.

## Reached consumers

### Hermes native context and memory

Native consumer publication v6 selects the original mission/source-plan
scope, the independently authenticated Workspace resource, and the exact
`mastermind-long-horizon` source plugin package digest. The package includes
the shared pure plan parser. The original held-release importer and package
registration reject missing or changed dependency bytes.

The actual `NativeAgentOsMemoryFactory` captures the original MCP
server/session/loop and native claim scope. Its existing prepare-turn barrier
acquires current help off the native event loop after base AgentOS context
becomes ready. The original MemoryManager prefetch renders that retained
claim; it does not create another memory store or add network work to the
existing eight-second prefetch boundary.

`mmx_project_context`, the existing pre-LLM hook, and the original prompt
construction consume the same qualified source-plan help. Prompt delivery
rechecks the original owner and source before and after construction.
Source edits, plugin lease removal, grant revocation, or packaged parser
changes cannot relabel the old help as current. Bounded context overflow is
reported as unavailable. Legacy publications preserve their existing
behavior.

### T3 project handoff and ordinary MCP

The reached ProjectTeam handoff/launch-request path can carry optional
parser-owned source-plan guidance. The exact plan source must match the
MissionBrief source reference. The guidance contains the advertised tool
name, only its `work_ref` argument, and the exact source comparison tuple.
Its state is `NOT_READ`; it does not claim to have called the API or launched
anything. Omitting the optional binding preserves the previous handoff
bytes.

An actually enrolled ordinary T3 API-principal session can call the new
tool through its existing MCP connection and compare the returned source
tuple with that guidance. The Python handoff compiler has no invented
outbound Executive client, and the app-item-bound native MCP UI is not
misrepresented as a pre-launch project reader.

### Installed App and private Control ingress

`build_installed_coo_settings` captures one original `CooFactsClient` for
authority, mission, context, and help. Its underlying
`CeoIngressWorkspaceClient` uses the canonical existing private socket.
The new help and context schemas receive strict input/result validation,
duplicate-aware bounded decoding, and finite cleanup under the existing
read budget. The Control service qualifies its actual peer, Runtime
namespace, COO host, and Session Bridge provider before reaching the same
read owner. No read arms the service or dispatches a provider.

## Qualification and remaining deployment boundaries

The source qualification includes actual current DATA and local Git adoption,
bounded Runtime/Mission/Plan owners, signed dual-resource JWTs, MCP SDK/App
transport, explicit T3 API profile selection, Company/Capacity source reads,
and native context/prompt delivery through the incumbent pinned native
lifecycle fixtures. Those fixtures retain explicit inert model,
credential, PluginManager, source-seal, and selected private-transport
boundaries. They do not prove installed activation, a live model turn, or
production socket custody.

The real Unix-Control replay lives in
`tests/test_coo_project_help_ingress.py`. Its two service cases use the actual
SDK, App, signed resource pair, original Unix client, Control service,
Runtime namespace and current-DATA/plan fixture. They cover successful
context/help delivery and revocation after the first original read. They
must execute on a host with the existing AF_UNIX capability; collection in
a restricted executor does not qualify the service.

The isolated installed-factory case in that file proves its real constructor,
one captured client, original catalogue, and disarm handling. It explicitly
controls only the physical root-seal/process-UID fixture edge and opens no
socket.

For the real service replay on the complete qualified source tree:

```sh
python -m pytest -q tests/test_coo_project_help_ingress.py
```

The repository still enforces one current catalogue per principal/work
enrollment. This v6 catalogue intentionally does not acquire the separate
requester-return ACK descriptors or delegation actions. Supporting help and
requester delegation in one real T3 or Paperclip project session requires
the separately versioned joint API catalogue and its own source/profile
qualification. That subsequent integration must preserve this read's
original-root/source proof and the selected-child claim/ACK owners; it
cannot silently union legacy grants.

Live enrollment, source publication/sealing, paired OAuth preparation,
service qualification, and any later runtime activation remain with their
existing owners. Source support and fixture proof do not attest that those
steps have happened on the estate.
