# T3 project-help paired-resource credential census

## Outcome and scope

The source-bound T3 handoff and the ordinary authenticated API contract are independently useful. A production T3 project-help read still needs its native MCP client to own both the Executive and Workspace resource authorizations on the same original request. The inspected T3 source does not own that pairing. Supplying generic headers or selecting the new disabled T3 API-principal source profile does not establish token acquisition, refresh or currentness.

The concrete inspected route is T3's Codex provider at `chriswong6031-creator/t3code@924ad5d194287441f825b8f2f6054e9539808534`, with official Codex 0.167 source `openai/codex@086ccc833bc9cf01024ad2dd6af7dbd421b6bf9a`. These are source facts. No live provider process, installed credential configuration, profile, token, service or authorization was changed or opened. The running native binary/connection was not requalified here. The T3 fork remains pull-only for the inspected identities.

## Why the real header helper is insufficient

Official `codex-rs/rmcp-client/src/http_headers.rs` (blob `59667de36866901a170b75218a42a669252407c3`) is a real dynamic-header transport extension. It calls a short-lived local process, bounds its output and duration, applies headers only to the configured origin, stops redirects, preserves explicit OAuth Authorization, and can refresh changed helper values once following an HTTP 401/403. This is materially stronger than static headers.

It still does not acquire a second OAuth grant or bind one to the original client, principal, resource, scope and store. It accepts a process-produced header object. The examined helper does not know Executive/Workspace resource semantics. It cannot be counted as paired OAuth solely because it could output the companion header. Further, the current v6 MCP factory authenticates the primary bearer before tool dispatch and turns a missing/invalid companion into a tool error; it does not promise an outer HTTP 401/403 that triggers this helper refresh. The helper must not be configured to extract/copy another profile's token as a workaround.

Likewise, `utils.rs::build_default_headers` (blob `dac42ca6118f9b1f620030645447407532582383`) reads static/env values while building the transport. That provides no acquisition or refresh contract.

The v6 source owners are `integrations/executive_mcp/server.py::_build_coo_mcp_app`, `integrations/mastermind_executive_app/coo.py::current_context_auth` and `coo_project_help.py::forward_project_help`. They require the original primary bearer plus exactly one independently authenticated `x-mastermind-workspace-authorization`, compare principal identity, and recheck both owners before returning. Preserve those independent authorizers.

## Smallest next implementation, if this provider path is selected

1. Add an opt-in, host-selected companion descriptor through Codex's existing MCP configuration owner. It must identify the exact independently enrolled Workspace credential/resource and the fixed allowed header/Executive destination. Ordinary model arguments, plugin metadata and arbitrary server response fields must not select credential custody.
2. Reuse the original OAuth login, credential store, refresh lock/transaction and issuer/client validation. Retain separate primary and companion entries; do not overwrite the ordinary server/URL slot or export tokens to a helper, argv, environment, T3 transcript or model.
3. Compose the companion into the existing `RmcpClient`/HTTP transport lifecycle. Refresh/read its current authorized token before an original request; fail closed with zero request sends when unavailable. Restrict transmission to the exact enrolled Executive endpoint, exclude metadata/token endpoints and redirects, and retain cancellation/deadline ownership. No new queue, watcher, token service or alternate connection is needed.
4. Preserve original-operation semantics. A lost response must not create a second tool call. Do not treat a tool-level authorization refusal as permission for generic replay or a primary-bearer fallback. Legacy configurations without the opt-in must retain their existing wire behavior.
5. Qualify through the actual native client with disposable OAuth/MCP endpoints, no model/session launch: distinct audiences/scopes, primary-only and companion-only refusal, wrong issuer/client/resource, expiry and independent refresh, revocation, credential-slot separation, concurrent refresh, cancellation, redaction, redirects, changed source configuration and uncertain tool response. Then separately qualify the selected installed binary and explicit resource enrollment before claiming production T3 reachability.

The Rust owner lives in the Codex source tree, not the T3 fork. Writable reviewable source artifacts can be retained under the Mastermind integration carrier in isolated scratch; neither write access to an appropriate Codex fork nor native installation/activation is established by this census. A T3-only wrapper would not close the credential-owner gap. The single-Executive-resource API-principal selected-child/return/acknowledgment avenue can proceed independently under its actual separately enabled source contract, without native-origin attribution.

## Verification boundary

This report is a bounded source census, not a paired OAuth implementation or installation proof. The composed T3 API tests deliberately provide two independently verified disposable resource credentials to the existing SDK transport. They prove API/source compatibility and authorizer behavior, not native acquisition/refresh. The frozen typed dynamic-tool patch and six-file source-plan handoff patch remain unchanged.
