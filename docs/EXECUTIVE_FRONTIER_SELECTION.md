# Requested CEO selection custody

## Supported source behavior

The authenticated OS launch path can preserve one optional, exact registered
`frontier_model_alias` as logical CEO intent. This does not start a selected
model, enroll a provider, claim a worker, or change the project's authority.

The source chain is:

1. The operator-supplied launch manifest may include `frontierModels`, a bounded
   list of exact aliases, display labels and optional unavailability reasons.
   The form records a **Requested CEO**. Missing, removed, unavailable and
   unenrolled selections refuse without a default substitution. The qualified
   asset preparer validates the same closed choice shape before building and
   retains the exact canonical manifest in its release-bound build receipt.
2. The selected alias participates in the existing canonical operation key.
   Omission preserves historical keys byte for byte. The retained command
   payload preserves the same alias during recovery.
3. The OS app and commission authentication entry explicitly use the additive
   authenticated-app validator. Legacy MCP and Slack business fields remain
   frozen. Authentication still binds the original argument bytes, including
   the alias; normalized defaults never rekey a commission.
4. Studio commission preparation requires an exact sealed authorization
   template containing that alias. It retains the alias in operation identity,
   immutable commission bytes and argument-digest verification. No alias is
   removed before authorization comparison.
5. Automated ingress accepts the alias only when the host has selected strict
   v2 admission. It enters the canonical intent fingerprint. A non-strict path
   refuses rather than accepting and dropping the choice.
6. Fresh strict-v2 admission resolves the alias through the host-loaded
   ModelRouter. The closed `mastermind.frontier_selection.v1` record contains
   the complete logical model identity, capabilities, routing-policy version,
   execution-profile identity and digest, and capability-policy identity and
   digest. Model identity is separately retained even when profiles are shared.
   The resolver is reobserved before the existing fresh-admission guard.
7. Runtime validates the requested/resolved alias and record at the canonical
   strict-v2 root writer. It stores the requested alias, record and canonical
   SHA-256 digest in immutable original-root `JOB_CREATED` provenance.
   Orchestration provenance, SQL schema, root identity and existing receipt
   versions are unchanged.
8. Inbox and bounded result readers validate present selection evidence.
   Durable command replay happens before current resolver, grounding or
   execution-binding calls. Explicit removal or replacement conflicts.
   Concurrent different resolutions cannot produce two roots or silently
   reconcile to another model.

The existing execution profile remains the capability/scope profile. It is
not a model selector. Worker placement, budgets, route suitability and final
reviewer independence remain owned by their existing contracts.

## Compatibility and evidence limits

Legacy omission remains omission. All three new provenance fields must be
present together; malformed records, inconsistent aliases and bad digests
refuse. A submit replay also checks its requested alias against the retained
record, so stripping or relabeling selection evidence cannot silently satisfy
that replay.

A status-only reader cannot distinguish deletion of *all* optional selection
fields from a historically unselected root using these bytes alone. Production
immutability remains the creation-event owner's responsibility. This extension
does not claim to reconstruct deleted evidence or add a second integrity store.

The accepted receipt still reports `dispatched: false`. The Requested CEO
control records intent; it is not evidence that the chosen model performed
cognition. A real host-qualified cognition/session adapter must associate that
model with this same original root before execution can be claimed.

## Enrollment and rollout

This change supplies no deployed model-choice catalog or authorization grant.
The currently protected registry at the implementation base has one eligible
frontier alias, `frontier.orchestrator`. Do not invent executable aliases for
Astra, Fable, Opus, Sol, Grok or GLM, infer account availability from a catalog,
or treat disabled worker providers as activated by logical selection.

The genuine configuration owner must supply matching public choices and
sealed commission templates. Every enabled execution choice additionally
needs the actual cognition/session owner and qualification. Existing
`FRONTIER_LEAD.job_constraints()` refusal remains effective.

Installation uses the existing privileged release owner and qualified asset
preparer, with an exact reviewed protected source. The readiness audit also
found that the installed Macro projection was stale; a Mastermind-only update
does not replace that selected snapshot. The existing cutover must include a
fresh sealed Macro root and its reviewed `ceo_ingress_app_macro_root` binding.
See the incumbent native-probe requalification and Executive app runbooks.
No source test substitutes for their installed, database, credential,
authenticated-launch and original-parent-return evidence.
