# Risk-tiered PR review — lower friction without removing real safeguards

**Status:** Proposed source policy for Chairman directive 2026-11-02. Not an installed GitHub rule or an approval/merge bypass. It becomes operative only after protected acceptance, alignment with source-law/instruction consumers and host enrollment. This document has no separate source of runtime authority.

**Owner:** Existing GitHub release workflow + `control_plane/github_release_assessment.py` (approval adjudication), Executive/Fabric (admission and independent results), and native branch rules/merge queue (enforcement). The pure `control_plane/github_review_risk_policy.py` only supplies a reproducible advisory risk tier. No new webhook, queue, reviewer registry, auth store, code owner, worker budget, retry process or release engine.

## Default: stop requiring a second person or agent for small ordinary work

Independent review is **not** a default prerequisite for every minor edit, every commit, every child build, every test update or every PR head. Qualify the *coherent change* once, at its source-verified exact revision, and apply the **smallest justified external review requirement**. The author still self-checks the diff, runs focused tests and required hosted CI, preserves honest evidence and must not approve or merge their own protected change.

| Tier | Source signals | Independent technical assessments | New non-author formal approvals required by **this policy** | Handling |
| --- | --- | ---: | ---: | --- |
| **FAST** | Verified current diff limited to positively identified passive user guides, documentation evidence and raster/font assets; no executable components, test/configuration changes or sensitive paths | **0** | **0** | Self-check + focused tests + required CI. Let existing authorized sweeper/native queue progress; no mandatory Fabric request or Dot ACK |
| **STANDARD** | Ordinary executable test/source, application behavior, non-sensitive integration or code beyond FAST proof | **0** | **0** | Run focused tests and required CI. Independent advisory is optional, not a blocking ritual; the owner may request one manually for uncertainty |
| **CRITICAL** | Auth, security, permissions, secrets, authority/source-law, review/merge automation, privileged CI, release/deployment, trade or financial execution, irreversible state changes | **2** | **0** | Two real distinct-context technical reviewers, which may be native read-only subagents managed inside the working session, plus targeted security/behavior tests. Native GitHub approvals and explicit security holds remain separately binding |
| **HOLD** | Complete exact-head source not proven, changed-path coverage missing, inconsistent metadata, identity/effect uncertainty | **Not inferred** | **Not inferred** | Reconcile the source or effect through its incumbent owner. No auto-exemption, duplicate reviews, merge or safety fallback |

A parent model's second pass is **SELF_REVIEWED**, not one of CRITICAL's two independent perspectives. Require attributable distinct child identity, exact immutable head, separate read-only analysis, actual START/return and finding adjudication; do not infer a native Web Pro/Codex/Claude subagent from a plan label. A separately authenticated GitHub `APPROVED` is required **only** where the current native rules/CODEOWNERS or explicit accepted hold demand it; neither a child review nor a GitHub comment is formal approval. Source classification by itself cannot grant review acceptance or merge authority.

The counts above are **additional policy demands**, not permission to reduce a higher native GitHub ruleset, CODEOWNERS, release hold or separately accepted security review. A technical Fabric `PASS` or GitHub `COMMENT` does not become `APPROVED`. If a native rule requires an approval even on FAST, that native rule governs until its legitimate owner amends it. Never silently admin-bypass. The merge actor must remain authorized and independent from the source author under applicable protected law.

## Exact-head source verification and pre-admission disposition

The additional pure `control_plane/github_review_risk_source.py` requires an **existing authenticated installation-scoped GitHub reader** to supply one current PR identity, every bounded changed-file page, and a second identical current PR read. `integrations/github_review_risk_reader.py` now supplies a narrow concrete adapter backed by the incumbent `GitHubReviewAPI`'s existing installation-token-scoped read transport; no second client, key, webhook or GitHub endpoint owner is introduced. Its read-only hermetic suite verifies whole-source-to-dispatch outcomes and refused malformed identities. The incumbent #1977 host must still install and call this read seam after signed webhook authority and before Executive admission. It refuses incomplete pagination, inconsistent totals, changed heads/base, forks, drafts, missing code patches, and missing original paths for renames. Deleted files escalate the risk tier; renamed files are assessed at both their old and new paths. These inputs are **not** permission or a GitHub credential source by themselves.

The pure `control_plane/github_review_risk_dispatch.py` is the integration seam: verified automatic origin + FAST => `SKIP_NO_REVIEW_NEEDED` **before Executive creates a review Job**; verified automatic STANDARD => SKIP_NO_REVIEW_NEEDED (CI/self-check continues); CRITICAL => normal existing review ingress; incomplete source => HOLD. Every assessment and positive dispatch advice is now tied to **repository, PR number, and exact 40-character head SHA**, with a mandatory matching signed-event identity and a **fresh current GitHub App PR read after the full census**. Head movement after classification, cross-PR reuse, missing current source, draft/fork drift or mismatched head => HOLD, never skip. The `advise_current_pr_review` helper performs source census, final current read and dispatch as one bounded read-only path; the signed host/authority must supply the arguments, never the PR author. An authenticated explicit manual review intent retains the original permission-gated path even if the source would ordinarily be FAST. This preflight is not connected to #1977's live host yet. Its binding must reuse the existing `GitHubReviewAPI` installation, source reader, signed receiver, Runtime ledger, and original exact command identity, not add a second review scheduler.

## Risk classification evidence and adversarial rules

The owner supplies complete changed filenames, additions/deletions and a verified exact current GitHub PR head. Diff coverage must include renames/deletions, not only visible excerpts. Agent PR descriptions, labels, comments, Markdown risk declarations, branch names and model claims **cannot lower** the tier. Allowed trusted source-owner hints can only escalate. Invalid paths, case aliases, stale heads, partial pagination or unverified files produce HOLD, not FAST. Small one-line edits to auth, release controls or protected rules remain CRITICAL.

Deterministic path patterns are conservative, not exhaustive semantic proof. A file ending in `.md` does not itself qualify as passive evidence; canonical operator/source-law documents in `docs/sol_*`, `docs/session_*`, `docs/executive_*`, `docs/agent_*`, `docs/github_*`, `docs/review_*`, installable `skills/` and `plugins/`, and test/CI control paths are CRITICAL. Unknown operational documentation remains STANDARD. Read-only user guides and verified visual evidence retain FAST eligibility. Existing CI security scans, test suites and source-code ownership constraints remain. Before a FAST release, the responsible builder must confirm that the diff really is reversible/routine and does not covertly alter a trust boundary, product decision, money/trading operation, external interface, migration or production data. Any actual contradictory evidence escalates the tier; lack of certainty means HOLD. The pure classifier cannot inspect code semantics and **must not be connected directly to a privileged auto-merge endpoint as an authorization oracle**.

**Evidence-aware scope budget:** Authenticated per-file stats distinguish executable changes from accompanying screenshots, documentation and verification logs. Executable tests, pytest/CI enforcement and installable agent skills are **not** considered inert supporting evidence: CI-policy tests, conftest, policy/configuration and skill instructions are protected even for one-line edits. Regular tests default to STANDARD until a separately trusted semantic qualification exists. A future semantically qualified UI/icon edit need not be escalated merely because its PR carries many large proof artifacts; the source collector requires complete pagination and matching additions/deletions, and its file metrics must cover every current and renamed prior path. Missing metrics revert to conservative aggregate counting. File deletions and high-risk security/source-law paths still escalate even when surrounded by evidence. This is not an author-controlled `skip-review` label or a semantic safety guarantee.

A review is requested **only** when its tier or an explicit eligible human request warrants it. Manual `independent-review` requests still use existing signed GitHub ingress and its source/identity controls. For a *new* review, preserve original builder/reviewer separation and one PR-head/scope operation: never spawn a new Fabric, Slack Dot or Cursor reviewer just because the first is queued, unconsumed, declined, uncertain or already reviewed. A changed head invalidates only review evidence that no longer covers the changed source; whether a formal approval remains valid follows GitHub's actual branch rules. Do not fabricate exact-head reviewer coverage.

## How this avoids administrative stalls

1. **Batch logically related tiny changes into a coherent PR**, not one PR per line or test fixture. Do not batch unrelated owners/sensitive paths just to avoid review.
2. **One review per substantive candidate**, not a mandatory separate worker review on every implementation subtask, tiny repair, test pass, comment, reviewer request or generated file. No duplicate worker work for the same head/scope.
3. **Do not require an Astra/Opus/Pro review for ordinary code.** FAST needs none. STANDARD **does not require** an independent reviewer or a Dot ACK. If a high-judgment concern arises the authorized owner can explicitly request a bounded independent advisory without making every small PR wait. CRITICAL uses qualified diversified judgment where its assurance needs it; model variety without true independence is not evidence.
4. **Parallelize CI and review** for STANDARD/CRITICAL when candidate is stable, and keep subsequent unrelated source work moving. CI green is a merge gate, not a human attention lock. No busywork observers.
5. **Use post-merge sampling**, provisionally 5–10% of source-verified FAST PRs, to discover classifier misses without stalling every merge. Sampled findings flow to the existing issue/defect owner, not a new reviewer state machine. Measure escapes and expand risk rules only on actual evidence.
6. **Preserve protected deployment gates.** Significant production changes still require service-path acceptance; routine source-only changes do not trigger irrelevant deployment review or reboot.
