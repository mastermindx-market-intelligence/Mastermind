## 1. Decision

**Use Paperclip as a substantial, selective donor for company work management and supervision. Retain Hermes for persistent teammates and conversations, T3 Code for engineering sessions and environments, DeepSeek Harness as an existing execution/plugin runtime, and Executive OS plus Capacity Fabric as the company execution authority.**

Paperclip is strongest where a company needs to turn intentions into assigned work, see why work is blocked, inspect outputs and manage recurrence. Those are valuable product requirements for Mastermind OS. Its own company server, issue database, runner, scheduler, budget gate and identity system would overlap incumbent owners. Importing that complete stack would make a superficially complete dashboard conceal conflicting execution decisions.

The prior plan already retained selective Paperclip reuse. Revision 6 changes this from a general future idea into a bounded product and reliability change order. It is an extension of the current build, not a restart or a reason to discard the current Team/Code designs.

| Option | Assessment | Decision |
|---|---|---|
| Ignore Paperclip | Misses coherent work detail, attention, routine policy and output discovery patterns; risks independently rediscovering their failure cases. | Reject. |
| Replace Hermes/T3/Executive with Paperclip | Introduces a different company lifecycle and sacrifices useful existing bot, chat, coding and capacity integration. The current evidence does not justify that migration. | Reject for this programme. |
| Run a complete Paperclip company beside Mastermind | Creates two assignment/schedule/approval/recovery authorities unless one becomes strictly subordinate. Mapping their labels is insufficient. | Do not introduce. |
| Adopt bounded code and proven workflow semantics inside existing owners | Gains the useful product without a second executive. Requires explicit identity joins, persistence and adapters. | Adopt. |

### What Paperclip actually contributes

Paperclip already ships both `hermes_local` and `hermes_gateway`. The latter starts work on an existing Hermes API server rather than replacing that server. It also has a reverse Hermes-to-Paperclip task bridge. Its own architecture therefore supports the interpretation that an organizational layer and an agent runtime are complementary. Do not inherit the adapter README's comparative marketing table as a verified comparison of other coding tools. [P1]

Paperclip's always-on behavior is principally durable work plus event-driven wakeups and recurrence. Official guidance says default agents do not require timer heartbeats; assignments, comments and routines can wake them. This is different from buying continuous model inference or keeping every model turn permanently active. [P2]

Paperclip also has an experimental native Runner with its own lifecycle and durable session recovery. A complete installation is therefore more than a UI donor. That runner would overlap responsibilities already being integrated in Executive, T3, DSH and the fabrics. [P7]

Hermes already provides profile-backed bots, canonical persistent Bot Chats, recurring routines, group conversations and communication across connected machines. Paperclip's experimental Agent Chat is a narrower current experience: one conversation per user-agent, task-backed, and documented completion updates that do not cover every blocked/failed/cancelled state. Paperclip is not demonstrated to be a generally better replacement for the current Hermes teammate experience. [H1, P6]

### What already exists in Mastermind

The protected app already has Today, Projects, Inbox, Conversations and Knowledge, with advanced operational views. The existing Paperclip-inspired organization bridge has a read-only organization/goal projection, but the inspected `MetaCeoOffice` mount does not supply `organizationObservation`. That composition gap is concrete; it is not a reason to create another organization database. [M1, M2]

The current leadership charter source contains eleven roles. Some older design/plan text describes nine; Paper examples show twelve; an older profile directory count is another different fact. Charter count, illustrative roster and observed live bot membership are not interchangeable. The actual user-facing roster must come from qualified profile/runtime observations and show coverage. [M3]

Existing Hermes team orchestration documentation describes a native Kanban SQLite store, acceptance-first task dependencies, dispatcher claims, task workspaces, evidence, creator wake and recovery. That is a dated operator/source record, not a fresh health check. Preserve incumbent native work and bind it to company execution; do not silently discard it or launch a duplicate Executive root for a card already running. [M4]

The mobile/team integration already distinguishes canonical Bot Chat from task and ordinary sessions. Its isolated qualification does not establish production enablement. Likewise the secretary routine catalog's paused shadow templates do not prove that no real Hermes routines run elsewhere. These are existing seams to complete, not proof of a blank system. [M5]

Use existing stable identifiers and extend incumbent bindings where a join is absent. The following is a logical model, not a request for another global registry or microservice.

|---|---|---|
| Goals, workstream decisions and continuity | Existing Agent OS workstreams and dated handoffs | Objective, decision and continuation links. |

| Admitted execution, attempts, leases, effects and acceptance | Executive OS and incumbent RuntimeBinding/continuity owners | Live task execution and authorized actions. |
| Native Hermes card/turn/session/cron state | Existing Hermes instance and its native store | Bound native detail, without independent company authority. |
| Canonical Bot Chat and group-room state | Hermes profile/gateway ownership | Team and Conversations. |
| T3 project/thread/run, provider and workspace operations | Selected T3 environment/server | Code workbench and native detail. |
| Host placement, shared capacity, reservations and quotas | Capacity Fabric and current host/resource owners | Capacity/Fleet and work admission explanations. |
| Code, PRs, plan revisions and source evidence | GitHub and existing source/evidence homes | Exact version/source links. |
| Artifact bytes and access | Existing authorized source/storage owner | Deliverable index with provenance and permission-respecting preview. |
| Portfolio projection and human transport | Existing Linear and Slack integrations | Projection/notification; not another fact owner. |

`DEC:AGENTOS-NO-TASK-STORE` is binding: Agent OS does not acquire a Task table/service. The visible word “task” is a product abstraction. A plan node may have zero Jobs, multiple admitted Jobs or multiple Attempts, and multiple outputs. A native card's “done” state must not silently mark the editorial node or company objective accepted. [M7]

Keep these identities separate and join them explicitly: project/plan node; Executive Job/Attempt; bot profile and host; native task card; conversation/group; native execution environment/thread/run; routine definition/revision/occurrence; deliverable/source version; decision or approval. A conversation can discuss multiple tasks. A persistent bot can execute multiple isolated task runs. A result can be delivered successfully while its work remains unaccepted.

### Existing Hermes Kanban and Executive

For existing native work, first observe the original card, dispatcher generation, worker and effect. Preserve a running card and its lease. Add a qualified reference/binding where authorized; never retroactively invent an admission receipt. For newly managed company work, Executive owns the company admission and native dispatch is its subordinate execution path. Only one path may initiate a given effect. If the old path lacks that join, leave its scope explicit and reconcile before moving it; do not start a second root as a migration technique.

## 6. Reliability requirements that precede stronger product claims

### 6.1 Complete the existing T3 durable boundary

The #2356 candidate is real work and has a valuable committed live proof. The receipt records a native T3 launch reaching success with a returned result. The adapter itself is explicitly built-but-unselected. Those facts should survive this revision. [M8, M9]

However, the inspected `T3ExecutionAdapter` constructor defaults launch intents and result references to Python dictionaries. Original references, launch receipts, cursors, cancellation records and start bindings/specifications are also dictionaries. Comments calling them “persisted” do not make them survive process loss. The current receipt establishes the scoped launch/return and recorded operation order, not coordinator restart durability. This is a concrete repair inside the existing D3/D4 adapter/Executive path, not a reason to create a new execution service.

Use the current durable Executive/broker transaction boundary for intent-before-effect, native receipt, original return address, authenticated namespace, cancellation request/settlement and retained result reference. Rehydrate and reconcile against the original T3 environment. Preserve the authentic OAuth/client identity namespace as well as the idempotency key; a namespace string alone does not substitute for the original principal. The same nominal key under different authenticated clients need not identify one launch.

A lost response or restart must lead to reconciliation of the original execution, not an automatic new host/provider/start. Demonstrate that on one representative real path after wiring the durable owner. T3's own event/projection/outbox/recovery code is useful reference, but its maintenance retention does not make it a company evidence archive. Preserve accepted result references in existing company/source homes. [T2]

### 6.2 Separate bot relationship from task execution

Use the legitimate shared-session gateway path when continuing an existing canonical Bot Chat. Hermes documents that `/v1/runs` cannot adopt a foreign CLI/Desktop/ACP/messaging session. Its run idempotency has a credential/profile scope and a retention window; it is not Mastermind's unlimited durable deduplication record. An API task session must not accidentally become the bot's permanent conversation. [H2]

For unattended teams, use qualified gateway-owned group/peer facilities where supported by the installed version. Desktop relay is useful while Desktop is connected, but is not evidence of operation after the client closes. Cross-host failover needs an exclusive owner/generation and reconciliation of old effects, not just replicated room text. Preserve native profile memory while Agent OS holds company continuity. [H1]

Treat queue, steer, interrupt, approval and stop as different operations. A stop request is not terminal proof; an unknown post-restart run is not automatically failed. The inspected Paperclip gateway execution adapter is a protocol donor, but default timeout and terminal polling behavior must be reconciled with long-running jobs, approvals, clarification, unknown outcomes and credential continuity before reuse. Source inspection here is not an executed fault test of that adapter. [P1, H2]

### 6.3 One recurrence owner per routine

Reuse the incumbent trigger owner. Existing Hermes cron routines remain native cron definitions unless an explicit authorized migration changes that owner. Add any missing version/history semantics through that existing owner; map each company-managed due occurrence to its Executive admission and result. Do not run a Paperclip scheduler in parallel for the same definition.

Specify timezone/DST behavior, missed occurrences, overlap, coalescing, manual runs and edit revisions. A defensible default for a recurring briefing is skip stale missed occurrences and coalesce while active; that is a proposed policy for that routine type, not a mandatory policy for every task. For financial/data collection or other completeness-sensitive work, use its existing domain rule. Name the trigger owner, policy owner and execution-admission path for each routine; do not replicate one definition in Hermes cron and Executive Wake. Native local routines outside company work retain their existing scope. Pause prevents future starts; stop addresses a currently running occurrence. Next due, last attempt, last successful result, execution success, delivery success and accepted output remain separate. [P2]

### 6.4 Make attention actionable

An Inbox item should answer: what happened; what is needed; who can do it; what that action changes; which source will confirm resolution. Suggested groups are Needs you, Blocked work, Review and Updates. A click must invoke the current authorized action owner, then read back the authoritative state. Do not mark a card resolved merely because a request was sent, and do not invent a universal approval privilege. Read/acknowledged is not resolved or completed. Existing selected-Mission attention and independent request sources retain their own scope and freshness. Missing company-wide coverage cannot truthfully produce “Nothing needs you.” If action submission is uncertain, reconcile the original operation. [P4]

### 6.5 Make deliverables durable and useful

Promote outputs that a person can use: document, dataset, PR, chart, deployed URL, decision brief or evidence package. Link author, originating task/attempt, version, creation/update time, source and acceptance status. Distinguish draft, reviewable, delivered and accepted, with original-parent consumption separately recorded. Preserve content/access state, version or digest, and superseded, missing, revoked or partial-output states. Reuse existing access controls; no copied private attachment into a weaker storage boundary. Execution logs remain supporting detail rather than filling the deliverables shelf.

A completed native run with a broken parent return is incomplete company delivery. Persist the result/reference before sending the return, use the original parent/conversation, and reconcile delivery separately from acceptance. [P3, M7]

## 8. Source reuse and maintenance discipline

Paperclip, Hermes and T3 identify their source under MIT licenses at the inspected revisions. For actual copied code, preserve applicable copyright/license notices, record upstream path/commit and inspect the dependencies included in the extraction. Use original Mastermind presentation and branding. This document copies no upstream implementation. [P8, H3, T3]

Start with bounded pure helpers/components and protocol mappings. Paperclip's larger issue, routine and Inbox modules depend on its company/schema/permission model; transplanting those services would carry architectural assumptions into Mastermind. For transactional behavior, use upstream as a specification and source of focused failure cases, then implement in the incumbent owner. Do not split out a service merely to match upstream module names.

Maintain one small donor inventory in the existing repository documentation: upstream commit/path, copied versus adapted behavior, owning module, license and relevant verification. This is source-maintenance metadata, not a new lifecycle registry. Update deliberately when upstream fixes affect the adopted behavior. No automatic latest-master ingestion, mirrored company DB or global compatibility promise is required.

Rollback should remove or disable a new projection/feature seam without losing native sessions, accepted evidence or existing routine ownership. Introducing a new task/control database would make that much harder; avoiding it is an immediate operational benefit.
