## Product behavior

### Team and conversations

Team has a conversation view and a roster view. The rail separates groups and teammates, supports search and attention filters, and shows real state independently of unread recency. A teammate is a persistent bot identity; a conversation is its session/history binding. Starting a fresh session must not silently create a new teammate, copy personal memory or change runtime ownership.

The centre timeline remains readable while tools stream. Tool activity, delegated work and returned artifacts use compact expandable rows. The work inspector links the active outcome, tasks, coding thread and shared context. On a phone, that inspector becomes a sheet/detail view; it does not squeeze an unusable four-column desktop layout into the viewport.

New Bot and New Group are visible creation actions. The bot flow separates saved profile, admitted startup and confirmed readiness. Cloning a safe template copies permitted configuration only; credentials, private history and personal memory require their own existing owner policy.

A room declares whether it is gateway-owned and able to continue without a viewer. A classic Desktop-driven room visibly requires Hermes Desktop. “Always-on” is therefore a capability/ownership statement, not a badge applied to every chat.

### Messages and follow-ups

The active room composer says **Send to room / Queued next** when the room is busy. A bot or child task may expose steering when that particular runtime advertises it. The UI must show what the receipt actually did: queued, steered, restarted or refused. Guidance queued is not guidance consumed.

Message actions include reply in thread, copy, inspect details, open/start linked Code, attachments/context, mentions, commands and supported voice entry. A message already linked to coding work opens that exact session; clicking it again does not launch another task. Queue editing preserves the original queued identity and the unrelated unsent composer draft.

Stream rendering must not move the reader away from earlier messages. New messages follow the bottom only when the reader is already there; user sends bring their own outgoing message into view. A full connection resync restores the same conversation, scroll anchor, selected thread/task and draft.

An unconfirmed send keeps its original intent and disables blind resubmission. Check status against the original owner. If the original is found, attach its acknowledgment once. A positive acknowledgment proves acceptance/delivery at that boundary, not that the bot processed the content or completed the outcome.

### Tasks, approvals and stopping

Show each child's parent, brief, execution status, provider/environment and available result. Native child dialogue is shown only when there is an addressable native child. ACP-reported task activity remains an activity view when native child transcript/lineage is unavailable.

Stop controls name their scope. Stopping one child leaves its siblings and parent relationship intact. Stop requested is not Stopped; only the terminal receipt settles the child and releases any owned capacity. Similarly, a parent stream finishing does not prove that background tasks have settled.

Approval actions bind the precise prompt, task/session and execution generation. A replayed, expired or already answered request is non-actionable. The browser/terminal panel identifies the execution environment. Browser access, observation and control are different states; “You have control” appears only after acknowledgment. Offline controls show last observed state and cannot mint new authority.

### Code and exact return

Starting coding from Team carries the origin bot/room/session/message, project and task into one launch intent. The page shows:

1. Admit the work and reserve capacity through the existing company owner.
2. Prepare the isolated workspace supplied by the existing workspace owner.
3. Bind T3 to that checkout and start the selected provider through one launch owner.
4. Show Working only after actual provider-start evidence.
5. Open the exact environment/project/thread and return to the exact originating conversation.

HC06 and HS02 were corrected to this order. A generic “Starting” spinner must not hide waiting for company admission or workspace preparation.

In Code, reuse the mature donor timeline, composer, tool stream, diff/PR view, terminal, browser, worktree and environment surfaces. Team retains a concise work/result card and a direct Open session link. A result returns once to its origin with the exact thread/run, artifacts and checks; repeated delivery events are deduplicated. Source-ready, PR-ready, merged, deployed, proven and parent-accepted remain separate. HC08 deliberately keeps the parent outcome open while another acceptance item remains.

Stopping one child leaves its sibling running.

Retry delivery reuses the retained result; a lost response checks the original delivery. Neither path reruns the routine or creates another result message.
