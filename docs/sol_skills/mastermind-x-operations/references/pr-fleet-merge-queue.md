# PR fleet: merge queue, protected carrier branches, CI forensics

Mechanics for landing work through the org repo's protected merge queue when head branches are carrier-owned. Read after "Lane PR rules" in SKILL.md.

## Repo laws (ruleset-enforced; verify with `gh api /repos/<o>/<r>/rulesets`)
- **Squash-only:** rebase and merge-commit methods are disallowed repo-wide. `gh pr merge --rebase` and `--merge` fail even with `--admin`; always `--squash`.
- **Admin bypass does not exist for the default branch:** `gh pr merge <n> --admin --squash` with base=master is refused — "Repository rule violations found — Changes must be made through the merge queue". `--admin` lifts carrier/stacked-PR restrictions only; landing on master goes exclusively through checks-green + queue admission, so never spend a cycle retrying bypass variants. Separately, drop `--delete-branch` whenever the base branch is queue-protected ("Cannot use -d or --delete-branch when merge queue enabled") — delete the head branch after landing if still needed.
- **Carrier head branches are push-restricted to the carrier identity** — even repo admin gets "protected branch hook declined". Never push fixes to the PR head branch; deliver via a stacked PR into it.
- **Merge queue on the default branch** evaluates PRs in position order; a queued PR whose branch went red sits UNMERGEABLE without self-healing.
- Queued `UNMERGEABLE` has two readings: branch went red, or the PR conflicts only when COMBINED with the current ahead-batch — the latter is normal, re-evaluates every time an ahead entry merges or fails out, and needs no action. Standalone `mergeable: MERGEABLE` + green checks is the signal that matters.
- **The queue auto-evicts on conflict:** when an ahead entry merges and moves master, queued entries are re-evaluated against the new master and a conflicting one is REMOVED by the merge-queue bot (PR stays OPEN, absent from queue, `autoMergeRequest` null, `mergeable` CONFLICTING/DIRTY). That is not a watcher failure — go straight to the dequeued remedy below; no close/reopen, the eviction already happened.
- Before evicting or intervening for a slow queue, inspect the ahead entries (`gh pr view <n> --json state,updatedAt,author`): all recently updated = busy, not clogged — red ahead entries fail out on their own and every ahead merge advances your position.

## Merge-queue mechanics
- A queued PR's head branch is **frozen**: a stacked PR targeting it fails with "Base branch is the protected head branch of a queued pull request", with or without `--admin`.
- **Evict a queued PR with `gh pr close <PR>`** — the only proven method. Draft-toggle (`gh pr ready --undo`) does NOT evict; the legacy auto-merge object does not exist; the `removePullRequestFromMergeQueue` mutation is unavailable.
- **Arm-strip law:** `autoMergeRequest: null` is normal ONLY once the PR is actually in the queue — and armed ≠ queued: an armed PR is admitted only after required checks pass on the CURRENT head, so a green PR legitimately sits armed-but-unadmitted while fresh CI runs. But on an un-admitted PR the arm can be silently stripped (was enabled, later null, no queue entry); that combination is a real disarm and the PR will never be admitted until you re-run `gh pr merge <n> --auto --squash` (idempotent; "merge strategy … set by the merge queue" is the healthy confirmation). When a green+CLEAN PR has gone unadmitted past one full CI cycle, read `autoMergeRequest.enabledAt` before anything else. An enabled, never-consumed arm SURVIVES head updates (a stacked convergence PR landing on the head) and dirty cycles — no re-arm between convergence rounds; re-issuing `--auto --squash` is idempotent anyway.
- Query the queue's PR list + positions (GraphQL `mergeQueue` on the default branch) before and after any eviction or merge action — it is the ground truth for what is frozen.

## Convergence target: plain master, and only when the queue is empty
- **Queue admission requires the head clean against PLAIN master.** Never converge the carrier to master + a simulated ahead-stack ("what's coming"): simulated stack content puts the head AHEAD of master, PR-level `mergeable` reads CONFLICTING from the old merge-base, and the arm can never admit — the PR is locked out of its own remedy.
- **Converging to plain master while entries sit AHEAD in the queue is a guaranteed repeat cycle:** ahead entries merge first (position order), advance master into the regions you just converged, and the re-evaluation evicts again. Fix → CI (~40 min) → admit → evict loses that race by construction, every round.
- **Break the treadmill by draining first:** dispatch a read-only drain watcher (below), wait for zero queue entries, converge to the drained master tip, arm into the empty queue — the only remaining competition is entries that join after you.
- **Draining is necessary but not sufficient — pass the WAVE, not just the queue:** fleet PRs armed OUTSIDE the queue mature toward admission in ~one CI cycle (~40 min here), and any of them landing inside your CI window re-dirties you; admission happens only after your own checks finish, so an entry already ahead when you arm wins by construction. Before converging, require BOTH zero queue entries AND no armed BEHIND fleet PRs on overlapping files (read `autoMergeRequest` on the fleet PRs + queue GraphQL); converge to the post-wave master tip and arm into the lull. Arm seniority (earlier `enabledAt`) admits first on simultaneous green — arm early, converge late.
- **Eviction from the queue does NOT neutralize an overlapper — "cleared" is not "safe":** a PR evicted UNMERGEABLE stays OPEN and the fleet can merge it directly (or re-arm) minutes later, landing on the hot surface mid-CI and re-dirtying you (observed: #780 evicted 22:27Z, merged directly ~22:45Z, re-dirtied a convergence pushed at 22:42Z). The lull test before converging is THREE-part: (1) queue contains no overlap>0 entries, (2) no OPEN overlapper PRs exist that could land inside your CI window — check recently-evicted and armed-BEHIND fleet PRs by state, not just queue membership, and (3) treat any OPEN PR touching the surface hot files as a live hazard until it is MERGED or CLOSED. When the contested zone is a fleet hotzone (same 2–3 files every round), expect the lull to be shorter than one CI cycle — converge the instant the three-part test passes, and re-verify it in the same minute you push.
- **Post-resync, verify mergeability with a LOCAL 2-arg merge-tree, not GitHub's `mergeable` field:** right after a convergence PR lands on the head, GitHub's computed `mergeable`/`mergeStateStatus` can be stale in EITHER direction (a MERGEABLE that flips to CONFLICTING minutes later with neither head nor master moved = stale cache; a fresh recompute after a master advance can equally lag). The deterministic check is the same squash-equivalent probe used pre-ship: `git merge-tree --write-tree origin/master <pr-head-sha>` (two refs) — exit 0 is the truth; treat the API field as a hint until it agrees.
- **Overlap math must use the PR's CURRENT head vs fresh master, recomputed every round:** a stale carrier ref (e.g. the `sol/*` branch the lane started from) diverges from the PR head after even one convergence round, and a diff against it silently misses real conflict files — a "0 overlap pipeline" verdict from a stale base is how a round gets wasted on a landing that re-dirties you. Fetch the head fresh (`git fetch origin refs/pull/<n>/head:refs/pr<n>head` — squash heads created server-side by stacked merges do NOT exist in the local object store until fetched), fetch master to a ref, then `git diff --name-only <prhead> <masterref>` is the surface and `file ∩ surface` is the predicate for BOTH decisions: pre-resync (wait for queued PRs with overlap>0 to land first) and post-arm (only overlap>0 entries ahead can hurt you). A landing can only re-dirty the PR if it touches a file in that fresh surface.
- **A PR that cycles CONFLICTING with zero failed checks is losing on timing, not code:** base movement is the only failure mode when checks never fail — stop investigating CI, fix the timing (wave-pass) or the convergence, never the checks.
- A local sequential merge of master + queued entries (queue simulation) is a PREDICTION tool only: use it to foresee which files will be contested next; never ship it as the tree while those entries are still ahead.

## Landing a fix on a queued, push-protected branch (proven cycle)
1. `gh pr close <queued-PR>` — evicts from the queue, unfreezes the branch.
2. `gh pr merge <stacked-fix-PR> --admin --squash --delete-branch` — lands the fix on the head branch.
3. `gh pr reopen <queued-PR>` → `gh pr ready <queued-PR>` → `gh pr merge <queued-PR> --auto --squash` — restore and re-arm.
4. If master moved while queued, resolve the new conflict (below) as another stacked PR and repeat.
- A PR stacked on an open base shows DIRTY/CONFLICTING as an artifact; it self-resolves when the base merges — don't "fix" the stacked PR.
- **Build the stacked fix branch ON the fetched current carrier head, never a local cousin:** a branch built from the pre-squash local state (same tree, different history) makes the stacked PR itself unmergeable — "the merge commit cannot be cleanly created" — even with `--admin --squash` (#2258). `git fetch origin refs/pull/<n>/head:refs/pr<n>head` then `git checkout -B <fix> refs/pr<n>head`, and `git merge <fresh-master-ref>` into THAT.

## Dequeued by the queue bot (conflict eviction) — proven remedy
1. Read the true head: `git ls-remote origin refs/heads/<head-branch>` (carriers force-push; never trust a cached tip).
2. Enumerate conflicts vs new master: `git merge-tree --write-tree --name-only origin/master <head-sha>` (two refs).
3. `git checkout -B <fixbranch> <head-sha>` then `git merge origin/master --no-commit`; resolve per the rules below.
4. Verify BEFORE shipping: squash-equivalent probe merge-tree vs `origin/master` exit 0 (recipe under "Resolving conflicts"), the registry consumer test green, `python3 -m py_compile` on every resolved module.
5. Push the fix branch, open a PR with `--base <head-branch> --head <fixbranch>`, land it `--admin --squash --delete-branch`.
6. Read back the original PR's `headRefOid` (must be the new squash head) and `mergeable` (must be MERGEABLE) BEFORE declaring success, then re-arm `--auto --squash`. If `mergeable` stays CONFLICTING with master unmoved and a clean probe, the head is AHEAD of master (adopted queue-stack content) — see "Convergence target" below; do not ship another blind fix round.

## Resolving conflicts so the merge actually clears
- **A squash-merged resolution does NOT clear a textual conflict:** squash adds no ancestry link, so the next three-way merge re-evaluates from the same old merge-base and re-collides wherever both sides added different content at the same anchor.
- **Merge commits are banned repo-wide, admin included** (`gh pr merge <n> --merge` → GraphQL "Merge commits are not allowed on this repository"; gh prints the error but can exit 0 — read the PR state back, never trust the exit echo). Therefore server-side ancestry repair of the carrier is IMPOSSIBLE: the carrier only advances via squash, the merge-base stays frozen (observed `3c3bfdf8` across 9+ convergences), and content-parity racing is the only endgame. Why parity works at all: git auto-resolves regions where both sides made byte-identical changes, so DIRTY clears once carrier content == master content at every contested anchor, ancestry or not — and every later master move in a mirrored region re-dirties. Only carrier-NATIVE regions (files the carrier changes by its own work vs base) are permanently safe; converge hot files to master verbatim so they stay in the identical-mirror class.
- Fix by **relocation, not just keep-both**: keep both sides' content but move your additions to a different region so (a) at the contested anchor both sides make byte-identical additions and (b) your additions land where the other side never touched (separate hunks). In additive pin/registry dicts, entry order is a semantic no-op — relocate freely.
- **Predict before pushing — with a squash-equivalent probe, never your branch tip:** `git merge-tree --write-tree origin/master HEAD` is only meaningful when HEAD does NOT contain master. If the fix branch is a merge commit that already merged master (or a master+queue simulation) into itself, merge-tree exits 0 trivially — one side contains the other — while GitHub still reports CONFLICTING: the squash onto the carrier discards that ancestry, and GitHub's check is a 3-way from the ancient merge-base. Gate on the commit GitHub will actually create: `X=$(git commit-tree HEAD^{tree} -p <carrier-head-sha> -m probe)` then `git merge-tree --write-tree origin/master $X` — exit 0 + tree oid there is GitHub's `mergeable: MERGEABLE`. Exactly TWO refs: passing an explicit merge-base as a third arg hits a usage error whose nonzero exit mimics "conflict". `--name-only` works alongside `--write-tree`.
- Resolve markers IN PLACE (strip `<<<<<<< HEAD` through `=======` and the `>>>>>>>` line) — `git checkout --theirs <file>` takes the WHOLE file from theirs and silently discards hunks that already auto-merged into the working copy.
- Read each hunk before choosing: an empty HEAD side is a pure append collision — take theirs verbatim. For a call-site conflict, grep the merged file for the callee's definition and confirm it supports the newer call's kwargs before adopting the newer call (the definition may have auto-merged from either side).
- **Full-scope take-theirs when the carrier carries earlier variants of fixes other agents already landed on master/queue** — the conflict is master's newer version of a fix your side already has, so there is nothing local to preserve and hunk-by-hunk judgment re-derives decisions master already made. (This is the complement of relocation: relocate NOVEL local additions; take-theirs DUPLICATED fleet fixes.) Take registry pin/SHA values together with the file content they pin — a pin must match the content actually adopted, never the value you authored.
- Mechanical take-theirs at scale: after `git merge --no-commit`, run a `re.S` regex over every `git diff --name-only --diff-filter=U` file replacing each `<<<<<<< HEAD … ======= … >>>>>>>` block with its theirs-side (keep group 2), assert zero markers remain, `py_compile` every touched module — whole-file `git checkout --theirs` stays forbidden (it discards hunks that auto-merged).
- **Adopt master verbatim at collision anchors; relocate only YOUR additions.** Once your branch's content equals master at an anchor, neither side changes the base there anymore, so future master appends at that anchor merge clean — each conflict resolved this way stays resolved; only your own distinct additions can re-collide.
- `python3 -m py_compile` every resolved module before committing.
- Validate a relocated registry by content: `shasum -a 256` the pinned sources and run the dedicated consumer test. A data-only registry module (no test defs) collects zero tests — `pytest <registry>.py` exits 5 with "no tests ran": import success validates syntax, the consumer test validates pins. Find the consumer with `grep -rln <module> tests/` instead of trusting the registry filename.
- Local-only reds that cannot exist in CI (e.g. `ValueError: asset path has a macOS ACL` from macOS extended attributes) are environment artifacts — don't chase them as regressions. To PROVE a red pre-existing rather than assert it, rerun the same tests on the pure base — `git worktree add -f /tmp/basechk <base-ref>` (master or the queue simulation) with the same pinned venv; failures that reproduce there were not introduced by the resolution, and a base failing MORE tests than your merged tree settles it outright.

## CI log forensics (ladder of last resort)
1. `gh run view <id> --log-failed` — often empty.
2. Per-job logs API `gh api repos/<o>/<r>/actions/jobs/<job-id>/logs` — often 0 lines.
3. **Run-level zip — the reliable floor:** `gh api repos/<o>/<r>/actions/runs/<id>/logs > runlogs.zip`, then parse with Python `zipfile` to reach any job's text. Use this before concluding "no logs available".

## Oversized-parametrize CI failures (E2BIG class)
- Symptom: every `execve` in a test dies `OSError: [Errno 7] Argument list too long` while the suite passes locally — the environment, not argv, is the carrier: pytest embeds the full parametrize payload in the node id, exports it as `PYTEST_CURRENT_TEST`, and the export exceeds Linux `MAX_ARG_STRLEN` (131,072).
- Fix at the source: explicit short `pytest.param(..., id="short-name")` ids, payloads unchanged; keep worst-case node id + variable name ≈100 bytes.
- **Reproduce CI failures with the lock-pinned dependency version** — newer versions can mask the mechanism (shortened ids) and turn a repro into a false negative.

## Read-only PR watcher delegation
- Dispatch watchers with: poll every ~4 min using `sleep` between polls inside ONE terminal call per cycle (never rapid tool-call loops); terminal states defined up front (MERGED with mergedAt + mergeCommit / CLOSED unmerged / red required check with job URL / DIRTY with mergeStateStatus / deadline); STRICT read-only — no push, merge, comment, dismiss, or edit; always read the CURRENT `headRefOid` because carriers force-push.
- A late-arriving watcher report describes state at ITS poll time — re-read current state before acting on it; treat superseded findings (old heads, old CI runs) as history, not blockers.
- **Drain-watcher variant** (before converging a drift-treadmill PR): poll the `mergeQueue` GraphQL every ~3 min until entries==0, capture the master tip (`git ls-remote origin refs/heads/master`) each poll to trace landings, report time-of-drain + final full tip SHA + landing order; deadline ~75 min; same strict read-only rules.

## Race-loop laws (rounds 10–11, 2026-11-08)
- **The auto-merge arm is CONSUMED at queue admission** — `autoMergeRequest` clears the moment the PR enters the queue. After every admission-then-eviction, the convergence remedy MUST end with an explicit re-arm (`gh pr merge <n> --auto`); the method arg may be reported back as the queue ruleset's own ("The merge strategy for master is set by the merge queue") — that is normal, the arm stands. The re-arm timestamp is junior: seniority is only as old as your last re-arm, so every lost round permanently weakens that lever.
- **UNMERGEABLE at admission** = the queue cannot build its intermediate branch with your head stacked on the entries ahead; eviction usually follows within ~an hour. Root cause is almost always a hot landing inside your CI window (round 10: #775 had been armed since 23:50Z and landed mid-window; the convergence shipped while it sat armed in the queue).
- **Pre-push gate (three-part lull test, final form):** (a) queue empty or only zero-overlap entries (verify via `gh pr view <n> --json files` comm'd against the fresh surface); (b) NO armed direct-overlap PR currently sitting in the queue mid-checks — pushing while one sits there wastes the round; (c) armed hot OPEN PRs BEHIND the queue are acceptable residual risk — no true lull exists, those are the irreducible race.
- **Queue GraphQL schema law:** the working shape is singular `mergeQueue` with NO args on `Repository` (returns the default-branch queue): `repository(...){mergeQueue{entries(first:10){nodes{position state pullRequest{number}}}}}`. Both `mergeQueues` (plural) and `mergeQueue(currentBranch:...)` are rejected by this schema.
- **Whole-file take-theirs (`git checkout <master-ref> -- <file>`) is preferred for mirror files** — files you intend to converge to master verbatim, where collision = pure staleness (this is the parity endgame, and rounds 10–11 landed MERGEABLE with it). It remains forbidden only for files carrying NATIVE carrier work, where it would discard auto-merged hunks. The squash-equivalent probe stays the authoritative gate either way.
