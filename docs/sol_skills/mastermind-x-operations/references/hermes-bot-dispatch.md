# Hermes dispatch and return evidence

Use this reference only within an existing authorized Hermes/Fabric assignment. The protected INDEX, ACTIVE_EXECUTION and the integration's enrolled admission and delivery owners govern the action. This file does not enroll a standalone chat, kanban queue, profile, scheduler or worker.

## Qualify one original dispatch

1. Recover the current assignment and full source-linked brief: outcome, scope, immutable inputs, retained gates, deliverables, DONE_WHEN, original root/operation and return path.
2. Inspect the actual enrolled tool schema and native owner for this session. Verify the exact identity, grant, model route, capacity and budget required by that action. A known CLI command, on-disk profile, tool listing or catalog row proves neither authority nor readiness.
3. Protect a live writer and reconcile any prior pending or uncertain dispatch at its original target. Do not introduce a second task identity, board row, profile or transport to avoid that obligation.
4. Submit one authorized request through the existing admitted route. Retain the actual request identity and result. Do not run raw Hermes chat or kanban commands as an alternative admission path.
5. Separate delivery, pickup ACK, QUEUED, STARTED/RUNNING, result return and acceptance. A chat answer or board status is evidence of that surface only. Durable execution requires the canonical running record and a return path.

Use the current paid-Fabric and principal-work rules in ACTIVE_EXECUTION. Do not hard-code a provider/model default from a dated chat, change credentials or bypass a rejected route based on catalog availability.

## Verify the actual return

Compare delivered artifacts with the named immutable source, expected path, content digest and complete acceptance criteria. Read enough actual content to judge correctness. File presence or mtime alone cannot identify the writer, prove the requested operation or establish semantic completion. A worker's quoted hash, transcript or paste-back is a claim until matched to the actual artifact and original receipt.

Preserve original source, capture timestamps and execution provenance. A new source composition may reuse evidence only when the relevant inputs and acceptance contract permit it. Do not manufacture fresh evidence by copying, renaming or restamping an older artifact.

Record the useful result and exact remaining obligation in the source-linked GitHub brief and the existing continuity owner where required. Slack carries recipient, scoped action, source link and return path; it is not a replacement task or result store.

## Recover failures without redispatching blindly

| Observation | Required disposition |
|---|---|
| Explicit safety or permission refusal | End that action; no shortened prompt, new account, route, model or transport replay. Continue genuinely independent authorized work. |
| Request/schema error | Classify the exact original request and effects; use at most the permitted bounded diagnostic. A corrected shape is not automatically retry permission. |
| Timeout, crash, lost output or owner-silent return | Preserve the original operation and reconcile its canonical effect. Do not infer absence from a missing artifact, task returning to ready or a vanished process. |
| Verified technical pre-effect refusal | Retain the original absence/cause evidence and applicable recovery rule. EFFECT_NONE alone does not grant a retry. |
| Completed worker result with a defect | Adjudicate the actual result, preserve existing effects, and issue only an authorized bounded repair through the same lifecycle owner. |

A board may display ready after a crash while a publication, external request or subprocess effect remains unresolved. An update drain does not prove that every child stopped before effects. Do not redispatch until the original owner establishes the necessary settlement and the recovery path is authorized.

Keep one bounded diagnostic per unchanged failure. Recheck only after a relevant schema, session, configuration or observed recovery change. Do not infer weak-model behavior or provider refusal from a malformed response without evidence.

## Capability checks and transport

Use an authorized real task or harmless read for capability verification. Never create an ALIVE file, fake telemetry or dummy write solely to test access. Do not turn a long-running process into an invented durable executor or duplicate watcher. Bound any observation by a useful next decision; a session is not a daemon.

Posting needs current explicit authorization. Keep shadow/no-send restrictions in the brief, and follow the existing Slack identity and channel rules. For an authorized Grok Secretary handoff, use the designated channel/mention and source-linked top-level/thread pattern; never substitute a DM. Verify actual service IDs and message metadata rather than trusting display names. Keep tokens and credential values out of every brief and result.
