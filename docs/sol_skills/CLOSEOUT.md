# CLOSEOUT — Make the Result Durable and Recoverable

Use after a substantive architecture ruling, accepted implementation, production proof, major
reconciliation or operator handoff.

## Mission

Leave the company in a state where a **brand-new Sol session can recover what became true,
what remains false, and the exact next action without this chat**.

Closeout is not paperwork after the real work. Cross-session recoverability is part of the product.

## Step 1 — State the capability delta

Write one precise before/after statement:

```text
Before: <what user/machine could not reliably do>
After:  <what can now be done and through what canonical path>
```

If the wave was records-only, say so. If implementation is built but not production-proven, say
`BUILT_NOT_PROVEN`. Do not inflate the capability because the team invested heavily in it.

## Step 2 — Re-run the completion law

Before marking anything done, answer:

* What did the commission say completion means?
* Was production/browser/machine-consumer proof required?
* Is the proof from the real path and exact accepted head/release?
* Did any degraded/negative state remain untested?
* Did a merge/Slack message/Linear automation accidentally advance projection farther than truth?

If proof is missing, keep the correct nonterminal capability state and name the proof owner/gate.

## Step 3 — Record immutable implementation evidence

For code/research work, preserve:

* repository;
* PR number;
* accepted/merge SHA;
* changed capability, not just changed files;
* CI/security/adversarial review receipt;
* production/release identity when owed;
* important negative proof (e.g. zero Attempts, no Wake, no second store).

Mutable branch heads are not closeout receipts.

## Step 4 — Update the correct durable homes

### Mastermind / owning repository research/docs
Update when architecture, source law, product contract or evaluation law changed.

### Agent OS
Update when cross-session organizational truth changed:

* workstream status/wave state;
* a decision/ruling;
* a discovery that future sessions must know;
* a continuation handoff.

Do not create an Agent OS workstream/program parent that the semantic registry does not support.

### Linear
Repair/selectively project the current portfolio state **after** canonical evidence is known.

Linear should expose action/gate/progress usefully; it need not duplicate the entire Agent OS or PR.

### Slack
Post bounded human/machine visibility/receipt where useful. Slack remains transport, not the durable
owner of the ruling.

### Shared Project
Do not rely on Project chat history as the durable closeout. It may remember the conversation, but
future correctness must not depend on it.

## Step 5 — Preserve supersession explicitly

When a new ruling replaces part of an older one, record:

* exact old source;
* exact new source;
* what clauses/assumptions are superseded;
* what old laws remain controlling.

Avoid “new doc replaces old doc” when only one narrow carrier/sequence assumption changed.

## Step 6 — Leave unresolveds visible

Record unresolved items with:

* concrete claim/gap;
* why it matters;
* current capability state;
* falsifier or evidence that would resolve it;
* named next owner/action.

Do not hide unresolveds inside “future work.”

Common Mastermind examples:

* production principal/credential not provisioned;
* natural-time proof still accruing;
* external entitlement unavailable;
* semantic registry gap prevents a lawful workstream;
* one platform capability unproven across all three Pro seats;
* user-facing producer exists but real consumer is not wired.

## Step 7 — Create the continuation handoff

A substantive handoff should let the next session answer immediately:

```text
mission just completed
state before
what changed
what was verified
what remains unverified
unresolved / danger areas
exact next actions in order
do-not-redo laws
return point / highest-authority sources
```

Use exact PR/SHA/MAS/WS identities. Do not paste private reasoning or secrets.

## Step 8 — Reconcile projections and transport

Before declaring closeout complete:

* compare Linear to canonical state;
* ensure architecture/docs merge did not auto-complete runtime/product issues;
* ensure Slack visibility does not imply execution/production acceptance;
* ensure no stale issue title still instructs a superseded sequence;
* ensure held downstream waves still list the correct predecessors.

Fix the projection, not the underlying truth, when the projection is wrong.

## Step 9 — Protect future cold starts

Ask:

> If a new Sol conversation starts tomorrow with only the Bootstrap Kernel and current repos/apps,
> what material thing from this session would it fail to know?

If the answer is a ruling, discovery, implementation status, proof requirement or exact next action,
put it in the appropriate durable source before closing.

Do not solve the question by expanding the Skillpack with live company state.

## Step 10 — State the next action precisely

End with exactly one primary continuation action and its gate, plus any independent parallel work.

Bad:

> Continue Slack integration.

Good:

> After PR-A head X closes the shared-normalizer blocker and hosted CI is green, Sol completes the
> remaining adversarial review; only on PASS may R0 state-read law be authored. S0/SHELL-1 may
> continue independently because they touch no PR-A runtime path.

## Closeout output

```text
Capability delta
Final capability state
Canonical receipts
Production proof status
Durable records updated
Projection/transport repairs
Unresolveds / falsifiers
Exact next action
Independent parallel actions
```

## K4 pass criteria

A fresh session can recover the accepted result, its evidence, its limits and the exact continuation
without chat archaeology, and no canonical/projection layer was advanced beyond what the evidence
supports.
