## 1. Outcome, not tool collection

A fresh worker must know the bounded assignment, relevant project facts, applicable
working method, actual tools, executable acceptance test and original return path.
A fresh operator needs those plus dependency decomposition, child-result consumption,
independent review and bounded escalation. Neither should spend its first half-turn
rediscovering the organization or claim access because a tool name appears in a prompt.

The acceptance ruler is a useful artifact produced by a fresh worker, using a required
real tool, with source/context/tool identity and cleanup proof, consumed by its original
parent. Installation, discovery, execution, model self-report, return and acceptance are
separate observations. A missing required tool must refuse before inference where the
preflight can observe it; provider-native effective-tool attestation remains the existing
adapter's responsibility.

## 3. Architectural decision

Use four composable inputs to the existing Craft compiler:

1. **Working method:** common Craft method plus exactly one assigned role. This is
   procedural guidance, not a new executive identity or execution grant.
2. **Project facts:** selected Agent OS/GitHub/Executive source facts with owner, exact
   reference/revision and observation time. These are advisory data, never overrides.
3. **Tool evidence:** scoped observations of actual actions, with missing/auth/denied/
   unknown states. A CLI version or MCP tools/list is not sufficient write permission.
4. **Task contract:** existing compact commission, preserving objective, why, source,
   write scope, non-goals, data/null/correction/rights, deliverables, proof and continuation.

The new launch-input consumer validates and contributes these inputs to #587/#588. It does
not become a second task compiler, retrieval engine, memory store, provider router,
credential service, job queue, retry controller or lifecycle authority.

There are two delivery levels:
- **Full prepared commission:** explicit facts, scoped tool requirements, fresh evidence,
  deterministic compiler/method/packet digests and PREPARED_NOT_ADMITTED status.
- **Legacy prompt-method compatibility:** small startup kernel and one class-derived
  Craft method, with the original task preserved exactly. Missing project context is
  explicitly NOT_SUPPLIED. This improves existing callers without inventing their scope.

Full packets require a bound execution scope. Automatic placement still belongs to the
existing dispatcher; the preparation layer must not silently choose another host to
make an old positive observation pass. Unbound legacy launches retain normal placement.

## 5. Tools and plugin integration strategy

### Source and delivery
Use existing GitHub integration or already-enrolled native `gh` for assigned source,
PR and CI operations. Read and write access are different capabilities. Scope workers to
assigned repositories and branch paths; reviewers normally read only. Preserve source
custody, exact PR head, independent approval and merge/deploy separation.

An upstream GitHub MCP client is appropriate only where a native actor is explicitly
enrolled. Use the official server and narrow toolsets/read-only variant where suitable.
Do not copy the Web user's OAuth token or assume ChatGPT's connector is available inside
a CLI worker. A selected method may teach `gh` without installing a redundant plugin.

### Company knowledge, project state and continuity
Agent OS remains the only organizational memory owner. Use its existing `compile-context`
for a named workstream, or pass exact selected records from its canonical reader. The
launcher only transports explicitly selected facts. It does not search the entire drive,
copy the whole CEO transcript or silently promote a worker's summary into company truth.

GitHub owns implementation state; Executive owns live work/attempts; Linear is a projection;
Slack is transport. Include their current source refs rather than flattening conflicting
claims into one apparently authoritative memory paragraph. Facts have freshness and
required/optional classifications; stale required facts stop dependent work.

### Slack and Linear
Operators should normally use the existing bound Company dialogue and existing projection
owners. Leaf workers return to their parent, not post unrestricted status messages across
Slack or rewrite project priorities. Generic Slack/Linear MCP access is an optional
separately enrolled capability, not a prerequisite for every worker. Official Slack MCP
requires an eligible registered app and OAuth/admin consent. Linear MCP also requires its
own authentication. There is no lawful token-inheritance shortcut from ChatGPT Web.

### Studio, Paper, Figma and browsers
Reuse the existing Studio/Paper gateway and provider projection (#1217); do not add a new
remote host-control gateway. `studio-fabric` is a read ceiling; design editing uses its
separately authorized route and exact target. A read tool inventory does not prove an
editor is usable. Load the canonical Paper domain skill before Paper work.

Use an isolated browser/profile scoped to the task. Logged-in browser sessions, downloads,
uploads, screenshot visibility and modifying actions each require actual proof. GLM vision
limitations are handled through the already-governed visual-helper path, not by granting
all workers an unrestricted desktop or another account's cookies.

### Documentation, research and data
Public developer-docs MCP is low-friction and does not require copying secrets. Select
only task-relevant docs/tools; do not put all available schemas into every launch. Web
research must retain primary URLs, access time, source dates and uncertainty. Data workers
also need provenance, licensing, point-in-time availability, null/correction behavior and
anti-leakage tests. API capability does not imply data redistribution rights.

### Environment and artifact handling
The existing reproducible-worker-environment owner supplies interpreter, lockfile, package,
PATH and vendored-input identity. A version probe alone does not prove dependency parity.
Use existing storage/worktree policy and explicit artifact paths. Keep screenshots/logs
out of the prompt; return digests and selected evidence references. Clean only owned
reproducible temporary outputs after their recovery evidence is safe.

## 6. Startup protocol

Before model spend when observable: validate the packet, source/method hashes, exact
observation scope, freshness, required project facts and required tool observations.
Do not start a substitute model/account when this fails. Missing optional inputs produce
named degraded entries rather than a silent omission. The existing launch owner still
checks provider account, host, quota, lease, sandbox and source permissions.

At model startup: read the assigned repository's AGENTS.md and task-specific source refs;
inspect the effective tools actually exposed in this native generation; reconcile any
mismatch before dependent effects. Report the source/method/context refs actually consumed.
This report is supporting evidence, not independent native Skill attestation.

During execution: keep one bounded objective, run the relevant method and tests, conserve
parent/root identity, checkpoint material source progress and preserve EFFECT_UNKNOWN on
its original carrier. A low-cost worker is not made more useful by a million tokens of
unfiltered history. Retrieve narrowly when needed; keep mandatory constraints intact.

On return: provide artifact/revision, verified behavior, tests and limitations, outstanding
effects, blockers and next action through the existing result contract. The original
parent independently consumes the return. A worker may propose a source-attributed
Agent OS update; the existing knowledge owner decides publication and supersession.

## 7. Memory and compaction policy

Use durable facts, not durable raw thought. Keep (a) project decisions and state in Agent
OS/GitHub; (b) run-local scratch and execution evidence in the assigned artifact directory;
(c) reusable procedures in source-controlled skills. Do not add a writable global memory
folder to every provider home. Do not share private chats, credentials or unrelated
customer/company data across workers merely because a model has a large context window.

Compaction must preserve exact objective, granted scope, important decisions, source refs,
required constraints, unresolved effects, current artifact revisions and next action.
It must mark omitted optional material. Context-window capacity and cheap token prices are
not reasons to omit bounds or to copy the parent transcript. Native/harness compaction is
a separate existing runtime owner; this launch consumer does not implement a new session
or compaction lifecycle.

## 8. Implementation and release slices

A. Census and exact reuse: recover #587/#588, package engine, live tool routes and Agent OS
context behavior. Save immutable refs and actual limitations. No incumbent source takeover.

B. Launch-input consumer: closed schemas; method/compiler reuse; exact source attribution;
required/optional tools; context freshness/budgets; deterministic receipts; explicit no-grant
semantics; malformed/tampered/foreign-scope negatives. Add an operator-facing bootstrap skill.

C. Existing pool integration: use one thin pre-launch method delivery hook. Keep the existing
`sub.sh`/`remote_sub.sh`, host placement, provider leases, native adapter and return handling.
Dry runs remain effect-free; failed/interrupted launches retain their prepared input for
same-carrier reconciliation. Do not disturb running workers or reinstall provider homes.

D. Real cold-start proof: full compiled packet on one enrolled worker uses a real required
tool and project fact to create a useful tested artifact; missing-tool negative performs
no provider launch. Then demonstrate compatibility on a second already-admitted provider
when available. Distinguish supplied method, actual use and native package attestation.

E. Native package profiles: source-review and release #587/#588 through their retained
owners; use existing v4 capability package/effective closure machinery for separate role
profiles. Do not alter the exact four-skill canary. Preserve profile digest and revocation
checks. No source merge or deployment is inferred from a successful attended task.

F. Authenticated app qualification: exact actor/repository/channel/project consent for
GitHub/Slack/Linear, read then bounded write canaries and explicit rollback/receipt. Complete
only through each existing OAuth/app owner. A missing consent is a real gate, not a naming
problem to bypass by creating another app.

G. Operator orchestration acceptance: fresh operator receives current context, decomposes,
launches authorized children with conserved budget, handles failure/review/repair, consumes
returns and reports completion to original parent. Preserve existing nested-identity and
Runtime/Capacity gates; a role playbook is not proof that this is enabled.

## 9. Verification and monitoring

Unit negatives: unknown fields/roles/tools; duplicate keys; malformed JSON; future/stale
observations; foreign mission/workspace; unknown permissions; optional gaps; required
context overflow; credential-like content; changed packet/compiler/method; source symlinks;
no-effect dry run; one invocation/no fallback; preserved original prompt and exit code.

Integration: current Craft golden bytes remain unchanged; all eight roles compile; the
shared reviewed adapter remains the same type; the real pool receives the enriched text;
result/cleanup/lease observations belong to the original launcher. Doctor runs harmless
reads, never dummy writes, and reports unprobed write/child/auth capabilities as unknown.

Live evaluation: measure useful accepted artifacts per original-root budget; startup
rediscovery turns; tool-call success/refusal reasons; context-mismatch errors; first-pass
acceptance; repair cost; missing-input stops; source/skill version coverage. Never optimize
for agent count, context fullness or elapsed runtime. Use existing telemetry/evaluation
owners rather than another watcher or metrics store.

## 11. Concrete delivery additions and coverage limit

The launch CLI now exposes `context` as a one-shot pass-through to the existing Agent OS
`compile-context` reader on the controlling host. It requires a named existing workstream,
preserves exact returned bytes, and retains no-answer/degraded/omitted accounting. It does
not create a remote memory service or silently grant native workers Agent OS access.

A reproducible `mastermind-workforce` plugin artifact is generated from the existing Craft
skill plus Worker Bootstrap without another canonical skill copy. The optional Docs variant
adds only the public OpenAI documentation MCP. Both Codex and Claude manifest layouts are
provided; source admission, native loading and tool authorization remain separate. No
provider, runtime, account or global plugin installation is performed by packaging.

The `pool` hook covers `pool run` and `pool remote` callers only. Direct `ext/sub.sh`,
`lane2.py`, existing queue launchers and Executive adapters are not silently intercepted.
They require their existing owner's explicit integration and exact-source acceptance.
Do not describe this bounded hook as universal fleet adoption.

Provider-specific documentation also matters: Slack's official Skills plugin currently
provides the Slack MCP connection on Claude Code and Cursor, while Codex receives skills
only. Installing a similarly named plugin is therefore not proof of Slack access in Codex.
Source: https://docs.slack.dev/ai/slack-skills-plugin/ (checked 2026-10-06).
