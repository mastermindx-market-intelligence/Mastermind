## 1. Decision in one page

**Productize the working native harnesses through the orchestration system already in Mastermind. Do not build another orchestration platform.**

The primary user job is: give one coherent outcome to Web Sol or Fable and receive reviewed useful work without selecting routine accounts, carrying messages between sessions, repeatedly saying continue, or reconstructing status from Slack.

The machine job is: admit a bounded program, reserve eligible capacity, execute the ready work on qualified native harnesses, preserve exact source/identity/effect boundaries, consume results, conduct independent review and bounded repair, wake the correct parent when judgment is needed, and recover after interruptions.

The differentiated capability is company-aware orchestration: existing organizational decisions and current code, real provider/account/host capacity, constrained tool packages, useful results and exact responsibility continuity, all under one execution authority. A generic multi-agent chat is not this outcome.

The reference experience is a compact principal view such as `5 running / 3 waiting on dependencies / 2 accepted / 1 needs Chairman`, with a useful next action and automatically delivered results. Those are display labels derived from current owners, not a new lifecycle vocabulary or database.

**Three completion levels must remain separate.**

1. **Governed useful loop:** one admitted program, at least two qualified real provider lanes, useful normalized results, independent review/repair where required, and parent consumption visible from the actual user surface.
2. **Orchestration parity:** genuinely overlapping independent work, dependency-aware parking, automatic result-driven continuation, actual skills/MCP/plugin use, and durable recovery without routine Chairman message relay.
3. **Fleet completion:** the committed provider matrix, a second authorized host, quota/identity changes, reconnect/restart and permission-negative journeys proven through that same system.

Level 1 is the first delivery, not a claim that levels 2 and 3 are complete. A native Fable demonstration does not prove Web ChatGPT re-entry.

## 5. Execution and dependency semantics to add to existing owners

### 5.1 A bounded plan, not imperative prose

Reuse the current root/plan/step/result representations. Where they lack the following semantics, introduce a reviewed versioned extension, not a second schema family with duplicate ownership:

- logical step identity; role; bounded objective and acceptance contract;
- prerequisite step IDs and the accepted output/revision each consumer depends on;
- required capabilities and suitable execution class, not raw provider credentials;
- declared source/workspace/write boundaries;
- review requirement, attempt/repair limits and global resource budget;
- exact parent return context authored by the current owner.

Admission validates a closed acyclic dependency graph, same-root references, no self-dependencies, compatible output/input contracts, bounded depth/count, shrink-only grants and write paths, review independence constraints, and worst-case child reservations. A plan is immutable once its effects begin. A material change creates an explicitly admitted revision preserving previous jobs/results; it does not rewrite history or reparent active work.

The first useful loop may use existing v1 semantics. Do not force a broad DAG migration before one real governed result works. The subsequent parity wave must implement true dependency readiness inside the Runtime/COO boundary rather than relying on launch order, sleeps or the principal's narrative.

### 5.2 Ready-frontier execution

For each existing run-once cycle call, reconcile owned outstanding effects, then determine whether a separately eligible queued child can be claimed. An active, healthy worker must not globally prevent dispatch of unrelated ready work onto another qualified worker. Preserve one committed action per cycle invocation if that remains the owner contract; repeated bounded invocations by the existing control-service driver can fill the admitted frontier. Do not add a polling LLM or new scheduler.

**Do not merely move the queued-child block above the active-child block.** That would risk bypassing ambiguous effects, source conflicts or capacity claims. Eligibility must be proven transactionally at claim: dependency revision, role/grant, exact realm/host generation, capacity reservation, source ownership and no applicable unresolved effect. Unknown effects stop the affected operation and any dependent use. Independence of other work is established by existing ownership and reviewed policy, not guessed from a different task title.

One authenticated control owner advances the cycle; duplicate triggers must converge on the existing command identity rather than create a second child or attempt. Apply bounded backpressure when no slot exists. No fallback to an unsuitable or policy-ineligible model.

### 5.3 Review and repair

Keep review as an ordinary read-scoped sibling Job referring to the exact completing attempt and artifact/source revision. A technically successful review can reject the work. Builder self-review is not independent. An accepted review of old bytes cannot approve later edits.

A rejection creates a bounded repair revision through the existing cycle and reserves a subsequent review. A successful aggregation is performed by the existing properly fenced aggregation Attempt, not an attemptless state patch. Parent success requires all mandatory results and qualifying reviews, with actual result consumption recorded.

Ordinary worker policy currently denies push/PR/merge/deploy/service/credential administration. A lane that writes an assigned branch must hand it to the existing authorized publisher/release owner. Do not copy `lane2.py` PR publication into the worker grant to make the journey appear complete.

### 5.4 Depth and child-budget revision

For initial delivery, retain depth 1 and the 16-child v1 envelope. For the full five-worker reference workflow, prepare one explicit versioned policy amendment in the existing authority map/policy loader, with a root-global descendant budget and bounded active frontier. Five fully reviewed logical steps require 46 reserved child records under the current worst-case formula. A proposed pilot ceiling of 64 total descendants would accommodate that example; it is a design proposal, not an active configuration or 64 concurrent processes.

Keep the existing worst-case reservation logic initially rather than replacing it with an optimistic allocator. Native helpers also consume observed resources and declared helper limits. A canonical depth-2 hierarchy, when genuinely necessary, requires the same reviewed amendment and root-global accounting; each child cannot mint another full parent budget. Start with a flat dependency graph because the screenshot does not require recursive managers.

Do not turn a policy amendment into blanket credential, host, merge or deployment authority. Validate the exact selected pilot limits with available host/provider capacity and leave unsupported cases refused.

## 6. Return-to-parent is its own product capability

There are three different receipts:

1. **Worker terminal result:** the original native turn finished and its output/cleanup was qualified.
2. **Delivery:** the existing transport delivered a bounded result notification to the correct current target.
3. **Consumption/adjudication:** that parent read the exact result revision and committed a valid continuation, repair, acceptance or escalation.

Neither a Slack post, `SubagentStop`, an MCP notification, nor a browser focus event proves item 3.

Extend the existing terminal-return projector and Wake owners so the result signal is bound to root/job/attempt/result digest plus the current target binding generation. It carries a small summary and exact source references, not raw transcripts or credentials. The parent fetches authoritative result details and its updated Program Frame before acting. Coalesce simultaneous child completions where the existing attention owner permits, without dropping any owed consumption.

Duplicate notifications are tolerated; accepted transitions must be effectively once through existing command IDs and current-generation fences. Do not claim exactly-once network delivery. If delivery is lost, reconcile the same operation. If the parent changes, use current RuntimeBinding succession; do not send the same modifying input to whichever account responds first.
