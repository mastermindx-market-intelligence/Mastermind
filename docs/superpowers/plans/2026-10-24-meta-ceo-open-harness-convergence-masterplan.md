## 0. Outcome, product job and 10/10 ruler

**Primary user job:** One conversation with a persistent Mastermind Meta-CEO can receive an idea, recover relevant company truth, interpret/correct intent, give a useful strategic answer, autonomously commission *authorized* bounded work, drive existing workers through questions/review/repair, and report a genuinely accepted result without ordinary manual message shuttling. It should initiate meaningful goal-aligned reviews on admitted events and routines, not generate tokens to remain 'busy'.

**Machine job:** DSH (or a later qualified alternate shell) realizes interactive agent-native sessions and a secretary/orchestrator agent; the model may be GLM-5.3, GLM-5.3-Flash or another qualified route. All company work is placed through the **existing** Executive OS, Model Router/Capacity, RuntimeBinding, Wake/Dialogue and Subagent Fabric; Agent OS remains the organizational memory/decision owner.

**10/10 measurable end-state:** A real signed-in Chairman starts and revises an intent in one office; correct current workstream is selected without duplicate creation; an eligible event wakes the same logical responsibility; a worker performs and independently verifies a useful effect through actual authorized paths; the accepted result is consumed by the initiating operation and appears in the same office; a mid-turn client disconnect/restart, quota exhaustion, conflicting update and ambiguous effect do not cause duplicate writes, false success, wrong audience or lost obligations. Owner/credentials, costs and effects are accurately attributed. A tested GLM route is replaceable by a different provider/local model without changing company authority.

**Non-goals this wave:** clone confidential xAI/OpenAI implementations; buy GPUs or subscriptions; switch protected default Sol cognition law; automate prohibited engagement on X or other services; create a new company lifecycle/queue/memory/router; install hosted endpoints or fetch account secrets; displace a *verified active* DSH/ACP/Fabric source writer or unresolved modifying operation; claim experimental UI as a completed autonomous company. An orphaned source area can be recovered through current source-custody procedure without retrieving its former chat.

## 1A. Permanent operating rule: a past session is evidence, not a required owner

**Chairman correction, 2026-10-24:** Don't require the Chairman or the next executing session to rediscover an archived/orphaned 'incumbent owner', its personal login, an old ChatGPT Web tab or Slack conversation in order to begin meaningful project work. Project accountability is a role and canonical source/result contract; a conversation is an expendable execution surface. **A fresh, authorized, appropriately admitted session owns the next recoverable action until an actual current live successor takes it.** This rule is an explicit requirement of the present masterplan and its handoffs; it does not itself override existing protected live-writer/effect-fencing laws.

**Operational playbook on every fresh pickup:**

1. Receive the Chairman's current instruction or an eligible *directly delivered* task in the actual receiver session; record current session/role/operation and the canonical PR/plan pointers. A message found in old history alone is not a receiver-assignment event.
2. Read one **latest** cumulative checkpoint if one exists, plus protected code/procedure and exact related PR HEADs. A name or prior PR authorship is not current runtime ownership.
3. Try one supported bounded read of actual live lease/source writer/pending operation/effects (if accessible). Classify each affected path/effect as **verified occupied**, **verified clear**, or **unknown**—not global 'owner unavailable'.
4. If verified clear, use existing lawful successor admission/current expected-head custody to begin the source work. If verified occupied, preserve that work and own an independent disjoint source/test lane. If unknown, fence only overlapping/effectful operations and continue independent research, hermetic smoke tests, docs or fixture work.
5. **Never wait for an ACK from a dead chat, repeatedly search Slack for the prior owner, or ask the Chairman to find the archived owner.** Escalate only a concrete true permission, live lease, source-write collision, unknown effect, or unavailable external capability, while continuing independent work where possible.
6. Save a concise cumulative GitHub/Agent OS checkpoint, including immutable source pins, completed proof, unresolved effects and exact next executable action. A new ChatGPT session can resume using that artifact without an incumbent chat URL.
7. A mere Slack request to a new session is **DELIVERY_SENT**, not evidence it has run. Require a real `PICKUP_ACK`, separate `START`, and real output/acceptance; return on the exact commission root. Don't claim work started because the Slack bot was tagged.

**Selector:** default `CAPACITY_SELECTABLE` new substantive work to an eligible fresh ChatGPT Web Pro/other capable session; use `EXACT_SESSION_REQUIRED` only when the actual provider conversation itself is the specific target. Request Pro mode only for legitimately qualifying long-horizon frontier judgment with a current-mode entitlement/required receipt; short routing, ACK, status, mechanical code and implementation work use the appropriate non-Pro/Fabric route. **A historical #1717 'owner' cannot force `EXACT_SESSION_REQUIRED` for a brand-new independent project commission.**

**Anti-regression acceptance:** give a new session only this PR/plan and the repository. It must produce a meaningful hermetic DSH/Rakazo artifact or an exact genuine technical obstruction *without a question asking where the old #1717 chat or owner is*. If an active source lease is present, it must preserve that protected modification while completing path-disjoint investigation. A zero-change answer of 'ask old owner' fails this plan.

## 1B. Reliable delegated-session delivery while the Chairman is unavailable

**2026-10-24 transport incident (observations, not a safety-filter reverse engineering claim):** a 3,817-character Slack project commission and a separate detailed GitHub PR comment were rejected with the generic `blocked by OpenAI's safety checks` error. A later approximately 380-character Slack message *successfully delivered* the same high-level request to Grok Secretary: launch an eligible ChatGPT Web Pro project session, use PR #1841, do not hunt an old #1717 chat, and follow existing authorization controls. Therefore **the Pro-session request, GitHub link and old-owner correction are not individually proven to be prohibited**. The exact reason for the two rejections was **not disclosed**; increased message length, packed multi-system instructions, and poorly scoped approval/custody language are confounded hypotheses, not proven keywords.

**Reliability rule for future handoffs:**

1. Put the task specification, legitimate scope, source hashes, edge cases and acceptance tests in the **versioned GitHub plan**. Keep the delivery message short: exact recipient, one actionable requested dispatch, the PR URL, and one return/receipt request. A target under ~500 characters is a clarity guideline, **not** a claimed safety bypass, official rate limit or guaranteed threshold.
2. State the request as conditional on **actual capabilities and existing admission/approval/source-custody controls**. A Slack ping may ask to find a qualified receiver; it must never itself assign bypass privileges, waive reviews or claim that an old lease has expired. The already protected no-orphan rule operates through normal successor and effect reconciliation.
3. Do **not** mix administrative routing, Pro reasoning-mode justification, source ownership recovery, tool grants, developer instructions, metered spending decisions and end-to-end build steps into one large Slack message. The current receiving session reads those details from the lawful canonical sources.
4. Record distinct delivery facts: `DELIVERY_SENT`, real receiver `PICKUP_ACK`, real `START`, and the first verified implementation result. Never infer a launched ChatGPT Web session from an accepted Slack send.
5. On **any tool safety rejection**, record the exact refusal/affected action and do not keep trying alternate connectors or paraphrased delivery to work around that rejection. Continue independent authorized research, CI, source review and test work via permitted established paths; surface a genuine blocked dispatch as unresolved, not as company-wide incapacity.
6. While the Chairman is away, a qualified delegated principal should make ordinary reversible in-scope decisions and handle recoverable delivery failures through existing Executive/Dialogue/Wake owners. Escalate only decisions actually reserved to the Chairman, hard authorization denials or consequential unknown effects. **Do not depend on an abandoned session, a mobile ping or a person locating #1717.**

**Validated short-form dispatch example (for documentation, not a new send):** "Please initiate an eligible ChatGPT Web Pro project session for the Meta-CEO harness from Mastermind PR #1841. Don't require the old #1717 chat. Report true pickup/START or a specific blocker in this thread. Follow existing source and authorization controls."

This is a **failure-prevention and traceability standard**, not knowledge of OpenAI's private safety-filter rules and not evidence that an agent started.
