## 5. Work-in-progress policy

The program minimizes simultaneous critical-path work.

At each gate:

- one carrier owns each logical operation;
- one independently useful vertical is in active implementation;
- one bounded reviewer/repair lane may run against it;
- the next dependent gate may be researched, but not STARTed, until the predecessor contract is accepted;
- existing unrelated company P0 work is not blocked, but it may not consume the Autonomy release/reviewer lane without explicit priority reason.

`one independently useful vertical at a time` applies inside each golden-path edge. Cross-root, path-disjoint company work may still proceed.

`Adjacent work may proceed only when it is path-disjoint`, authority-disjoint, and does not delay the current golden-path merge/proof/canary.

## 6. Anti-churn law

The following do not count as substantive progress:

- ancestry-only branch joins;
- rerunning a full semantic review over byte-identical candidate blobs;
- opening a replacement PR because a branch is behind protected master;
- rewriting PR prose while the real producer/consumer remains disconnected;
- adding a second plan for an already-frozen vertical;
- starting a future generalized platform before the first real consumer works;
- calling a protected source capability live.

`current-base movement alone is not substantive work`.

Use the companion release-compatibility law. Refresh integration proof against the latest protected base; reuse immutable semantic review when allowed; run full re-review only for material change.

Never reset, rebase, force-push, blind-retry, or cross-carrier fail over to accelerate release.

`do not open a replacement carrier` for the same logical operation.
