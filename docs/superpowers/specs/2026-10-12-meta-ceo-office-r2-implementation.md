## Failure, security and recovery requirements

Receiving services resolve authority from trusted current assignments; caller role strings, task IDs and final-answer JSON cannot grant permissions. Cross-channel app, Slack, direct Dot and event-triggered modifying entries must use the same authority rules. If exact concurrent-turn provenance is unavailable, narrow modifying eligibility through the existing owner rather than inventing attestation.

Qualify each participating account's actual connected-app permissions and data audience. A local worker UID and a read-only prompt do not seal cloud-connected write tools. Credentials remain at legitimate owning services and must not appear in prompts, logs, artifacts or browser clients. Existing saved-auth consent does not replace MFA, passkey presence, CAPTCHA or new provider consent.

Duplicate or out-of-order callbacks must not duplicate rulings or overwrite later accepted revisions. Subscription expiry and missing events must preserve durable obligations under existing Wake reconciliation. A changed requirement invalidates affected work while retaining unaffected accepted evidence.

Timeout after provider acceptance must inspect the original task. A child admitted before a lost Dot answer must reconcile the original provider task and Executive command. Cancellation must preserve a completion race. A relieved principal must not acquire current write authority; predecessor effects stay recoverable. Explicit permission refusals are not eligible for another-account or alternate-carrier workarounds.

Rollback disables new admission for the affected route while retaining original task/effect IDs, results and unconsumed obligations. Stopping a provider or uninstalling a client does not prove a child stopped. Administrative pause and recovery must remain available without a responsive Dot.
