Extend the existing `ExecutionCapabilityRegistry` so it can represent and verify one immutable company-owned, Skills-only source-package generation and compile its exact effective Skill closures into the already-existing Operator Harness `CapabilityIdentity.skill_content_digest` field.

## 6. V4 package-source grant

Conceptual closed form:

```json
{
  "mastermind-operator.p1": {
    "kind": "skills-only-source",
    "repository": "mastermindx-market-intelligence/Mastermind",
    "source_commit": "12c2cb8993f78e81c6cb9e9a75a9829f9b194dab",
    "source_tree_sha": "783ae81b44e9606baf13e2402a75a2130df9758a",
    "package_root": "plugins/mastermind-operator",
    "manifest_path": ".codex-plugin/plugin.json",
    "generation": "mastermind-operator.p1.2026-09-01",
    "source_state": "SOURCE_PROTECTED",
    "revoked": false,
    "package_content_digest": "a82a274a82ed84c6e82a1c34b67c1f2f0a70cc465c26d0fcf64f648ac295cf16",
    "files": {},
    "skills": {},
    "required_app_references": []
  }
}
```

### 6.1 Package grant semantics

- `kind="skills-only-source"` is the only V4 kind.
- Top-level package presence does not enable or install a provider plugin.
- `revoked=true` makes every contained Skill unavailable for newly resolved profiles.
- `source_state` is closed to `SOURCE_PROTECTED` in V4.
- `repository`, `source_commit` and `source_tree_sha` are provenance.
- `package_content_digest` and exact file rows are behavior/source content identity.
- `manifest_path` must name one listed regular file.
- `required_app_references` must be empty in V4.
- Credentials, OAuth identifiers, provider sessions, host paths and Business workspace IDs are forbidden.

### 6.2 File row

Each exact file row contains:

```json
{
  "relative_path": "skills/receive-commission/SKILL.md",
  "sha256": "212f...",
  "byte_length": 1695,
  "executable": false
}
```

Bounds:

```text
1-64 files
1 MiB maximum per file
8 MiB maximum package bytes
UTF-8/POSIX normalized relative paths
no NUL, dot segments, absolute paths or case-fold collisions
```

### 6.3 Skill grant

Each package-local Skill grant contains:

```json
{
  "runtime_name": "receive-commission",
  "entrypoint_path": "skills/receive-commission/SKILL.md",
  "closure_paths": [
    "references/dialogue-boundary.md",
    "skills/receive-commission/SKILL.md"
  ],
  "skill_content_digest": "d795..."
}
```

Rules:

- capability ID is the enclosing key;
- runtime names are unique across the complete registry;
- entrypoint path is present in closure paths and exact package inventory;
- every closure path is present in package inventory;
- closure paths are sorted, unique and package-relative;
- expected digest is recomputed from exact package rows using `mastermind.effective_skill_closure/v1`;
- source generation and package grant digest remain linked to the Skill grant digest;
- natural-language reference crawling and model-declared closure membership are forbidden.

## 7. Local source verification

SCF-PKG1 adds a pure package verifier under the existing registry owner. It consumes:

```text
one v4 package grant + one explicit source_root
```

and returns one immutable verified grant or a typed `CapabilityPolicyError`.

### 7.1 Default and fixture roots

- default `source_root` is the exact repository/release root containing the capability policy module;
- tests may pass an explicit fixture root;
- callers/models cannot supply a source root through Job constraints or provider requests;
- source root is composition configuration, not profile authority.

### 7.2 Filesystem law

Verification must:

1. reject a symlink source root or package root;
2. reject symlinks in every package-root path component and descendant;
3. reject hardlinked files (`st_nlink != 1`) for the accepted source projection;
4. reject devices, FIFOs, sockets and non-regular files;
5. enumerate the complete package tree and require exact file-set equality;
6. reject missing and extra files;
7. require exact byte length, SHA-256 and executable bit;
8. reject case-fold collisions and duplicate normalized paths;
9. enforce count and byte bounds before unbounded reads;
10. recompute package-content and every closure digest;
11. never read credentials, provider homes or environment secrets;
12. never mutate source files.

Git object IDs are useful provenance but are not the runtime filesystem verifier. The exact SHA-256 inventory is the portable content proof.

### 7.3 Current protected descendant behavior

Unrelated protected-master movement does not mint a new package generation. A later release may consume the same package generation only when local package verification still matches every accepted row. Any material package movement requires a new explicit generation and profile/policy review.

### 8.1 Profile Skill input

In v4, `profiles.<id>.skills` contains Skill capability IDs, not runtime names.

The loader resolves every ID exactly once. Unknown, duplicate, revoked or ambiguous IDs refuse.

### 8.2 Required capability names


### 8.3 OHF manifest

`capability_manifest(harness_binary_digest=...)` compiles each Skill grant into the existing identity:

```python
CapabilityIdentity(
    name=grant.runtime_name,
    kind="skill",
    harness_binary_digest=harness_binary_digest,
    skill_content_digest=grant.skill_content_digest,
)
```

No new OHF identity class is permitted.

### 8.4 Digest law

- package content digest binds only canonical file rows;
- package grant digest binds provenance, generation, source/revocation state, content digest, exact Skill grant digests and app-reference inventory;
- Skill grant digest binds capability ID, runtime name, entrypoint, closure mapping, closure digest and package grant identity;
- profile digest binds exact Skill capability IDs and Skill grant digests;
- policy digest binds actual schema version, package grant digests and profile digests.

For SCF-PKG1 fixture proof:

- changing one package byte changes package, Skill-when-in-closure, profile and policy digests;
- changing an unrelated package file changes package/profile/policy provenance while leaving unaffected closure digest stable;
- revocation changes grant/policy identity and refuses resolution;
- current v3 default policy/profile digests stay byte-identical.

## 11. Revocation and correction behavior

### 11.1 Source correction

A package source change creates a new generation. Do not mutate the historical generation's file rows or digest to make a newer tree appear identical.

### 11.2 Revocation

- `revoked=true` refuses new profile resolution and new Attempt sealing;
- a pre-turn Attempt revalidating against current policy refuses;
- an already-running Attempt is not silently killed by source parsing; emergency termination requires existing Executive/OHF authority and a separately reviewed response;
- no provider/host failover follows ambiguous termination.

### 11.3 Duplicate generation

Same package capability ID + same exact normalized payload is the same generation. Same ID + changed payload is a policy conflict/refusal, not a silent replacement.

### 11.4 Missing source

Missing, unreadable or unverifiable source is not `revoked=false` or “temporarily unavailable but allowed.” Registry load/profile resolution fails closed.

### 11.5 Policy migration

When CAP-S1 moves the default policy to v4, the policy digest rotates. Existing installed readiness/arm receipts remain historical and must fail current validation until a fresh exact-release requalification. No code path may auto-refresh or rewrite those receipts.
