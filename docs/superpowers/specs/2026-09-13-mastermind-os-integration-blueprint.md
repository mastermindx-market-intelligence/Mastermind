## 1. Feasibility and the actual product

The proposed product is implementable: a unified place to direct the company, read and address its permitted conversations, understand its projects and current execution, inspect why work is waiting, follow evidence and intervene within accepted authority. It is substantially more than a showcase frontend. Its value is that the same outcome can be followed across the existing systems without the user carrying context between them.

It should not be implemented as one replacement scheduler, universal agent runtime, omnipotent API or copied database containing the entire company. The right integration is **one coherent product over explicit existing owners, connected by exact references and finite operations**.

The product is complete only when two different journeys work:

- **Human journey:** direction -> readable CEO conversation -> exact project/work -> full available operator conversation -> relevant dependency, route and evidence -> an appropriately addressed message or decision -> actual receipt and useful outcome.
- **Machine journey:** approved intent -> admitted work -> qualified execution -> reliable return -> accountable parent consumption -> the next permitted useful action -> evidence and learning, even while every viewer is closed.

The user interface must not be the machine that keeps this second journey alive. Conversely, a backend that runs work but cannot give Chris an intelligible, addressable view has not delivered the product.

## 3. The topology needs engineering once, not an AI caretaker forever

There are three different activities that should never be conflated.

**Reasoning:** interpret an outcome, choose a useful decomposition, identify a previously unknown dependency, decide whether an answer is sufficient, or propose a better next move. The accountable CEO, principal or specialist does this within its scope.

**Recording and enforcement:** validate the proposal, derive trusted identity, bind it to its parent, reserve capacity, constrain effects, record the current Attempt and session generation, and preserve the outcome. Existing deterministic owners do this.

**Presentation:** join those exact references, show source-qualified state, draw the appropriate relationship, group conversations and restore the view after reconnect. Deterministic projection and ordinary application code do this.

A planner can propose “implement the API contract.” It does not manually label every future screen. When the owner admits that step, it records its parent/root and scope. When a worker is claimed, that same work acquires a current Attempt. When the provider is materialized, the qualified binding identifies the exact session. The UI renders those facts, so the child appears without any separate diagram-writing action.

### Relationship origins

| Relationship shown | Where it must originate | Deterministic consequence |
|---|---|---|
| Strategic outcome contains a project | Accepted strategy/membership owner, read back from its projection | Program navigation groups the exact project |
| Project represents a workstream | Existing Agent OS -> Linear mapping owner | Open either surface without title matching |
| A selected issue represents a work packet | Existing selective Issue/operation binding owner | Link portfolio work to its admitted execution; do not create an issue per token or helper |
| Root has a child | Executive admission with immutable lineage | Add a parent-child view edge |
| Job has current execution | Existing atomic claim/current-attempt owner | Associate the exact Attempt and Worker |
| Execution has a conversation | SessionTarget/RuntimeBinding and qualified provider observation | Open that permitted conversation, not the newest similar tab |
| Participant consults a colleague | Authenticated consultation operation on its accepted carrier | Show sender, recipient and correlated question/answer |
| Work waits on an accepted artifact revision | Existing dependency owner accepting a structured prerequisite | Display the wait; enable dependent work only under the same owner |
| Worker returns and parent consumes | Result/Dialogue/Wake/consumption owners | Show return first and consumption separately |
| Candidate is reviewed or deployed | Existing exact artifact/review/release owner | Attach applicable proof, without translating CI into acceptance |

There is no second write of a “graph node” required alongside these business operations. A disposable view map may be cached, but its authority comes from the owners. If the cache is lost, the UI can reconstruct from available snapshots/history without replaying commands.

This is automatic for **managed, instrumented paths**. It is not magic discovery of relationships never recorded. Legacy tabs, ungoverned processes and missing joins remain observed/unjoined. A one-time qualified association or enrollment can be needed; continuing managed work should not need repetitive human or AI annotation.

### Who wires it

The incumbent Fable integration program owns the runtime/provider/communication composition it already accepted. Its bounded specialists implement the owning seams. The Live/CCR producer-consumer implementation supplies authenticated views and conversation interaction over those seams. The existing portfolio-projector owner supplies Linear joins and change projection. Sol owns the shared acceptance contracts and cross-program adjudication.

This is a finite set of adapter and contract tasks. It is not a standing job called “figure out the topology.” Adding a provider or evolving a protocol requires compatibility work, just as adding a new data connector does. A model's output is not sufficient evidence that the connector works.

## 4. One connected information model, several different graphs

A single visual tree cannot faithfully represent the company. The shared product needs several related views of the same records.

1. **Capability and outcome map:** what the company is trying to deliver, which capability unlocks which job, and what evidence establishes its state. This lives in accepted strategy, workstream, architecture and evidence records, not a new scored feature database.
2. **Portfolio structure:** existing Initiatives, Projects, selected Issues and their explicit organizational joins. Preserve the actual accepted membership policy; do not assume every API-supported many-to-many relationship is admitted company structure.
3. **Execution containment:** admitted roots, children, Attempts, Workers and native helpers. A helper and an independently admitted Job are different entities.
4. **Execution prerequisites:** accepted, versioned conditions that govern readiness. This is not every link in the portfolio or every sentence saying “blocked.”
5. **Conversation and consultation:** messages, replies, turns, deliveries and consumption. Cycles are normal; they need not be execution cycles.
6. **Authority and attention:** who is accountable, which current target may act, and what obligation actually awaits that target or Chris.
7. **Evidence and resources:** artifacts, reviews, deployments, observed capabilities, host placement and measured resource facts.

These are conceptual lenses, not seven new databases or seven mandatory top-level screens. They share exact source references. A shared prerequisite can be displayed in two projects without duplicating the underlying work, source cost or authority. Display aliases cannot become new canonical identities.

### What a complete relationship contract must answer

For every new join, the owning implementation must specify: source system and type; accepted endpoint identity; relevant revision/generation; exact predicate; scope and field visibility; construction rule; correction/removal behavior; source coverage; whether it is recorded or merely observed; and whether it has any execution consequence.

These are review questions for each existing-owner adapter, not a newly mandated universal wire envelope. Reuse existing schemas and extend them narrowly when a necessary field is absent. A header containing a trace ID is diagnostic correlation, not authentication, job admission or proof of an accepted dependency.

A trace tree can help explain low-level tool calls. It cannot replace company authority or prove that a parent accepted a child's result. OpenTelemetry's context propagation and span links are useful diagnostic patterns for asynchronous work, not another lifecycle model.

## 8. The useful graph is a versioned graph of conditions, not a wall of arrows

The target must support parallel work and shared prerequisites through the existing orchestration owner. Current protected COO source still enforces a narrow depth-one model; the target expansion is not installed by this document.

The planner proposes dependencies using semantic work/artifact references. The owner validates scope, version, admission, acyclicity where required, child and review reservations, and effect ownership. A declared dependency becomes an execution gate only after that owner's acceptance. Consultation links and portfolio associations never automatically become scheduler barriers.

For an ordinary ALL-prerequisite step, readiness conceptually requires: current admitted plan; every required accepted artifact revision available; no unresolved invalidating correction; a current authority envelope; eligible reserved capacity; and no conflicting or uncertain effect. A returned artifact that has not met the required review is not ready merely because its author says it is.

ANY or quorum prerequisites require an explicit future owner contract: which results are selected, how conflicting candidates are resolved, how unused work is stopped or retained and how deterministic reconstruction works. They must not be improvised in the frontend or inferred from arrival order. Start with the actually supported, reviewed dependency model.

### Corrections and shared work

If accepted API artifact v1 is corrected to v2, retain what happened under v1. The owner determines which pending dependents require revalidation and whether an already-running child must be stopped, repaired or allowed to finish with a superseded result. Do not silently rewrite historical edges or accept a v1 result as a v2 result because the filenames match.

Shared dependencies point to the same accepted produced artifact. They do not create a multi-parent execution Job by cloning it into each consuming project. Costs stay with the actual work/approved allocation owner rather than being counted once per visual appearance.

Changes to an executing plan are separate accepted revisions. Removing a node from the current design does not erase an admitted child or cancel its external effects. Regenerating a conversation reply is a new potential operation, not a reversible text edit when the original turn used tools.

### Deadlocks and resource ceilings

Two participants may ask one another questions; that conversation cycle is legitimate. They should not both synchronously retain the only resource needed to answer. The current coordinator must distinguish inference capacity from parked conversation state and from source custody. It may release only safely releasable capacity, never a write fence just because a model is waiting.

Bound total child records, simultaneous execution, repair/review rounds, consultation turns, fanout and cost. A hierarchy that looks deep in a drawing does not escape the same limits through invisible provider helpers. Current policy's nine reserved slots per reviewed step explains why two such steps exceed a sixteen-child ceiling. The existing owner must change that whole contract deliberately before broader governed concurrency is claimed.

## 9. Conversation-first does not mean conversation-authoritative

The normal experience is a readable chat application: the CEO office, project orchestrators and permitted worker conversations; full available history; expandable communicated plans/tools; inline work and evidence; exact-recipient messaging; optional paired conversations and context.

The main distinctions belong in the model and in concise UI explanations, not a compliance badge beside every sentence. Users should not have to interpret schema names or process IDs to read a response. But selecting evidence must recover those exact references.

The first rich provider-content task must extend the existing receive/controller path. The previously inspected `AppServerClient._read_stdout` already receives frames continuously; the later rich-adapter projection waits for completion and excludes normal response content. A second stdout reader or a GUI draining the controller's notification list would be the wrong repair.

Required proof: withhold terminal completion, emit a safe response item through the real managed lane, show it to the spectator, then deliver the terminal event to the original controller exactly once. A slow spectator must not block control or return processing. History must be read without starting/resuming another session. Content released before its exact turn/Attempt binding is established must be withheld rather than guessed.

The UI uses available user-visible responses, communicated plans, qualified summaries and tool evidence. It never reconstructs private hidden reasoning. A provider that supplies only completion-level child messages is shown at that capability level; the product does not masquerade parent tokens as a child's live response.

### Chat delivery is an effect-bearing workflow

The composer distinguishes a durable office from an exact session. Office-addressed delivery resolves the current accepted office implementation and records where the message actually went. An exact-session draft remains attached to its original target; a changed target requires an explicit decision before sending.

Normal in-scope messaging can be immediate in presentation: pending locally, accepted by the owner, then actual delivery/consumption and response. Checks need not become repetitive confirmation dialogs. Consequential new scope, privilege, spend or interruption invokes the appropriate existing approval, not a generic click-through for every sentence.

The backend must enforce both request-key handling and semantic single-consumption where relevant. Two clients can generate different keys for the same obligation. Lost acknowledgement after possible dispatch remains an uncertain original operation; neither refresh nor switching from web to Mac resubmits it.

Reading or marking a conversation read is a viewer preference. It is never a parent's authoritative consumption of a worker result. Pausing visual updates does not pause agents. Opening a comparison does not forward one participant's transcript to the other.

## 10. Workspace Agents and always-on supervision

Always-on supervision has a deterministic foundation: persist admitted work and unresolved obligations, detect a relevant source change or overdue condition under existing policy, route attention to a qualified current responsibility, and retain the result until consumed. No reasoning model must remain continuously generating to keep these records alive.

A Workspace Agent can add bounded judgment: inspect one responsibility, assess an exception, review an artifact or propose the next step. It is a replaceable reasoning client alongside native supervisor and supported Web routes, not the layer through which every other agent must pass.

The current official trigger API provides triggering, idempotency and run-status observation, but does not retrieve the agent's answer. Current #607 is a bounded status observer, not the missing authenticated candidate-return and parent-consumption mechanism. The handoff and #603 already put that missing return at the existing result/attention owners. Preserve that placement.

A provider run reaching completed cannot close a company obligation. A candidate callback can arrive before provider terminal status; keep both facts. No trusted actor or run association may be established from agent-authored IDs alone. A late callback after revocation is evidence to reconcile, not authorization to act on a successor responsibility.

Do not turn monitoring into infinite inference or message loops. Batch/coalesce unchanged observations, preserve all material obligations, and use bounded judgment when it can improve an outcome. Silence can indicate unavailable observation, not necessarily a dead agent. Semantic lack of progress may need a bounded diagnostic decision, not an automatic kill based only on elapsed time.

For unavailable supervisors, recovery stays with existing continuity/effect owners. Verify old-writer fencing at actual sinks before transfer. An expired lease alone cannot stop a process with direct filesystem access. Known no-effect/pre-start work may be placed lawfully; uncertain dispatched work may not be invisibly failed over. Useful disjoint work can continue while one effect is reconciled.

## 11. Read path, action path and background progress are separate

**Read path:** authenticated scope -> owner-qualified snapshot -> exact relations and source coverage -> UI projection. Selected conversation content is subscribed separately from portfolio metadata. Not every token causes an Agent OS/GitHub/Linear refresh.

**Action path:** expressed intent -> actual principal/grant/preimage checks -> owner-persisted intent and admission -> one qualified effect path -> reconciled receipt. An action never executes merely because a graph item exists or a read returned an action hint.

**Background progress:** existing Runtime/COO/Dialogue/Wake service sees accepted work or a return -> performs eligible deterministic transitions or wakes the exact qualified reasoning target -> records the outcome and next obligation. This is independent of viewers and does not require a new universal workflow engine.

Publication is atomic only within each owning boundary. The company is not one cross-SaaS transaction. Carry source-specific revisions, history coverage, identity generations and correction status. A current transport heartbeat cannot refresh an old source value. A late response from an old user/session/selected scope cannot replace the current view.

Caches and view indexes are rebuildable and scope-separated. If durable retention is required for actual business evidence, place it with the declared existing evidence/content owner. Do not put raw histories into Agent OS, a new graph database and a UI cache and then call three copies organizational memory.

## 12. Authentication, security and privacy are connection design

Visibility, ability to message, ability to delegate, source writing, resource placement and acceptance are different capabilities. The user may be allowed to inspect a whole project while a worker can inspect only one artifact. A graph must not leak restricted object names, IDs or counts through hidden-node placeholders.

Each finite API validates its principal, resource, scope, target revision and data contract. A trusted network route is not user identity. A trace/span ID or native session identifier is not a grant. A message from a more privileged peer cannot launder a denied operation through that peer.

Content is untrusted: repository text, issue comments, chat, tool output, web research and artifacts do not become instructions merely by appearing in the CEO workspace. Isolate rich previews, constrain links and terminal escape behavior, redact before serialization and preserve original provenance. Native IPC is not granted to embedded remote content.

A provider's arbitrary text cannot be made reliably safe by renaming a field `redacted`. Use scoped allowlists and an accepted content policy. Split streaming secrets need streaming-safe filtering or completion-time release. Credentials, cookies, provider homes and environment dumps stay out of UI records, source documents and traces.

The unified product may reuse a sign-in experience, but it cannot flatten backend resource scopes. The Executive five-tool app is not a file reader, generic transcript service, peer-message gateway or administrative terminal. New useful resources are separately reviewed extensions through their owning authentication/application contracts.

## 13. Hosting, Mac access and survival when clients disappear

The intended product has a hosted web surface and a Mac client using the same permitted APIs. A traveling MacBook can inspect and communicate without being the controller machine.

Initial deployment can put web assets and a finite authenticated gateway on the existing VPS, connected through the approved private transport to the current canonical services. Existing Runtime authority and provider credentials remain with their owners. Public network processes receive bounded projections and commands, not direct database or worker-lease access.

There is one logical authoritative execution owner. That does not require every component to be a single process; it forbids two independent writable runtimes claiming the same work. A future controller relocation or high-availability arrangement needs explicit replication, leader/fence, restart and cutover proof. Publishing a website does not perform that migration.

A sleeping client does not stop remote work. A sleeping worker host can stop its native tasks; the UI must say so. Portable new tasks can use an already-qualified always-on worker through Capacity. Do not migrate an uncertain in-flight effect or copy authenticated browser/provider homes merely to simulate mobility.

A private tailnet-only surface and an internet-accessible authenticated website are different access products. Choose and prove the supported mode. An outbound tunnel is not authentication. The Mac app's fixed, narrow local bridge is optional; its origin, WebView, signing, token handling and update behavior have separate proof requirements. Neither app updates nor reconnects can restart the company, rewrite its database or replay queued provider instructions.

## 17. The reference journey that will prove the system is woven together

Use one approved, useful integration task rather than a fleet-wide demo. The scenario should have an exact existing workstream and selected project/work packet, two qualified participants and a source-backed question that matters to completing an artifact.

4. A produces the useful artifact. Existing independent review and accepted revision rules govern any dependent integration work.

## 18. Acceptance questions and architectural limits

Before expanding the next implementation slice, answer these concrete questions:

- Does every displayed authoritative relationship have an exact owning source, without fuzzy-name joins?
- Can a managed child appear automatically when admitted, and remain honestly unbound before provider materialization?
- Does the actual stream show safe nonterminal content, not a final summary relabeled live?
- Can a worker consult another without privileged-peer laundering, a new execution cycle or a synchronous capacity deadlock?
- Is the selected dependency satisfied by an accepted applicable revision, not merely an answer or completed provider run?
- Can a human read the full available thread and message the intended office/session without context moving silently?
- Do project and runtime disagreement remain visible without a competing synchronizer?
- Does the parent consume and continue with the UI closed? Does recovery fence the old effect owner?
- Can an external client authenticate and operate within its real scopes without database copying or an unrestricted host proxy?
- Does the outcome improve useful completion and reduce Chairman relay/approval burden?

These are required acceptance questions, not tests claimed executed here. Reuse the existing 72-case campaign and incumbent fabric cases; attach the cross-system cases to their actual owner rather than creating another assurance authority.

Feasibility does not imply universal provider access. Some surfaces lack full history, safe mid-turn input, remote cancellation or unattended re-entry. The honest product can expose a qualified subset while retaining those parity gates. It cannot infer unavailable content, bypass platform restrictions or call an unproved surface fully autonomous.

A complete high-level contract should precede a principal handoff; a mythical perfect design for every future provider should not prevent a small end-to-end proof. The missing seams, their owners and their falsifiers must be explicit enough that implementation is bounded. This blueprint is intended to reach that boundary, not make the active build wait for another months-long redesign.
