## 1. Decision and intended outcome

Adopt a reuse-first execution strategy, not the DeepSeek application as Mastermind OS. Preserve native Codex and native Claude as direct execution backends. Add an opt-in, isolated DeepSeek Harness worker only where it supplies a useful generic tool-using runtime. Reuse the existing capability-policy, immutable package, worker-adapter, supervisor, result, status-projection, and organizational-continuity owners. Deliver useful tools on the existing native path independently of the donor qualification. A working native capability package must not wait for a new harness, and the current interactive CEO launch must not wait for this project.

The user outcome is that an admitted worker can perform a real assigned task with the required repository, browser, research, and company tools; the original parent receives attributable results; the OS shows what is actually usable and why a required capability is unavailable. The engineering outcome is less bespoke protocol code without losing permissions, accounting, cancellation, source custody, or recovery. Installing a framework, listing tools, passing fixtures, and returning a model's claim of tool use are not that outcome.

## 2. Preserve the existing architecture

Executive OS continues to own Job/Attempt/Worker lifecycle, admission, claim, reservations, cancellation, and recovery. Provider Control and existing Capacity/Model Router own provider facts, eligibility, route/account selection, and resource accounting. Agent OS in Macro remains the durable organizational knowledge plane. GitHub remains implementation and evidence; Slack/Relay/Wake remain transport and attention. The DSH process is a subordinate execution engine for one existing Attempt, not an alternative company runtime. Its transcript, request queues, timers, and internal session identifiers are execution artifacts, not a replacement organizational memory or placement system.

Use `control_plane/worker_adapter.py::WorkerExecutionAdapter` as the insertion boundary. Its existing methods are `start(spec) -> WorkerProcessRef`, `status(ref) -> WorkerRunStatus`, `collect_result(ref) -> CollectionReceipt`, `cancel(ref, reason) -> CancelReceipt`, and `run_validation_argv(spec, argv, timeout_seconds=...) -> ValidationReceipt`. Optional `reattach(spec, binding)` belongs to the existing recoverable interface. Do not add a new Job database, application command queue, quota ledger, retry supervisor, credential store, capability registry, or session/watcher service. Do not broaden neutral `WorkerLaunchSpec` into an arbitrary provider configuration or credential carrier.

The current source already includes `executive_capability_packages.py` for immutable source-package identities and local verification, with `executive_agent_capabilities.py` as its sole policy consumer. It also includes `sol_capability_status.py`, a pure projection with `CapabilityFact`, `CapabilityStatus`, proof state, required/current scopes, dependencies, and read/write serviceability. Extend those owners. In particular, do not build the proposed UI availability model as a second status database or free-form collection of frontend booleans.

## 3. What the donor does — and does not — establish

The official donor is a Cordis/Node plugin composition with a provider-neutral agent loop, MCP bridge, multi-provider adapter, SDK transport, and optional native-product providers. Its README calls it a rapidly changing developer preview; its safety notice explicitly says it has not undergone a security audit and is not production-ready. The inspected SDK package metadata says `0.1.7-rc.2`; that string alone does not identify the complete executable dependency closure. The MIT repository license does not establish transferable rights for every optional product binary. Record and review the exact dependency closure and notices before distribution.

The SDK is not a drop-in interactive CEO/session backend. Its protocol has `initialize`, `session/prompt`, and `shutdown`; `session/prompt` returns a durable enqueue message ID. High-level `run()` collects from that message's inbox receipt until whole-agent idle and returns the last committed root-session assistant response. It is explicitly not a response causally assigned to one prompt when steering or other queued work is present. The wire has no mid-turn cancel or session-close method; abandoning a turn means closing its runtime. Its version field is not a validated protocol negotiation. Therefore R1 uses one runtime, one fresh session, one submitted task, and no other input producers per Mastermind Attempt. Never substitute this SDK for the current interactive root launch/message/reopen work.

The native-product donor providers are optional, one-shot integrations, not fleet integration. They create fresh non-resumable product conversations and do not inherit the parent transcript. They pin their own Codex/Claude SDK and CLI payloads rather than selecting our already-qualified native installations. The Claude provider intentionally reads native user/project/local settings. Do not import these packages into R1. Preserve our direct native worker adapters; mine their documented protocol and cleanup tests as reference evidence only. Do not redistribute optional proprietary payloads on the assumption that upstream's distribution authorization automatically extends to us.

## 4. Reuse choices and rejected alternatives

**Preferred composition:** the existing `integrations/acp_worker/adapter.py::AcpWorkerAdapter` and `AcpNativeProcessOwner` own the fixed DSH ACP process and common collection/cancellation path. Recover and integrate #825's two common-owner amendments: private provider/model selector encoding and cancellation-time frame admission. Extend the existing bounded DSH fixture/profile into a useful read-only journey after pre-prompt, tool-lifecycle and host-isolation requirements are met. Do not implement another Worker adapter or process owner. #825's native tests used donor `0d1f50007f9bca3f52b06e1c3074fa14d5fb0720`; this packet inspected `21638c56315ae6a2b552d6091945d3144c9af32e`. Those pins are not interchangeable proof. Select one actual qualified artifact; a later donor upgrade requires its own relevant compatibility evidence.

**Fallback, not commissioned:** a public TypeScript SDK runner remains an alternative only if a concrete required behavior cannot be delivered by the existing ACP owners. The fallback must retire or replace the same execution role rather than coexist as another DSH process/result/cancellation implementation. No listening service or new daemon is needed for the preferred path.

**Why not an unmodified Python SDK inside Executive:** its inspected `HarnessClient.start()` copies `os.environ` and merges overrides; passing `env={}` does not create an empty environment. It directly spawns a process and keeps the handle private. A separately scrubbed Python runner could make it usable, but importing it into the control process adds another dependency/ownership problem without improving the first slice. The TypeScript client's public options explicitly replace the child environment when an object is supplied and expose initialization/shutdown/disposal bounds. Use that documented interface, not private SDK fields. This is an integration choice, not a claim that the Python SDK is inherently unsafe.

**Why not whole-app adoption:** it brings account/settings management, plugin installation, UI, sessions, teams/jobs, and background mechanisms we already own or must deliberately constrain. **Why not copy the whole tool stack into Python:** Cordis dependencies and lifecycle assumptions would become our maintenance burden. **Why not build a fresh MCP client:** the donor or official MCP SDK should supply transport/framing; only Mastermind-specific admission and receipt translation warrant new code. A later standalone extraction is justified only by a measured dependency or maintenance advantage that retires existing code.

## 5. R1 execution and process contract

`AcpWorkerAdapter` is the existing implementation to reuse; `DshWorkerAdapter` and `control_plane/dsh_worker.py` are no longer proposed deliverables. Its trusted native resource factory owns the immutable executable/profile binding and common `WorkerProcessRef`. The useful-tool extension must preserve current spec, workspace, exact base, identity, deadline, cancellation and result checks. Add only the missing pre-prompt attestation/tool evidence to those owners. No authenticated provider request is allowed during readiness unless the current admitted task explicitly authorizes it. SDK-specific option names in the following historical observations are not the ACP API and must not be copied into its profile blindly.

The SDK enqueue/whole-agent-idle limitations in section 3 apply to that high-level SDK, not to all DSH transports. #825's actual ACP fixture exercises request-correlated prompt completion and cancellation through the existing process owner. Keep one owned runtime/session/task per initial Attempt for containment, but do not reimplement or discard the ACP cancellation/collection mechanisms on the basis of an unrelated SDK limitation.

The runner accepts one bounded host-authored request artifact in the existing run directory. It contains the already-selected route/model/effort, workspace, one task, session correlation, and non-secret grant references; it is not a second command bus. The existing provider owner supplies the exact credential/endpoint through an approved private mechanism. Neither model output nor the artifact chooses accounts, installs packages, changes authentication, enables fallback, or selects a second provider. The adapter must reject unsupported launch requirements rather than silently downgrade them.

Create one fresh private DSH home per Attempt and one fresh session identifier mechanically bound to that Attempt. Do not use a developer's `~/.dsh`, `.claude`, `.codex`, ambient cloud identity, or mutable global package tree. Keep the executable profile/package closure immutable and writable session artifacts separately scoped. Set `dshHome`, `processCwd`, workspace `cwd`, exact `dshBin`, route/model, and a complete child environment explicitly. The runner's own environment must also be positively allowlisted. DSH's `.env` loading means environment scrubbing alone is insufficient: runtime startup must occur in a private directory without an inherited project/home `.env`; the agent workspace is passed separately, and an executable test must prove project `.env` cannot affect launch or routing.

The outer existing supervisor deadline is authoritative. Derive initialization, request, tool, and disposal bounds from its remaining budget; do not copy the minimal profile's 48-hour stream-idle setting or rely on an SDK default unbounded turn. Preserve enough reserved time for cleanup and result collection. There is no new fixed universal runtime limit in this design. A timeout at the SDK call boundary is not remote cancellation. Close the same owned runtime, observe the entire owned tree through the common process inspector/cleanup mechanism, and preserve uncertainty when termination or a tool's external effect cannot be established.

A signal sent, a root PID exiting, an empty SDK response, and a clean process-tree census prove different things. The SDK's own cleanup is cooperative first-line cleanup, not a substitute for the host's existing PID/start-identity/boot/session/UID fences. Test surviving descendants and PID reuse. Recovery may collect or reattach only the exact surviving owned execution supported by the common recovery binding. It must never call `session/prompt` again to reconstruct a missing result. A fresh DSH session is a new execution, not recovery of a lost one.

## 6. Profile and plugin closure

Use `sdk-minimal` only as a composition reference. As shipped it contains unrestricted persistent shell access, model-request retry, JSONL sessions, MCP resource support, and local job services. The README's exclusion of job tools is not evidence that no internal job service exists. A safe profile must be compiled from a reviewed explicit allowlist and verified from both its configured closure and actual ready capabilities. A dump of configured rows is not readiness: app-boot can skip a bundle or leave an optional plugin inactive, and `--dump-config` can still display a denied plugin row.

The preferred initial profile enables the fixed ACP endpoint, one root agent/loop, required prompt/session/value services, selected LLM transport, explicitly granted tools, the Mastermind grant guard, bounded diagnostics, and attempt-local transcript output. MCP and its separate resource/instruction controls enter only when that bridge is actually enabled; the public SDK endpoint is not an additional control path. Retain internal support services only when the tested dependency graph requires them. R1 exposes no shell, file-write tool, arbitrary code runner/PTC, plugin manager, authorization UI, memory MCP, remote configuration, HMR, webhook, native-product subagent, team/taskboard, model-selected provider switch, or background-job tool. Do not remove a dependency such as `jobs-local` blindly; prove that no model-facing or independently scheduled execution becomes possible through retained support services.

All profile files, includes, package manifests, resolution roots, compatibility exemptions, and ordered patches enter the immutable runtime closure. No project-supplied `!!js`, home patch, compatibility exception, skipped required bundle, or profile-local package replacement may silently alter the executable composition. Any exception is an explicit source/profile change reviewed under the same owner. Record exact runtime artifact digests, not merely package versions or the SDK handshake's `0.0.1` version string. Build/install once through the existing approved artifact/release owner; do not run `npx latest` or an install command during a job.

The in-process guard is not a sandbox against arbitrary hostile plugin code. Only the reviewed immutable plugin closure may load; filesystem, process, credential, and network containment must be enforced by the existing host isolation boundary. The registration-replacement tests validate the supported tool interface, not immunity to arbitrary code execution inside the runtime.

## 7. Portable capabilities and the MCP admission seam

Define a capability once in the existing policy/package owner and compile it into backend-specific mechanisms. Logical parity means that an admitted task can perform its required operations within the same restrictions; it does not mean every backend has the same implementation or is eligible for every job. Start with read-only repository/context access and an already-owned browser/research service. Native Codex's established MCP/browser profile is the baseline. Native Claude additions belong to its incumbent adapter/profile owner and must be additive reviewed profiles, not a global removal of its sealed-worker prohibitions. This packet grants no source custody over those files.

DSH's MCP namespace is derived from local `serverName` and raw tool name; its public name may be normalized/truncated with a hash. Never recover wire identity by splitting a displayed name. Bind the approved server's actual endpoint/transport/auth realm, reviewed server identity/version, raw tool identities, complete input/output schema digests, semantic package/profile identity, and any approved instructions/resources. Successful MCP negotiation, `readOnlyHint`, or discovery alone grants nothing. A genuinely dangerous server cannot be made safe by trusting its annotations; least-privilege credentials and server-side enforcement remain necessary.

The inspected `mcp-client/src/tools.ts::syncTools()` creates definitions for every discovered tool and replaces generations automatically. There is no existing Mastermind admission callback in `ToolBridgeOptions`. The smallest justified donor delta is an optional, trusted pre-registration generation-admission seam at that exact boundary, called on initial discovery and every resync/reconnect before any new definition is exposed. It must validate the full discovered generation, select only the approved subset, and return immutable admitted bindings for execution-time checks. Default upstream behavior can remain unchanged when the optional seam is absent; our profile requires it. The implementation belongs in a tiny maintained/upstreamable donor patch, not a second MCP proxy or registry.

Generation refusal must also make the prior generation non-executable when its current server/schema/authorization can no longer be proven; retaining stale listed definitions is not continuing permission. The execution closure must hold and recheck the admitted binding immediately before `client.callTool`. Tie the guard to the exact definition and server generation, not just its public name. A malicious later plugin must not replace an allowed name and inherit permission. Retained per-connection generation state is transport state within the existing client; it is not a new company capability database.

Use DSH's documented `ctx.tools.guard(guard)` monotonic synchronous execution-guard mechanism for the final all-tools check, not a reorderable approval/pre-execution hook. Reject ungranted own-scope tools as well as inherited tools; scoped visibility restrictions alone can exempt own-scope registrations. Keep PTC disabled in R1. Schema filtering reduces exposure and token cost, while the execution guard enforces authority even against a directly submitted tool call. Test both layers independently.

`server-context.ts::registerServerContext()` automatically registers resources and inserts server instructions into the system-prompt section. R1 disables resource discovery/read unless explicitly included in the existing grant. Instructions must be empty or match reviewed bounded content and remain attributed reference material, never authority to widen the grant. A companion admission check at this same client-owned connection boundary must precede publication of instructions/resources. Do not assume the tool allowlist controls these other surfaces. Test changed instructions on reconnect and direct resource access separately from tool-list changes.

## 8. Retry, authentication, and effects

Keep account selection, refresh, reservations, and provider policy with existing owners. The pi-ai adapter can otherwise discover ambient credentials and supports a separate stored-login system; neither is permitted in R1. Configure exactly one admitted route/model for the Attempt and prove the request reaches that endpoint with the intended credential mechanism. A provider-compatible API is not a subscription entitlement, and native developer subscriptions are not automatically eligible for this harness or customer workloads. No new paid provider or metered budget is authorized here.

Disable donor model-request recovery in R1 by omitting/disabling the `dsh-llm-retry` executor in the effective composition and proving actual request counts. Do not rely solely on an unverified `maxRetries: 0` field. Also qualify transport-library retries and redirects with a counting endpoint. A later bounded retry policy may be accepted only as a delegated mechanism under the existing owner with explicit error classes, budget, accounting, and effect semantics. Model request retry, MCP connection retry, tool execution retry, and Executive Attempt retry are different operations; connection re-establishment must never replay a potentially executed tool call.

Treat an absent return after tool dispatch, cancellation after dispatch, MCP `isError`, output-schema rejection after the server acted, postprocessing failure, and transport loss as separate observations. None proves no side effect. First qualification permits read-only tools, but the implementation must retain dispatch/result provenance so later write-capable qualification cannot collapse these outcomes. Use the existing supervisor/runtime's accepted uncertain-effect semantics; do not add an `EFFECT_UNKNOWN` enum to `WorkerRunStatus` merely for convenience or mark an uncertain operation safely retryable because a Node process exited.

## 9. Result, usage, and acceptance translation

Translate into the existing `WorkerResult` and `CollectionReceipt`: exact job/run/worker identity, terminal process facts, structured output, validated artifact manifest, Git manifest, usage, provider-session identity, start/end times, and bounded error. DSH prose is untrusted task output. A nonempty final response or SDK idle is not success. Require the intended root session's accepted input receipt, terminal turn reason, schema-valid task output, correct identities, required tool evidence and artifacts, and required process cleanup. Root versus descendant events must never be confused. `max-tokens`, error, cancelled, malformed/no terminal event, and empty output cannot become ordinary success.

On the preferred ACP path, retain `AcpReadOnlyTurn` / `AcpWorkerAdapter._collection` and native completion evidence. Current protected source already checks exact identities/model, stop reason, schema, forbidden artifacts, Git HEAD/status plus complete changed paths, and settled process evidence before returning `CollectionReceipt`. Add missing useful-tool evidence there, not a parallel result translator. The high-level TypeScript `RunResult`/root `turn/end` analysis is fallback-only; it is not the ACP return contract. Reject foreign sessions, duplicate/extra inputs, oversized frames and inconsistent ordering under the current owners. An Executive MCP bounded preview is not the full canonical result: parent consumption must use the existing complete result/artifact contract. DSH transcripts remain supplementary evidence, not a new queue/store.

Usage is evidence from actual provider/runtime counters with provider/model/source units, cache categories, and known/unknown cost. Preserve requested identity separately from served identity; absent served identity stays unknown. Per-request output caps do not cap total task spend, input/context size, compaction, retries, or descendants. The existing reservation and budget owner must constrain the complete Attempt. The private runtime binding carries that owner’s admitted limits and reference; local enforcement counters are subordinate per-Attempt checks, not a new quota ledger. Stop before an additional request when the admitted bound cannot be satisfied, including auxiliary title/compaction requests. Do not sum incompatible subscription percentages, tokens, requests, or money into a fictitious common pool. A reused credential or shared entitlement cannot create additional capacity through a second harness.

## 12. Acceptance, rollout, rollback, and stop criteria

The accompanying machine-readable matrix contains proposed cases with `NOT_RUN` execution status. Hermetic tests must run the exact donor runtime and actual MCP/tool path against a loopback deterministic model, not merely mock the adapter. Assert positive tool use and negative denied effects. No provider keys, developer logins, production services, or production writes are needed for this first proof. An installed runtime alone proves neither the common-adapter path nor production acceptance.

The first live task is a bounded Mastermind OS build-readiness diagnosis on an incumbent-approved source snapshot and devserver: identify the actual launch/result/capability producer-consumer boundary, cite source evidence, and return a browser artifact when browser access is granted. It must add a useful current finding or confirm a specifically named integration boundary; it is not another generic architecture audit. The exact task/output schema and devserver identity come from the current app owner before admission. The native and DSH routes use equivalent input and authority, not privileged exceptions to make the canary pass. A second admitted provider proves portable behavior only for those tested routes, not the entire catalog.

Source release requires current-owner acceptance under the Chairman's current review direction, required hosted checks and current-base compatibility. A separate reviewer is not a new waiting gate where the Chairman has explicitly waived it. Production acceptance additionally requires runtime artifact verification, admitted worker execution and actual original-parent consumption. Measure accepted result quality, successful required tool use, denied forbidden operations, end-to-end latency, actual usage/cost, cleanup, and maintenance delta. Compare with the native baseline without presuming DSH is cheaper or better. Pause or reject adoption when the maintained donor patch spreads into a parallel lifecycle/account/capability system, when required restrictions cannot be enforced, or when the representative job has no useful advantage. Keep the portable native capability work even if this donor fails.

Rollback excludes the DSH route/profile from new placement through the existing owner, drains or reconciles existing Attempts without killing unrelated workers, retains their evidence, and returns the UI to the exact supported availability. Never switch an uncertain in-flight operation to another harness. Native routes remain unchanged and available to eligible new work. A code rollback is not reconciliation of external tool effects.
