## 4. Identity model

A physical Mac is not a Worker, provider account or session. Keep these identities separate:

```text
Executive Job / Attempt
  -> Executive Worker
      -> execution profile / capabilities
      -> provider realm + harness binding
      -> provider economic capacity identity
      -> opaque host_ref + boot/resource generation
      -> optional RuntimeBinding/native session
      -> optional exclusive resource realm (GUI/browser/computer-use)
```
One paid subscription may expose several host-bound execution candidates while still consuming one Provider Control capacity pool. Conversely, one Mac may expose several independent provider realms. `account_label`, browser seat, host path, hostname, machine number and array position never mint economic capacity identity.

## 5. Four independent capacity dimensions

Every placement resolves four different questions in order:

1. **Reasoning capacity:** which model classes are inside the first lawful quality tier for this mission?
2. **Economic capacity:** among equivalent-quality choices, which current subscription/API capacity should be consumed given headroom, reset horizon, reserve and marginal cost?
3. **Realm capacity:** which concrete reviewed Worker/provider/harness realm can accept the Attempt now?
4. **Physical capacity:** which host can safely admit the qualified workload while preserving protected reserves and required exclusive resources?

These dimensions must remain separately sourced. A cheap provider never repairs inadequate reasoning quality. A free host never creates provider quota. A provider account cannot make an overloaded host schedulable. A duplicate host binding cannot multiply one weekly entitlement.

## 14. Cordon, drain and dead-host semantics

`CORDON` is an admission fact owned by the existing Capacity/host policy path: new candidates on that host are excluded. It does not cancel existing Attempts.

`DRAIN` composes cordon with current Executive lifecycle. It waits for existing Attempts to become safely terminal or reach an explicitly accepted checkpoint/cancel state. There is no generic force-evict semantic for ambiguous model/provider work.

```text
safe no-effect / terminal -> release reservation and finish
checkpoint-safe           -> use accepted continuation/rebind law
EFFECT_UNKNOWN            -> DRAIN_BLOCKED / reconcile same operation
non-migratable running    -> wait or explicitly stop under current authority
```

If a host disappears, each Attempt is adjudicated independently. New Jobs exclude the host once current capacity evidence makes it ineligible. Pre-effect work may rebind only after no-effect proof; ambiguous work remains sticky and blocks duplicate execution elsewhere.
## 15. Time, freshness, null and correction behavior

All placement inputs are point-in-time evidence. Every load-bearing dynamic fact must carry an owner, generation/identity and freshness state suitable for claim-time revalidation. Provider reset horizons remain Provider Control facts; host boot/resource generations remain host/Capacity facts; occupancy and current Attempt/Worker bindings remain Executive/RuntimeBinding facts.

Null or unreadable load-bearing evidence is never translated to an optimistic default. Examples:

- unknown quota/headroom -> candidate not economically/admission-authoritative;
- unknown host pressure/boot identity -> candidate not physically admissible;
- absent exact-session binding when reuse is required -> no fresh-session substitution;

Corrections are appended/superseded through the owning system. Fleet projections must expose disagreements and stale generations; they must not rewrite Executive, Provider Control or host evidence to make a dashboard green.
