### 6.3 Run validity and outcome states

```text
VALID_PASS
VALID_FAIL
VALID_PARTIAL
INVALID_CONFIGURATION
INVALID_LEAKAGE
INVALID_EFFECT_UNKNOWN
INVALID_CLEANUP
DEGRADED_DEPENDENCY
UNSCORED
```

Validity and outcome are distinct. An invalid run is visible and excluded from valid-pass denominators; it is never silently converted to a failure or pass. `DEGRADED_DEPENDENCY` is valid only when the scenario explicitly allows degraded execution and the degraded state is itself attested; otherwise the run is invalid configuration.

## 7. Canonical contracts

The first implementation wave must provide closed schemas, pure validation, canonical serialization, deterministic digests, and create-only identity without requiring Inspect, Promptfoo, a service, a database, or a model call.

### 7.1 Canonical byte law

For all V1 contracts:

- input is UTF-8 JSON;
- all object schemas are closed;
- unknown fields fail validation;
- numbers are finite; NaN and infinity are forbidden;
- timestamps are RFC 3339 UTC with `Z` and no leap-second acceptance;
- strings used in identifiers are ASCII from explicit patterns;
- free-text strings are valid Unicode and are normalized to NFC before construction;
- canonical bytes use Python-equivalent `json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False).encode("utf-8")` after validation and normalization;
- digests use lower-case `sha256:<64 hex>` over canonical bytes;
- an implementation must never normalize or coerce an already accepted object during verification; it reconstructs canonical bytes and compares the supplied digest.

If an existing protected canonical serializer proves stricter and reusable during EVAL-R0 archaeology, EVAL-R0 may adopt it only by an explicit compatibility test and a source-law amendment. It may not silently change these bytes.

## 8. Identity, time, correction, null, and storage law

### 8.1 Identity

- Scenario identity is family + stable case slug + explicit version.
- Experiment identity groups intentionally comparable arms.
- Run identity is unique and create-only.
- Provider-native process/session identities remain owner-native and appear only as non-secret fingerprints.
- Executive Job/Attempt/Worker/Event IDs remain Executive identities and are referenced, never copied or redefined.
- GitHub refs use repository + object type + immutable SHA or PR/review identifier with observed head.

### 8.2 Time

- `started_at <= completed_at <= created_at` for a finalized receipt.
- `monotonic_duration_ms` is the authoritative duration measurement within one process; wall-clock fields support joins and audit.
- Scenario `temporal_cutoff` defines the latest knowledge allowed to the evaluated agent.
- Source visibility is frozen by immutable refs, not by current branch names.
- A future timestamp or source beyond the cutoff invalidates the run.
- Historical replay and post-hoc comprehension are distinct phases; post-solution sources invalidate a claimed replay.

### 8.3 Null and unknown

Unknown values are explicit `null` only where the closed schema permits them. A missing cost, trace, token count, provider usage, or native session fingerprint never becomes zero. A required unknown invalidates the relevant comparison or lowers evidence grade; it is not imputed by a model.

### 8.4 Correction

- Scenario changes create new versions.
- Run receipts are immutable.
- Scorer changes append scorer passes.
- Analysis changes create new analysis artifacts.
- An evidence reference may be superseded but not erased.
- Corrupt or privacy-violating artifacts are quarantined with a tombstone/reference record; they are not silently rewritten.
- A later production contradiction remains visible and is routed to Outcome Learning or the owning system; it does not rewrite the original offline result.

### 8.5 Storage

V1 uses immutable artifacts under an approved private evidence root plus public-safe repository schemas, fixtures, and sanitized receipts. A preferred private layout is:

```text
private-eval-root/
  scenarios/<family>/<scenario-id>/<version>/scenario.json
  experiments/<experiment-id>/manifest.json
  experiments/<experiment-id>/runs/<run-id>/
    receipt.json
    private-output.*
    private-events.*
    trace-ref.json
    scorer-passes/<pass-id>.json
  projections/
    valid-run-summary.parquet
    configuration-frontier.parquet
```

Writes are create-only and atomic: create a temporary file on the same filesystem, flush, fsync, rename without overwrite, fsync the directory, then read back and verify the digest. A local index may be derived for speed but must be rebuildable. No SQLite/Postgres/ClickHouse/vector store becomes canonical experiment truth in V1.

## 9. Execution architecture

### 9.1 Native contract and validity core — first

### 9.2 OHF exact-run adapter — first real runner

- fresh isolated workspace;
- fresh App Server process/private process group;
- exactly one new thread start and no resume/fork;
- exact immutable Skillpack bytes from the declared Git commit;
- exact requested and served model;
- exact capability profile and observed tool schemas;

### 9.3 Inspect adapter — subordinate and later

Inspect is a strong orchestration candidate because it provides tasks, datasets, solvers/agents, tools, sandboxes, parallel evaluation, scorers, detailed logs, retries, checkpoints, control surfaces, and analysis APIs. It is not the V1 canonical core.

EVAL-I1 may adopt a pinned Inspect package only after supply-chain admission and a production-inert spike proves:

- exact version and artifact hashes;
- Mastermind scenario/run IDs remain canonical;
- a Mastermind capability profile is attested independently of Inspect configuration;
- provider-side `web_search`, `web_fetch`, `code_execution`, and remote MCP are withheld unless the scenario explicitly grants them;
- in-process agent bridges are not treated as sandboxed;
- checkpoint/resume is disabled for fresh-start task classes;
- Inspect control-channel cancellation cannot become Executive Job cancellation;
- raw model API logging, image/media retention, sharing, and remote storage are configured according to scenario privacy;
- Inspect logs are referenced evidence, never the sole receipt or policy truth;
- framework schema upgrades cannot silently reinterpret old runs.

### 9.4 Promptfoo adapter — public-safe adversarial complement

Promptfoo may later generate/execute bounded attacks for retrieved-authority injection, memory poisoning, excessive agency, tool discovery/widening, source attribution, RBAC, shell/SSRF, repository prompt injection, network-egress bypass, credential reads, verifier sabotage, and delayed-CI exfiltration.

EVAL-A1 requirements:

- exact pinned version/hash and dependency admission;
- telemetry disabled;
- sharing disabled;
- deny-egress runtime with explicit provider allowlist;
- synthetic or explicitly `PUBLIC_SAFE` inputs only for remote-generation plugins;
- no raw private repositories, chats, credentials, transcripts, or evidence sent to hosted generation endpoints;
- generated attacks imported through the Mastermind scenario contract and reviewed before execution;
- deterministic Mastermind scorers remain authoritative for company invariants;
- Promptfoo pass/fail is one evidence input, never a safety or release authority.

### 9.5 Langfuse — held for V1

Langfuse is not installed in V1. Its experiment/tracing UI could become useful at high volume, but another service, retention policy, migration surface, access-control plane, and experiment schema are not justified before the native receipt/OHF/analysis vertical proves value. Reconsider only when:

1. valid experiment volume makes local artifact analysis materially inadequate;
2. private retention, backup, deletion and role access are solved;
3. exact self-hosted version compatibility is proven;
4. all data is a rebuildable projection from canonical receipts;
5. a measured user-workflow improvement exceeds operational cost.

### 9.6 Derived analysis

Parquet plus DuckDB is the preferred later analysis substrate because it can remain local and rebuildable. It owns no lifecycle, identity, acceptance, score truth, or policy. EVAL-M1 must prove paired calculations and invalid-sample denominator behavior against fixed fixtures before it reads real receipts.

## 10. Corpus governance and first scenario families

### 10.1 Sources

The corpus deliberately combines:

1. Synthetic authority/security invariants.
2. Historical replay using only sources available at the original cutoff.
3. Mutation-generated cases from known defects.
4. Completed Mastermind tasks converted into replayable cases.
5. Prospective shadow tasks sealed before the production answer exists.
6. Adverse runtime/fault-injection scenarios.
7. Human-composed product tasks where usefulness requires rubric review.

### 10.2 Leakage controls

Every replay scenario must:

- pin allowed repository refs at the temporal cutoff;
- hide final solution branches, PRs, commits, reviews, outcomes, and post-cutoff Agent OS records;
- record every source exposed to the agent;
- detect known answer strings and solution identifiers in context;
- prohibit unrestricted current web/GitHub search unless that is the capability under test;
- keep private holdout families inaccessible to builders;
- separate scenario author, implementation owner, and final evaluator where risk warrants;
- invalidate unauthorized source/tool access rather than merely subtract points.

### 10.3 Initial representative families

The first governed corpus should contain 15–30 cases across at least these families:

1. `COLD_START_CANONICAL_OWNER` — identify current owner/source/capability/disagreement/next action.

3. `EFFECT_UNKNOWN_HANDLING` — reconcile same operation and refuse blind retry/failover.
4. `NO_DUPLICATE_CONTROL_PLANE` — subordinate an external framework instead of creating a lifecycle/memory/router.
5. `PROVIDER_FAILURE_RECONCILIATION` — distinguish pre-effect retry-safe failure from post-dispatch uncertainty.
6. `PR_REVIEW_MISSED_CONSUMER` — catch an unmodified broken consumer despite green local tests.
7. `CXI_CURRENT_SOURCE` — reject stale indexed context and open current source.
8. `CODEINTEL_IMPACT_RECALL` — compare consumer/reference discovery with and without CodeIntel.

## 11. Scoring and comparison

### 11.1 Deterministic scorers first

Initial scorers should test:

- required source opened before action;
- source SHA/currentness/cutoff match;
- forbidden source/tool/capability absent;
- exact owner and operation identity preserved;
- no duplicate Job, branch, PR, workstream, lifecycle, memory or router;
- no blind retry/failover under effect uncertainty;
- exact changed-path fence;
- tests and mutation kills;
- expected output schema and invariant coverage;
- citations/evidence references;
- cleanup proof;
- served-model and tool-census attestation;
- secret-shape and privacy exclusions;
- product consumer and real proof when required.

Each scorer emits exact reason codes and evidence references. A boolean pass without reasons is insufficient.

### 11.2 Statistical analysis

Repeated experiments report:

- valid pass/partial/fail counts;
- invalid and degraded counts by reason;
- paired differences where arms share cases;
- confidence intervals or exact intervals appropriate to sample size;
- resource distributions and tail latency;
- repair/rework probability;
- disagreement and variance by task family/risk tier;
- missingness and nonindependence.

No claim such as “7% better” is permitted from unmatched case mixes or an underpowered sample without uncertainty and limitations.

### 11.3 Model graders

Model grading is permitted only for dimensions not adequately captured deterministically. A valid model-grade pass records exact grader model/version, rubric digest, candidate-order blinding where possible, grader output/evidence, disagreement, and independence. Same-model self-grading cannot be the sole evidence for a load-bearing conclusion.

### 11.4 Human review

Sol/human review is reserved for architecture coherence, product usefulness, leakage adjudication, grader calibration, ambiguous failures, and promotion decisions. The system optimizes scarce judgment; it does not pretend subjective product quality can always be reduced to deterministic code.

## 12. Failure-state behavior

Every failure preserves evidence and avoids fabricating a clean result.

| Failure | Required behavior |
|---|---|
| Scenario/schema invalid | Refuse before execution; emit no run receipt except a bounded validation artifact |
| Corpus/source cutoff unavailable | Refuse or mark invalid configuration; do not substitute current sources |
| Solution leakage | `INVALID_LEAKAGE`; preserve offending source reference |
| Provider/model mismatch | `INVALID_CONFIGURATION`; no approximate-equivalence claim |
| Tool/capability drift | `INVALID_CONFIGURATION`; list unexpected schema digests |
| Unexpected network/provider-side access | `INVALID_CONFIGURATION` or `INVALID_LEAKAGE` according to source effect |
| Sandbox unavailable | Refuse; do not silently run on host |
| Timeout before any effect | Preserve partial events; new run only under scenario retry law |
| Timeout after possible effect | `INVALID_EFFECT_UNKNOWN`; reconcile same native operation before any rerun |
| Cleanup uncertainty | `INVALID_CLEANUP`; no process/workspace reuse |
| Provider rate limit | `DEGRADED_DEPENDENCY` only if scenario permits; otherwise invalid configuration |
| Scorer crash | Run remains unscored; append repaired scorer pass later |
| Grader disagreement | Report disagreement; no consensus fabrication |
| Grader prompt injection | Quarantine grader pass; deterministic evidence remains intact |
| Missing trace | Explicit null/degradation; validity follows scenario requirement |
| Corrupt artifact | Quarantine and mark insufficient/invalid; never rewrite receipt |
| Duplicate run ID with same digest | Idempotent import/no-op |
| Duplicate run ID with changed payload | Hard conflict and stop |
| Private evidence unavailable | `INSUFFICIENT_EVIDENCE`; no public surrogate |
| Too few samples | `INSUFFICIENT_EVIDENCE`; no promotion-grade inference |
| Nonindependent comparison | Report limitation and evidence grade |
| Cost data unknown | Keep null; no zero-cost claim |
| Retrospective/prospective ambiguity | Default to retrospective and block forward-learning claim |
| Offline result contradicts production | Preserve both; route to owning learning/decision process |
| Framework upgrade/schema drift | New configuration/version; no silent cross-version pooling |
| Evaluation service unavailable | Native receipt/OHF path remains operable; no lifecycle failover |
