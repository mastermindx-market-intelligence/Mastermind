Mastermind needs a reproducible evidence fabric that answers:

> For a precisely defined task class, which exact model, provider, execution surface, procedure, context, retrieval behavior, tool-capability profile, review topology, and environment satisfies the required outcome on the best defensible quality–resource frontier?

The selected composition is:

```text
Mastermind-native scenario, experiment, run-validity, scorer-pass,
```

Mastermind owns the closed contracts, canonical bytes, immutable identities, deterministic technical-validity law, append-only scorer-pass history, evidence references, privacy boundary, and no-authority rule.

OHF owns fresh App Server process/workspace/thread mechanics. Inspect AI may later orchestrate batches and produce framework-native logs under a subordinate adapter. The decisive ownership law is:

> **Agent Evaluation produces reproducible technical evidence. Outcome Learning adjudicates organizational consequence and policy change.**

### 1.1 Architecture-review correction

The first draft incorrectly allowed a runner-asserted `PASS` to be fused with technical validity, placed future scorer references inside an immutable run, omitted exact experiment-arm/pair identity, and failed to preserve all validity inputs needed for independent recomputation.

Those designs are rejected.

The binding V1 law is:

1. A runner reports execution observations, never accepted task correctness.
2. The immutable run receipt contains raw bounded observations and a deterministic technical-validity decision only.
3. Every validity decision is recomputable from the scenario plus the run receipt; no unstored `RunFacts` side input exists.
4. Scorer passes are separate append-only artifacts referencing the immutable run.
5. A scored result such as `VALID_PASS` is a derived projection over one technically valid run and the exact required scorer passes—not a field asserted by the runner.
6. A run participating in an experiment binds exact arm, configuration, pair key, and replicate identity.
7. Canonical IDs are mapped to filesystem-safe path segments by schema-aware parsing; raw colon-bearing IDs are never used as path components.

## 2. Product thesis and jobs

### 2.1 First useful product

The first product is not a leaderboard or dashboard. It is a complete evidence journey:

```text
versioned scenario
-> frozen experiment/configuration arm
-> closed run draft from one runner
-> deterministic finalization
-> immutable technical run receipt
-> append-only deterministic scorer pass
-> comparison-ready sanitized evidence reference
```

A reviewer can inspect why a run was valid, invalid, degraded, scored, unscored, or incomparable and can reproduce the decision without chat history or a narrative claim.

### 2.2 Chairman job

The Chairman should be able to ask:

- Are Mastermind agents actually improving?
- Which tools and procedures repay their complexity?
- Which lower-scarcity routes safely match stronger routes for a defined task class?
- Where do failures cluster and can one be reproduced?
- Which finding is retrospective, replayed, prospectively shadowed, canaried, or promoted?
- What uncertainty and invalid evidence remain?
- Which current owner has authority to act?

The answer must be concise at the top, non-scalar where dimensions conflict, and auditable beneath it.

### 2.3 CEO Sol job

Sol defines scenario families, freezes source visibility, detects leakage, compares exact configurations, inspects failures, decides whether evidence is decision-grade, commissions bounded repairs, and hands accepted evidence to the correct owner without creating a self-modifying executive.

### 2.4 Platform-owner job

A component owner needs the exact scenario, configuration, output/event digests, source/tool/network observations, validity reasons, scorer versions, trace/artifact refs, reproduction command, and paired comparator—not merely a score.

### 2.5 Independent-auditor job

An auditor attacks benchmark leakage, hidden solution access, tool widening, requested/served model mismatch, nonindependent grading, cherry-picked tasks, invalid denominator handling, privacy leakage, cleanup uncertainty, effect uncertainty, missing samples, and causal overclaiming.

### 2.6 Value model

**User value:** fewer wrong-owner conclusions, incomplete products, missed consumers, stale-source errors, repeated repair waves, and manual Chairman archaeology.

**Machine value:** stable evidence for improving procedures, retrieval, capability profiles, review topology, model tiers, and tooling.

**Research value:** point-in-time comparisons, uncertainty, failure clusters, prospective falsification, and exact counterevidence.

**Commercial value:** lower marginal cognition cost and faster delivery without silently trading away correctness, authority safety, privacy, or product quality.

**Data moat:** a private correction-safe corpus of Mastermind task configurations, failures, and forward outcomes that survives model/framework replacement.

### 2.7 10/10 end state

A complete system can:

1. Select a versioned Mastermind task class and risk tier.
2. Freeze a corpus and hidden holdout family with exact temporal/source boundaries.
3. Bind every comparator arm to an immutable configuration reference and digest.
4. Execute candidate configurations with exact requested/served model, capability, environment, procedure, context, network, source, effect, and cleanup evidence.
5. Recompute technical validity from stored evidence.
6. Append deterministic, statistical, model-generated, and human scorer passes without rewriting runs.
7. Reproduce valid failures and invalidate contaminated runs.
8. Compare paired arms with sample size, uncertainty, invalid/degraded rates, tails, and resource use.
9. Show a quality–cost–scarcity frontier without a universal “best model” score.
10. Emit bounded technical evidence references for Outcome Learning, Router, CXI, CodeIntel, Skillpack, Professional Practice, and other owners.
11. Run prospective shadow/canary comparisons only after the owning policy program authorizes them.
12. Demonstrate at least one accepted forward improvement with no hidden authority, privacy, correctness, or product regression.

Initial families include executive cold start, architecture recovery, authority adjudication, cross-repository collision, bounded implementation, debugging, PR review, product design, research synthesis, handoff execution, dialogue continuation, effect reconciliation, tool use, retrieval, security adversarial, and production diagnosis.

Each binds risk tier, expected output contract, source/authority behavior, capabilities, invalidation conditions, and required scoring dimensions.

### 5.2 Outcome dimensions remain separate

1. Correctness.
2. Authority safety.
3. Current-source compliance.
4. Completeness.
5. No-rebuild compliance.
6. Evidence quality.
7. Efficiency/resource use.
8. Operational fluency.
9. Implementation quality.
10. Robustness.
11. Product usefulness.
12. Reviewability/reproducibility.

No universal weighted aggregate may originate routing, release, merge, policy, or acceptance. Use hard gates and a visible Pareto frontier.

### 5.3 Three different states

V1 never collapses these concepts:

**Execution completion** describes what the runner process did:

```text
COMPLETED | FAILED | PARTIAL | TIMED_OUT | CANCELLED
```

**Technical validity** describes whether the run is admissible evidence under the frozen scenario:

```text
VALID
INVALID_CONFIGURATION
INVALID_LEAKAGE
INVALID_EFFECT_UNKNOWN
INVALID_CLEANUP
DEGRADED_DEPENDENCY
```

**Scored result projection** is derived later from technical validity plus exact required scorer passes:

```text
VALID_PASS
VALID_FAIL
VALID_PARTIAL
UNSCORED
INVALID_CONFIGURATION
INVALID_LEAKAGE
INVALID_EFFECT_UNKNOWN
INVALID_CLEANUP
DEGRADED_DEPENDENCY
```

`INSUFFICIENT_EVIDENCE` is an evidence-set grade, not a runner outcome.

An invalid run remains visible and is excluded from valid denominators. Its process completion and raw evidence remain preserved. A runner cannot label its own answer `VALID_PASS`.

## 6. Canonical byte and identity law

### 6.1 Canonical JSON

For all V1 canonical artifacts:

- input is UTF-8 JSON;
- objects and nested objects are closed;
- unknown fields fail;
- accepted primitives are only `null`, boolean, signed 64-bit integer, NFC string, array, and object;
- floats, tuples, non-string keys, NaN, infinity, and silent coercion are forbidden;
- timestamps are exact whole-second RFC 3339 UTC: `YYYY-MM-DDTHH:MM:SSZ`;
- identifiers are ASCII and match explicit patterns;
- decimal measurements such as money/confidence are canonical decimal strings, never binary floats;
- arrays representing sets are sorted and unique;
- canonical bytes are equivalent to `json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False).encode("utf-8")` after strict type validation;
- a document digest is lower-case `sha256:<64 hex>` over the canonical object with its own digest field omitted;
- verification never normalizes/coerces an accepted object; it reconstructs bytes and compares.

A stricter protected house serializer may replace this only after explicit byte-for-byte compatibility tests and a source-law amendment.

### 6.2 IDs

```text
scenario:<family-slug>:<case-slug>
experiment:<uuid4>
run:<uuid4>
scorer-pass:<uuid4>
evidence-ref:<uuid4>
```

UUIDs are canonical lower-case UUID4. Re-running creates a new run ID. Same ID + identical canonical bytes is idempotent import. Same ID + changed bytes is a hard conflict.

### 7.3 Run draft

A runner adapter produces a closed in-memory/on-disk draft consumed only by the finalizer. The draft is not a canonical stored artifact and cannot be imported as truth.

It has the same fields as the run receipt except `validity`, `created_at`, and `run_digest`. It includes every raw input needed to derive validity:

- exact scenario and experiment/configuration identity;
- requested/served model;
- observed tool schemas/capabilities;
- observed source refs;
- observed network destinations;
- freshness/resume observations;
- effect state;
- cleanup state/proof;
- dependency degradations;
- execution completion;
- evidence/resource/timing fields.

The finalizer validates the scenario and experiment, validates the draft, derives validity, inserts the validity object, adds creation time/digest, validates the final run, and only then permits create-only storage.

No parallel unstored `RunFacts`, model judgment, or runner pass/fail label is accepted.

### 7.5 Deterministic validity

The finalizer derives all reasons from the scenario, optional experiment, and draft fields. At minimum:

```text
MODEL_SERVED_MISMATCH
TOOL_SCHEMA_DRIFT
UNEXPECTED_CAPABILITY
UNAUTHORIZED_SOURCE
HIDDEN_SOLUTION_SOURCE
UNEXPECTED_NETWORK_DESTINATION
FRESH_PROCESS_UNPROVEN
FRESH_WORKSPACE_UNPROVEN
FRESH_SESSION_UNPROVEN
RESUME_FORBIDDEN
NETWORK_POLICY_MISMATCH
DEGRADATION_NOT_ALLOWED
CLEANUP_UNPROVEN
EFFECT_UNKNOWN
EXPERIMENT_ARM_MISMATCH
PAIR_IDENTITY_MISSING
CONFIGURATION_MISMATCH
TEMPORAL_CUTOFF_MISMATCH
```

Precedence is:

```text
EFFECT_UNKNOWN
-> INVALID_EFFECT_UNKNOWN

else unauthorized/hidden source
-> INVALID_LEAKAGE

else cleanup required and not proven
-> INVALID_CLEANUP

else configuration/freshness/tool/network/arm/cutoff mismatch
-> INVALID_CONFIGURATION

else non-empty allowed degradations
-> DEGRADED_DEPENDENCY

else
-> VALID
```

The final run validator recomputes validity and requires exact equality with the stored status and reasons. A forged or stale validity object fails verification.

### 7.6 Scorer pass — `mastermind.agent_evaluation_scorer_pass.v1`

A scorer pass binds:

- `scorer_pass_id`;
- exact run ref/digest;
- scorer ID/version/code commit/configuration digest;
- method `DETERMINISTIC | STATISTICAL | MODEL_GENERATED | HUMAN`;
- exact input evidence refs/digests;
- sorted dimension results;
- grader identity/version/rubric digest where applicable;
- human reviewer identity where applicable;
- creation time;
- superseded prior pass or null;
- own digest.

Each dimension result is `PASS | FAIL | PARTIAL | UNKNOWN | NOT_APPLICABLE` with reason codes and evidence refs. There is no universal aggregate score or winner field.

A changed scorer appends a new pass. It never rewrites a run or prior scorer pass.

### 7.7 Evidence reference — `mastermind.agent_evaluation_evidence_ref.v1`

A sanitized reference binds:

- task class and exact scenario/corpus revisions;
- experiment ref/digest;
- per-run arm, pair, technical-validity, and scored-result projection;
- compared configuration refs/digests;
- required dimension gate matrix;
- valid/invalid/degraded/unscored counts;
- sample size, uncertainty method, and limitations;
- receipt/scorer/analysis refs;
- retrospective/replay/prospective/canary phase;
- intended owner and review/expiry time;
- exact non-authority statement;
- own digest.

For a technically valid run:

- all required accepted dimension results `PASS` => `VALID_PASS`;
- any required result `FAIL` => `VALID_FAIL`;
- no failures and at least one `PARTIAL` => `VALID_PARTIAL`;
- missing/unknown required scoring => `UNSCORED`.

Invalid/degraded states pass through unchanged. No invalid run enters a valid denominator. The reference is evidence, not a policy candidate; current owners ingest it only through their own admission/decision process.

## 8. Identity, time, null, correction, and storage

### 8.1 Time and null

- `started_at <= completed_at <= validated_at <= created_at`.
- `monotonic_duration_ms` is authoritative duration and equals `resources.elapsed_ms`.
- Scenario cutoff equals the run’s recorded cutoff.
- Unknown is explicit `null` only where allowed; missing cost, trace, tokens, usage, or session fingerprint never becomes zero.
- Required unknowns invalidate the comparison or yield `UNSCORED`/`INSUFFICIENT_EVIDENCE`; no model imputes them.

### 8.2 Correction

- Scenario changes create new versions.
- Experiment changes create new experiment IDs or explicitly superseding manifests.
- Runs are immutable.
- Scorer changes append passes.
- Analysis changes create new artifacts.
- Evidence references may be superseded but not erased.
- Corrupt/private artifacts are quarantined with a tombstone; never silently rewritten.
- Production contradiction remains visible and routes to Outcome Learning/current owner; offline history is not rewritten.

### 8.3 Filesystem-safe artifact mapping

Canonical IDs are parsed, never slugified generically:

```text
scenario:<family>:<case>
  -> scenarios/<family>/<case>/v<version>/scenario.json

experiment:<uuid>
  -> experiments/<uuid>/manifest.json

run:<uuid>
  -> experiments/<experiment-uuid-or-standalone>/runs/<uuid>/receipt.json

scorer-pass:<uuid>
  -> .../runs/<run-uuid>/scorer-passes/<uuid>.json

evidence-ref:<uuid>
  -> evidence-refs/<uuid>.json
```

Every segment is validated safe ASCII and contains no colon, slash, backslash, dot-segment, device name, control character, or trailing dot/space.

### 8.4 Create-only storage

V1 uses immutable JSON artifacts in an approved private root; repositories contain only public-safe schemas, fixtures, and sanitized receipts.

Writer sequence:

1. validate document and secret policy;
2. derive schema-aware safe path under a resolved root;
3. refuse symlinks in the parent chain;
4. create parents with private permissions;
5. write canonical bytes to a same-directory temporary regular file;
6. flush/fsync;
7. hard-link temp to the absent final path as the no-overwrite publication primitive;
8. fsync directory, unlink temp, read back, parse, validate, recompute digest;
9. on existing final path, accept only byte-identical idempotent import; otherwise hard conflict.

Filesystems lacking reliable same-filesystem hard-link/create-only semantics fail closed. A local index or Parquet/DuckDB projection is rebuildable and never canonical truth.

No SQLite, Postgres, ClickHouse, vector store, or service is canonical experiment truth in V1.

## 9. Execution architecture

### 9.1 Native core first

EVAL-R0 is Python-standard-library contract/finalization/storage/scoring code with one synthetic two-arm journey. It performs no provider call, process launch, network access, credential read, Executive/Agent OS mutation, route change, deployment, or external dependency installation.

### 9.2 OHF first real runner

PR #162 remains the sole fresh-Sol runner carrier. A valid fresh constitutional sample must prove:

- isolated workspace and fresh private process group;
- exactly one new thread start, no resume/fork/checkpoint;
- exact immutable Skillpack bytes;
- requested and served model exact;
- exact capability profile/tool census;
- read-only/approval-never behavior;
- independently authenticated non-default realm without credential-content reads;
- exact source/network observations;
- canonical output/events;
- effect state and cleanup proof;
- zero Executive, Agent OS, Slack, Linear, route, or production mutation.

A crash creates a new run only after effect/cleanup reconciliation. Fresh-start samples never resume or fail over.

### 9.3 Inspect later and subordinate

Inspect is the strongest orchestration candidate, but EVAL-I1 may adopt a pinned version only after supply-chain admission and a production-inert spike proves:

- Mastermind IDs/contracts remain canonical;
- provider-side web/code/remote-MCP capabilities are withheld unless explicitly allowed and are independently attested;
- in-process bridges are not called sandboxed;
- checkpoint/resume is disabled for fresh-start classes;
- Inspect cancellation/control does not become Executive cancellation;
- raw API/media/log retention matches scenario privacy;
- editable framework logs are evidence refs, never canonical run/policy truth;
- schema upgrades cannot silently reinterpret history.

### 9.4 Promptfoo later and public-safe

Promptfoo may generate/execute bounded retrieved-authority, RAG/tool, RBAC, shell/SSRF, repository, egress, credential-read, verifier-sabotage, and delayed-CI attacks only after:

- exact version/hash/dependency admission;
- telemetry, update checks, sharing, and uncontrolled remote generation disabled;
- deny-egress with explicit provider allowlist;
- synthetic or explicitly `PUBLIC_SAFE` remote inputs;
- generated cases reviewed into the Mastermind scenario contract;
- deterministic Mastermind scorers retain authority over company invariants.

A Promptfoo pass is evidence only.

### 9.5 Langfuse held from V1

Do not install Langfuse in V1. Reconsider only when valid experiment volume proves local artifacts/analysis materially inadequate and private retention, deletion, backup, audit, RBAC, migration, exact versioning, and rebuildability are solved. A decorative dashboard is not a reason.

### 9.6 Derived analysis

Parquet/DuckDB may later calculate paired deltas, invalid/degraded counts, uncertainty inputs, tails, and quality/resource frontiers. Projection manifests bind source receipt digests and analysis version. Projections are disposable and rebuildable.

## 10. Corpus, leakage, and scoring

### 10.1 Corpus sources

Use deliberately distinct sources:

1. Synthetic authority/security invariants.
2. Historical replay limited to information available at the cutoff.
3. Mutation-generated cases from known defects.
4. Completed Mastermind tasks converted to replayable cases.
5. Prospective shadow tasks sealed before outcomes.
6. Adverse runtime/fault-injection cases.
7. Human-composed product tasks.

### 10.2 Leakage controls

Every replay case must:

- pin allowed immutable refs;
- hide final branches/PRs/commits/reviews/outcomes/post-cutoff Agent OS records;
- record every exposed source;
- detect solution identifiers/answer strings;
- prohibit unrestricted current search unless it is the tested capability;
- keep private holdouts inaccessible to builders;
- separate author/builder/evaluator where risk warrants;
- invalidate unauthorized source/tool access rather than subtract points.

If post-solution sources cannot be hidden, label the task post-hoc comprehension or discard it; never call it replay.

### 10.3 Initial scenario families

At least 15–30 cases across:

- `COLD_START_CANONICAL_OWNER`
- `CROSS_REPO_COLLISION`
- `EFFECT_UNKNOWN_HANDLING`
- `NO_DUPLICATE_CONTROL_PLANE`
- `PROVIDER_FAILURE_RECONCILIATION`
- `PR_REVIEW_MISSED_CONSUMER`
- `CXI_CURRENT_SOURCE`
- `CODEINTEL_IMPACT_RECALL`
- `WORKER_HANDOFF_COMPLETENESS`
- `ROUTING_TIER_EQUIVALENCE`
- `RETRIEVED_AUTHORITY_INJECTION`
- `TOOL_SCHEMA_DRIFT`
- `SESSION_CLOSE_DISCIPLINE`
- `PRODUCT_COMPLETE_NOT_INFRA_ONLY`
- `SOLUTION_LEAKAGE_SENTINEL`
- `CLEANUP_UNCERTAINTY`
- `MODEL_SERVED_MISMATCH`
- `SCORER_PROMPT_INJECTION`

### 10.4 Scoring methods

**Deterministic first:** source opened/cutoff, forbidden tools, operation/owner identity, no duplicate systems, effect handling, path fence, tests/mutations, output contract, citations, cleanup, model/tool census, privacy, and real consumer/proof.

**Statistical:** paired designs, valid/invalid/degraded counts, confidence/exact intervals, tails, repair probability, variance, calibration, missingness, nonindependence, and sample size.

**Model graders:** only where deterministic scoring is insufficient; exact grader/rubric, blinded order where possible, disagreement, multiple graders or human audit for high stakes, and no same-model self-grade as sole evidence.

**Human/Sol:** architecture coherence, product usefulness, leakage, grader calibration, ambiguous failures, and promotion decisions.

## 11. Privacy and failure behavior

### 11.1 Never ingest by default

- raw private Chairman chats;
- private chain of thought;
- OAuth tokens, cookies, API keys, or credentials;
- raw provider homes or environment dumps;
- unrelated private repositories;
- personal account identifiers/private host addresses;
- broad Slack history;
- full transcripts without scenario need.

Use sanitized receipts, digests, bounded excerpts, exact refs, sensitivity labels, approved encrypted roots, retention/deletion procedures, and explicit model-visible boundaries.

### 11.2 Required failure behavior

| Failure | Behavior |
|---|---|
| Invalid schema/draft | Refuse before canonical run creation |
| Cutoff/source unavailable | Refuse or invalid configuration; no current-source substitution |
| Solution/unauthorized source | `INVALID_LEAKAGE`, preserve bounded offending refs |
| Model/tool/capability/arm mismatch | `INVALID_CONFIGURATION` |
| Unexpected network access | invalid configuration or leakage according to source effect |
| Sandbox unavailable | refuse; never silently run on host |
| Timeout before effect | preserve partial evidence; rerun only under scenario law |
| Possible effect unresolved | `INVALID_EFFECT_UNKNOWN`; no retry/failover |
| Cleanup unproven | `INVALID_CLEANUP`; no reuse |
| Allowed dependency degradation | `DEGRADED_DEPENDENCY` |
| Disallowed degradation | `INVALID_CONFIGURATION` |
| Scorer crash | immutable run remains; append repaired pass later |
| Grader disagreement/injection | expose disagreement/quarantine pass |
| Missing trace/cost/tokens | explicit null/degradation; no zero fabrication |
| Duplicate ID same bytes | idempotent no-op |
| Duplicate ID changed bytes | hard conflict and stop |
| Private evidence unavailable | `INSUFFICIENT_EVIDENCE`; no public surrogate |
| Too few/nonindependent samples | report limitation; no promotion-grade inference |
| Retrospective/prospective ambiguity | default retrospective |
| Offline/production contradiction | preserve both; route to current owner |
| Framework schema drift | new configuration/version; no silent pooling |

Every failure preserves evidence and avoids fabricating a clean result.
