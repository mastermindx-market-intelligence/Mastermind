## 1. Executive ruling

The current Chairman Control Room is technically useful as an engineering and operations inspector, but it is not an effective Chairman product.

It exposes the structure of Mastermind's internal control machinery—workstream references, source clocks, autonomy states, provider destinations, PR counts, responsibility chains, runtime vocabulary, bindings, gates, and raw source failures—and requires the Chairman to synthesize the executive meaning. Its primary experience competes with Linear's stronger portfolio and issue-management experience while offering less intuitive navigation and more internal terminology.

The resulting inversion is unacceptable:

> The Chairman is operating the control plane instead of the control plane serving the Chairman.

The corrected product architecture is:

```text
canonical company truth
  Executive OS + Agent OS + GitHub + Linear projection + Slack transport
                  |
                  v
existing deterministic Control Room composition
                  |
                  v
mastermind.chairman_brief.v1
pure decision-compression projection
                  |
        +---------+----------+
        |                    |
        v                    v
Decision-first Today      Explicit Advanced
Chairman product          operator/evidence inspector
```

The default surface answers, in order:

1. Does anything genuinely require Chris?
2. What materially changed?
3. What is Sol already handling?
4. What exceptions threaten outcomes?
5. Where can Chris ask Sol or inspect evidence?

The current Work, Autonomy, Surfaces, System, raw evidence, and setup tools remain available behind **Advanced**. They do not compete for default attention.

Linear remains the selected human portfolio and project-management projection. The Control Room does not rebuild Linear. It provides what Linear does not: **decision compression across exact canonical owners, honest degradation, Sol accountability, evidence-backed intervention, and a direct path from executive question to safe action.**

## 4. Why the current default fails

The live screenshots expose a product-level failure, not a cosmetic issue.

### 4.1 It reproduces Linear's object hierarchy

The current default foregrounds a long board of work references, statuses, PR counts, blockers, filters, and project navigation. Linear already performs project and issue navigation more coherently. A weaker duplicate increases cognitive load and creates another place to inspect without providing a differentiated executive job.

### 4.2 It gives every internal object equal visual altitude

Large counts such as Autonomy, Work, and System advertise organizational volume rather than compressing it. Dozens of routine workstreams compete with the few items that may actually require Chris.

### 4.3 It exposes machine ontology before human meaning

Phrases such as `RECORDED FRONTIER`, `DISPATCH STATE UNKNOWN`, `ROOT UNKNOWN`, `W3C`, responsibility chains, binding states, source schemas, and provider census information are legitimate advanced evidence. They are not the first language a Chairman should parse.

### 4.4 It makes failures technically truthful but experientially hostile

A missing Executive database currently appears as a dominant raw path-level alarm. Truthfulness is required, but default presentation should explain impact first:

> Runtime visibility is unavailable. Current runtime claims are withheld. Sol owns recovery.

The raw path belongs in diagnostics.

### 4.5 It does not tell the Chairman what to do

The interface shows state but does not reliably provide:

- the decision;
- why it is ready now;
- Sol's recommendation;
- the cost of waiting;
- reversibility;
- what the action will and will not change.

The Chairman must reconstruct those facts from multiple rows and sources.

### 4.6 It makes healthy emptiness feel broken

When no Chairman item exists, the page fills with routine work. The correct experience should confidently say that no Chairman action is admitted and show only enough context to establish that Sol has coverage.

### 4.7 It confuses presence with usefulness

A surface can be technically present, source-grounded, and navigable while still failing the primary persona's task. Infrastructure, provenance, and internal completeness are necessary; they are not the product outcome.

## 5. Approaches considered

### 5.1 Approved approach A — decision-first default, machinery in Advanced

The default is a briefing and decision cockpit. It contains only Chairman decisions/attention, material changes, Sol-owned outcomes, material exceptions, and a grounded Ask Sol entry when that capability is genuinely available. The existing inspector is preserved behind Advanced.

**Advantages**

- maximally reduces Chairman cognitive load;
- clearly differentiates the Control Room from Linear;
- preserves existing evidence and operator capabilities;
- supports progressive disclosure;
- creates a coherent path from understanding to safe action;
- makes healthy empty states calm rather than noisy.

**Trade-off**

- requires a new deterministic compression contract rather than a simple CSS cleanup;
- rich decision cards require explicit upstream fields or honest unavailability;
- the old default cannot remain the product center merely because it already exists.

**Ruling:** approved by the Chairman.

### 5.2 Rejected approach B — compress the existing dashboard

This would reduce row density, rename labels, collapse panels, and improve typography while retaining Today/Autonomy/Work/Surfaces/System as equal first-class navigation.

**Why rejected:** it preserves the wrong information architecture. A less cluttered control-plane inspector is still not a Chairman briefing.

### 5.3 Rejected approach C — use Linear as the only executive surface

This would abandon or minimize the Control Room and rely on Linear Initiatives, Projects, and Issues.

**Why rejected:** Linear is valuable as a portfolio projection but does not own or safely compose Executive runtime, Agent OS organizational truth, GitHub proof, source disagreement, exact provider bindings, effect uncertainty, or canonical action admission. The differentiated executive intelligence layer remains necessary.

## 6. Product thesis and moat

The Control Room is not valuable because it aggregates many tools. Its value is:

> **Decision compression with exact receipts.**

The Chairman should receive a small, intelligible set of decisions and exceptions while retaining one-click access to the underlying evidence. The system must reduce effort without flattening truth, inventing confidence, or hiding important uncertainty.

The durable moat is the combination of:

- exact cross-system identity;
- canonical-owner-aware composition;
- correction-safe and freshness-aware presentation;
- deterministic attention and decision admission;
- explicit Sol accountability;
- action preflight and effect reconciliation;
- a learning loop measuring whether the product actually reduces orientation and intervention cost.

A generic dashboard, issue board, or agent chat can imitate the surface appearance. It cannot easily reproduce the authority, provenance, correction, and action-safety architecture beneath it.

```text
Today     Programs     Ask Sol
```

Before Programs or Ask Sol has a production-proven useful path, it is not shown as an enabled primary destination. The product must not ship dead equal-weight navigation merely to match the end-state diagram.

### 8.2 Default behavior

- The default launch always enters Today.

- Advanced may preserve its own local filter/subview preference without changing the Chairman default.
- A direct deep link to Advanced remains available for operators.
- No permanent source rail, surface dock, responsibility graph, or global project board appears on Today.

### 8.3 Progressive disclosure

Every material item has three depths:

```text
Level 1 — executive statement
Level 2 — consequence, recommendation, next checkpoint
Level 3 — exact evidence and internal machinery
```

Level 1 is visible by default. Level 2 expands in place or in a clean drawer. Level 3 opens the Evidence/Advanced surface.

### 8.4 Above-the-fold object budget

At a 1440×900 desktop viewport, the first screen may contain:

- one headline;
- one expanded priority decision/attention card;
- up to two compact decision/attention summaries;
- one compact source-state indicator;
- no more than seven primary interactive controls excluding browser chrome.

All three priority entries remain visible, but only one is expanded above the fold. The page must not use empty space as justification to add more work objects.

## 9. Today — the default Chairman product

### 9.1 Headline

The headline is deterministic and template-driven. It never comes from unrestricted model prose.

Closed headline kinds:

```text
CLEAR
DECISIONS_REQUIRED
ATTENTION_REQUIRED
PARTIAL
UNAVAILABLE
```

Examples:

```text
CLEAR
You are clear. No Chairman decision or intervention is currently admitted.

DECISIONS_REQUIRED
Two decisions need you. Sol is handling everything else shown in this briefing.

ATTENTION_REQUIRED
One item needs your attention. It is not yet a complete decision packet.

PARTIAL
Partial briefing. Some present-tense claims are withheld because a required source is unavailable.

UNAVAILABLE
A current briefing cannot be established. No present-tense company claim is being made.
```

The headline may include counts only when the corresponding section is current and exact. It never says `healthy` merely because no failure was detected.

### 9.2 Source-state indicator

The top bar shows one quiet state:

```text
Current · refreshed 1m ago
Partial · Executive runtime unavailable
Historical · last verified 14m ago
Unavailable · open diagnostics
```

Source clocks, schemas, commit hashes, database paths, and provider capability census remain in Advanced.

### 9.3 Needs your decision

This section appears first only when at least one exact, current, complete Chairman decision packet is admitted.

Maximum visible priority entries: **three**. The first entry is expanded. The next two are compact summaries containing the decision question, one-line Sol recommendation state, and evidence affordance; either may expand without opening Advanced.

Across progressive disclosure, each decision contains:

1. **Decision question** — one sentence.
2. **Why now** — why the decision is ready and why Chairman authority is required.
3. **Sol recommends** — one option, explicitly attributed to an accepted Sol-authored source.
4. **Consequence of acting** — what advances or changes.
5. **Cost of waiting** — what remains blocked or exposed.
6. **Reversibility** — reversible, boundedly reversible, or irreversible with explanation.
7. **Actions** — read-only navigation in the first vertical; canonical action controls only after the action path is independently proven.
8. **Inspect evidence** — exact source drawer.

Example expanded presentation:

```text
Approve the decision-first Control Room experience reset

Why now
The current default duplicates Linear and exposes internal machinery before executive meaning.

Sol recommends
Approve the reset while preserving the existing compositor and Advanced inspector.

Acting advances
One bounded Today vertical and a protected experience contract.

Waiting costs
Additional work may harden the wrong default experience.

[Review recommendation] [Ask Sol] [Inspect evidence]
```

### 9.4 Decision completeness law

A Chairman-targeted attention item is not automatically a decision.

A decision card is eligible only when all of the following are exact and current:

- stable `decision_id`;
- exact `work_ref` or an explicit `NOT_APPLICABLE`;
- `authority_required == CHAIRMAN`;
- nonblank decision question;
- explicit reason the decision is ready now;
- two to four closed options;
- consequence of acting;
- consequence of waiting;
- reversibility classification;
- evidence references;
- source freshness;
- current conflict/effect state;
- accepted source for Sol's recommendation, or an explicit `RECOMMENDATION_NOT_RECORDED`.

`decision_id` must be an existing Agent OS decision key or an accepted Executive/Steward decision reference. The Today reducer and browser may not mint a new decision identity. Sol's recommendation must be projected from an accepted Agent OS decision/handoff or an accepted Steward-owned field; a UI model cannot create it.

An incomplete packet appears under **Needs your attention**, not under Needs your decision. The UI never invents missing options, consequences, or a recommendation.

### 9.5 Decision overflow

The first three entries are selected by a deterministic closed policy, never an LLM.

Priority order:

1. unresolved safety/effect-uncertainty items that require Chairman authority;
2. production/customer/security regressions requiring Chairman authority;
3. decisions with an exact time boundary or blocked critical path;
4. remaining decisions in source-declared order, then stable identity order.

Overflow behavior:

- `N more decisions` is always visible;
- constitutional/safety classes can never disappear without a visible count and class warning;
- opening overflow reveals the remaining cards without changing priority or closing anything;
- the UI does not silently suppress a fourth decision because three is aesthetically convenient.

More than three simultaneous Chairman decisions is also an organizational signal. The page states that Sol must sequence or compress the queue rather than normalizing executive overload.

### 9.6 Needs your attention

This section is used when a current canonical Chairman attention item exists but lacks a complete decision packet.

It shows:

- what needs attention;
- why it was admitted;
- what is missing before it can become a decision;
- whether Sol owns packet completion;
- a path to exact evidence.

No Approve/Hold controls appear for an incomplete packet.

### 9.7 What changed

This section answers what materially differs from the previous successfully loaded briefing.

Eligible material changes are limited to:

- a new or removed Chairman decision/attention item;
- a decision packet materially changing;
- a new or removed material exception;
- an accepted milestone or proof changing;
- a source disagreement appearing or disappearing;
- a source moving from current to stale/unavailable or back;
- the exact next owner/action changing;
- a correction changing a previously displayed material claim.

Excluded noise includes:

- refreshes with byte-identical semantic state;
- comment volume;
- routine heartbeats;
- timestamps changing without semantic change;
- every CI job;
- every Slack message;
- PR metadata churn without capability effect;
- unchanged Linear `In Progress` state.

When no prior checkpoint exists, the heading is **Latest material developments**, not `since your last visit`.

When an item disappears from the current composition, the copy says:

> This item is no longer present in the current briefing.

It does not claim resolution, completion, or success unless a canonical owner supplies that fact.

### 9.8 Sol is handling

This section exists to tell Chris what not to worry about.

It contains four to six outcome-level cards, not a complete workstream list. Each card answers:

- what outcome is being pursued;
- why it matters;
- what Sol or the explicitly named operator is handling now;
- the next proof/checkpoint;
- whether Chairman involvement is currently required.

Eligibility requires an exact accountable owner or next-action owner. A surface binding, Linear assignee, open PR author, or running process is not enough.

Example:

```text
Control Room experience reset
Sol is freezing the decision-first product and preserving the existing evidence substrate.
Next checkpoint: protected architecture and one real Today canary.
No Chairman action required.
```

The section does not show percentages, arbitrary ETAs, every worker, every branch, or every issue.

If ownership cannot be established, the item belongs in Exceptions as `OWNER_NOT_ESTABLISHED`, not in Sol is handling.

### 9.9 Exceptions

Exceptions are impact-oriented and grouped into a closed set:

```text
WORK_WAITING
WORK_BLOCKED
PROOF_MISSING
SOURCE_CONFLICT
SOURCE_UNAVAILABLE
EFFECT_UNKNOWN
PRODUCTION_REGRESSION
OWNER_NOT_ESTABLISHED
CAPACITY_BLOCKED
```

Each exception shows:

- human impact;
- affected outcome/work reference;
- exact repair owner or `UNKNOWN`;
- whether the Chairman must act;
- evidence link;
- currentness.

Default copy never prints raw stack traces, absolute paths, bearer/token material, provider identifiers, or schema dumps.

Example translation:

```text
Runtime visibility is unavailable
Current execution claims are withheld. Agent OS and GitHub evidence remain available.
Repair owner: Sol / system recovery.
[See impact] [Open diagnostics]
```

The raw missing-database path remains available in local Advanced diagnostics.

### 9.10 Ask Sol entry

Today includes a compact Ask Sol entry only when a grounded, production-proven query path exists.

Target prompt examples:

Before that path is proven, the first vertical may show a context-sensitive `Open exact Sol` navigation control only when the existing binding is genuinely openable. It must not present a dead text box or fake conversational capability.

### 9.11 Healthy empty states

## 11. Ask Sol — grounded conversation, not a pasted chatbot

Ask Sol is the conversational interface to the same canonical composition.

### 11.1 Read-only question contract

A query binds:

- current briefing digest;
- current source-freshness envelope;
- optional exact Initiative/workstream context;
- user question;
- read-only intent.

The answer contains:

1. direct answer;
2. Sol recommendation, labeled advisory;
3. exact supporting evidence;
4. uncertainty and unavailable sources;
5. any currently available safe next action.

### 11.2 Authority boundary

Ask Sol may explain, compare, synthesize, and draft. It may not independently:

- create or close attention;
- rank the company roadmap;
- declare runtime state;
- mark work complete;
- originate a Chairman decision;
- dispatch or wake a worker;
- retry an effect-unknown action;
- mutate Linear, Slack, GitHub, Agent OS, or Executive OS;
- hide a source conflict.

A user request to act transitions into a separate deterministic preflight and confirmation flow. Conversational prose is never the mutation receipt.

### 11.3 Feature gate

Ask Sol is hidden or explicitly unavailable until the exact grounded provider/runtime/session path, permission, transcript boundary, and return contract are production-proven. The UI must not infer this capability from the presence of ChatGPT tabs or surface bindings.

## 14. Local presentation checkpoint and material changes

The What changed feature uses a disposable browser-local presentation checkpoint, never a company truth store.

### 14.1 Checkpoint contract

```text
mastermind.chairman_display_checkpoint.v1
```

Allowed fields:

```text
last_displayed_at
brief_schema
brief_digest
material_item_fingerprints[]
```

Each fingerprint contains only:

```text
section
authoritative_identity
semantic_digest
```

It contains no source text, prompt, transcript, recommendation, credential, runtime lifecycle, decision authority, or current status assertion.

### 14.2 Semantics

- The checkpoint means the briefing was successfully displayed, not read, accepted, or acknowledged.
- It cannot close attention or decisions.
- It cannot make an old fact current.
- Deleting it changes only the change-summary mode.
- Corruption resets to `LATEST_MATERIAL_DEVELOPMENTS` with no canonical effect.
- A semantic digest change produces `CURRENT_EVIDENCE_CHANGED`, not an inferred resolution.
- An identity disappearing produces `NO_LONGER_PRESENT`, not `COMPLETED`.

### 14.3 Determinism

Material fingerprints are computed from explicit allowlisted fields. Timestamp-only movement and collection-order changes do not change the semantic digest.

A later model layer may provide:

- concise explanations;
- option comparisons;

## 16. Action architecture

The decision-first surface begins read-only.

### 16.1 Initial action state

Allowed controls:

- inspect evidence;
- open the exact program/workroom;
- open Advanced diagnostics;
- open an exact verified Sol destination when available;
- open Linear/GitHub source links when exact.

No Approve/Hold/Stop/Continue control is enabled merely because a decision card renders.

### 16.2 Future canonical preflight

A modifying action requires:

1. fresh canonical read;
2. exact user permission and authority;
3. exact workstream/operation/runtime/carrier/source identities;
4. stable operation key and normalized fingerprint;
5. deterministic statement of what will change;
6. deterministic statement of what will not change;
7. one explicit confirmation;
8. one submission through the existing canonical admission owner;
9. reconciliation to accepted, refused, conflict, or `EFFECT_UNKNOWN`;
10. no blind retry or alternate-carrier failover.

### 16.3 Confirmation design

A future confirmation drawer uses this structure:

```text
You are approving
<exact decision and selected option>

This will authorize
<bounded effect>

This will not
<explicit non-effects>

Current source revision
<exact identity>

[Confirm once] [Cancel]
```

A client timeout disables resubmission and enters reconciliation. It never displays optimistic success.

### 16.4 No conversational mutation

Ask Sol prose cannot bypass the preflight. `Yes`, `do it`, or natural-language approval is interpreted only through the existing accepted Chairman-intent procedure and still requires the canonical action gates applicable to that effect.

## 17. Degradation, correction, and truthfulness

### 17.1 Default degradation language

The default view explains consequence first:

```text
Runtime visibility is unavailable.
Current runtime claims are withheld. Organizational and GitHub evidence remain available.
```

Advanced retains the exact technical details.

### 17.2 Last-good composition

A cached last-good document may be displayed only as explicitly dated historical evidence. A background refresh banner cannot silently make historical data present-tense.

### 17.3 Partial usability

One failed source does not automatically blank the entire product. Each section declares whether it remains usable. Examples:

- Executive runtime unavailable: current runtime/worker claims withheld; Agent OS/GitHub program evidence may remain.
- GitHub unavailable: implementation/proof changes withheld; current Executive/Agent OS attention may remain.
- Agent OS unavailable: outcome/ownership/program sections withheld; exact Executive attention may remain if independently supported.
- model unavailable: deterministic briefing remains.

### 17.4 Corrections

When current evidence contradicts a previous display, the product says:

> **Correction:** current evidence no longer supports the earlier claim.

It does not silently erase the previous display history or majority-vote among sources.

### 17.5 Source disagreement

A disagreement becomes an exception with both claims and their owners available in evidence. The default summary does not choose a winner unless the canonical ownership law already does so.

## 19. Security and privacy

The default brief has a narrower data surface than Advanced.

It must never render or serialize:

- credentials, tokens, cookies, bearer values;
- hidden provider prompts;
- private chain of thought or reasoning traces;
- raw chat transcripts;
- raw exception/traceback bodies;
- absolute host paths;
- browser profile/session secrets;
- arbitrary upstream mappings;
- unreviewed external HTML.

Every section uses explicit field allowlists. Unknown fields are omitted or typed unavailable. Payload size is bounded before response bytes are written. The current local loopback/token threat-boundary law remains honest: a per-process token is not proof of a separately authenticated human identity.

Advanced may expose additional local diagnostics only under its existing local threat boundary and redaction law. Moving a field into Advanced does not waive security requirements.
