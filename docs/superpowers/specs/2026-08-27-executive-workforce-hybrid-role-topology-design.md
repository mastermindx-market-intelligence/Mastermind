## 1. Outcome

Mastermind-X must operate as one coherent AI company across native ChatGPT/Codex/Claude surfaces, terminal/API workers, and multiple physical computers without forcing the Chairman to choose providers, move prompts, remember which session is alive, or manually route work when a cheaper lawful model could perform it.

The end state preserves premium native interfaces for high-level cognition while moving task lifecycle, worker selection, continuation, cost/capacity placement, and cross-host execution underneath one canonical Executive OS.

The architecture is deliberately **hybrid**:

- native ChatGPT remains the primary Sol CEO cognition surface;
- Codex may serve as a technical/CTO-style reasoning arm of the Sol seat and may also run ordinary bounded worker jobs;
- Claude/Fable remains the preferred sustained COO/program-owner surface;
- Opus/Sonnet and similar frontier workers remain available for higher-ambiguity subwork;
- GLM, Grok, Qwen, DeepSeek, local models and later providers become governed lower-cost workers where their quality class is sufficient;
- native apps, App Server, CLI, API, ACP and tmux are execution substrates, not lifecycle authorities;
- one canonical Executive Runtime owns Jobs/Attempts/Workers/Events across all machines;
- Agent OS remains durable organizational memory;
- GitHub remains implementation/evidence truth;
- Slack remains conversation/attention transport;
- Wake Fabric resumes the right reasoning surface when canonical state says attention is owed.

### 1.1 Chairman job

Give Sol an outcome once. Do not manually decide which subscription, model, Mac, PC, Claude window, Codex thread or tmux shell should do each child task. Do not carry routine worker results and decision requests among sessions. Keep the ability to view and interact with the native app experiences when desired.

### 1.2 Sol job

Own product thesis, company/system architecture, authority boundaries, high-impact adjudication and final acceptance. Delegate technical continuations and architecture-preserving implementation detail to a Codex-Sol technical arm; delegate sustained program execution to Fable; let Executive OS place lower-level child work on the cheapest suitable governed capacity.

### 1.3 Fable job

Hold a sustained program seat across many bounded waves, decompose dependency-feasible work, delegate child Jobs, consume results, perform ordinary repair/review loops, and escalate only real architecture/authority/scope/rights/security/final-acceptance boundaries.

### 1.4 Machine job

Represent executive responsibility, reasoning surface, runtime session, provider/account capacity, physical host and transport as separate identities. Determine required reasoning quality first; choose cost/capacity only among already-lawful candidates; execute on host-local credentials; return results to the canonical parent Job; and wake/resume the owning reasoning surface without creating a second queue/session registry/scheduler.

## 3. Identity model — never collapse these layers

The following identities are distinct even when a single paid subscription economically supplies several of them:

```text
EXECUTIVE SEAT       chairman | ceo | coo (existing authority identity)
ROLE / DUTY          CEO cognition, technical staff, COO program control, planner, builder, reviewer, mechanical work
REASONING SURFACE    chatgpt-sol | codex | claude | grok | glm | qwen | deepseek | local | ...
EXECUTIVE WORKER     canonical Worker claimed for an Attempt
PROVIDER REALM       codex-pro-01, Claude account/capability, API/local slot, etc.
RUNTIME BINDING      current provider-native process/thread/session handle + generation
HOST                 opaque reviewed host_ref
SLACK PRINCIPAL      communication identity only
COMMISSION / JOB     immutable permitted work identity
```

A Slack username cannot prove Worker identity. A provider process cannot prove Job ownership. A model name cannot grant executive authority.

## 4. Sol and Codex — dual-surface CEO architecture

### 4.1 Sol remains the canonical CEO role

The Chairman delegates company/product/system authority to Sol, not to a specific chat window or provider-native process. Interactive ChatGPT Sol is the primary cognition surface because it is best suited to company-wide intent recovery, product synthesis, research architecture, cross-program arbitration and final acceptance.

### 4.2 Codex-Sol is a technical staff / CTO reasoning surface

Codex is not permanently classified as a routine worker. A Codex runtime may be bound to the `ceo` executive seat for one scoped operation when the duty is **Sol technical staff**.

Conceptually:

```text
seat = ceo
reasoning_surface = codex
role = sol_technical_staff
```

The exact role representation must reuse or minimally extend existing accepted Executive/Model Router contracts; do not invent a parallel seat system merely to store `sol_technical_staff`.

A Codex-Sol technical arm may autonomously:

- perform repository archaeology and technical feasibility work;
- convert an already-approved architecture into bounded implementation plans;
- execute architecture-preserving technical decisions delegated in the commission;
- review implementation/CI/runtime evidence inside an already-frozen acceptance law;
- manage ordinary repair/test/review loops inside an authorized technical wave;
- delegate child Jobs whose authority is a strict subset of the parent.

It may **not** autonomously:

- materially change Chairman intent;
- change product thesis, user outcome, company architecture or canonical ownership boundaries without a current Sol ruling/source-law update;
- create a new lifecycle/identity/state/control plane;
- grant itself merge/deploy/rights/security/spend/trading authority not present in the parent operation;
- launder a provider-native capability into executive authority.

### 4.3 Codex worker mode remains valid

The same provider/model may also be used as a normal Executive Worker for bounded implementation or review. Therefore `codex` describes a reasoning/execution surface, not a permanent organizational rank.

## 5. Fable / Claude — sustained COO program control

Fable remains the preferred sustained COO/principal-builder surface for ambiguous or cross-repository programs after Sol freezes the architecture.

Fable may:

- own the full program journey across many bounded PRs/waves;
- decompose work into child Executive Jobs;
- delegate to suitable lower-level workers;
- continue through routine tests, reviews, repair cycles, CI and production-proof capture;
- resequence dependency-feasible work without Chairman routing;
- request Sol only at declared executive boundaries.

Fable does not become a second scheduler. Its child work must enter the canonical Executive Job/Attempt/Worker lineage when it is material independent work.

Native Claude subagents may be used as ephemeral cognition inside the parent session, but any independently reviewable mutation, proof-bearing work product or worker result that matters to company lifecycle must be represented by the accepted Executive child-work mechanism rather than hidden as an untracked subagent.

## 6. Worker quality and cost hierarchy

Mastermind optimizes cost **after** quality, authority and independence constraints.

Conceptual hierarchy:

```text
Tier A — executive / architecture / highest ambiguity
  Sol; Fable; selected frontier reasoning

Tier B — high-level technical/planning/review
  Codex-Sol technical staff; Opus; strong frontier peers

Tier C — bounded implementation/research/review
  Codex worker; Sonnet; Grok; strong GLM/Qwen/DeepSeek classes where validated

Tier D — low-ambiguity / mechanical / repetitive
  lower-cost GLM/Qwen/DeepSeek/local/mechanical agents
```

The exact provider-neutral tier vocabulary belongs to RF1 / the existing Model Router and must be validated empirically. This architecture does not hard-code a provider brand as permanently superior or inferior.

### 6.1 Selection law

```text
Executive authority / job constraints
        ↓
independence requirements
        ↓
Model Router: first lawful quality/execution tier
        ↓
Capacity Fabric: availability / host / quota / marginal cost / reserve policy
        ↓
Executive claim among eligible Worker realms
```

Cost cannot promote an inadequate model into a higher-authority task. Unknown capacity is not free capacity. Provider health cannot waive review independence.

### 6.2 Frontier reserve

Scarce/high-cost frontier capacity may be reserved for interactive, architecture-sensitive, review-critical or otherwise high-value work. Subscription/local/credit capacity should be preferred for routine eligible work where quality is equivalent.

## 7. Native apps vs terminal workers — hybrid harness law

Native ChatGPT, Codex and Claude interfaces are retained as high-value **cockpits**. They are not replaced by a terminal-only Agent OS.

The execution layer underneath them may use:

- native desktop app;
- Codex App Server / CLI;
- Claude Code;
- ACP/supported tools;
- provider API;
- local inference runtime;
- tmux or another host-local process container.

### 7.1 Tmux is not orchestration authority

A model/session must not create untracked durable work merely by running:

```text
tmux new ...
```

Canonical flow is:

```text
parent reasoning surface
  → Executive child Job
  → Worker claim
  → approved provider adapter
  → optional tmux/CLI/API/native process
  → adapter result receipt
  → Executive Attempt/Job transition
  → parent continuation / wake
```

Tmux may preserve process continuity, logs and local shell state. It never owns Job identity, retry, completion, provider failover or company memory.

### 7.2 One common Worker Harness

HF1 must generalize the existing WorkerExecutionAdapter/broker boundary rather than creating `grok_broker`, `glm_broker`, `qwen_broker`, etc.

Each approved adapter owns only provider-private mechanics:

- authentication/login location;
- native process/thread/session start/resume;
- provider-native tool invocation;
- result/receipt extraction;
- cancellation/reconciliation behavior;
- local secret isolation.

The parent Executive lifecycle remains provider-neutral.

## 8. Multi-host architecture

Mastermind uses **one canonical Executive Runtime** on the control host. Additional physical machines are execution hosts, not new control planes.

Target:

```text
                 CANONICAL EXECUTIVE OS
                      control host
                          │
                authenticated MH1 transport
           ┌──────────────┼──────────────┐
           ▼              ▼              ▼
        M1 host         M2 host         PC host
     Worker Broker    Worker Broker    Worker Broker
      local creds      local creds      local creds
     Codex/Claude/     Codex/Claude/    Codex/other/
     cheap workers     cheap workers    cheap workers
```

### 8.1 Host identity

Use the existing opaque reviewed `host_ref` semantics from Capacity Fabric. Do not expose hostnames, IPs, serials, usernames or private addresses in provider-capacity projections.

### 8.2 Credentials remain local

A provider account attached to M1 is not automatically usable from M2/PC. Remote Executive placement routes an Attempt to a host-local broker; it does not copy provider credentials to the control host or another worker machine.

### 8.3 Remote effect uncertainty

Remote timeout/disconnect is `EFFECT_UNKNOWN`. Reconcile the same Attempt/host/Worker operation before any retry or placement change. Never cross-host fail over an ambiguous modifying Attempt.

### 8.4 Git/worktree behavior

Each host uses its own bounded clean repository/worktree context. GitHub carries implementation/evidence truth across machines. The architecture assumes no shared writable filesystem and no host-local branch state as canonical company memory.

## 9. Codex app placement and computer-use isolation

Preferred physical topology is one primary Codex-Sol realm per worker host when the provider-supported app/runtime exists there:

```text
M1 → Codex-Sol realm A
M2 → Codex-Sol realm B
PC → Codex-Sol realm C
```

This is a **capacity topology**, not a permanent binding `ChatGPT1=M1`, `ChatGPT2=M2`, `ChatGPT3=PC`. Wake/RuntimeBinding may bind a current Sol technical continuation to an eligible realm dynamically under accepted policy.

If a provider-supported native app is unavailable on one host, use the accepted CLI/App Server/supported-tool adapter on that host; do not fabricate a GUI capability.

### 9.1 GUI/computer-use mutex

One physical desktop can support many headless workers but should have at most one active computer-use actuator controlling the same interactive GUI seat at a time unless an independently proven isolation mechanism provides separate desktops/sessions.

Multiple Codex or Claude processes may compute concurrently on a host. They may not concurrently fight over one keyboard/mouse/display/browser profile and then call the resulting state deterministic.

A future resource allocator may project GUI actuator availability, but it must extend the accepted resource/Worker lifecycle rather than create a second desktop scheduler.

## 10. Slack communication identities

Personal Claude Slack accounts are retained as first-class communication/fallback endpoints. ChatGPT1/2/3 remain Sol-seat communication principals. Slack identity is never Worker identity.

Human-readable conversation may occur directly from those principals.

Machine-consumable `ACK`, `BLOCKED`, `DECISION_REQUEST`, `PROGRESS`, `RESULT`, `RULING`, `CONTINUE`, `STOP` flows use the accepted ASD/Agent Relay contract where production-proven, because it carries exact commission/session/applicability identity and secret isolation.

Codex-Sol may use a Sol Slack principal for ordinary human conversation because the accountable executive seat is Sol. Machine authority must still bind the exact Executive seat/role/runtime/commission rather than infer it from the Slack sender.

## 11. Wake and continuation

Wake Fabric, not Slack delivery or tmux, owns the canonical wake obligation/delivery/ACK relationship.

Expected patterns:

```text
child Job completes
  → Executive source fact / inbox attention
  → WAKE obligation for parent seat
  → route to current RuntimeBinding
  → provider-native adapter resumes/wakes exact reasoning surface
  → target ACK
  → parent retrieves canonical result and continues
```

For Claude/Fable this may resolve to a Claude Code native resume/wait path. For Codex-Sol it may resolve to Codex App Server/native thread continuation. For ChatGPT Sol, current hourly Tasks may remain a supervisory continuation mechanism while production Wake transports mature.

Do not create one independent watcher/cron/tmux loop per worker as the permanent architecture. Temporary watchers may bridge an unbuilt transport but must remain explicitly transitional and subordinate to canonical state.

## 12. Delegation semantics

### 12.1 Sol → Codex-Sol

Use for architecture-preserving technical continuation, implementation planning, deep code archaeology, runtime proof/review and technical staff work. The parent commission states what decisions are delegated and what requires a Sol return.

### 12.2 Sol → Fable

Use for sustained program ownership after architecture freeze. Fable may fan out child Jobs and continue through ordinary reversible execution without a Sol round-trip for each wave.

### 12.3 Codex-Sol/Fable → lower-level workers

Allowed only as strict-subset delegation:

- child objective is bounded;
- allowed repositories/paths/authorities do not exceed parent;
- quality/execution class is declared through the accepted router contract;
- independent review requirements remain intact;
- parent remains accountable for integrating/rejecting the child result;
- child completion cannot self-accept architecture/product/final program state.

### 12.4 Return boundaries

Codex-Sol/Fable returns to interactive Sol for material product-thesis changes, canonical ownership/architecture changes, new persistent state/control/identity planes, unresolved security/rights/credential questions, destructive/irreversible actions, material spend, rank/trade/financial authority changes, and final program acceptance.

## 14. Acceptance

This architecture is successful only when a real Chairman outcome can flow through Sol, Fable/Codex-Sol delegation, provider-neutral child Jobs, quality-before-cost routing, lower-cost workers where appropriate, material Sol escalation, native session continuation, independent review, and multi-host execution without manual prompt carriage or a hidden second control plane.
