This diagram describes an intended integration, not installed routes. There is no mandatory `Sol -> Workspace -> Grok -> Fable -> worker` chain. **Single decision owner:** at a decision boundary, existing RuntimeBinding and the current grant identify the action-authoritative parent. **No universal gate:** lack of a Grok allowance, supported trigger or helper route parks only the Grok-dependent obligation. Independently admitted native work continues. Conversely, native availability does not permit replaying an effect-unknown Grok operation elsewhere.

## 4. Role and authority design

### Grok Operations: Sentinel mode

Mission: inspect one material attention event and current evidence; distinguish a true operational exception from a normal wait, stale projection or expected empty result; produce the smallest useful diagnosis and next action.

Suitable inputs include a returned artifact awaiting consumption, a canonical overdue obligation, a failed publication step, or a disagreement between a selected portfolio projection and its owner. Absence of a Slack message or a heartbeat alone is not proof of non-execution.

Outputs are evidence-bound findings, affected user/machine capability, exact owner, and a proposed action or an explicit unknown. Initial authority is approved reads and, after qualification, a purpose-limited candidate return. No direct job creation, reviewer election, account selection or repair launch comes from the Sentinel title.

### Grok Operations: Foreman mode

Mission: within one already-admitted mission, identify a bounded useful subtask, request a suitable helper through the existing owner, evaluate the returned artifact, and prepare the upstream result. It decomposes execution inside the frozen outcome, not company strategy.

A later separately qualified operational grant can allow specified repair/continuation edges. That progression must use the existing `mastermind.chairman_delegation_envelope.v1` and #612 decision classes, not a new Grok permission database. The foreman acts under its real identity; it never writes `SOL ACCEPTED` merely because it can send text.

### Workspace Agent profiles

Keep the already-proposed Program Continuity Adviser and Independent Outcome Reviewer as optional clients. Their initial output is a candidate. They do not automatically supervise every Grok turn, and provider `completed` does not mean a reviewed answer reached the company.

### Permission ladder

| Level | Useful capability | Admission boundary |
| --- | --- | --- |
| Read | Explain a real exception accurately | Intended account, approved data and live read path |
| Return candidate | Deliver a bounded artifact to the current parent | Qualified shared result ingress, authenticated scope, current obligation and replay checks |
| Request helper | Delegate one bounded subtask | Existing broker, exact provider/mode eligibility, parent grant and enforced budget |
| Operational continuation | Consume/reject exact results and issue permitted next edges | Qualified parent identity and explicit current decision-class grant under #612 |
| Reserved decisions | Change thesis, architecture, release policy or major spending | Existing Sol/Chairman authority; never acquired by progression through Bot levels |

Selecting a provider or model does not advance this ladder. A working account-level connection does not prove exact Bot/run identity. Program-specific exceptions, including programs explicitly assigned away from this Sol/Secretary surface, remain outside the grant.

## 5. Account, computer and connection boundary

Grok Bot's documented cloud computer is assigned per user, and that user's Bots share files, sessions and command-line credentials. Separate screens and role prompts are not isolation. Its documented access is the signed-in member's access, not a distinct Bot principal. [V1, V2]

For the pilot, use the existing authorized account only after its actual scope is inspected. Do not assume a second Bot creates a safe low-privilege compartment. Do not copy production-admin browser sessions, shell credentials, provider keys or private data onto the Bot computer. A narrow plugin cannot constrain a separate broad browser login to the same service. Enterprise-only controls are not assumed present. [V2]

Authentication belongs to the existing app/auth owner. Prefer its supported scoped connection over browser clicking. Reuse the intended installed transport and identity; do not add an alternative public listener, new tunnel or second `user-openclaw` registration to avoid #188's unresolved state. This document authorizes none of #188's package/proxy/host changes and does not reproduce its private coordinates.

At initial qualification, account-authenticated output can be accepted only as a candidate attributable to that account. Bot name, message text, source IP and model-supplied run ID cannot establish a stronger principal. Missing run-specific attestation must remain visible. It must not generate a trusted Wake ACK, Worker claim, or action-authoritative operational session.

The hosted workspace holds disposable working artifacts and cached context. Agent OS and GitHub hold durable accepted records; Executive owns runtime truth. A cloud reset or routine pause must not erase company obligations.

### Helper boundary

The Foreman requests a task capability, not a credential, arbitrary endpoint or account. Existing suitability/Capacity/broker owners select an eligible execution route. A helper request binds the parent, allowed task, exact input/output contract, expiry, tool ceiling, cost/usage envelope and permitted repair count. Request text cannot enlarge any of these.

Read-only, prompt-only ephemeral help may remain inside the already-admitted parent's helper authority. Independent deliverables, persistent activity, source writes, separate review obligations or work that outlives the parent must enter the existing Executive child-Job path. Neither a vendor subagent ID nor an engineering-broker receipt substitutes for Job/Attempt proof.

No model receives raw general SSH to the Studio to evade missing broker capability. No helper creates another helper in the initial profile. Output is candidate data, never a command. A validator checks identities, schema, evidence, bounds and task meaning; exit code zero is insufficient.

## 7. Event topology and routines

The normal trigger is an existing material attention event. Deterministic services perform health checks, freshness checks, exact deduplication and ordinary lifecycle bookkeeping. Wake a reasoning client only for an unresolved judgment worth its cost.

Vendor routines can receive narrowly filtered events, but are transport hints, not authorization or the canonical event queue. Grok's documented event integrations are separate from its Slack/GitHub plugins and require actual-account qualification. Unattended routines may pause after inactivity. [V3]

The pilot enables no timer and no broad channel listener. A future event rule must bind the intended account, source/channel, publisher and one already-admitted obligation. A matching phrase alone cannot start company work. Backend reread is mandatory; edited/deleted or corrected source text does not silently cancel or replace a started operation.

Prevent two common loops: do not trigger from the Bot's own reports; do not have Sentinel wake Foreman, which wakes Workspace, which wakes Sentinel for the same obligation. Deduplication and the one-decision-owner rule remain in existing stores. No Bot-local durable polling cursor or retry scheduler is introduced.

A periodic Chairman digest is optional and separately authorized. It should summarize meaningful changes and decisions, not become a heartbeat expense. No routine is created by this source PR.

## 11. Highest-return workload sequence

**First: returned-work triage.** A parent has an exact returned artifact but no useful next step. The Bot distinguishes whether independent review, proof, a bounded repair or a genuine reserved ruling is missing. It returns a cited diagnosis and next action that the existing owner consumes. Success reduces a manual nudge and moves an actual admitted task, not merely produces a summary.

**Second: product/data incident preparation.** Read a real health/freshness exception and identify the broken producer-to-consumer step. Prophet freshness and alert delivery are good candidates after their exact product owners supply expectations. No takeover of an active incident writer or manufactured production failure for demonstration.

**Third: evidence-heavy bounded coordination.** Compare artifact revisions, assemble a repro pack or check a frozen acceptance contract with economical help. Avoid another premium review layer when deterministic checks or a direct Terra task suffice.

**Fourth: periodic executive explanation and public-source intelligence.** Use only when the first three show net benefit. Browser-only tasks can exploit the cloud computer, but such browsing is not inherently better than connectors and does not justify broad logins.

## 12. Proof and ROI

A valid end-to-end proof has all joins: real attention source -> intended Bot consumption -> current scoped reads -> permitted helper if included -> independently validated artifact -> authenticated candidate return -> current parent consumption -> visible/machine next action. Synthetic tests prove parser and refusal behavior only. A transcript, screenshot, provider terminal state, green CI or merged spec cannot prove the whole path.

For the helper-enabled proof include a genuinely rejected candidate and one bounded repair. Do not secretly sabotage production; test rejection in an isolated canary or use a naturally rejected permitted artifact. Include an explicit no-helper path so Grok's marginal contribution can be measured.

Measure through existing evidence/telemetry owners: accepted useful results, unnecessary escalations, missed actionable exceptions, human interventions per completed mission, time to applicable parent consumption, first-pass quality, repair rounds, Grok usage delta with actual accounting basis, helper usage/cost, duplicate effects and unsafe claims. Keep model/process success and product acceptance separate.

Compare matched task classes under direct qualified worker, Grok alone, and Grok plus helper; compare Workspace only when qualified and relevant. This is evaluation of marginal value, not an instruction to triple every production task. Account-wide meter changes with concurrent unrelated work are not attributable per-run savings. No historical benchmark promotes a route by itself.

Promotion requires no duplicate or unauthorized effects, truthful stale/unknown handling, successful offline-parent continuation within a real grant, and a demonstrated net reduction in scarce cognition/human attention without worse acceptance quality. The number of pilot examples and the economic threshold must be frozen by the accepted canary owner before promotion, not chosen after seeing favorable outcomes.
