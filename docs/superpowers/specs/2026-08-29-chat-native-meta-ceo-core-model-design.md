## 1. Chairman outcome

Mastermind must use the highest-value fixed-subscription ChatGPT reasoning capacity as its default
executive cognition plane rather than replacing it with per-run Workspace Agents, ChatGPT Work, or
API inference.

The target company experience is:

```text
Chairman Chris
    -> one logical Meta-CEO Sol office in ChatGPT Pro Chat
    -> several bounded Program CEO / Project Sol / Integrator / Auditor Chat sessions
    -> existing Mastermind Executive OS + Agent OS + RuntimeBinding + Wake + Capacity owners
    -> bounded workers and implementation surfaces
```

The Chairman communicates with one Meta-CEO. The Meta-CEO creates and supervises a hierarchy of
replaceable Chat-native Sol responsibilities, consolidates their work, and reports exceptions and
material outcomes without requiring the Chairman to shuttle messages, hunt sessions, or allocate
routine provider capacity.

The architecture is economically successful only if ordinary Sol executive cognition does not incur
a new per-token or per-run bill when an included-plan Chat surface can perform the work reliably.

## 2. Core economic invariant

### 2.1 Default cognition route

While an approved ChatGPT plan provides included interactive Sol cognition, the default route for
Meta-CEO, Program CEO, Project Sol, Integrator Sol, and Auditor Sol reasoning is:

```text
COGNITION_ROUTE: CHAT_PRO_DEFAULT
```

This is a marginal-cost preference, not a claim that a subscription has no limits. Current account,
model, rate, quota, usage-policy, and session availability remain live Capacity/platform facts.

### 2.2 Default control route

The always-on company control plane remains deterministic and local or already-paid infrastructure:

```text
Executive OS
Agent OS
RuntimeBinding / SessionTargetRegistry
Wake / Agent Relay / dialogue transport
Capacity Fabric / Model Router
GitHub / Linear / Control Room projections
```

No language model must remain continuously generating merely to keep the company alive. Deterministic
systems hold state and wake the exact Chat responsibility only when judgment is required.

### 2.3 Metered exception route

API inference, Workspace Agents, ChatGPT Work credits, Business agentic credits, or another
incrementally billed reasoning surface are exception routes.

A metered Sol-class cognition commission is invalid without all of:

```text
COGNITION_ROUTE: METERED_EXCEPTION
WHY_METERED: <specific capability or availability need>
WHY_PRO_CHAT_INSUFFICIENT: <specific reason included Chat cannot reliably complete this mission>
EXPECTED_MAX_COST: <bounded estimate or approved accounting unit>
HARD_BUDGET_CAP: <enforceable maximum>
STOP_CONDITION: <observable completion or abort condition>
BUDGET_AUTHORITY: <current approved envelope or explicit Chairman decision>
```

Convenience, easier orchestration, a larger advertised context window, preference for programmatic
APIs, or the importance of a project is not by itself sufficient justification.

If the receipt or budget authority is absent, the route is:

```text
METERED_ROUTE_REFUSED / WAITING_FOR_LAWFUL_ROUTE
```

A metered route never grants greater organizational authority than the same logical responsibility
would have on Chat.

## 3. Corrected architecture decision

The following prior proposal is rejected:

```text
Workspace Agent front-end
    -> API Meta-CEO supervisor
    -> replacement of Chat-native Sol CEOs
```

It creates two metered reasoning layers, pays again for already-purchased cognition, and demotes the
highest-ROI Chat surface to a thin UI.

The protected core model is instead:

```text
Chairman-facing cognition:       ChatGPT Pro Chat Meta-CEO Sol
Program cognition:               ChatGPT Pro Chat Sol sessions
Deep planning councils:          ChatGPT Pro Chat Sol sessions
Integration and audit:           ChatGPT Pro Chat Sol sessions
Always-on lifecycle/control:     existing deterministic Mastermind owners
Worker execution:                least-cost / least-scarce capable existing avenue
Business MCP / plugins:          optional connection and authority adapters
Workspace Agents / Work / API:   budgeted exception surfaces
```

## 4. One logical office, replaceable Chat surfaces

The Meta-CEO is one logical organizational responsibility, not one immortal transcript.

Conceptually:

```text
responsibility_ref = SOL:META-CEO:MASTERMIND
role               = META_CEO
current_surface    = one exact RuntimeBinding
binding_generation = monotonically advancing generation
```

When a Chat conversation approaches context exhaustion, becomes unavailable, or is intentionally
retired:

1. the current Sol records the durable continuation in Agent OS and exact evidence in GitHub;
2. unresolved effects and operations remain visible;
3. the existing RuntimeBinding / SessionTarget owner transfers the exact logical responsibility;
4. the successor Chat loads a deterministic bootstrap from canonical owners;
5. the predecessor loses modifying authority through lease/fence/binding law;
6. the Chairman continues with the same logical Meta-CEO office.

No transcript database, Business-session database, browser-tab registry, or second Sol-election
service is authorized.

## 5. Sol hierarchy and authority

The Chat-native hierarchy uses typed roles:

| Role | Default surface | Authority |
|---|---|---|
| `META_CEO` | ChatGPT Pro Chat / Sol Pro where warranted | portfolio topology, cross-program adjudication, final in-policy acceptance |
| `PROGRAM_CEO` | ChatGPT Pro Chat | one major program and its bounded child graph |
| `PROJECT_SOL` | ChatGPT Pro Chat | one bounded project or workstream |
| `INTEGRATOR_SOL` | ChatGPT Pro Chat | canonical synthesis of assigned child outputs |
| `AUDITOR_SOL` | ChatGPT Pro Chat | read-only adversarial verification and attention creation |
| bounded worker | current least-cost capable avenue | exact commissioned implementation/research effect |

Shared Sol cognition or naming never grants equal authority. Authority remains contextual and derives
from the existing responsibility, Job/Attempt/Worker, RuntimeBinding, lease/fence, exact tool effect,
and current Chairman authorization owners.

For one unresolved child semantic turn, exactly one Sol target is action-authoritative. Other Sols may
observe or advise but may not independently issue `CONTINUE`, `RULING`, `STOP`, merge, retry, or a
successor commission.

## 6. Work topology

The company separates three graphs:

### Authority tree

```text
Chairman
    -> Meta-CEO
        -> Program CEO
            -> Project Sol or bounded worker
```

Every modifying decision has one action-authoritative parent.

### Work dependency DAG

Programs and projects may depend on shared data, releases, infrastructure, research, or product
capabilities. Dependency does not confer command authority.

### Event and dialogue fabric

Wake, Agent Relay, Company Dialogue, Slack, and future exact Chat adapters transport typed attention,
ACK, START, PROGRESS, BLOCKED, DECISION_REQUEST, RESULT, CONTINUE, and STOP edges. Transport text does
not become lifecycle or authority truth.

## 7. Chat session provisioning boundary

A future exact Chat provisioning capability must extend existing owners rather than introduce a new
session control plane.

The intended sequence is:

```text
Meta-CEO admits deterministic child responsibility
-> Capacity selects an eligible included-plan Chat surface
-> exact account/project/conversation target is resolved
-> approved Web-Sol/native adapter creates or selects the exact conversation
-> required model/effort mode is observed and receipted
-> compact bootstrap + exact commission is delivered
-> target PICKUP_ACK
-> continuation watcher armed/reused
-> separate START after current gates
-> RuntimeBinding records the exact current surface
```

Creating a tab, selecting a model, delivering text, or seeing a generated response is not ACK, START,
execution, or RESULT.

Provisioning must never choose by newest tab, title similarity, apparent browser activity, or account
nickname. It must not scrape transcripts as organizational memory or authority.

## 8. Pro-mode and capability honesty

`Sol Pro` or another high-effort mode is a cognition class selected for missions that justify it. A
session must not self-attest its model or effort mode merely through prose.

Where the host exposes observable model/effort state, the adapter records a bounded surface receipt.
If exact verification is unavailable, report:

```text
MODEL_MODE_UNVERIFIED
```

Do not claim a Pro-mode planning council or production proof from an unverified selector state.

## 9. Planning councils and consolidation

For a major ambiguous objective, the Meta-CEO may create several independent Chat-native Sol
responsibilities, such as:

```text
Product / thesis Sol
Systems architecture Sol
Research / competitor Sol
Execution-program Sol
Adversarial audit Sol
```

Default process:

1. independent first pass from the same frozen intent and current-source receipt;
2. one bounded contradiction/cross-examination pass where useful;
3. one Integrator Sol produces the canonical master plan with dissent preserved;
4. one independent Auditor Sol checks intent, authority, duplication, evidence, and executable scope;
5. the Meta-CEO accepts, rejects, or requests a bounded repair.

Repeated undirected “think harder” loops are not a substitute for independent decomposition and
adversarial integration.

## 10. Context and durable memory

Context scaling uses progressive disclosure:

```text
Tier 1: compact constitution and current operating envelope
Tier 2: portfolio hot state and attention summary
Tier 3: one program/project evidence bundle on demand
Tier 4: raw immutable evidence only when needed
```

The Meta-CEO does not ingest every project transcript. Program CEOs carry their bounded context and
return concise claims, decisions, evidence references, unresolved risks, and exact next actions.

Agent OS remains durable organizational memory. GitHub remains implementation and immutable evidence
truth. Chat history remains advisory and disposable.

## 11. Portfolio scaling model

Scale by durable responsibilities, not continuously generating tabs.

A large portfolio may contain hundreds of Agent OS responsibilities while only the currently
attention-worthy subset has live Chat bindings.

Use:

- multiplexing: one Program CEO supervises several related projects;
- parking: dependency-gated work consumes no active reasoning turn;
- session recycling: successor Chats recover from canonical state;
- bounded fanout: every commission states maximum depth and active children;
- backpressure: Capacity holds new work rather than silently spending on a metered route;
- independent integration and audit for consequential programs.

The production acceptance target is not “hundreds of tabs.” It is hundreds of recoverable
responsibilities with zero Chairman session hunting and exactly one current action-authoritative
executor per live turn.

## 12. Role of Business, plugins, MCP, Workspace Agents, Work, and API

### Business / plugins / MCP

Business and plugin work remains valuable as an optional companion connection layer for stronger
read/write adapters, app attestation, OAuth separation, and reversible cockpit canaries. It must not
replace Personal-Pro Chat as the default Sol cognition plane or imply that every CEO requires a
Business seat.

The existing Business Sol Surface Convergence program must reconcile to this law before any
Business-first or fleet-wide cognition cutover. Its no-super-MCP, no-session-database, federated
authority, and immutable-generation boundaries remain compatible.

### Workspace Agents

Use only when a recurring/event-driven capability cannot be served reliably by included Chat plus
existing deterministic wake/continuity mechanisms and the metered exception receipt is approved.
Workspace Agent trigger acceptance is not worker ACK, START, or RESULT.

### ChatGPT Work

Use only when its computer-use, artifact-production, or long-running bounded execution capability
materially improves the mission and the current credit/budget route is approved. A longer context
window alone does not override Chat-first decomposition.

### API inference

API inference is default-off for Sol-class cognition. Use it only under an approved metered exception
for a specific capability, availability, or bounded economic advantage. An API model must not become
a parallel Meta-CEO lifecycle, authority, session, retry, or memory owner.

## 13. Existing owner preservation

This architecture creates no new canonical owner.

| Fact | Existing owner |
|---|---|
| Job / Attempt / Worker / Event lifecycle, CEO admission | Executive OS |
| durable responsibility / decision / discovery / handoff | Agent OS |
| current exact reasoning surface | SessionTargetRegistry / RuntimeBinding |
| capacity and provider/account eligibility | existing Capacity Fabric / Model Router |
| attention, delivery, ACK, and source resolution | existing Wake owners |
| dialogue and transport | Company Dialogue / Agent Relay / Slack |
| implementation and immutable evidence | GitHub |
| selected portfolio projection | Linear |
| operating composition | Steward / Control Room |

Forbidden replacements include a Meta-CEO database, Chat-session database, Workspace-Agent lifecycle,
API supervisor lifecycle, browser-tab election service, duplicate scheduler, duplicate capacity
router, transcript memory store, retry ledger, or authority registry.

unreconciled cross-surface failover.

## 15. Implementation program

The architecture becomes operational through bounded vertical waves:

1. **CNM-F0 — protected core law:** make Chat-first cognition and metered-exception receipts canonical.
2. **CNM-R1 — route contract:** add a deterministic validation/projection seam in the existing routing
   owner; no second router.
3. **CNM-S1 — exact Chat surface receipt:** prove exact account/project/conversation and model-mode
   observation on a disposable non-Chairman surface.
4. **CNM-P1 — exact Chat provisioning:** create/select one disposable conversation, deliver bootstrap,
   and obtain ACK/START without transcript scraping.
5. **CNM-H1 — hierarchy canary:** one Meta-CEO coordinates three Chat-native planning Sols, one
   Integrator, and one Auditor with automatic returns.
6. **CNM-C1 — context rotation:** replace a context-exhausted Sol while preserving logical
   responsibility and fencing the predecessor.
7. **CNM-FLEET1 — bounded portfolio:** operate many durable responsibilities with a smaller active Chat
   pool, no manual session hunting, and no unapproved metered cognition.

Runtime waves remain blocked on their own current source, collision, authority, and production-proof
gates. Merging this architecture does not claim that exact Chat creation, model-mode selection,
mechanical return, or fleet cutover is live.

## 16. Acceptance

This architecture freeze is complete when:

- the law is protected in Mastermind;
- the mandatory routing source references it;
- deterministic tests prevent silent return to API/Workspace-Agent-first cognition;
- Business/MCP work is explicitly a companion rather than default cognition replacement;
- metered routes require a bounded justification and budget receipt;
- all existing lifecycle, memory, binding, wake, capacity, and evidence owners remain unchanged.

The full product is complete only when one Chairman-facing Meta-CEO Chat can create, supervise,
consolidate, audit, rotate, and close subordinate Chat-native Sol responsibilities without Chairman
message shuttling or unapproved metered inference.
