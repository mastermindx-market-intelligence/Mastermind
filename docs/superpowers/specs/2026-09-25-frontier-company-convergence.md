### Bounded Secretary decision-provider contract

The first AI Secretary implementation is a **provider contract, not a service**. Existing event detectors/owners assemble one short-lived owner-qualified snapshot and an eligible existing cognition route may return one recommendation. A deterministic validator admits only the closed Chairman action vocabulary:

`CONTINUE_CURRENT_SESSION`, `SWITCH_MODE_THEN_CONTINUE`, `REQUEST_CHECKPOINT`, `ROTATE_TO_SUCCESSOR`, `FANOUT`, `WAIT_FOR_RETURN`, `HOLD_EFFECT_UNKNOWN`, `ESCALATE_HUMAN`, or `STOP_COMPLETE`.

The validator owns no lifecycle fact and performs no action. It fail-closes stale/malformed snapshots and recommendation contradictions. Hard owner facts dominate AI preference: `EFFECT_UNKNOWN` may only recommend `HOLD_EFFECT_UNKNOWN`; an exact human gate may only recommend `ESCALATE_HUMAN`; owner-proven completion may only recommend `STOP_COMPLETE`. Rotation requires a ready checkpoint. Mode switching requires the session's bounded requested mode and never clears a denial/effect uncertainty. Fanout may select only caller-provided independent candidate IDs; it cannot author child bodies, place workers, or create a queue. Raw AI rationale is hashed for audit and is not forwarded as an execution instruction.

Every validated result keeps `execution_authorized=false`, `lifecycle_mutation_performed=false`, `browser_mutation_performed=false`, and `requires_owner_admission=true`. Existing Executive/RuntimeBinding/Capacity/Dialogue owners must independently re-read current state and admit or refuse the recommended action immediately before any effect. Repeated recommendations may later inform deterministic-rule promotion, but this contract creates no promotion registry or learning state. A pure shadow baseline may identify actions already forced by current owner-qualified safety facts (for example effect hold, exact human escalation, completed mission stop, checkpoint-before-rotation, wait-for-child, or an already-issued mode recommendation). It may also identify snapshots where multiple safe next actions remain and AI judgment is actually useful. Shadow receipts never promote a rule, persist a score, or execute an action; existing evaluation/records owners may aggregate them later. The provider request itself reuses the existing worker-execution seam: a pure renderer may supply only a bounded prompt string plus a closed JSON result schema for an existing admitted worker owner to place into its provider-neutral `WorkerLaunchSpec`. The renderer does not create that launch spec, select a worker/model/account, write a schema file, or start a process. Raw owner source refs never enter the prompt; the snapshot digest and source-ref count bind provenance while the model sees only the normalized decision facts needed to choose among the closed actions. A correlated provider-return validator must then rebuild the provider request from the **current** snapshot, require it to equal the exact request that was launched, hash the structured output, and only then pass the recommendation into the Task-4 semantic validator. This closes stale/mixed request reuse. It does not attest that the bytes came from a real provider/worker run: existing WorkerResult/CollectionReceipt/launch owners must supply that provenance before any recommendation can be consumed. A separate composition bridge may bind the exact Secretary provider request to an **existing** READ-only `WorkerLaunchSpec` and later correlate the existing `CollectionReceipt` by run/job/worker identity and successful no-write result. That bridge owns no worker lifecycle and does not re-implement collection. It may prove `worker_collection_correlated=true`; it must keep `provider_result_attested=false` unless an existing provider/adapter owner supplies stronger attestation.
