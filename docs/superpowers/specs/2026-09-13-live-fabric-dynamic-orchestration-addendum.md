## 1. What changes, and what does not

The Chairman's expanded requirement is a real operating workspace: see sessions communicate, see work spawn and return through several levels, control routing within authorized policies, understand waiting relationships, speak to a durable Master CEO office, and use the same system away from the primary Mac. A static organization diagram with an occasional status refresh does not satisfy it.

This amendment takes narrow precedence over the original September 13 Live Fabric design and delivery program for product scope, first-live-journey requirements, technology selection, CEO portability and remote topology. Exact identity, existing authority ownership, source qualification, effect reconciliation and production-proof laws remain unchanged. The five original records are retained, not rewritten as though these requirements had already been implemented.

Two conversational suggestions are withdrawn: a new Node-based routing/transcript/backend service family, and a new canonical append-only event store beside Executive OS. The existing repository already contains the Model Router, Operator Harness events, Company Dialogue and authenticated Python application seams. Extend those owners. Do not transplant a second operating system beneath the new interface.

The term **Live Fabric** names the presentation and interaction product. It does not grant that frontend organizational, runtime or permission authority. Its visible sophistication must come from real connected capabilities, not extra tables, arbitrary model confidence scores or perpetual decorative animation.

## 2. The product is a connected workspace, not six unrelated dashboards

Keep Decision-First Today as the Chairman's brief. From there, enter a full-screen operating workspace. A persistent mission/selection context joins four working areas: a topology canvas, actual dialogue, route/obligation detail, and an exact operator workspace. Each area can be enlarged or detached into a view; all refer to the same qualified source objects.

Clicking a delegation edge selects the corresponding commission and its delivery/consumption receipts. Selecting a message highlights its sender, recipient and admitted work where the join exists. Selecting a blocking relationship shows its originating decision or dependency, the accountable role, the actual target session or its absence, and the existing recovery action. Selecting an artifact opens its exact version and applicable review, not merely a similarly titled PR.

The first useful live release must contain real message content from at least one qualified managed provider lane, alongside a real mission and its actual recorded descendants. A graph that can show only synthetic dialogue is still a preview. We do not require every legacy provider or every account to work before that release; we require honest coverage and an independently useful real journey.

Three operating layouts serve different jobs:

- **Company operations:** progressive-disclosure topology, compact conversation rail, obligations and program outcomes. It is not a constant full-fleet hairball.
- **Mission room:** parent/child topology, simultaneous dialogue lanes, route decision, files/evidence and wait relationships for one outcome.
- **CEO office:** the Chairman's conversation with the durable executive office, accompanied by live delegation cards, accepted decisions and outcomes. Full transcripts remain available on demand, not copied into every CEO turn.

The UI answers “what happens next?” from an admitted next action or source-authored continuation. A model can offer a labeled recommendation, but cannot manufacture a scheduled next action, live owner or accepted priority.

## 3. Three kinds of information must meet without becoming one authority

| Information | Existing owner | What the UI may assert |
|---|---|---|
| Job, Attempt, Worker, session epoch, process generation and effect receipt | Executive OS and Operator Harness owners | The recorded lifecycle and exact applicability; provider activity is separately qualified |
| Commission, question, return, ruling, consumption and attention | Company Dialogue / Agent Relay / Wake | The actual semantic edge and receipt, not execution inferred from prose |
| Model response, visible commentary, plan, tool output and provider-native helper activity | Exact qualified provider adapter / its existing content owner | What that provider emitted, with content class and completeness; not organizational authority |

Agent OS supplies durable responsibility, intent, dependencies, decisions and continuity; GitHub supplies implementation and proof. Their records enrich the journey without being reclassified as native chat or runtime execution.

The existing rich harness already supplies `NormalizedEvent` and a generation-scoped `EventCursor`. Reuse their Attempt, epoch, process, turn, provider-event and native-subordinate references. A frontend publication sequence may order a view's updates; it is not another canonical event ID or replay authority.

A read-model document is one composed publication, not a distributed transaction across GitHub, Slack, provider streams and SQLite. Keep each source revision and coverage. Join exact references through their owning resolver; preserve unjoined observations when applicability cannot be established. Do not resolve conflicts by newest timestamp or majority vote.

### Recorded dialogue and provider dialogue are different panes

An operator's ordinary response may say “I have finished.” That is viewable dialogue, not final Job completion. A canonical RESULT may link to that output; parent consumption, independent review and final acceptance remain later facts. A sender writing another session's name is not evidence the other session received a message.

Each content block has a visibly selectable class: **message**, **tool activity**, **provider-visible plan/summary**, **system receipt**, or **advisory synthesis**. Hidden model reasoning is neither promised nor reconstructed. Show public commentary, available provider-approved reasoning summaries and tool evidence instead. An unavailable reasoning channel is a capability limit, not an empty transcript secretly filled by inference.

## 4. Provider capability reality changes the implementation

Public provider documentation establishes possibilities, not Mastermind installation or permission. Pin the actual binary/SDK/protocol version and the relevant existing adapter before enabling a capability.

| Lane | Current evidence | Design consequence |
|---|---|---|
| Managed Codex App Server | Official docs describe thread/turn/item events, response deltas, completed items, plan/diff updates and collaboration items. Local Mastermind already has a rich adapter. | Preferred first detailed observer candidate, subject to current admission and installed proof. Observe the existing owner; do not start a second App Server to inspect it. |
| Claude Agent SDK | Official streaming docs expose main-session partial output and complete subagent messages. Subagent token deltas are not forwarded by that documented stream. | Show a genuine parent stream plus completion-level child content. Do not animate root tokens as a child's thoughts. A richer future child stream needs separate evidence. |
| Claude's current Mastermind first lane | The protected provider-convergence design selects a sealed foreground CLI floor before a richer SDK port. | Do not silently substitute an SDK supervisor for PF1. The richer observer is a bounded extension through the existing Claude/provider owner. |
| Grok/other ACP providers | Mastermind's provider-convergence design selects an ACP-based direction and retains capability gaps. | Inspect and qualify the actual adapter/version. Never assume every provider implements resume, per-token streams or native fork equivalently. |
| ChatGPT Web / Pro research | Existing exact Web-Sol / RuntimeBinding / Wake program owns the browser session path. | A supported API research run is not the same object as a ChatGPT Web Pro session. Never rename one as the other. |
| Detected legacy/native session | Process or tab observation can prove presence only to its observer's ceiling. | Put it in an observed/unmanaged lane. Reading or adopting its conversation requires explicit existing-owner support and authorization. |

The inspected harness contract explicitly sets live App Server adoption to `NOT_SUPPORTED`. Detection cannot silently seize an already-running writer. Existing sessions retain their provider state and ownership. The first proof uses a deliberately admitted managed session, then expands compatibility without pretending legacy inventory is already controlled.

### Observation must not interfere with execution

One existing adapter owns the primary provider stream and its control responses. Spectator subscriptions receive a qualified projection from that owner. They do not compete to drain the event source, advance its execution cursor, send a hidden prompt, or keep a model turn alive merely because the GUI is open.

History reads must not resume or start a provider session as a side effect. In Codex, documented read methods can inspect history without starting a thread; experimental pagination methods require version-specific qualification. Other providers may have a lower supported ceiling. Unsupported history stays unavailable rather than being recreated by a new transcript scraper.

No new transcript archive is authorized. Existing source histories and approved artifact/content stores retain their material. Where a retained, access-controlled message body is genuinely missing, add a finite content-reference capability to the existing owner, with explicit retention and deletion behavior. Do not put an entire fleet's raw conversations into the lifecycle database or a new Live-owned memory service.

## 5. Streaming that remains correct under loss and correction

The interaction model distinguishes temporary deltas from authoritative completed items. A terminal item replaces its partial display, even when some or all earlier deltas were missed. Multiple completed blocks sharing a message identifier must not be dropped merely because the message identifier was seen once. Source block/item identity and revision govern replacement.

Late data from a prior selected mission, auth session, connection or provider generation cannot overwrite the current view. Duplicate source items reconcile to their existing display identity. A gap cannot be repaired by inventing text or by advancing a cursor past missing evidence. Reconnect obtains the applicable snapshot/history window from the same owner, then resumes from its supported cursor.

Streaming buffers are transient view mechanics. They never authorize resubmission of a command. Render coalescing may reduce token paint frequency; it must not acknowledge, suppress or drop a result, decision or action receipt from canonical handling.

Authorization precedes content release and is rechecked when a stream's principal or grant changes. Sensitive tool output is not accepted wholesale because the field is named `payload_redacted`. Whitelist display fields by event type and scope. Treat output, Markdown, links and terminal escape sequences as untrusted content.

Redaction is an additional protection, not proof that arbitrary text is safe. Split tokens can span stream chunks. The source owner must either use a tested streaming-safe content policy with bounded holdback or release that content only after complete-item filtering. Tool outputs without a safe preview contract remain scoped evidence links or completion summaries. Never export provider homes, cookies, environment dumps, credentials or unrelated personal conversations to make the dialogue panel look complete.

Proposed qualification targets, not measurements: at most 10 visual text updates per second per selected lane; 500 logical entities with no more than 120 rich cards expanded by default; a 2 MiB soft in-memory display-update buffer followed by explicit resynchronization rather than unbounded growth. Source limits may be stricter and always win. Measure owner-event-to-visible latency separately from provider generation latency; target p95 below two seconds on the qualified private observation path and below three seconds on the tested remote path, with network and load conditions recorded. These are product budgets, not permission-expiry clocks.

## 6. Dynamic spawning and multi-level orchestration

A role definition, an active session, an Executive child Job and a provider-native helper are distinct objects. The graph can render all four; only the owning records determine their relationships.

For independent work, the required sequence is: approved parent scope; child request; existing routing/capability decision; atomic capacity claim and admitted work; exact worker/session materialization; pickup/start receipts; observable activity; result; parent consumption; and the permitted next action. The canvas shows a proposed child distinctly from a launched child. It does not paint a successful spawn when only a request was submitted.

For ephemeral native helpers, show the native subordinate reference under the exact parent Attempt. They remain within the parent's effective capabilities and budget. Do not mint retrospective Jobs to make an observed helper look governed. Independently effectful work and independently accepted products must use the existing admitted child-work mechanism before those effects occur.

The desired full program can use several levels: CEO, program lead, principal orchestrator, bounded specialists and short-lived helpers. Depth, width, total spend, maximum wall time, repair rounds and workspace ownership are admitted constraints in the existing policy/capacity owners. Child grants cannot widen parent authority, and total reserved child budgets cannot silently multiply the parent's envelope. Current source law may permit less parallel effectful work than a provider SDK can technically spawn; the UI and rollout obey the actual accepted ceiling.

Use separate worktrees and effect scopes for concurrent writers. A principal reconciles artifacts against the frozen outcome and exact source versions. A reviewer must be independent in responsibility and evidence access; using a second account for the same author is not independence.

A late result remains attached to its original Attempt and artifact. It cannot satisfy a successor's acceptance by title similarity. A parent's CONTINUE is not permission for a stopped child to originate arbitrary next work. Approved recurring progression uses existing admission and continuation owners, not a frontend event handler.

## 7. Router controls: explain, simulate, approve, apply

The existing `ModelRouter` already returns `RoutingDecision`, including policy version, suitability tiers, capability profile, exclusions and reason codes. It chooses a logical route, not a running account. Capacity and Executive admission make the later concrete selection.

Expose four distinct interactions:

1. **Inspect actual route:** show the recorded request, policy/profile revision, available reason codes, chosen suitability tier and the separate concrete claim/binding receipt. Missing historical exclusions are `not recorded`, not an LLM explanation passed off as the router's reason.
2. **Simulate a proposal:** evaluate a bounded request against an explicit policy revision and observed capacity snapshot. Label hypothetical results. Simulation creates no Job, reservation, session, Wake or provider call.
3. **Propose a policy change:** show exact diff, current preimage, affected future request classes, budgets, provider eligibility and rollback. Use the existing reviewed policy/source owner; the GUI does not write an unreviewed parallel router configuration.
4. **Apply within current authority:** after accepted review/admission, activate the new policy through its owner and display readback. Existing in-flight Attempts keep their admitted policy and binding unless a separate accepted continuity operation changes them.

Routing criteria include task capability and quality, privacy, data residency where required, worktree/toolchain availability, review independence, quota/cost evidence, host pressure and exact-session constraints. Unsupported candidates are excluded, not tried until something works. Unknown quota is not free capacity. A powerful model name does not prove a usable tool environment.

“Pause new work” is an admission control on a stated scope. It does not kill running processes. “Re-evaluate” is not permission to move an in-flight writer. Rebinding after an uncertain effect is reconciliation, never a retry hidden by a different account.

## 8. The model-independent Master CEO office

The new product uses **Master CEO** as the Chairman-facing name for the existing logical Meta-CEO responsibility, not a second executive. Its provider and model are configurable implementations. The design does not elect a final model or assert that every frontier model becomes equivalent merely by receiving the same prompt.

The office receives current procedure, the approved capability profile, bounded source-grounded context, admitted mission/budget, durable continuity and exact tools. It is evaluated on tool use, long-horizon decomposition, correct authority, honest uncertainty, result consumption, recovery, cost and accepted useful outcomes. A provider switch requires a safe role-binding transition and stale-writer fencing; it is not a cosmetic dropdown change.

The current protected Chat-native cognition and budget laws still govern actual runtime routing. The Chairman's model-independent product requirement removes hard-coded provider identity from this design; it does not silently arm a metered API CEO or change existing production entitlements. Any eventual default-route change requires the corresponding narrow accepted policy change and real canary.

The CEO is awakened for decisions and material exceptions. Existing deterministic services retain obligations and perform eligible mechanical progress while no model is generating. The CEO does not spend tokens polling every worker or absorb every token from every transcript.

### Research-to-delivery journey

For an ambiguous program, the office may commission a qualified ChatGPT Web Pro research session when the exact supported browser path, mode evidence and current exception/budget rules permit it. The researcher returns source-backed findings, competing options, risks, unanswered questions and a versioned artifact. The CEO or designated integrator adjudicates that artifact and freezes the build outcome.

A genuinely cross-system/high-ambiguity build can then go to Fable as principal orchestrator. Fable receives the accepted artifact, bounded authority, source/workspace contract, integration sequence and acceptance ruler; it routes bounded work to the least-scarce capable workers. Review and production proof return to the appropriate parent. Straightforward work bypasses scarce principal capacity.

This chain is visible as actual delegations and artifact versions. API research, unverified browser automation and a ChatGPT Web Pro run are different execution surfaces and must stay labeled correctly. A source-generated summary never supplies evidence that a web session was created or consumed a request.

## 9. One hosted product, two clients, one authoritative runtime

**Product decision:** hosted web is the universal access surface; a Tauri macOS client provides a native shell over the same application model. Both can be used from a traveling MacBook. Neither client is the always-on company controller.

**Recommended first deployment topology:**

```text
Traveling MacBook / desktop browser / responsive web
        | HTTPS + authenticated, scoped application session
        v
Existing Mastermind VPS: web assets + approved application gateway
        | private encrypted connection; fixed enrolled services only
        v
Current single Executive / Steward / Dialogue authority services
        | existing admitted host/provider adapters
        +--> Mac workers and managed browser realms
        +--> qualified Linux/VPS workers
        +--> other enrolled hosts
```

The gateway exposes the existing owners through finite reviewed read/action routes. It owns no second scheduler, Worker registry, effect log or transcript brain. Reuse the existing Python/Starlette/Business-auth direction rather than inventing a parallel Node service family. The current MCP application is not automatically a public web-session backend; adding browser-facing resources, session handling and scopes is a bounded change through that same auth/application owner.

The present loopback Control Room nonce is not a remotely authenticated principal. Do not publish port 8787, tunnel the legacy UI as an unrestricted control API, or treat a trusted network header as application authorization. Keep provider credentials and host secrets at their existing owners.

Use the current approved private-network/host transport where possible. Tailscale Serve is tailnet-private and requires the appropriate enrolled client/access policy; it is not an internet-public website. A Cloudflare Tunnel is an optional outbound connector, not application authentication by itself. Either requires explicit deployment qualification; neither changes canonical ownership or permits automatic cross-carrier action replay.

The Mac app signs in to the hosted service through the established authorization flow. Its local bridge is optional and limited to proven fixed operations, such as opening an exact local surface. No generic terminal, arbitrary HTTP proxy or secret extraction bridge is bundled. WKWebView, client origin, CSP, signing and update behavior receive their own qualification.

### Hosting and availability are separate decisions

Hosting web assets on a VPS does not move the current Executive database there. Do not create an empty SQLite database to clear the screenshot's warning, copy an active database to a second writer, or mount its live files across machines. First establish the intended installed authority service and correct configured read target. The screenshot reports a missing runtime at one local path; it does not establish that the company's authoritative runtime is globally absent.

Moving the canonical controller to a VPS is a later explicit single-writer migration with accepted backup/restore, fencing, identity, rollback and restart proof. A gateway can be highly available before that migration without creating two controller authorities.

A sleeping home Mac cannot continue native browser or CLI work just because a remote page is accessible. Portable tasks need a qualified always-on worker; native/account-bound work remains attached to its enrolled host. The traveling MacBook can sleep or disconnect without stopping work running elsewhere. On reconnection it refreshes source state and reconciles pending action receipts. It never replays an offline queue of provider commands.

## 10. Technology selection and implementation boundary

| Layer | Decision | Deliberate exclusion |
|---|---|---|
| Shared UI | React + TypeScript, isolated Vite build, existing design tokens | No rewrite of Today or legacy shared assets to start the project |
| Graph | React Flow, incremental node/edge updates, bounded group layout | No whole-graph re-layout on every token; no new graph database |
| Server-state reads | TanStack Query; one qualified snapshot/subscription contract | No second authoritative client cache or polling every source per widget |
| Local presentation | Small Zustand store for selection, layout, filters and paused playback | No Redux + Zustand + XState stack; no client-owned runtime state machine |
| Long dialogue lists | TanStack Virtual; safe text/code components | No full transcript DOM or privileged artifact HTML |
| Terminal inspection | xterm.js only when a proven terminal adapter is admitted | Renderer does not grant terminal input, shell or host access |
| Auth/API/owner integration | Existing Python, Starlette and Business/Executive owners | No blanket new Node routing/transcript services; no unversioned MCP widening |
| Observation transport | Existing authenticated reads first; reviewed fetch streaming for updates | No token-in-URL EventSource workaround or new event bus |
| Desktop | Tauri over shared UI with narrow platform adapter | No second company runtime inside the Mac app |
| Verification | Existing Python tests plus Vitest/Testing Library and Playwright for the new UI | Fixture-only or screenshot-only proof cannot close the live capability |

Exact package versions and donor components are pinned during the source-admission/build step after license and compatibility checks. CodePress is workflow/UX evidence only in this pass; its linked pages do not establish a permissive code license. React Flow/Paperclip/OpenHands remain separately scoped donor candidates from the original intake record.
