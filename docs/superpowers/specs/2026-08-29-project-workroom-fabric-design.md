## 2. Product thesis

Slack is useful because it is a rich, shared collaboration environment: persistent channels, threads, Canvases, Lists, Workflows, links, files and human-readable notifications. Linear is useful because it is a structured human portfolio and project surface. Neither should be discarded.

The failure was not choosing Slack or Linear. The failure was asking each to perform jobs owned elsewhere:

- Slack became a queue, session registry, project board, watcher console and decision log.
- Linear was sometimes treated as either too weak to matter or authoritative enough to imply runtime/completion.
- Agent/provider sessions were allowed to choose or infer project context from prose.
- one giant `#agent-dispatch` channel became the place where unrelated programs collided visually.

The corrected thesis is:

> **Linear organizes the human portfolio. Slack hosts the project team. Agent OS preserves the organization. Executive OS runs the work. GitHub proves the effect. Steward composes the truth.**

A Project Workroom is therefore a premium collaboration **projection** over canonical owners, not another operating system.

## 6. Definitions

### 6.1 Initiative

A Linear Initiative is one company-level strategic outcome. It answers **why Mastermind is investing**. Initiative membership is owned by the accepted Initiative architecture and external rollout carrier.

### 6.2 Project

A Linear Project is the selected human projection of one exact Agent OS `WS:<KEY>` workstream unless a separately accepted architecture establishes another durable parent.

A Project is not a provider session, one PR, a temporary recovery attempt or an automatically running team.

### 6.3 Project Workroom

A Project Workroom is one persistent Slack channel bound to one exact eligible Project/workstream. It is the shared collaboration room for the Sol Project Steward, COO-grade operators, workers, reviewers and Chairman.

A Workroom is not:

- a lifecycle;
- a Job queue;
- an assignment registry;
- an Agent OS replacement;
- a decision authority;
- a completion store;
- a worker/session identity;
- a retry plane;
- a private memory database.

### 6.4 Operation thread

An operation thread is the exact Slack parent/thread for one bounded selected wave, gate, deliverable, review, decision or production-proof object. It is the dialogue carrier, not the operation identity or lifecycle owner.

### 6.5 Sol Project Steward

The Sol Project Steward is the logical CEO responsibility accountable for product thesis, architecture, decomposition, operator routing, adversarial review, acceptance and exact next action for a Project.

It is not one immortal ChatGPT tab, Slack user, provider account, browser seat or runtime process. Current action authority is resolved through existing responsibility/Executive/RuntimeBinding/dialogue owners.

### 6.6 COO/operator

A COO-grade operator owns one or more bounded operations under the Project Steward. Fable, CTO Sol, Terra, Opus or another governed worker does not become Project owner merely because it executes work in the channel.

### 6.7 Workroom Projector

The Workroom Projector is a least-privilege Slack presentation/projection actor that may create or reconcile approved Workroom channels and managed surfaces. It owns no dialogue authority, lifecycle, completion, capacity, provider, merge or organizational truth.

### 6.8 Agent Relay

Agent Relay remains the exact dialogue transport for approved operation threads. It does not provision channels, manage Project Radars or infer organizational parents.

## 7. Identity model

The architecture preserves distinct identity layers.

### 7.1 Organizational identity

```text
responsibility_ref = exact Agent OS WS:<KEY>
linear_project_id  = immutable exact Linear Project ID
```

No title similarity, channel name, Project summary, provider label or model judgment may manufacture this join.

### 7.2 Workroom projection identity

One deterministic workroom identity is derived from the exact `responsibility_ref`:

```text
domain       = b"mastermind.project_workroom.v1\x00"
workroom_ref = "wr-" + sha256(domain + responsibility_ref.encode("utf-8")).hexdigest()[:24]
```

The public schema is:

```text
mastermind.project_workroom_binding.v1
```

`workroom_ref` identifies the projection relationship. It does not become Job, operation, runtime, Agent OS or Slack identity.

### 7.3 Slack locator identity

```text
slack_workspace_id
slack_channel_id
```

The channel name is presentation only. Rename does not change the binding. A stable managed marker in the channel topic/purpose binds the Slack object to `workroom_ref` and `responsibility_ref`.

Conceptual marker:

```text
MMX-WR1 <workroom_ref> <responsibility_ref>
```

The exact serialized form is frozen in implementation tests. It must fit Slack's accepted field limits and use a closed grammar.

The Workroom Projector re-derives the binding from a complete read-only channel snapshot:

- zero matching channel -> `WORKROOM_MISSING`;
- exactly one exact match -> bound;
- more than one exact match -> `DUPLICATE_WORKROOM` and zero mutation;
- marker present but malformed/conflicting -> `WORKROOM_MARKER_INVALID` and zero mutation.

No mutable database of `WS -> channel` is created.

### 7.4 Operation/dialogue identity

```text
Executive child Job / canonical company operation identity
  -> one canonical Agent Dialogue parent
  -> exact slack_channel_id + thread_ts
  -> zero or more sequential Attempts
  -> at most one current action-authoritative Attempt/Worker
```

Slack timestamp IDs are transport locators, not logical operation identity.

### 7.5 GitHub identity

Repository, branch, PR, exact head and merge/proof identities remain separately bound evidence. A Project may span repositories. One operation may have zero or one current modifying carrier according to its commission.

### 7.6 No fuzzy joins

Forbidden identity inputs include:

- channel title similarity;
- most recent message;
- visible provider account;
- tab/window title;
- Slack user alone;
- Linear assignee alone;
- model prose saying "this belongs to X";
- newest matching PR;
- same market/department label.

Missing exact joins remain `UNKNOWN / UNBOUND`.

## 8. Workroom eligibility and lifecycle

### 8.1 Promotion criteria

A Project receives a dedicated Workroom only when the accepted static Workroom policy explicitly selects its exact `WS:<KEY>` and the current normalized Project is eligible.

Initial promotion criteria include:

- material multi-wave program;
- expected sustained duration rather than one small PR;
- multiple agents/operators or recurring Sol/COO dialogue;
- repeated decisions, reviews, gates or production evidence;
- material value to Chairman/project-team navigation;
- no unresolved organizational parent or duplicate Project identity;
- no privacy/audience conflict.

A Project is not promoted merely because it is `In Progress`, has many PRs or appeared recently in Slack.

### 8.2 Static policy, dynamic state

One versioned static policy may contain only stable presentation strategy:

```text
responsibility_ref
promotion_tier
visibility_policy
preferred_channel_slug
surface_set
retention_policy
```

It may not contain runtime, worker, retry, progress, completion, attention or provider state.

Dynamic state is recomputed from canonical owners on every plan/apply/readback cycle.

### 8.3 Visibility

V1 supports explicit visibility values only:

```text
PUBLIC_INTERNAL
PRIVATE_RESTRICTED
```

The policy must name the audience rule. Private Workrooms require exact membership and app-access proof; the projector never silently downgrades a requested private room to public.

### 8.4 Demotion and archival

A parked/completed Project may retain a historical Workroom. Archival is a separate reviewed projection action after:

- canonical organizational state is known;
- no active/effect-unknown operation remains;
- current dialogue has no unresolved turn;
- required evidence/links remain recoverable;
- readback proves the exact intended channel.

No channel is deleted merely to make Slack look tidy. Reopening a Project does not reuse an archived channel blindly; the binding is re-read and reconciled.

### 8.5 Initial scale

V1 begins with one inert canary, then three real Project pilots, then a bounded 10-15 Workroom fleet. It does not create channels for every visible Linear Project at once.

## 9. Organizational operating model

### 9.1 One Project Steward responsibility

Each materially active Workroom has one logical Sol Project Steward responsibility. One Sol reasoning surface may steward several Projects where capacity and attention law permit it.

For every unresolved child semantic turn, however, exactly one Sol target is action-authoritative. Sister Sols may observe and assist read-only; they may not independently emit competing `CONTINUE`, `RULING`, `REQUEST_REPAIR`, `STOP`, merge, retry or successor admissions.

### 9.2 Multiple operators in one Workroom

Multiple operators/workers may coexist in the same channel because the channel is a namespace, not a lock.

Each operation still has:

```text
one exact parent workstream
one stable operation identity
one selected Linear Issue when human-relevant
one Slack parent/thread
one current Executive child Job
one current Attempt/Worker/fence
one current modification carrier
one action-authoritative operator
one action-authoritative Sol turn
```

### 9.3 Concurrency law

The Workroom never grants concurrency authority.

Initial allowed company-scale concurrency follows protected autonomous-delegation law:

- multiple independent roots may execute concurrently on distinct lawful Worker realms after AD-FLEET1 proof;
- each root has at most one action-authoritative active child by default;
- broad same-root parallel write children remain held until separate workspace/branch/path/integration/failure-isolation proof.

A Project Workroom may display several planned, waiting, review-only or read-only operations while only the currently lawful subset executes.

### 9.4 Path and authority collision fence

Before any modifying START, the current owner must prove:

- exact repository/worktree/branch;
- intended changed paths or authority surface;
- current same-path PR/branch census;
- no effect-unknown predecessor;
- current Executive Attempt/Worker/fence;
- current Workroom/thread binding;
- current source-law revision.

Overlapping operations become `CROSS_OPERATION_PATH_COLLISION` and return to Sol before effect.

## 14. Dialogue and operation flow

### 14.1 New selected wave

```text
Sol freezes one bounded mission
-> canonical parent/work identity exists
-> selected Linear Issue is planned/bound when eligible
-> Workroom binding resolves exactly
-> AD-CHILD1 supplies deterministic operation identity
-> AD-DLG2 ensures exactly one parent in the correct Workroom
-> Executive admits/claims current Attempt/Worker
-> worker receives only the exact bound dialogue capability
```

A channel-level announcement is emitted only after the parent is known. It is a pointer, not admission.

### 14.2 Worker execution and return

```text
worker ACK / START / PROGRESS inside exact thread
-> canonical Executive/runtime remains authoritative
-> governed harness projects BLOCKED / DECISION_REQUEST / RESULT
-> WP-TW classifies turn
-> Wake targets exact current Sol
-> Steward/Radar show needs_sol or other exact turn
-> Sol CONTINUE / REQUEST_REPAIR / ACCEPTED-STOP
```

Provider/model etiquette is not the production return bridge.

### 14.3 Independent next wave

Terminal child STOP closes that operation thread/watcher cycle only. An active Project does not automatically create the next child.

If the parent remains active and no successor is admitted, Steward/Radar shows:

```text
PARENT_ACTIVE_NO_SUCCESSOR / needs_sol
```

A new child requires fresh identity, selection, admission, parent ensure and continuation setup.

### 14.4 Existing carriers during transition

Already-started/effect-unknown `#agent-dispatch` threads remain in place. The system may attach the correct Linear/Workroom projection around them but does not relocate/repost/restart them merely for cleanliness.

New operations enter Project Workrooms only after their work class passes the relevant cutover gate.

## 16. Security, privacy and rights law

### 16.1 Least privilege

Workroom Projector, Agent Relay and official Linear integration use separate principals/scopes because their authority surfaces differ. One superbot is rejected.

### 16.2 Secret handling

Tokens/client secrets are entered only through reviewed host-native hidden ceremonies using existing secret-owning patterns. Never place secrets in:

- chat;
- Slack;
- Linear;
- Canvas/List fields;
- GitHub;
- Agent OS;
- argv/environment/temp files/logs/receipts;
- model-visible browser settings.

### 16.3 Audience and licensed data

Workroom visibility and membership must match the strictest source/audience restriction of material projected there. A public/internal channel must not unfurl private customer, credential, licensed locator or restricted research content.

Links may be shown without copying underlying protected data.

### 16.4 Model-generated text

Models may summarize and propose. They may not author canonical IDs, runtime status, acceptance, authority or completion.

### 16.5 Slack edits/deletes

Edits/deletes do not cancel already-admitted operations. The owning canonical state is reconciled. Historical evidence is preserved according to current dialogue law.

## 17. Plugin policy

Plugins are evaluated as sources/actuators under the same owner law.

### 17.1 Sentry — optional later read-only adapter

Sentry may later provide source-attributed production issue/event evidence to Steward, Control Room and the relevant Workroom. It may not:

- originate Project state;
- automatically admit/retry work;
- close incidents or Linear Issues;
- become the alert/attention lifecycle owner;
- replace GitHub/production evidence.

It is not a core Workroom dependency.

### 17.2 Google Drive — optional external evidence navigation

Drive may hold lawful external documents that cannot live in GitHub. The Workroom may link or read them under audience/rights rules. Drive never becomes architecture, decision, project or handoff authority.

### 17.3 Notion, Confluence/Rovo, Airtable, Asana, ClickUp and monday.com — rejected as operating planes

These products are not added as Project/task/memory/workflow systems because they would duplicate Agent OS, Linear or Executive OS. A future narrow source integration requires a separate exact need and authority ruling.

### 17.4 Codex Security — bounded review only

Codex Security may be used as an additional adversarial review surface. GitHub/CodeQL/current repository security evidence remains controlling.
