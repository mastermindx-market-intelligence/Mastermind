## 1. Review finding

The original #313 records correctly rejected an Agent OS tools runtime, a second capability registry,
provider-specific brokers, ambient desktop access and name-only custom-skill identity. They were not yet
release-safe because they under-specified two existing architecture owners and promoted an older
`BSC-F2` milestone label as though it were a current executable carrier.

The missing subtractions were:

1. **Sol Capability Fabric (SCF)** already owns the one Chat-native model-facing capability experience,
   typed app/tool composition, capability-status projection, fleet commissioning surface and the rule
   that plugins/MCP/native connectors are adapters over existing canonical owners.
2. **Professional Practice Fabric (PPF)** already owns the future authority-free Professional Practice
   Pack and practice-to-surface adapter binding. Skills/plugins may project a practice, but neither this
   carrier nor an execution materializer owns professional doctrine, practice admission or evaluation.
3. The protected Business Sol program currently names `BSC-P1`, `BSC-A1`, `BSC-S1`, `BSC-E1`, `BSC-U1`
   and later canaries/cutover. It does not currently expose an active implementation carrier named
   `BSC-F2`, even though the protected Surface Fabric amendment still contains the valid architectural
   requirement for immutable installed plugin/app generation attestation in the existing
   `ExecutionCapabilityRegistry`.

Treating those omissions as harmless would create a parallel capability program and an imaginary
predecessor. They are therefore corrected before #313 release.

## 4. Corrected Business package-generation dependency

### 4.1 What remains valid from the older `BSC-F2` architecture concept

Before an exact custom plugin/skill generation can authorize or satisfy an execution profile, the
existing capability owner must bind at least:

- capability/package identity;
- immutable repository and commit;
- package root and native manifest digest;
- exact skill inventory and per-file/content digests;
- required app references where relevant;
- package/app generation;
- release/revocation state;
- exact capability/profile digest linkage.

A plugin cannot attest itself, and an installed/enabled label is not sufficient identity.

`BSC-F2`. Therefore the original wording:

## 6. Correct relationship to Professional Practice Fabric

PPF owns professional method. Its future `PracticeAdapterBinding` binds one accepted practice
generation to an exact execution-capability profile and exact adapter generation. The generic worker
capability substrate may help satisfy that binding, but it does not own or derive:

- `PracticePackDocument`;
- `PracticeSourceIdentity`;
- professional source precedence;
- practice coverage/admission;
- professional duties;
- artifact acceptance;
- independent practice evaluation;
- evidence-to-doctrine promotion.

The composition is:

```text
accepted Professional Practice Pack
   -> PPF-A0 adapter binding
       -> exact existing execution_profile_id / digest
           -> existing capability registry package/skill generation
               -> HF1/provider-native materialization and runtime observation
```

Practice source and executable capability source remain distinct identities even if one generated
Skill contains practice guidance. A capability digest proves exact bytes loaded; it does not prove the
model applied the professional method correctly. PPF's real evaluation still decides that.

No code in this program should import PPF parser/runtime concerns merely to hash or stage a Skill.
Likewise PPF must not fork provider materializers or the execution capability registry.
