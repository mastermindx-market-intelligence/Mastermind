The Chairman must not be the organization's message bus, session registry, worker-recovery daemon, watcher operator, provider-account load balancer, or the person who discovers that one executive/worker has silently stopped talking to another.

After the Chairman establishes or changes company intent, Mastermind must be able to answer and act on the following without requiring the Chairman to inspect `#agent-dispatch` or hunt among ChatGPT, Claude or Codex windows:

- which parent programs remain active;
- which child operations are actually executing, intentionally waiting, blocked, returned or terminal;
- which logical responsibility owes the next semantic turn;
- which exact runtime/session binding currently carries that responsibility when canonically known;
- whether the dialogue/attention path is healthy, degraded, split or unknown;

The target experience remains the accepted Operating-Surface Convergence end state: Control Room + Executive Steward + selected Linear projection show the company clearly while Slack becomes transport plumbing rather than the Chairman's operating dashboard.

## 2. Incident evidence requiring this amendment

### 2.1 Session-local watchers are not organizational continuity

Current transition-era handoffs routinely use session-local scheduled tasks/crons as temporary watcher bridges. Workers truthfully report that these watchers die with the session and often auto-expire after seven days.

This is lawful scaffolding only when the watcher reads the exact canonical dialogue carrier. It cannot be treated as durable organizational continuity, Worker liveness, Job state or proof that the responsible reasoning surface will return.

A repeated local poll that reports `NO_MATERIAL_CHANGE` does not prove the organization is healthy. It may instead prove that the polling surface is looking in the wrong place.

### 2.2 Parent programs can become orphaned after a correct child STOP

Multiple current programs demonstrate the same structural hole:

```text
parent remains active
→ child completes correctly
→ Sol sends terminal STOP
→ child watcher is disarmed
→ next child requires fresh operation identity and commission
→ no deterministic parent-level attention edge wakes Sol
→ program can remain active but organizationally idle
```

The universal session-close law is correct that terminal child A must not implicitly authorize child B. The missing behavior is a **parent-continuation attention edge**, not automatic next-wave execution.

A terminal child and an active parent are therefore distinct facts. Child STOP must close only the child dialogue cycle. If the parent remains active and has an authored next dependency/action with no active/admitted successor, the operating surface must derive `needs_sol` / `PARENT_ACTIVE_NO_SUCCESSOR` rather than silently treating the program as complete.

Observed examples during the incident census include Breathing Platform, Options Intelligence and the F04 Theme / Ontology / Transmission parent, where child STOPs were correct but the parent remained active and required fresh Sol admission.

### 2.3 Carrier-split watcher incident — Grok Secretary F0 review

Exact operation:

```text
grok-secretary-mcp-openclaw-f0-final-review-20260828-sol-004
```

Canonical Slack carrier:

```text
#agent-dispatch
channel C0BSBM78V1N
parent 1787908360.063299
```

Observed canonical Slack history contains only:

1. the direct-targeted Sol commission; and
2. Sol's `WATCH_ARMED` receipt.

There is no worker ACK, BLOCKED, DECISION_REQUEST, RESULT, PASS, REQUEST_CHANGES, HOLD or BLOCK on that carrier.

Chairman-supplied screenshot evidence from the target Codex task shows a separate session-local scheduled task repeatedly running roughly every fifteen minutes and reporting that the review remains nonterminal at `REQUEST_CHANGES`, while it waits for a Chairman/Sol repair packet **inside that Codex task**.

Thus:

```text
Sol watcher observes Slack for worker return
Codex watcher observes local Codex task for Sol repair
→ both watchers can remain alive
→ neither sees the other's semantic edge
→ dialogue never progresses
```

This is not healthy watching and not ordinary worker slowness. It is a **dialogue-carrier split**.

### 2.4 Codex workers repeatedly fail to project semantic edges to Slack

Chairman operational evidence indicates a repeated provider/surface asymmetry: Claude workers usually post the expected Slack dialogue edges, while Codex workers frequently continue working or polling locally without projecting the required company-dialogue edge back to Slack unless the Chairman intervenes.

This must not be solved by telling the Chairman to remind Codex more forcefully, or by relying on model obedience to remember Slack.

Current protected Codex-Sol law already separates:

```text
reasoning surface: codex
Slack principal: communication identity only
```

A Codex reasoning surface is therefore not itself a Slack communication guarantee. The company currently behaves as if starting a Codex task implies that the corresponding communication principal will project its semantic transitions. The incident disproves that assumption.

The system must enforce the bridge mechanically.

### 2.5 Manual account binding has recreated the Chairman dispatcher role

Current transition-era `OPEN_PICKUP` commissions commonly contain:

```text
ACCOUNT_BINDING: CHAIRMAN_SELECTS
```

This was a lawful safety boundary while Executive capacity/placement was not production-proven. At current company scale it recreates the Chairman as a manual provider-account allocator and prevents otherwise frozen work from starting unless the Chairman chooses a concrete Claude/Codex session.

The final architecture must remove this from the normal path. Until automatic placement is accepted, lack of a lawful receiver is represented explicitly as `WAITING_CAPACITY` / `needs_placement`, not as an invisible requirement that the Chairman find a window.

## 4. Canonical dialogue-carrier integrity

Every watcher-enabled reciprocal operation has exactly one lawful semantic dialogue carrier for the current child operation.

A temporary watcher is valid only when one of the following is true:

1. it directly reads the exact canonical carrier; or
2. it wakes a reasoning/communication surface that immediately rereads the exact canonical carrier before adjudication.

A watcher that polls only a local provider task, local transcript, task memory, GitHub comment stream or another noncanonical surface while the peer is waiting on Slack **must not claim healthy `WATCH_ARMED` coverage**.

The derived defect is:

```text
DIALOGUE_CARRIER_SPLIT
```

Minimum evidence:

- same operation key;
- two different observed semantic carriers or wait surfaces;
- at least one side is waiting for an opposite-side edge on a surface the opposite side is not projecting to.

The repair is reconciliation of the existing operation/carrier binding. It never authorizes a replacement Job, a new operation key, a new provider session, blind retransmission or cross-carrier failover.

## 5. Semantic edge projection conformance

### 5.1 Local execution is not company pickup

For any manual/transition worker commission, including Codex:

```text
local task exists != PICKUP_ACK
local task running != START
local task result exists != RESULT projected
scheduled task firing != dialogue alive
GitHub PR exists != worker returned to Sol
```

A worker is considered to have completed the **communication handshake** only when the required semantic edge is visible on the canonical dialogue carrier or has been accepted through the future canonical Agent Dialogue machine contract.

### 5.2 Required projected edges

Where the current dialogue contract requires them, the communication path must project the semantic equivalents of:

```text
PICKUP_ACK / ACK
WATCH_ARMED or WATCH_UNAVAILABLE
START
BLOCKED / DECISION_REQUEST
RESULT
terminal STOP consumption / WATCH_STOP_FAILED when applicable
```

The model/provider is not trusted to remember this as an etiquette rule. Production enforcement belongs in the existing Agent Dialogue / Worker Presence / Worker Harness / Wake owners.

### 5.3 Projection defects

Use these as **derived exception reason codes**, not a new persisted lifecycle:

```text
WORKER_RETURN_NOT_PROJECTED
SOL_RETURN_NOT_PROJECTED
DIALOGUE_CARRIER_SPLIT
ATTENTION_OWNER_UNRESPONSIVE
```

Examples:

- a Codex task has produced a review result locally but no canonical Slack/Agent Dialogue return exists → `WORKER_RETURN_NOT_PROJECTED`;
- Sol has adjudicated on a local/alternate surface but the worker's canonical carrier never receives that ruling → `SOL_RETURN_NOT_PROJECTED`;
- both sides are polling different carriers → `DIALOGUE_CARRIER_SPLIT`;
- a canonical attention obligation remains actionable but the exact bound reasoning/communication surface cannot be resumed or acknowledged within the accepted freshness window → `ATTENTION_OWNER_UNRESPONSIVE`.

These reason codes do not infer Job failure. They describe attention/transport defects only.

## 8. Parent-continuation attention

A terminal child never starts its successor automatically.

However, when all of the following are true:

```text
parent program/workstream is nonterminal
current child is terminal
no active/admitted successor child exists
parent record / accepted handoff has a lawful authored next dependency/action
no Chairman-only gate currently blocks merely surfacing the need for Sol adjudication
```

the Steward/attention composition must derive:

```text
PARENT_ACTIVE_NO_SUCCESSOR
turn_owner = SOL
```

This creates **attention**, not execution authority. Sol still performs current-state/collision reconciliation and commissions a fresh child only when current Chairman-authorized program scope and normal gates permit it.

This closes the current hole where correct child STOP silently strands the active parent.

## 15. Failure behavior

- local task says `REQUEST_CHANGES`, canonical carrier has no worker return → `WORKER_RETURN_NOT_PROJECTED`; do not pretend Sol owes a Slack response until the carrier split is reconciled.
- Slack has worker RESULT but Sol local task does not → turn owner remains Sol; attention path is degraded/unresponsive according to exact Wake/runtime evidence.
- both peers have live scheduled tasks but watch different surfaces → `DIALOGUE_CARRIER_SPLIT / SPLIT`.
- child STOPped correctly, parent active, no successor → `PARENT_ACTIVE_NO_SUCCESSOR`; wake/surface Sol for adjudication, do not auto-start child B.
- provider session vanished after an effect-unknown modification → preserve `EFFECT_UNKNOWN`; no reroute/failover.
- no legal capacity placement → `WAITING_CAPACITY`; do not make Chairman binding invisible and do not fabricate a provider.
- watcher cannot access exact canonical carrier → `WATCH_UNAVAILABLE / COMMUNICATION_BRIDGE_UNAVAILABLE`, not `WATCH_ARMED`.
- Slack delivery exists but Executive claim is absent → transport only; runtime remains unknown.
