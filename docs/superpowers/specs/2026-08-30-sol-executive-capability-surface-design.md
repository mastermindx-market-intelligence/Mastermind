## 1. Chairman outcome

Mastermind's primary executive intelligence should live in high-quality ChatGPT Sol conversations rather than in a continuously billed API supervisor. Those conversations must nevertheless operate the company with much greater visibility, precision and reach than an isolated chat normally has.

The desired experience is:

> The Chairman can give one outcome to CEO Sol in ChatGPT. Sol can understand the current company, inspect exact implementation and runtime evidence, commission bounded work through canonical owners, provision or retire exact reasoning surfaces, review returns and pull requests, diagnose CI/runner/host bottlenecks, execute permitted bounded actions, reconcile uncertain effects, close durable records, and report the result without making the Chairman shuttle messages or hunt through GitHub, Slack, Linear, provider windows, terminals or browser profiles.

The system must make the following jobs routine:

1. **Company orientation.** What material responsibilities exist, what is actually running, what needs attention, what is stale or contradictory, and what is the exact next lawful action?
2. **Implementation control.** Which branch, PR, commit, diff, checks, reviews and proof correspond to an operation? Is the exact carrier releasable now?
3. **Execution control.** Which canonical Job, Attempt, Worker and current binding own work? Can Sol commission, continue, stop, reconcile or close it?
4. **Surface control.** Which exact Sol or worker reasoning surface is current? Can it be provisioned, foregrounded, awakened, rotated or retired safely?
5. **Fleet control.** Why was a worker/model/realm chosen, what capacity exists, where is the bottleneck, and which lower-cost avenue can reliably execute the next bounded mission?
6. **Infrastructure diagnosis.** Are CI runners, tunnels, services, adapters, indices, hosts and transports healthy? What exact bounded repair is available?
7. **Evidence-based acceptance.** What user or machine capability exists now that did not exist before? Is it protected, installed, production-proven and accepted, or merely coded/green?
8. **Durable closeout.** Are GitHub evidence, Agent OS organizational state, Executive terminal state, Linear projection and reciprocal dialogue all reconciled?

The goal is not to maximize the number of tools. The goal is to minimize the distance between a justified executive decision and a correctly executed, source-attributed company operation.

### W1 — Bound routine semantic action

Examples:

- already-bound dialogue ACK/progress/block/decision request/result;
- exact same-carrier continuation or terminal STOP when the current action-target and dialogue law permit it;
- request a GitHub review;
- rerun one explicitly retry-safe failed CI job;
- acknowledge a Wake delivery;
- update a non-authoritative hot-state projection where an existing owner already defines that action.

### W2 — Consequential company action

Examples:

- submit one bounded CEO intent to CeoIngress;
- stop/requeue/roll over one exact Executive Attempt under typed lifecycle law;
- commission one canonical child responsibility;
- perform one expected-head guarded PR merge after current release gates;
- provision, transfer, rotate or retire one exact Sol surface;
- deploy or promote one exact accepted artifact.

W2 requires explicit current authority, stable operation identity, action-time state, no effect uncertainty, native confirmation where applicable and a closed post-effect receipt.

### A3 — Administrative infrastructure action

Examples:

- change branch protection, rulesets or organization settings;
- publish or replace a Business app generation;
- enroll/rotate credentials;
- change tunnel, host principal or service installation;
- modify provider/workspace administration.

A3 lives behind a separate principal and app generation, normally disabled. It is never bundled merely because an R0 observability app can see the same resource. Where an endpoint lacks a documented atomic or otherwise accepted mutation contract, the capability remains assessment-only.

## 6. GitHub executive capability architecture

GitHub remains the implementation, review, CI and immutable evidence owner. The new capability surface makes that truth cheaper and safer for Sol to consume.

### 6.1 Read-only release evidence

`mastermind.github_release_evidence.v1` evaluates one exact carrier from typed, complete GitHub facts plus one exact release policy.

It must account for:

- repository, PR number, base branch and head branch;
- protected base SHA, candidate head SHA and merge base;
- ahead/behind relation;
- complete exact changed-path census;
- draft/open/closed/merged state;
- mergeability, including an explicit unknown state;
- current protected-branch required checks and allowed merge methods;
- exact check identity, target SHA, terminal status and conclusion;
- complete review gate and unresolved review threads;
- evidence source references, freshness and pagination completeness;
- effect reconciliation when an exact PR is already merged after a lost response.

Its positive state is only:

```text
READY_FOR_EXPECTED_HEAD_RELEASE
```

The result may provide the exact tuple:

```text
repository
pr_number
expected_head_branch
expected_head_sha
merge_method
```

It must also state:

```text
organizational_authority_granted = false
production_acceptance_claimed = false
```

The tuple is evidence for a separate action-time release workflow, not a bearer token and not permission.

### 6.2 Collision census

A later read capability should answer whether another active operation owns overlapping source or semantics. It composes:

- open PR changed paths;
- exact branch/head identities;
- declared operation/carrier metadata;
- protected-source movement;
- current exclusive owners from accepted source law;
- known effect-unknown or already-started carriers.

It may classify:

```text
CLEAR
PATH_COLLISION
SEMANTIC_OWNER_COLLISION
SOURCE_LAW_MOVED
CARRIER_DUPLICATE
EFFECT_UNKNOWN_HOLD
EVIDENCE_INCOMPLETE
```

It may never select a winning writer, close another PR, branch deletion, transfer work, or create a replacement carrier.

### 6.3 Runner observatory

The runner observatory is read-only in its first generation. It should expose:

- exact runner ID and opaque host reference;
- online/offline/busy state;
- accepted labels, runner group and supported repository scope;
- current assigned job/workflow where available;
- software/agent version and staleness;
- queue demand by required labels;
- eligible-runner count and saturation;
- source timestamp and completeness;
- a typed explanation of why a workflow remains queued.

It must not expose credentials, registration tokens, raw host inventory, arbitrary process lists or SSH coordinates. Count alone does not prove overload; queue-to-label-to-runner evidence is required.

Runner registration, deletion, labels and group changes belong to A3 and remain separate.

### 6.4 Release action

The normal first release action remains the native GitHub expected-head merge call because GitHub documents the head SHA as an optimistic merge guard. A release skill must reacquire current policy and evidence immediately before the call. A `409`, timeout or lost response never triggers an alternate merge or blind retry; it triggers read-only reconciliation of the same PR and head.

A GitHub merge proves only that GitHub accepted the merge. It does not prove deployment, production behavior, user acceptance, Agent OS closeout, Executive terminal state or dialogue closure.

## 10. Tool contract law

Every model-visible tool must satisfy all applicable rules below.

1. **Closed schema.** `additionalProperties=false` or equivalent. Caller fields are the minimum semantic inputs.
2. **Host-owned privileged identity.** Actor, principal, bound operation, current Job/Attempt/Worker, target surface, channel/thread, repository credential and host coordinate are injected by trusted composition where possible.
3. **Static descriptions.** Retrieved GitHub/Slack/Agent OS/model text never enters tool descriptions or system instructions.
4. **No read-to-write chaining.** A read tool returns inert data. The server never interprets retrieved text and calls a write tool.
5. **Freshness and completeness.** Every load-bearing current claim includes owner, source reference, observation time, freshness and pagination/coverage status.
6. **Typed null and disagreement.** Missing, stale, conflicting and unavailable are distinct. No latest/newest/title/prose heuristic elects a winner.
7. **One operation, one carrier.** Modifying actions bind to a stable operation key and exact effect owner.
8. **No blind retry.** A mutation is attempted at most once inside the edge. Ambiguity becomes `EFFECT_UNKNOWN` and same-target read-only reconciliation.
9. **Idempotency where supported.** Executive roots, dialogue messages and other accepted owners use their current canonical idempotency keys. The app creates no parallel retry ledger.
10. **Exact release guards.** GitHub merge uses the expected head SHA. Base/head/path movement returns to reconciliation.
11. **Authority non-transfer.** Tool access, urgency, model confidence, OAuth role or connected-app permission never changes organizational authority.
12. **Bounded output.** Results contain only facts needed for the workflow; credentials, tokens, raw transcripts and broad source bodies are excluded.
13. **Immutable app generations.** Breaking schemas create a new reviewed generation and dual-run/cutover; no silent live schema drift.
14. **Disable and rollback.** Every live app/action has an explicit disable path that changes no canonical company fact beyond loss of that interface.

## 13. Cost and efficiency architecture

The main economic benefit is not that MCP calls are free. The benefit is moving deterministic archaeology and control out of frontier reasoning.

Today expensive cognition is often spent finding:

- the current PR and SHA;
- the current owner and carrier;
- check and runner state;
- whether a worker or Sol returned;
- whether the current surface is stale;
- which source disagrees;
- whether a write may already have happened;
- what exact next action is lawful.

The target division is:

```text
deterministic layer
  identity, state, evidence, health, freshness, routing, effect reconciliation

frontier Sol cognition
  strategy, architecture, synthesis, ambiguity, prioritization, review, adjudication
```

A later telemetry wave should measure, without capturing raw prompts/transcripts by default:

- Chairman manual navigation/message-carriage interventions per program;
- Sol turns spent on state archaeology;
- time from worker return to Sol adjudication;
- duplicate/stale carrier incidents;
- effect-unknown incidents and successful reconciliation;
- Fable/principal turns avoided by bounded routing;
- metered Sol-cognition exceptions and bounded cost;
- cheap-worker share by mission class;
- PR cycle time, repair loops and production-proof latency;
- tool-call failure, degradation and schema mismatch rates;
- source coverage and false-green prevention.

The architecture does not claim a dollar saving before baseline and canary telemetry exist. It predicts a large leverage opportunity because high-cost reasoning is replaced by deterministic typed reads and bounded low-cost execution, but promotion remains evidence-based.

## 17. Security and privacy boundaries

The capability surface must never expose or capture by default:

- OAuth access/refresh tokens, GitHub installation tokens or runner registration tokens;
- browser cookies, provider storage, passwords, Keychain values or secret file contents;
- raw environment variables, broad process argv, SSH keys or host shell history;
- arbitrary filesystem contents;
- full ChatGPT/Claude/Codex transcripts as company memory;
- private surface URLs, browser coordinates or native handles in model-visible outputs unless a separately reviewed opaque reference is required;
- hidden app authority tokens in UI props/local storage;
- unbounded CI logs or artifacts without size/redaction controls.

Pseudonymous principal/host/runner references are preferred. Exact raw identifiers stay inside the owner boundary where possible.

## 18. Product acceptance ruler

The end-to-end acceptance canary is:

```text
Chairman supplies one multi-program objective in ChatGPT
-> Meta-CEO Sol bootstraps current procedure and company state
-> Sol identifies real dependencies and attention owners
-> Sol commissions bounded independent work through canonical Executive/Capacity owners
-> appropriate cheap workers and subordinate Sols ACK and START
-> mechanical returns reach canonical dialogue/runtime state
-> Sol reviews exact code, CI, runner and production evidence
-> one blocked PR is correctly repaired; one ready PR is expected-head released
-> exact production/user capability is proven
-> Sol rotates one context and fences the predecessor
-> durable Agent OS, Executive, GitHub, Linear and dialogue closeout is reconciled
-> Chairman receives one truthful completion report
```

During the canary the Chairman performs zero routine:

- Slack archaeology or message shuttling;
- GitHub/CI/runner page hunting;
- provider/account/host selection;
- session/window hunting;
- watcher repair;
- duplicate-carrier reconciliation;
- manual compilation of project state.

The canary must also prove adverse states: stale evidence, effect uncertainty, runner outage, unavailable capacity, stale session, conflicting authority, hostile retrieved instructions and app disable/rollback.

## 19. No-rebuild boundaries

This program must not create:

- another Job/Attempt/Worker/Event lifecycle;
- another workstream/task/project database;
- another SessionTarget/RuntimeBinding registry;
- another Wake/attention inbox or scheduler;
- another Capacity/provider/account router;
- another retry/effect ledger;
- another Agent OS or plugin memory store;
- another GitHub source of implementation truth;
- another Linear synchronizer;
- another Slack task queue;
- another CodeIntel index/semantic owner beyond the accepted program;
- another Steward truth store;
- provider-specific `spawn_subagent` authority;
- generic root shell, SSH, SQL, browser or filesystem tools;
- a super-MCP that collapses privilege classes.

A new interface is acceptable only when it is a removable facade over an existing owner or a narrowly justified deterministic computation that stores no parallel truth.

## 20. Architecture freeze decision

Mastermind will build CEO Sol's power as a **coherent plugin experience over federated, least-privilege capability edges**.

The architecture intentionally maximizes:

- included-plan frontier cognition;
- deterministic state/evidence retrieval;
- exact source and effect semantics;
- cheap bounded worker execution;
- current-session operational clarity;
- reversible incremental rollout.

It intentionally minimizes:

- repeated frontier-model archaeology;
- Chairman operational labor;
- Fable/principal use for routine glue;
- generic credentials and broad tools;
- duplicate owners and silent failover;
- false completion claims.
