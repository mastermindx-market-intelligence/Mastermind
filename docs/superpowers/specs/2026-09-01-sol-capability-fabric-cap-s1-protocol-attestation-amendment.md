## 1. Final protocol-review finding

The protected AOC source required an exact provider-reported path for each `skills/list` row. Current
Mastermind fake-App-Server tests happen to return `path`, but the current official App Server protocol
documentation shows `skills/list` rows with name, description, enabled/interface and nullable plugin
ownership—not a required source path. The same official contract provides a stronger explicit
invocation primitive: a `turn/start` `skill` input item carries both the Skill name and absolute
`SKILL.md` path, and the backend uses that item to inject the full instructions. It also documents
process-local `skills/extraRoots/set`, `forceReload` and `skills/changed` invalidation.

A fake server's convenient `path` field cannot become production protocol truth. Conversely, the
absence of `path` from one moving upstream README cannot justify name-only attestation. CAP-S1 must
bind protocol facts to the exact pinned Codex binary used by the canary and combine provider
observation with deterministic source proof and causal process isolation.

The ruling is:

> **Prefer exact provider-returned path evidence when the pinned binary supplies it. Otherwise prove
> one-source causality in a fresh isolated process and invoke every Skill through an exact
> server-authored path-bearing input item. If the pinned binary supports neither path mechanism, no
> model turn is allowed.**

## 2. Protocol source precedence

For one CAP-S1 canary, protocol truth is established in this order:

1. exact candidate-selected Codex executable path, binary SHA-256, signed identity and version;
2. stable JSON Schema generated by that exact binary with
   `codex app-server generate-json-schema --out <sealed-temp-dir>`;
3. experimental JSON Schema generated by that exact binary with `--experimental` because the current
   adapter negotiates `experimentalApi=true`; experimental fields are not used merely because they
   exist;
4. a real initialization and request/response probe against that same binary;
5. current official OpenAI App Server documentation as corroborating discovery, not as an authority
   over a different installed version;
6. Mastermind's fake App Server only as a protocol test double.

The generated schema artifacts are bounded, secret-free, hashed, attached to the canary evidence and
deleted during cleanup. Their digest is part of the protocol-attestation receipt. If generation fails,
outputs are incomplete, or the runtime response shape contradicts the exact generated schema, return
`SKILL_PROTOCOL_SCHEMA_UNATTESTED` and do not start a model turn.

The canary may use only schema members accepted by the exact binary. It does not silently depend on a
future `main` branch feature or infer a field from a test fixture.

## 4. Exact source-root modes

CAP-S1 may use exactly one of two server-selected source modes:

```text
INSTALLED_RELEASE
VERIFIED_EPHEMERAL_GIT_ARCHIVE
```

### 4.1 `INSTALLED_RELEASE`

Use one already-installed exact Mastermind release whose release manifest, commit/tree and immutable
metadata are verified and whose package generation equals the accepted source contract.

### 4.2 `VERIFIED_EPHEMERAL_GIT_ARCHIVE`

For a pre-merge canary or a host without the needed installed release, create one fresh temporary
archive from the exact accepted Git commit/tree through a fixed server-owned Git repository. Verify
the archive's package with the same complete-tree/no-follow contract, make the source non-writable for
the canary principal where the host permits it, and delete it during cleanup.

This mode is a test artifact, not an installed package generation or replacement release owner. It
must not use the dirty candidate worktree's package bytes, network-fetch a package, depend on a user
plugin cache or persist a package installation record.

In either mode, the only accepted extra root is:

```text
<exact package root>/skills
```

and each explicit turn path is:

```text
<exact package root>/skills/<exact runtime name>/SKILL.md
```

The source mode, lexical and descriptor-resolved roots, source commit/tree, package source/generation
digests, directory identities and all seven file rows are bound into the canary receipt.

## 5. Fresh-process causal isolation

Every pathless-list CAP-S1 canary starts a **new App Server process** with:

- one dedicated independently authenticated `CODEX_HOME` selected by the canary owner, never the
  Chairman/default home and never model-selected;
- one fresh synthetic read-only Git workspace containing no `.agents`, `.codex`, plugin marketplace,
  Skill directory or project configuration;
- existing exact read-only sandbox and `approval=never`;
- command network disabled;
- MCP registry empty;
- plugin registry empty;
- apps/plugins/remote-plugin/MCP-app/auth-elicitation/multi-agent features disabled;
- `skills.config=[]`;
- `skills.bundled.enabled=false` for this exact V4 Skill canary;
- no extra Skill roots at process initialization.

The V4 canary profile's security config projection and digest must include
`skills.bundled.enabled=false`. Valid V3 profiles and current V3 config/profile/policy digests remain
byte-identical; the new field is not backported into V3 normalization.

After initialization and before `thread/start`, CAP-S1 executes this exact causal sequence:

```text
fresh process
-> skills/extraRoots/set []
-> skills/list forceReload=true == enabled set {}
-> verify exact package source snapshot
```

Every listed row must carry a nonblank bounded name and `enabled` must be a real boolean. The effective

The add-root set must be exactly the four required Skills. The clear-root set must exactly equal the
baseline. Otherwise return `SKILL_SET_CAUSALITY_FAILED`.

## 6. Two lawful source-attestation modes

### 6.1 Mode A — provider path present

When the exact generated schema and real response include one path/source locator per Skill row:

- require one row per runtime name;
- require the locator to equal the expected exact Skill directory or `SKILL.md` path under the one
  verified package root, according to the generated schema's semantics;
- reject relative, normalized-away, alternate-root, symlinked, missing or duplicate paths;
- recompute the effective closure before constructing the observed identity;
- still perform baseline/add/clear causality and explicit path-bound invocation.

### 6.2 Mode B — provider path absent

When the exact generated schema lawfully omits provider-returned path:

- exact provider evidence supplies the enabled name set and process-local add/clear outcomes;
- deterministic Mastermind verification supplies package source/generation and closure digests;
- the fresh empty baseline plus one server-owned extra root proves there is no alternate listed Skill
  source in the process;
- the client supplies the exact `SKILL.md` path in every `turn/start` Skill input;
- the exact generated input schema must prove that `type=skill`, `name` and absolute `path` are accepted;
- each turn's text contains the same `$<name>` marker, but that marker is never accepted as the source
  binding by itself;
- pre/post descriptor-relative source checks prove the invoked path and closure did not move.

This composite evidence may construct
`ObservedCapabilityIdentity(kind="skill", name=<runtime>, skill_content_digest=<closure>)`. The
receipt must preserve the provenance of each field rather than mislabelling the closure digest as a
provider-returned value.

### 6.3 Neither path mechanism available

If the pinned binary neither returns a usable exact path nor accepts an explicit path-bearing Skill
input item, return:

```text
SKILL_PATH_ATTESTATION_UNAVAILABLE
```

No model turn, `$name` fallback, prompt-pasted Skill body, provider-home copy, implicit search or lower
identity precision is allowed.

## 7. Closed structured turn-input seam

The current `CodexOperatorAdapter` accepts only a plain text string from `TurnInputLoader`. CAP-S1 may
extend the **Codex adapter**, without changing the provider-neutral `OperatorHarnessAdapter` method
contract, with one closed optional structured input:

```python
@dataclasses.dataclass(frozen=True)
class CodexSkillTurnInput:
    capability_id: str
    runtime_name: str
    skill_md_path: str
    skill_content_digest: str
    package_generation_digest: str


@dataclasses.dataclass(frozen=True)
class CodexTurnInputEnvelope:
    text: str
    skills: tuple[CodexSkillTurnInput, ...]
```

Rules:

- existing plain-string loaders remain valid and produce the exact current text-only wire payload;
- a structured envelope is accepted only when the adapter was constructed with one exact resolved V4
  canary profile and one verified source-root receipt;
- caller values are identities to match, never arbitrary paths to trust;
- the adapter derives the final absolute path from the resolved grant/source receipt and requires
  exact equality with the envelope;
- each Skill input must belong to the sealed profile, use one exact runtime name and closure digest,
  and be unique in the turn;
- CAP-S1 uses one relevant Skill per turn, in the frozen four-turn order;
- the wire input is one text item followed by one exact `skill` item;
- no raw path enters Executive Job constraints, remote worker wire, provider selection, model input or
  general routing;
- current worker production composition and `RemoteCodexOperatorAdapter` remain unchanged.

If implementing this seam would require widening the common provider-neutral wire or production
worker configuration, return `CAP_S1_STRUCTURED_INPUT_SCOPE_COLLISION` to Sol rather than silently
absorbing HF1 or a live route.

## 8. Source stability and invalidation

Before constructing observed identities, immediately before every path-bound turn, and immediately
after every turn, the canary revalidates:

- retained source/package directory identities;
- exact seven-file complete tree;
- package content/source/generation digests;
- all four closure and Skill grant digests;
- exact Skill input path;
- exact enabled four-Skill list with `forceReload=true` before each turn;
- exact Codex binary and generated-protocol schema digests.

Any `skills/changed` notification after the accepted list observation invalidates the launch
attestation. Before a turn starts, re-list and re-compare. During or after a turn, interrupt if safely
possible, refuse the candidate result, reconcile provider/process effect, clean up and record
`SKILLS_CHANGED_DURING_CANARY`. Do not rerun the same canary operation automatically.

A source/list/schema mismatch is never repaired by recomputing a new requested profile after the
process has started. That would change the target under an existing operation.

## 9. Exact real-model journey

After one `LaunchDecision.ALLOW`, CAP-S1 starts one ephemeral/synthetic provider thread and executes:

```text
turn 1: receive-commission
turn 2: return-progress
turn 3: escalate-decision
synthetic deterministic Sol ruling inserted as ordinary bounded text
turn 4: finish-operation
```

Each Skill turn includes:

```json
[
  {"type": "text", "text": "$<exact-name> <bounded synthetic instruction>"},
  {"type": "skill", "name": "<exact-name>", "path": "<server-derived absolute SKILL.md path>"}
]
```

The model output must satisfy a closed JSON schema or an equally closed parser proving these observable
behaviors:

- pickup ACK is separated from START;
- progress does not claim completion;
- the decision boundary is escalated rather than self-authorized;
- RESULT does not claim Sol acceptance or STOP;
- no live company operation, person, credential, branch, Slack channel or Executive Job is named.

The provider thread and model prose have zero authority. Bounded model output proves usefulness only;
it cannot prove its own source, grant, success or cleanup.
