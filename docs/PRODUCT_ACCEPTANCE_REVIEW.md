# Source-bound product acceptance

This optional composition connects the existing Agent OS compiler, Executive
review result, Company Dialogue request and COO-principal COMMIT owner. It does
not create a programme, worker, admission, grant, queue, listener or installer.
The ordinary six-tool Company Dialogue catalogue remains version 1.0.0 until a
trusted host explicitly composes the acceptance owner; that host advertises the
same six tools at version 1.1.0.

## Required existing owners

- Agent OS must explicitly associate the immutable execution commission with
  one current programme declaration. Matching objective text is insufficient.
  The declaration retains the original wording/source, current interpretation,
  correction chain, every criterion and every original proof obligation.
- The existing Executive supervisor may receive `product_acceptance_macro_root`.
  For a commissioned review with criteria, it acquires the full current basis
  through the canonical boot-packet CLI and retains it before provider launch.
  Recovery reads this original retained input; it never silently substitutes a
  newer source basis. Review v2 binds every expected criterion and obligation.
- An already admitted V3/V4 dependent work child may request a ruling for an
  independently approved prerequisite in its current dependency manifest. The
  product owner creates no acceptance step. The programme's existing plan must
  already commission useful consumer work and its prerequisite relationship.
  An aggregation root cannot request a ruling from its own COO principal.
- The trusted principal host must provide its existing Runtime, current
  principal binding, current requesting-child resolver and qualified Macro root.
  Existing binding, capability, transport and principal generation checks remain
  necessary. Source references, DTOs and matching hashes grant no authority.

## Decision and consumption

The only additional model argument is the bounded selector:

```json
{"purpose":"PRODUCT_ACCEPTANCE","subject_job_id":"JOB-subject"}
```

The owner derives the live issuer, exact terminal subject and reviewer, complete
source basis and proof. It retains the original send-start identity before one
Dialogue send. Repeating the selector reconciles that same request; an uncertain
send cannot be replaced by changing a session or inventing another request ID.

A reviewer must report SATISFIED, UNSATISFIED or UNPROVEN for every expected row.
Missing evidence or one unsatisfied/unproven required outcome prevents request
issuance and identifies the exact row requiring repair. This mechanical check
does not establish whether the review's evidence is true: the authorized principal
must inspect the actual original intent and delivered artifacts.

Qualification requires the exact visible original request, the existing Relay's
reply/authority validation, and the existing principal COMMIT owner confirming
identical committed RULING bytes in the current principal generation. The accepted
option must be within the existing commission. The result is
`RULING_QUALIFIED_PARENT_RETURN_PENDING`, never product acceptance.

The qualified receipt digest must occur in both the requesting child's canonical
terminal work result and the original root's canonical terminal aggregation. The
aggregate must retain the same subject/reviewer revisions and the exact consumer
result. The host's read-only `observe_product_acceptance(message_key)` projects
`PRODUCT_ACCEPTED` only after those joins and a fresh unchanged source-declaration
check. A summary, generic approve review, copied digest or visible uncommitted
ruling is insufficient.

Unrelated Git or workstream progress may change the source observation while
leaving the declaration unchanged. The original issued digest remains intact.
A changed criterion, correction, association, original clause or unknown field
requires source reconciliation; no hand-restamped digest repairs it.

## Qualification boundary

Tests exercise actual Runtime admission, independent review, terminal receipts,
COMMIT fencing and the MCP SDK. Their provider and Relay messages are explicit
fixtures. They do not establish authenticated delivery, principal judgment,
installed provider schema support, Office presentation or the seven-day R2
campaign. Qualified source/CI, protected merge, installation and observed original
parent consumption remain separate delivery facts.

A sealed `-I`/`-S` context runtime remains `CONTEXT_RUNTIME_UNQUALIFIED`; this module
does not choose another interpreter or relax isolation. Rollout must use the
incumbent Context and Executive release owners and their actual grants.
