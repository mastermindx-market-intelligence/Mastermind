## 1. Product ruling: one company, not a separate Meta-CEO office

**Mastermind OS is the working environment for a persistent AI company. Meta-CEO is a teammate in that company, not an isolated control panel.** The Chairman can speak directly to any permitted teammate, join a project room, inspect real teammate-to-teammate communication, follow a shared plan and work board, and open the documents/code/results produced by that work.

The default experience is conversational and collaborative. AI writes and maintains the project goals and plans under [AI-led project intake](MASTERMIND_OS_AI_LED_PROJECT_INTAKE.md). The human should not become a dispatcher, repeatedly relay messages, manually author planning forms or navigate unrelated bot sessions to reconstruct progress.

**Always-on means persistent identity and a real gateway/runtime wake path.** It does not mean permanent model inference, a green dot, a polling browser tab or an assistant promise to continue in the background. Identity, gateway availability, current task execution, last observation, scheduled wake and delivery state are distinct. A persistent teammate can be available, working, waiting, scheduled, paused, blocked or offline.

The Chairman reports a twelve-bot team. The designs use twelve illustrative role profiles; names, counts, messages and activity are explicitly sample data until an authenticated dynamic roster proves them. Do not hard-code twelve as an enrollment rule or pretend that this design census verified the live team.

### Navigation and ownership

The existing top-level **Team** destination owns the company experience: **Overview, Conversations, Work, Routines, Artifacts and People**. **Projects** remains the existing top-level project destination; company cards open its contextual plan/work/artifact views without creating a second project index or registry. The Meta-CEO shortcut opens the same persistent teammate DM as People/Conversations. Existing Inbox owns human attention and reserved decisions. Existing Knowledge, embedded Code and Settings retain their deeper jobs.

“Company” names the environment; it is not another bot platform, company-control backend or permission authority. Preserve the existing selected company/workspace/project identities throughout.

## 5. Core journeys and interaction contracts

### 5.1 Talk to Meta-CEO or any teammate

A person selects a persistent teammate from People, a room, a task owner or the pinned Meta-CEO shortcut. All routes resolve the same authorized profile/conversation identity; route changes do not create another bot or session. History and source links remain accessible when the gateway is offline, with new-send state reported honestly.

The chat composer supports text, permitted attachments, mentions and contextual actions. A profile inspector exposes role, permitted scope, relevant tools/skills, current project, actual work and recent results through existing settings/read APIs. It must not expose secrets or private chain-of-thought. Context selection is visible and scoped; changing context is not silent cross-project authorization.

Meta-CEO can infer a project from casual direction and maintain its plan, as required by AI-led intake. “Prioritize mobile” creates a versioned planning delta without erasing active work or requiring the Chairman to author a new plan. Changes to scope/spend/security or other reserved choices use the actual owner decision path.

### 5.2 Group rooms and actual collaboration

A project room joins named human and bot members, messages, threads, attachments, pinned decisions, work and artifact references. A bot-to-bot handoff is a real message/event with actor, target, originating room/message, task and result reference. Clicking an edge in C01 opens that actual record, not a generated summary masquerading as a conversation.

Mentions and bot activation follow the existing room policy. Do not wake every bot on every message or allow unlimited recursive bot replies. Respect admission/budgets, deduplication, per-room reply rules, cancellation and actual owner-held loop bounds. The UI shows the next responsible teammate and current work, not a fictional always-busy team.

Create-group and member-edit actions reuse page 16's existing flows: select enrolled profiles, purpose/project and permitted audience; commit through the actual membership owner; read back membership. A room member does not automatically gain access to every attached source. Membership changes revoke future access according to the source policy; avoid copying restricted full text into a broader room.

### 5.3 Work board and deep project execution

C04 is a coherent view of canonical work, not a new task engine. Preserve stable work/project/parent references. Backlog, ready, working, review and done are projections of owner-backed state. “Waiting for capacity” is not running. A returned artifact is not accepted. A merged PR is not production proof.

Dragging a card requests the allowed owner transition with target identity and expected revision; retain the old authoritative state until acknowledgement/readback. Show a reason for refused transitions. Keyboard users need a move/status action with the same contract. Moving a card to Done cannot manufacture acceptance, silently start work, close a GitHub issue or bypass review.

C05 joins the versioned plan/task tree, dependencies, owners, source materials, acceptance conditions, actual coding session and returned results. Opening Code preserves the originating project/task/conversation references. Every GitHub issue/PR status links to GitHub's current source; draft/ready/checks/review/merge/deploy are separate. Source permissions and actual merge controls bind.

### 5.4 Routines, scheduled work and continuous availability

Routines expose purpose, real owner, source scheduling system, trigger/schedule, IANA timezone, destination, expected output, permitted scope, overlap policy, next fire, latest run and complete return evidence. The UI can project multiple already-existing scheduling owners, but each routine resolves to exactly one of them; never mirror the same schedule into a second scheduler.

“Every Friday, prepare the customer brief” produces an AI-authored draft schedule and work definition, not an activated job. Activation/edit/pause/run-once use the enrolled owner and actual user grants. Run-once preserves original identity and cannot create duplicates on reconnect. Pausing a routine and cancelling an already-running task are distinct actions. Scheduler missed-run/DST semantics must come from the owner, not client arithmetic.

### 5.5 Artifacts, drafts and external systems

The artifact view joins the produced result to its author, project/task, original room, version, source and current audience. It is not another artifact store or a wholesale copy of external documents. Use current artifact owners, GitHub-native sources and real connector APIs.

Google Docs/Notion/Paper/GitHub rows have explicit connected, restricted, stale, unavailable or link-only states. A URL alone proves neither authorization nor successful ingestion. Do not fetch arbitrary private URLs from a server based on client input. Use allowlisted connector resource IDs and authenticated scope; redact restricted titles/content where required.

Draft, proposed, review, accepted, published and archived remain distinct. Comments must identify whether they are native source comments or a linked team discussion; do not pretend a local comment has been posted to Google Docs/Notion. “Ask Design to revise” is a real conversation/work request; it is not a direct document write. Direct editing, sharing or publication requires that source's explicit supported write and permission contract, exact revision/conflict handling and receipt.

### 5.6 Human control without making the human the coordinator

Surface only relevant decisions through the existing Inbox, with the recommendation, consequences and target. Ordinary planning and admitted work should progress without repeated human checkpoints. Stop/cancel/pause must name the exact work or schedule and report the actual owner acknowledgement. Global stop, role grants, spend or external sharing must never be inferred from “keep working.”

## 7. Failure, access and recovery behavior

C09 gives visual specimens; builders must implement their actual causes and transitions.

- **Empty:** show a useful permitted next action, not a fabricated twelve-bot company.
- **Loading:** retain the last known useful content with its timestamp; loading does not imply work advanced.
- **Offline/stale:** preserve conversation history; availability has an observed-at stamp. Do not silently queue a send unless the owner has durably accepted it.
- **Accepted but waiting:** retain the existing task and queue receipt; do not relaunch on a different provider to make it look active.
- **Delivery/effect uncertain:** keep original message/action/operation IDs; reconcile through the original owner before offering retry. A retry button must not duplicate a side effect.
- **Access denied or connector absent:** no fabricated document preview, cross-room disclosure, account fallback or permission elevation.
- **Conflicting updates:** preserve expected revision and newer accepted state; explain the conflict rather than overwrite work from another teammate.
- **Returned but not accepted:** link evidence and actual parent review; never turn a pretty artifact card or green CI badge into Done.

## 8. Donor implementation ladder and acceptance

This is the future implementation sequence, not work started by this design turn. Use the shallowest existing owner integration and preserve incumbent live writers.

1. **Identity and read composition:** bind actual enrolled Hermes profiles, Teamlink rooms, project/work identity, gateway freshness and real messages into C01/C02/C06. Prove cross-principal/project isolation and correct direct-message target.
2. **Conversation to work:** implement one real room request, bounded delegation, persistent work item and actual worker return with original room/message/task refs. C03/C04 must agree with the existing owner, including unavailable capacity and denied actions.
3. **Plan to code/document:** connect C05 to the existing plan writer and embedded Code or authorized document workflow. Preserve actual GitHub issue/PR state or source document revision, reviews and original-parent acceptance.
4. **Routines and artifacts:** compose existing schedule/run owners and source-native artifact/connector views. Prove pause versus cancel, run-once idempotency, access changes, original-result return and permission-aware previews.
5. **Hardening and parity:** signed-in web/macOS, mobile/desktop, EN/ZH and intentional dark/light designs; screen-reader semantics, visible focus, keyboard actions, appropriate touch targets and reduced motion. No CSS token swap alone counts as light-theme acceptance. Test real reconnect, interrupted writes, stale data and browser-closed wake.

### Required real-path acceptance witnesses

| Witness | Passing proof | Falsifier |
| --- | --- | --- |
| Persistent Meta-CEO | Same enrolled teammate and conversation survive navigation, reconnect and app re-entry | Each route opens a new bot, loses intent or requires a manually filled project charter |
| Direct teammate steering | A permitted message reaches the selected teammate with project context and source receipt | Wrong recipient, cross-project context leak, fake delivery or a new duplicate job |
| Team collaboration | At least two actual teammates exchange relevant work/results and the visible thread/graph resolves to the source records | Generated bot chatter, private reasoning exposure or activity with no underlying message/event |
| Granular delivery | Same plan → task/subtask → real code/document result → original room → original parent acceptance | Disconnected tasks, source status contradiction, PR green treated as production completion |
| Recurring work | Existing scheduled owner fires and returns a result with the UI/browser closed; show original run identity | Browser polling is the scheduler, duplicated cron or a completed schedule proposal mistaken for execution |
| Artifact access | Real document/code preview, comments and source links obey the principal's current ACL and revision | Joining a room reveals a restricted doc, local reply falsely claims native posting or an unconnected link renders invented content |
| Recovery | Lost response is reconciled against the original effect; no duplicate writes/runs | Automatic cross-carrier retry or state reset hides uncertainty |
| Mobile use | Human can read/reply, inspect task/subtasks/evidence and return to the original room on a narrow screen | Desktop-only inspector, clipped composer or inaccessible transition controls |
