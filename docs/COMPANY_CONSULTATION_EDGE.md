# Company consultation edge

The Company SDK is a separate product runtime. The sealed Executive control service stays SDK-free and owns the optional Company Unix listener in its existing launchd service. The listener is absent unless its exact `company_consultation` configuration is armed.

The capability registry has one fixed Company stdio grant and a distinct `operator.appserver.interactive.company-mcp.v1` profile. **That profile is disabled.** Its installed native admission and answer-consumption qualification are still outstanding; the ordinary interactive profile remains MCP-free. Building this edge does not prove live consultation, delivery, or original-parent consumption.

## Provisioning owner

After the exact reviewed release is installed and Company intake is disabled, root runs the installed release's `ops/executive_os/company_mcp_edge.py provision` with the signed framework Python and `-I -S -B`. The entry accepts no path, package, interpreter, index, socket, or UID selectors. It derives the release from its installed location, verifies the complete release manifest, invokes the existing Python runtime owner's `--verify-only`, and validates the installed control configuration before any package mutation.

The runtime is built at its final release-specific path under `/Library/Application Support/MastermindExecutive/mcp-runtimes/`. A root-only provision lock excludes concurrent builders; `.incomplete` marks an unpublished build. The existing product lock `requirements/executive-mcp-macos-arm64-py312.lock` is the only dependency source. The signed framework's bundled pip wheel runs with host pip configuration disabled, binary wheels only, required hashes, no cache and no bytecode compilation. Pip is not installed into the final runtime.

The complete read-only inventory and base/source evidence are sealed in `.company-mcp-runtime.json`. Startup hooks and bytecode caches are refused before the SDK interpreter is executed. A root-owned public configuration is published last at `config/company-consultation-edge.json`; it contains only fixed identity/digest fields, no credentials. The fixed stdio bootstrap verifies it, verifies the installed entry, and enters a stdlib verifier. That verifier checks the source, interpreter and complete SDK tree before executing the immutable SDK Python with `-I -B`.

## Interrupted provisioning

`verify` is read-only. A completed runtime with a valid receipt but no public configuration can be reverified by `provision`, which publishes the missing configuration without rebuilding packages. Failed builds are not silently reused or deleted. The explicit `recover-incomplete` command requires the same installed release, disabled Company intake, absent public configuration and exclusive provision lock; it preserves the marked partial tree (or the exact empty directory left before marker creation) under the fixed `mcp-runtime-archive` root and returns its archive path. `provision` can then perform one fresh build. A published or mismatched binding refuses this recovery path and requires reconciliation through its actual installed owner.

No provider session, CEO intake, trade authority, scheduler, extra service, or remote credential is created by this provisioner.

## Original caller RETURN composition

The installed Web CEO Sessions profile composes the existing `session_reply_read` tool through the existing private CEO ingress. Before the canonical CONTINUE writer runs, one immutable `SESSION_BRIDGE_CONTINUE_REQUESTED` event binds the authenticated caller to the exact root, Attempt, native generation, input digest, and physical dialogue thread. It proves only that the request was bound. The existing Dialogue writer still owns commit and deduplication; W3C still owns attention. No new session registry, return store, scheduler, or subscription is created.

A successful send returns an opaque `read_ref`. Reading it requires the same currently authorized caller identity and current native generation, original CONTINUE, deterministic native reply key, and matching validated Wake source on the same physical thread. Parent-message advancement on that thread is permitted; replacement threads and ambiguous replies refuse. The read has no state-changing effect and always returns `parent_consumed: false`. The public host requires its verified principal; only the installed private peer accepts the existing neutral projection. Live native consumption and the original parent's actual read still require acceptance evidence.

## Native read evidence

The Codex adapter records a digest-only Company read receipt for an exact successful MCP item in its current parent thread and turn, with the required and observed Company capability identities matching. Ordinary turns retain that projection in candidate evidence. Attention turns use the existing notification queue's atomic prefix selection through the exact native completion; foreign completion frames do not discard earlier evidence, late frames remain queued, and timeout reconciliation never sends another turn. One bounded unambiguous receipt is carried in the typed attention observation. Failed turns and absent, repeated, malformed or unqualified reads produce no projection.

The closed Operator Harness wire contract is `mastermind.operator_harness/v2`. Remote capability admission rejects earlier versions before a broker call; deploy matching reviewed controller and worker releases together. The projection is evidence only. It does not acknowledge a Wake, append `CONSUMED_BY_REQUESTER`, or establish parent RETURN. The Runtime consumption reducer is described below; its installed dispatch composition remains outstanding.

The current-writer Wake client carries this optional Company projection through its existing transport completion after checking the exact Attempt, process generation, RuntimeBinding, native session/turn and nudge. Foreign Company evidence is withheld while confirmed delivery and independently validated Wake acknowledgement remain intact. The projection is transient and excluded from receipt details and representations; the legacy Wake normalizer still returns delivery and acknowledgement only. No Runtime consumption follows from this transport extension alone.

Native read receipt v2 retains the full response and native-item hashes and adds a separate immutable answer attestation. It binds the available requester's exact answer, admitted INTENT and current ANSWER_AVAILABLE event identities, actor/counterpart, question, evidence revision, peer, deadline and Wake obligation. Delivery status and owed-turn labels may advance without changing this attestation. Historical-only, consumed, unavailable or ambiguous answers cannot produce it. A future Runtime consumer must still validate current binding, durable native delivery and exact carrier inside its existing transaction; this digest alone never grants consumption.

A qualified single-obligation delivery now stores the native read observation in the existing `DELIVERED` event. The closed `NativeCompanyReadEvidence` keeps all three read hashes, hashes the provider session and native turn identifiers, and binds the persisted route, nudge and outer Runtime Attempt. Coalesced or mismatched optional evidence is withheld while delivery remains recorded. Existing terminal replay returns this same evidence without another provider call; changed proof on the same delivery command conflicts. This closes the crash window between delivery and a later reducer, but still creates no consumption event.

The host now has an internal stored-delivery consumption seam, outside the public MCP tool set. It reconstructs a fresh service-owned Runtime caller and re-reads the exact Relay answer. Inside the existing consumption transaction, Runtime reloads the selected delivery and requires the current MCP capability, writer generation, session hash, frozen requester binding, exact requester answer-Wake and immutable answer attestation. The existing consumption event stores the original hash-only proof and owns idempotent replay. No connected-caller authority survives its request.

Production integration still has a specific gap: `company.reply` currently persists requester `WAKE_REQUESTED` only. It does not invoke the existing Wake carrier, so no requester native turn or stored-delivery reducer is reachable from that reply yet. Source tests deliberately invoke the existing dispatcher with a fake provider to qualify the Runtime/Relay consumer; they do not claim an installed native journey. The next composition must reuse the existing Wake owner and exact persisted request for dispatch/reconciliation, including restart recovery.
