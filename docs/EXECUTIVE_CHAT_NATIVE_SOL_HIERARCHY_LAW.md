**Detailed architecture:** `docs/superpowers/specs/2026-08-29-chat-native-meta-ceo-core-model-design.md`.

For Sol-class cognition economics, Meta-CEO hierarchy, Chat-first routing, reasoning-mode admission,
paid-surface exception admission, and the relationship between Chat, Business, plugins, Workspace
Agents, Work, and API inference, this law wins over older planning text that treats a metered agent,
API supervisor, or Pro reasoning mode as the default executive brain. It supplements the protected
Personal-Pro Sol Executive Shell and does not weaken any current lifecycle, authority,
runtime-binding, capacity, dialogue, retry, or evidence law.

## 1. Core ruling

**Personal-Pro Chat remains the primary Sol cognition plane; non-Pro reasoning is its default
mode.**

Personal-Pro subscription/account, Chat web surface, and reasoning mode are separate. A
Personal-Pro account provides an included Chat web surface; it does not make the turn-billed Pro
reasoning mode the default. The normal company architecture uses included Chat web with non-Pro
reasoning for Meta-CEO, Program CEO, Project Sol, integration, audit, and other Sol-class work unless
the bounded Pro-mode exception below is fully satisfied.

The current default receipt is:

```text
COGNITION_ROUTE: CHAT_INCLUDED_DEFAULT
CHAT_REASONING_MODE: NON_PRO_DEFAULT
```

`CHAT_PRO_DEFAULT` is deprecated and ambiguous. Historical plans, research, and receipts may retain
that frozen label, where it identifies the included Chat surface only. It grants no Pro-mode
authorization. New and amended receipts must separate cognition route from reasoning mode using the
current two-field form above.

The rejected default is:

```text
Workspace Agent front end
    -> API Meta-CEO supervisor
    -> replacement of Chat-native Sol CEOs
```

That stack may contain useful optional components, but as the default it duplicates paid cognition,
turns Chat into a thin interface, and makes executive cost scale linearly with every reasoning turn.
It is `REJECTED_BY_DESIGN` as Mastermind's core operating model.

This is an economic routing law, not a claim that any subscription is literally unlimited. Current
account eligibility, plan terms, model availability, usage policy, rate limits, session health, and
capacity remain current platform and Capacity-owner facts. Mastermind must not share accounts, evade
limits, scrape transcripts as a substitute for governed returns, or misstate an unavailable Chat
surface as ready.

### 1.1 Pro reasoning-mode exception

Turn-billed Pro reasoning mode is an exception, never a default. It is actionable only with this
complete receipt:

```text
COGNITION_ROUTE: CHAT_INCLUDED_DEFAULT
CHAT_REASONING_MODE: PRO_MODE_EXCEPTION
WHY_PRO_MODE: <specific frontier-reasoning advantage required by this mission>
WHY_NON_PRO_INSUFFICIENT: <specific evidence that non-Pro reasoning cannot reliably meet the bar>
PRO_MODE_TASK_CLASS: <one allowed class below>
EXPECTED_DURATION_MINUTES: <integer between 80 and 1440 minutes, inclusive>
STOP_CONDITION: <observable completion or abort condition>
```

The closed allowed classes are:

```text
LONG_HORIZON_FRONTIER_REASONING
CROSS_SYSTEM_ARCHITECTURE
HARD_DEBUGGING
ADVERSARIAL_JUDGMENT
```

All fields are required. `EXPECTED_DURATION_MINUTES` must be an integer between 80 and 1440 minutes,
inclusive, and therefore at least 80 minutes. The work must genuinely belong to the named class. A
class label, importance, model prestige, or a desire for more effort is not sufficient.

Pro mode is categorically refused for handoffs; `ACK / PICKUP_ACK / START / CONTINUE / STOP`
lifecycle or routing packets; status checks; monitoring / watchers / polling; message relay;
routing / placement / foregrounding; mechanical edits or tests; simple reviews; and other short
bounded work. Those turns remain `NON_PRO_DEFAULT` even when they support a larger program that may
separately contain a qualifying Pro-mode reasoning turn. An absent, incomplete, under-duration,
over-duration, ineligible, or stale receipt produces:

```text
PRO_MODE_REFUSED / USE_NON_PRO_MODE
```

Reasoning-mode selection does not grant organizational authority, a Job, lifecycle progress,
receiver identity, RuntimeBinding, effect permission, budget authority, or permission to keep a
reasoning session alive as a polling daemon.

## 2. Metered exception contract

API inference, Workspace Agents, ChatGPT Work credits, Business agentic credits, or another
incrementally billed Sol-class reasoning route is an exception:

```text
COGNITION_ROUTE: METERED_EXCEPTION
WHY_METERED: <specific capability, availability, or bounded economic advantage>
WHY_PRO_CHAT_INSUFFICIENT: <specific reason included Chat cannot reliably perform this mission>
EXPECTED_MAX_COST: <bounded estimate or approved accounting unit>
HARD_BUDGET_CAP: <enforceable maximum>
STOP_CONDITION: <observable completion or abort condition>
BUDGET_AUTHORITY: <current approved envelope or explicit Chairman decision>
```

All fields are required before a metered Sol-class reasoning commission is actionable. Missing or
unapproved fields produce:

```text
METERED_ROUTE_REFUSED / WAITING_FOR_LAWFUL_ROUTE
```

Convenience, easier programmatic orchestration, project importance, provider novelty, or a larger
advertised context window is not sufficient by itself. First determine whether the problem can be
solved by bounded decomposition, progressive disclosure, an additional Chat-native Sol session,
session rotation, or an already-paid worker avenue.

A metered route never grants broader organizational authority. It receives the same or narrower
responsibility, operation, RuntimeBinding, lease/fence, effect, and budget constraints as any other
surface.

Pro reasoning mode is not a metered cognition surface and `PRO_MODE_EXCEPTION` is not
`METERED_EXCEPTION`. The Pro-mode receipt controls turn-billed reasoning mode on the included Chat
surface; the metered receipt above controls selection of a different incrementally billed surface.
Neither receipt satisfies, implies, or replaces the other. The historical
`WHY_PRO_CHAT_INSUFFICIENT` field name remains unchanged in the metered schema and refers to the
included Chat surface, not authorization to select Pro reasoning mode.

## 3. One Chairman-facing Meta-CEO

The Chairman communicates with one logical Meta-CEO office:

```text
responsibility_ref = SOL:META-CEO:MASTERMIND
role               = META_CEO
cognition_default  = CHAT_INCLUDED_DEFAULT / NON_PRO_DEFAULT
current_surface    = one exact current RuntimeBinding
```

The office is durable; the Chat transcript is replaceable. A context-exhausted, unavailable, or
retired conversation hands off through existing Agent OS continuation records and existing
SessionTargetRegistry / RuntimeBinding succession. The successor receives the current binding
generation; the predecessor loses modifying authority through existing lease/fence and stale-binding
law.

Do not create a Meta-CEO database, transcript store, Business-session registry, browser-tab registry,
or Sol-election service to preserve this office.

The Meta-CEO owns company portfolio orientation, topology selection, cross-program adjudication,
allocation within approved envelopes, integration decisions, in-policy final acceptance, and
Chairman reporting. It should not absorb every project's raw context or perform routine
implementation labor.

## 4. Chat-native Sol hierarchy

The default organizational hierarchy is:

```text
Chairman
    -> META_CEO
        -> PROGRAM_CEO
            -> PROJECT_SOL or bounded worker
        -> INTEGRATOR_SOL
        -> AUDITOR_SOL
```

| Role | Default cognition surface | Bounded responsibility |
|---|---|---|
| `META_CEO` | included Chat web / `NON_PRO_DEFAULT` | company portfolio and cross-program decisions |
| `PROGRAM_CEO` | included Chat web / `NON_PRO_DEFAULT` | one major program and its child graph |
| `PROJECT_SOL` | included Chat web / `NON_PRO_DEFAULT` | one bounded project or workstream |
| `INTEGRATOR_SOL` | included Chat web / `NON_PRO_DEFAULT` | assigned synthesis and contradiction resolution |
| `AUDITOR_SOL` | included Chat web / `NON_PRO_DEFAULT` | independent read-only adversarial verification |
| bounded worker | lowest-cost / least-scarce capable avenue | exact implementation, research, or review mission |

Shared Sol cognition or naming never grants equal authority. The word `Sol`, a powerful model, a
workspace role, account access, app installation, or a browser session is not an authority grant.

For one unresolved child semantic turn, exactly one Sol target is action-authoritative. Other Sol
surfaces may observe, reconcile read-only evidence, advise, or audit. They may not independently
issue `CONTINUE`, `RULING`, `REQUEST_REPAIR`, `STOP`, merge, release, retry, or a successor
commission.

Authority remains the intersection of current Chairman intent, canonical responsibility or Job,
current Attempt/Worker where applicable, trusted surface identity, RuntimeBinding, lease/fence,
exact capability grant, current source state, and exact tool/effect contract.

## 5. Three separate graphs

### 5.1 Authority tree

Every modifying decision has one current action-authoritative parent. Sibling Sol sessions cannot
command one another merely because they share a project or model.

### 5.2 Work dependency DAG

Programs may depend on shared data, research, infrastructure, product, security, or release outputs.
Dependency does not transfer authority. A common prerequisite can block several programs without
becoming their executive owner.

### 5.3 Event and dialogue fabric

Wake, Agent Relay, Company Dialogue, Slack, and future exact Chat adapters transport typed attention
and reciprocal edges. Delivery, `ACK`, `START`, execution, `RESULT`, parent consumption, merge, and
production proof remain distinct facts.

## 6. Deterministic always-on control

**The always-on layer is deterministic.**

It consists of the existing Mastermind owners, including:

```text
Executive OS
Agent OS
SessionTargetRegistry / RuntimeBinding
Wake / Agent Relay / Company Dialogue
Capacity Fabric / Model Router
GitHub / Linear / Steward / Control Room projections
```

No language model must remain continuously generating merely to keep the organization alive.
Deterministic services hold lifecycle, memory, binding, attention, capacity, and evidence state. On a
qualifying event, they wake the exact Chat responsibility only when judgment is required.

A scheduled watcher is an attention re-entry hook, not a second executive or lifecycle. A healthy
open tab is not execution proof. A transport delivery is not target consumption.

## 7. Planning councils, integration, and audit

A major ambiguous objective may be decomposed into independent Chat-native Sol responsibilities,
for example:

```text
Product / thesis Sol
Systems architecture Sol
Research / competitor Sol
Execution-program Sol
Adversarial audit Sol
```

The default council process is:

1. each Sol receives the same frozen Chairman intent and current-source receipt, plus one distinct
   mandate;
2. independent first-pass conclusions are produced without mutual anchoring;
3. one bounded contradiction or cross-examination round occurs where material;
4. an `INTEGRATOR_SOL` produces one canonical master plan while preserving material dissent;
5. an independent `AUDITOR_SOL` verifies outcome, authority, duplication, evidence, executable
   scope, and acceptance;
6. the `META_CEO` accepts, rejects, or requests a bounded repair.

Repeated undirected “think harder” turns are not a substitute for independent decomposition,
evidence, integration, and audit.

## 8. Exact Chat provisioning boundary

A future exact Chat provisioning capability must extend existing SessionTargetRegistry,
RuntimeBinding, Capacity, Wake, and Web-Sol/native owners. It must not create a parallel Chat-session
control plane.

The intended sequence is:

```text
canonical child responsibility admitted
-> Capacity selects an eligible included-plan Chat surface
-> exact account / project / conversation target resolved
-> approved adapter creates or selects that exact conversation
-> required model / effort state observed where available
-> compact bootstrap + exact commission delivered
-> target PICKUP_ACK
-> continuation watcher armed or reused
-> separate START after current gates
-> RuntimeBinding records the current exact surface
```

Creating a tab, selecting a model, delivering text, or seeing generated content is not `ACK`,
`START`, execution, or `RESULT`.

Provisioning must not choose by newest tab, title similarity, account nickname, apparent browser
activity, or whichever Sol responds first. It must not extract whole transcripts as company memory.
Raw browser control never establishes Chairman or Executive authority.

Where model or effort state cannot be established from trusted host evidence, the truthful result is:

```text
MODEL_MODE_UNVERIFIED
```

The model cannot self-attest Pro mode through prose.

## 9. Context and memory economy

The Meta-CEO uses progressive disclosure:

```text
Tier 1: compact constitution and operating envelope
Tier 2: portfolio hot state and attention summary
Tier 3: one program or project evidence bundle on demand
Tier 4: raw immutable evidence only when necessary
```

A large API context window does not justify moving the whole executive organization to API billing.
The Meta-CEO should receive compact Program CEO returns containing claims, decisions, evidence
references, unresolved risks, and exact next actions rather than every child transcript.

Agent OS remains organizational memory. GitHub remains implementation and immutable evidence truth.
Chat history remains useful advisory context and can be retired after durable closeout.

## 10. Portfolio scaling

**Scale by durable responsibilities, not continuously generating tabs.**

A portfolio may hold hundreds of recoverable responsibilities while only the currently
attention-worthy subset has live Chat bindings. Scale through:

- **multiplexing:** one Program CEO supervises several related projects;
- **parking:** dependency-gated or inactive responsibilities consume no active reasoning turn;
- **session recycling:** a successor Chat reconstructs from canonical state;
- **bounded fanout:** each parent receives an explicit maximum depth and active-child envelope;
- **backpressure:** Capacity holds work rather than silently selecting a metered route;
- **independent integration and audit:** consequential programs do not self-approve.

The acceptance target is not hundreds of browser tabs. It is hundreds of recoverable
responsibilities with no Chairman session hunting, no routine message shuttling, no unapproved
metered inference, and exactly one current action-authoritative executor for every live turn.

## 11. Business, plugins, MCP, Workspace Agents, Work, and API

### 11.1 Business, plugins, and MCP

Business and plugin work remains valuable as an optional companion connection layer for stronger
read/write adapters, immutable package generations, app attestation, OAuth separation, and
reversible cockpit canaries. Those capabilities must not replace Personal-Pro Chat as the default
account/surface family and must not replace included Chat web with non-Pro reasoning as the default
Sol cognition plane or imply that every Sol responsibility requires a Business seat.

The Business Sol Surface Convergence program remains compatible where it preserves one experience,
federated authority, immutable generations, no super-MCP, no Business-session database, and no
parallel lifecycle. Before any Business-first or fleet-wide cognition cutover, it must reconcile to
this Chat-native economic default.

### 11.2 Workspace Agents

Workspace Agents are metered exception surfaces. Use one only when an event-driven or reusable role
cannot be served reliably through included Chat plus existing deterministic wake/continuity and the
complete exception receipt is approved. Trigger acceptance is not target `ACK`, `START`, or
`RESULT`.

### 11.3 ChatGPT Work

ChatGPT Work is a metered or quota-bearing specialist surface. Use it when computer use,
artifact-production, or long-running bounded execution materially improves the mission and an
approved exception receipt exists. A larger context window alone does not defeat Chat-first
decomposition.

### 11.4 API inference

**API inference is default-off for Sol-class cognition.**

Use API inference only for a specific capability, availability requirement, or bounded economic
advantage under the complete metered exception receipt. An API model may execute a bounded Attempt;
it must not become a parallel Meta-CEO lifecycle, authority owner, session registry, retry engine,
capacity router, or durable memory system.

## 14. Route receipt

For every meaningful Sol-class cognition commission, record before the worker/model route:

```text
COGNITION_ROUTE: CHAT_INCLUDED_DEFAULT
CHAT_REASONING_MODE: NON_PRO_DEFAULT
```

For a qualifying Pro reasoning turn, replace only the reasoning-mode line with
`CHAT_REASONING_MODE: PRO_MODE_EXCEPTION` and include the complete `ProModeReceipt` from Section
1.1. For a different incrementally billed surface, use the complete `METERED_EXCEPTION` receipt
from Section 2. These are independent gates.

Then apply the existing worker avenue and receiver-binding law:

```text
ROUTE: <worker/model + execution surface>
WHY: <mission fit>
WHY NOT FABLE: <why principal capacity is unnecessary>
```

or the existing `WHY FABLE` form. Cognition economics, worker capability, concrete surface,
organizational authority, and lifecycle state remain separate dimensions.
