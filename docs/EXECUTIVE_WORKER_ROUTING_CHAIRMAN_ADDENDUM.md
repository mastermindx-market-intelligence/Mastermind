# Executive Worker Routing — Chairman Addendum

**Authority:** standing Chairman routing law.  
**Status:** canonical organizational/CEO routing source law. It supplements `docs/EXECUTIVE_WORKER_ROUTING.md`; it does not by itself arm any runtime alias, provider, account, model, Cursor/Codex/Claude surface, Executive worker, queue or credential.  
**Precedence:** for CEO/manual delegation choice, scarcity policy, Fable admission and routing receipts, this addendum wins over older generic language that treats Fable/COO as the default operator. Existing Executive OS lifecycle, atomic claim, quota and provider-attestation law remains unchanged.

## 1. Core rule

**Fable is not the default worker.**

Mastermind has multiple execution surfaces and worker/model tiers. CEO sessions must choose the **lowest-cost / least-scarce worker that can reliably complete the bounded mission while preserving required quality, authority and independence**.

Do not send work to Fable merely because Fable is available, because the program is important, because the task is large, or because Fable carries the COO title.

Before every meaningful delegation, classify:

- task kind;
- ambiguity;
- technical/product risk;
- repository/system scope;
- architecture/authority sensitivity;
- expected continuity;
- whether the mission is sufficiently frozen to be executed by a bounded worker.

Importance and difficulty are not the same as ambiguity. A critical but fully specified migration may still belong to a bounded engineering worker with stronger review.

## 2. Organizational routing defaults

### SOL — executive/architecture owner

Owns product thesis, systems/experience/intelligence architecture, authority adjudication, program decomposition, architecture freeze, adversarial review and final acceptance.

Sol should not become routine implementation labor.

### LUNA — default fast bounded worker

Use for low-ambiguity bounded labor such as:

- mechanical edits;
- fixtures;
- tests;
- extraction;
- simple bugs;
- straightforward migrations;
- small, well-specified implementation.

Prefer Luna when the packet can state the expected behavior and proof precisely enough that little independent architectural judgment is needed.

### TERRA — default standard engineering/research worker

Use for:

- normal feature implementation;
- meaningful but bounded refactors;
- elevated research;
- standard debugging;
- independent technical review.

A substantial share of ordinary engineering that would otherwise drift to Fable should route here.

### SONNET — default Claude workhorse

Use for bounded multi-step engineering, research, documentation and general execution when the Claude tool/workflow environment is materially useful.

Prefer Sonnet over Opus or Fable unless the mission actually requires deeper judgment or principal continuity.

### OPUS — premium bounded specialist

Use for difficult but still bounded work such as:

- hard debugging;
- complex bounded refactors;
- adversarial review;
- multi-service technical investigation;
- reasoning-heavy execution after Sol has frozen the strategic boundary.

Opus is not the default worker for ordinary implementation.

### CODEX — preferred engineering execution surface

Use for well-specified repository work, parallel implementation waves, tests, migrations, refactors and isolated worktree execution.

Within Codex, prefer the least-scarce capable model tier: Luna for routine work and Terra for standard/elevated work where those bindings are actually available. Do not automatically select Sol-tier execution for worker labor.

### CURSOR — interactive engineering surface

Use when repo-local exploration, rapid implementation, browser/visual work, or long agentic IDE workflows materially improve execution.

Cursor is an execution surface, not a capability tier. Select the appropriate model inside Cursor rather than treating “Cursor” as the worker identity. Prefer faster/economical models for normal coding and stronger long-horizon models only when the work requires them.

### FABLE — scarce principal / escalation capacity

Reserve Fable for materially high ambiguity or principal-level demands, especially:

- sustained cross-repository programs whose boundaries cannot yet be safely frozen;
- architecture-sensitive implementation where contradictions must be continuously adjudicated;
- major system integration involving several existing authorities;
- recovery of stalled/orphaned programs where true state and next architecture must be reconstructed;
- unusually difficult long-horizon work requiring principal-builder continuity;
- exceptional strategic/technical review where lesser lanes are demonstrably insufficient.

Prefer Fable as a **principal/advisor** when possible: Fable resolves ambiguity, establishes the plan or adjudicates the difficult boundary, then bounded implementation waves route to Codex/Terra/Luna/Sonnet/Opus/Cursor as appropriate.

## 3. Fable admission rule

Before commissioning Fable, the CEO must record:

```text
WHY FABLE: <specific ambiguity, cross-system dependency, architecture sensitivity, or continuity requirement that makes ordinary bounded workers insufficient>
```

Insufficient justifications include:

- “important project”;
- “large task”;
- “Fable is our COO”;
- “Fable is strongest”;
- “Fable is available.”

If Sol cannot write a convincing `WHY FABLE`, route elsewhere or decompose the mission further.

## 4. Decomposition law

Do not select one worker/model for an entire major program by habit.

The normal shape is:

```text
Sol recovers intent and freezes architecture
→ Luna / Terra / Sonnet / Codex / Cursor execute bounded vertical waves
→ Opus / Terra / another independent worker reviews where warranted
→ Sol reviews against the original outcome and accepts/rejects
→ Fable enters only where principal-level ambiguity or continuity actually justifies it
```

One independently useful capability per commission remains the default.

A major program may legitimately contain several worker tiers. Routing is per bounded mission, not per program prestige.

## 5. Builder / reviewer separation

When practical, do not use the same worker/model as both builder and independent reviewer.

For consequential waves, prefer cross-model or cross-provider review when that improves independence without violating confidentiality, authority or availability constraints.

Independent review never grants the reviewer merge/release/authority rights beyond the review packet.

## 6. Surface ≠ worker ≠ authority

Keep three concepts separate:

```text
execution surface: Cursor / Codex / Claude Code / browser / other tool
worker/model: Luna / Terra / Sonnet / Opus / Fable / Sol / other approved model
organizational authority: Sol / COO responsibility / Executive OS admission / accepted role law
```

Choosing a model or execution surface never grants additional organizational authority.

Executive OS remains lifecycle authority where applicable. Agent OS remains durable organizational memory. Slack/Relay remains transport/hot-state. GitHub remains implementation/evidence truth.

## 7. Runtime-alias honesty

`docs/EXECUTIVE_WORKER_ROUTING.md` and `config/executive_worker_routes.json` describe the currently implemented Executive routing aliases and runtime capability. This addendum is broader CEO/manual routing policy.

Therefore:

- do not claim Sonnet, Opus, Fable, Cursor or any named account is Executive-runtime-armed unless current canonical runtime evidence proves it;
- do not fabricate provider aliases, model slugs, credentials or quotas to make the organizational policy look implemented;
- future runtime routing should converge toward this policy through the existing deterministic router and Executive OS claim path, not through a second router/queue.

Manual/session delegation may use an approved available surface even when the Executive runtime alias does not yet exist, but that remains manual transport and must not be mislabeled as Executive dispatch.

## 8. No blind failover

Once a modifying operation begins on one carrier/session, do not silently resend the same logical operation through another worker or surface because the first appears slow, disconnected or ambiguous.

Reconcile the first operation's canonical effect/state before rerouting. `EFFECT_UNKNOWN` blocks blind failover.

A new worker after a reconciled terminal/failed operation receives a new lawful commission/operation identity as required by current source law.

## 9. CEO routing receipt

For every meaningful worker commission, record internally or visibly:

```text
ROUTE: <worker/model + execution surface>
WHY: <why this route can reliably satisfy the mission>
WHY NOT FABLE: <why principal capacity is unnecessary>
```

For a Fable commission:

```text
ROUTE: Fable + <execution surface>
WHY: <mission fit>
WHY FABLE: <specific principal-level reason ordinary bounded workers are insufficient>
```

The receipt is explanatory/audit evidence. It is not lifecycle truth and does not replace Executive admission/claim records when those are applicable.

## 10. Default principle

> **Use the cheapest / least-scarce worker that can reliably achieve the required quality. Escalate capability when evidence requires it; do not start at Fable.**
