## 1. Core ruling

Mastermind will develop **professional specialization as a first-class quality system**, but it will
not create a second executive hierarchy or a permanent zoo of title-bearing agents.

The durable unit is a versioned **Professional Practice Pack**: an authority-free, surface-neutral
package of professional method, information boundaries, artifact contracts, evaluation criteria,
failure modes and learning rules. Existing `META_CEO`, `PROGRAM_CEO`, `PROJECT_SOL`,
`INTEGRATOR_SOL`, `AUDITOR_SOL` and bounded-worker responsibilities apply those practices.

```text
organizational responsibility
        x
professional practice
        x
exact execution-capability profile
        x
model / reasoning surface
```

These are separate dimensions. A practice label, Skill, tool, model, provider, Figma seat, browser
session or title grants no organizational authority.

## 2. Practice is not a session

A practice is reusable institutional expertise. A Chat, Codex, Claude, Cursor, Figma or API session
is a replaceable execution surface.

One capable `PROJECT_SOL` may apply several compatible practices sequentially. Additional specialist
sessions are admitted only where independence, contradictory objectives, information separation,
unique tools, genuine parallelism or empirically useful model diversity justify them.

The rejected default is:

```text
one role name = one permanent agent = one new control surface
```

Mastermind scales by durable responsibilities, reusable practices and bounded fanout, not by keeping
hundreds of nearly identical agent tabs alive.

## 3. Professional specialization is not persona theater

A task-irrelevant biography or prestige prompt does not constitute specialization. The following is
not an accepted professional control:

```text
You are a world-class designer with 25 years of elite experience.
```

A specialist composition must instead bind:

```text
MANDATE
INFORMATION BOUNDARY
METHOD
ARTIFACT CONTRACT
QUALITY / FAILURE RUBRIC
EXACT CAPABILITY REQUIREMENTS
AUTHORITY CEILING
INDEPENDENCE REQUIREMENTS
LEARNING / FALSIFICATION RULE
```

Role language may describe duty, but never substitutes for reproducible method, evidence and proof.

## 5. Practice Pack contract

Every accepted Practice Pack must be immutable at the selected Git commit or package generation and
must contain, directly or by bounded references:

1. `practice_id` and version;
2. mission classes and exclusions;
3. professional mandate and authority ceiling;
4. required and forbidden information;
5. ordered methods and decision gates;
6. required artifacts and rejection conditions;
7. professional, deterministic and outcome evaluation;
8. independence and conflict-of-interest requirements;
9. semantic capability requirements, never credentials or concrete accounts;
10. failure vocabulary and degradation behavior;
11. learning, promotion and doctrine-falsification rules;
12. surface-adapter status without claiming unavailable Skills or tools are live.

A Practice Pack must never contain current Job state, RuntimeBinding, credentials, numbered account
selection, live quotas, Slack receipts, mutable worker claims, current PR state or authority grants.

## 6. Skills and tools are adapters, not the profession

ChatGPT Skills, Codex Skills, Claude Skills, plugins, MCP servers and reference bundles are valid
surface-specific projections of one Practice Pack. They are not the canonical professional owner.

The existing Executive capability profile remains the sole reviewed grant for Skills, MCP servers,
plugins, sandbox, network, native helpers and write capacity. Practice source may request semantic
capability classes; it may not widen the selected capability profile, invoke an ambient tool, or
reinterpret technical access as organizational permission.

Where a surface cannot load the practice reliably, the truthful state is
`PRACTICE_ADAPTER_UNAVAILABLE` or `PRACTICE_GENERATION_UNVERIFIED`, not an improvised pasted persona
presented as equivalent.

## 7. Professional coverage admission

Before implementation starts on material work, the responsible Sol classifies professional coverage:

```text
GENERALIST
SPECIALIST_REVIEW
SPECIALIST_LEAD
SPECIALIST_LEAD_WITH_INDEPENDENT_AUDIT
SPECIALIST_COUNCIL
```

The classification is based on craft risk, user harm, reversibility, unique method/tool need,
independence need and cost of discovering professional defects after build. Project prestige or agent
availability is not sufficient.

A product artifact whose quality is not captured by functional correctness must not silently route
from general planning directly to coding. Where design, security, quant validation, data science,
research, growth or another practice is load-bearing, the corresponding artifact gate precedes
expensive implementation.

## 8. Diversity, selection and integration

Multiple sessions are useful only when they create meaningful independence or complementary search.
Diversity can arise from different mandates, information slices, methods, tools, models or creative
constraints. Multiple identical sessions with cosmetic titles do not prove professional coverage.

Consequential divergent work follows:

```text
independent first passes
-> explicit candidate artifacts
-> rubric-aware selection, not indiscriminate blending
-> bounded contradiction / repair where material
-> one accountable integration
-> independent audit
-> parent Sol acceptance
```

The selector/integrator is a first-class responsibility. A weak selector can erase the value of strong
or diverse candidate generators. Material dissent is preserved rather than averaged away.

## 9. Artifact and build gates

A professional claim is not shipped capability. Each practice defines tangible artifacts that must
exist before the next stage.

For Product Design, the minimum path is:

```text
current-state experience audit
-> user/task flow and information architecture
-> divergent reference compositions
-> selected design direction
-> responsive + loading + empty + error + stale + permission states
-> design freeze and implementation rubric
-> bounded implementation
-> live browser fidelity and usability audit
-> production proof and learning capture
```

A prose design plan without a real composition is `SPEC_ONLY`. A Figma frame without implementation
is not shipped product. Green frontend CI without real browser and breakpoint proof is not design
acceptance.

## 10. Evaluation and learning

Professional quality is evaluated through three separate layers:

1. deterministic gates such as state completeness, accessibility, overflow, contrast, schema or
   statistical invariants;
2. professional judgment such as hierarchy, coherence, information architecture, research quality or
   threat-model completeness;
3. real outcomes such as task success, time-to-insight, error rate, adoption, retention, drawdown or
   incident reduction.

Open-ended work should prefer evidence-bearing pairwise comparison and explicit tradeoffs over a
single fake-precision quality number.

Individual decisions and outcomes live in existing Agent OS/GitHub/evidence owners. Repeated evidence
may promote a rule into versioned repository doctrine. One result or one transient preference never
silently rewrites the practice. Stable doctrine carries scope, rationale, evidence, counterexamples,
version and a reconsideration trigger.

No `specialist_memory.db`, persona-resume store, transcript brain or practice lifecycle database is
created.

## 11. Composition-level reputation

Performance attaches to a reproducible composition:

```text
practice pack version
+ task class
+ model / reasoning surface
+ capability profile / tool generation
+ evaluation protocol
```

It does not attach to an anthropomorphic permanent agent identity. Model upgrades, practice revisions
and tool changes require fresh evidence. Provider marketing, model self-attestation or title seniority
cannot establish professional competence.

## 12. Product Design is the first falsifier

Product/Experience Design is the first vertical because the current generalist plan-to-builder path can
produce technically correct but professionally mediocre interfaces, while the output is observable
and can be compared against a generalist control.

The first real pilot must compare at least:

```text
Arm A  generalist Sol -> builder
Arm B  Product Design Practice -> builder -> independent Design Audit
```

A preferred three-arm experiment adds:

```text
Arm C  Product Design Practice + governed visual/Figma toolchain
```

The program does not generalize specialization until the specialist composition materially improves
professional artifact completeness and product outcome at an acceptable cost.

A missing specialist or tool blocks only the stage that genuinely requires it. It does not authorize a
weaker route to mislabel itself as professional completion.

## 15. Completion ruler

Professional specialization is complete only when a Chairman outcome can cause Mastermind to:

- identify the professional practices genuinely required;
- assemble the smallest sufficient specialist composition;
- bind exact current practice and capability generations;
- produce the required professional artifacts before build;
- route implementation to economical capable workers;
- obtain independent professional audit;
- prove the result through the real product path;
- measure whether specialization improved quality and outcomes;
- update existing durable doctrine and records without creating another control plane;
- recover the full ruling in a fresh Sol session without this chat.
