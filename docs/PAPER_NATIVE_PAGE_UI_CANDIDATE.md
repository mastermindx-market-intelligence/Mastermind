# Exact-target Paper native UI page pruning — candidate, not installed

**Scope:** One page deletion from an already cloned, exact-ID Paper file using the current first-party Paper desktop app; original file is immutable. This is **not** authorization for deletion, an active MCP tool, or a substitute for GitHub review and selected-seat installation.

## Evidence

In Paper Desktop 0.5.15 on the M1, right-clicking a page exposes **Copy link** and **Delete page**. Copy link on scratch clone `01M5HRAG5659SFE58D3PTA7D0V` for `p-1-0` returned the exact `https://app.paper.design/file/<fileId>/<pageId>` form, independently matching the Paper catalog's exact-file read. Native whole-file duplicate of the 57-page MASTERMIND PAGES original `01M2WGNCX9475G79JRKJTCM08P` created `01M5HVW84WZFE62DREB6QB9ZDJ` without modifying the source. Per-page reads: 57 equal page identities, 137,113 nodes, 887 boards, matching font lists and design tokens; 11 representative native JSX artboards equal, two image-bearing board screenshots byte-identical. **No pages were deleted on the production clone or original.**

## Candidate code

`integrations/paper_desktop/native_page_ui.py` is a private *opt-in candidate*, NOT exposed from the current MCP catalog. It reuses the exact source/clone plan from `clone_prune_guard.py`, bridge schema admission and lock. Before a deletion it requires original source identity/pages unchanged, clone metadata and page order matching, one kept page or more, a uniquely named page selected for removal, verified foreground clone, exact target page link from the first-party Copy link action, a freshly reopened observed Delete page menu, and pre-delete rechecks. Then it attempts **one** deletion and reads the original source and clone to establish observed outcome. It must not repeat after a lost subprocess response. A reported confirmation is metadata-specific, not full fidelity acceptance.

### Real first-party UI canary — October 22, 2026

M2's **live Business Paper plugin** created a disposable source file `01M5JRN1HWF62YK527NKCY7WD5`, created and renamed/reordered its two pages, then made a whole-file clone `01M5JS8TNZKQ01SJS4D0S9VQFC`. Separate exact-file reads confirmed source and clone each held `p-2-0,p-1-0` in that order. The M1's v14 Paper bridge and stacked native UI candidate `b6120e31...` with reviewed 0.5.15 schema built an immutable source/clone plan to retain `p-1-0` and delete `p-2-0` **from the disposable clone only**.

The first UI attempt returned `UI_MENU_ITEM_UNVERIFIED` because live Peekaboo OCR saw Delete page and Add divider but **missed Copy link** despite its clearly visible first-party menu presence. Readback confirmed NO page was removed; operation `paper-e2e-native-ui-prune-20261022-a` was not retried. A narrowly reviewed fallback locates the **non-destructive** Copy link coordinate only when precisely one Add divider and one Delete page OCR element share a first-party menu column and their row geometry matches bounded criteria; the clicked link must still return the exact file and page IDs, or deletion is prohibited. This fallback has positive and negative synthetic tests.

A new, separate same-carrier operation `paper-e2e-native-ui-prune-20261022-b` returned `CLONE_PAGE_UI_DELETE_VERIFIED`, `removed_page_id=p-2-0`, `retry_allowed:false`, `source_unchanged:true`. Two independent exact-file Paper reads subsequently confirmed the original scratch source still contained `p-2-0,p-1-0`, while the clone retained only `p-1-0`. Separate `clone_prune_guard verify` returned `CLONE_PRUNE_METADATA_VERIFIED` with `production_migration_accepted:false`. **This establishes a real one-page deletion from a disposable clone via the native UI candidate, with independent post-effect proof.**

### Independent review — second-menu target and source-fidelity repairs

The separate Fabric reviewer `paper-pr1780-independent-review-0466824f-20261022-b` returned **REQUEST_CHANGES** at exact head `0466824f25` with two independently reproduced P1 findings and a P2 OCR-anchor concern. (1) After copying a verified link from the first menu, a changed sidebar row could make the second menu target a *retained* page before the delete click; the original code detected the wrong deletion only afterwards. (2) The earlier `source_unchanged:true` receipt claimed more than the post-effect page-list/token comparison proved. The P2 issue concerned two unrelated OCR labels spoofing the inferred Copy-link location.

The revised candidate requires a **second real Copy-link action after the second menu opens**, preceded by a unique macOS pasteboard marker; if the link is stale, wrong file or wrong page, it refuses *without delete*. It then opens the final menu, requires Delete-page coordinates to remain anchored near the verified menu position and clicked sidebar row, and rechecks the current source/clone identity before the one destructive click. **After** the click it again checks retained native metadata and selected JSX on both source and clone; the success receipt now says `source_page_list_unchanged:true` and `retained_native_structure_reverified:true`, never `source_unchanged:true`. Reproducible tests assert zero destructive clicks on a second-menu page drift, stale second clipboard, final-menu relocation, spoofed distant anchors and bool-valued OCR fields; a content-only source drift after the click must return `EFFECT_UNKNOWN` rather than success.

The earlier M1 real canary remains proof of the *previous* version, not automatic proof of the revised three-menu implementation. A fresh scratch-clone real-path canary and exact-head hosted CI/independent review must be completed before enabling a user-facing destructive tool. Remaining non-atomic UI races require one selected UI owner; a Paper native API for atomic page movement remains unavailable.

### Further independent review and sidebar-content binding candidate

A second Fabric review `paper-pr1780-fix-rereview-b55ce7f-20261022-c` independently reproduced a **remaining P1**: moving the retained page under the unchanged coordinate at the *third* context-menu opening causes a wrong-page delete; menu-relative coordinates remain identical, and the old post-delete guard only reports `EFFECT_UNKNOWN` after damage. It also found a P2: a lone or persistent forged near-row `Delete page` OCR label can masquerade as menu content. That review is accepted as **REQUEST_CHANGES**, not approval.

The subsequent candidate guards the actual final menu differently: it fingerprints the left **sidebar row and its neighboring visible page labels** from first-party Paper screenshots captured on all three menu openings, using the macOS built-in `sips` crop and SHA-256 of PNG pixels. The crop is strictly **left of the opened menu/cursor** (a 15px origin, width bounded by the exact row click coordinate), so the menu cannot overwrite the visual evidence. Any changed row/list pixels or missing native screenshot, size/scale metadata, native `sips` support or digest refuses **before** the irreversible click with `UI_PAGE_ROW_CHANGED` / `UI_ROW_VISUAL_UNVERIFIED`. The final-menu OCR `Delete page` is additionally required to form a unique, aligned 42–80px vertical stack with real observed `Add divider`; a lone matching word is no longer enough. No Paper RPC occurs between the final visual check and the single click. The preexisting two fresh Copy-link ID proofs, catalog/lock admission, immutable clone-source plan and post-effect native readback remain mandatory.

A real **read-only M1 Paper Desktop 0.5.15 native screenshot check** found identical SHA-256 for sidebar crops of the same page across two independently opened context menus, and a different SHA for the adjoining page / shifted sidebar context. Targeted adversarial tests assert no Delete dispatch on a final third-menu *same-geometry different-page* substitution, missing/mismatched row fingerprint, lone forged Delete OCR or misaligned corroborator. A mutation test deliberately disables the fingerprint guard and reproduces the wrong-page deletion in a disposable fake, demonstrating that the new negative actually distinguishes the safety law. M2 full Paper tests: **256 passed, 29 skipped**. This is a new engineering candidate and does not inherit production acceptance from the previous real scratch canary.

### Exact-head independent review — screenshot freshness and strict metadata

Independent Fabric reviewer `paper-pr1780-visual-bound-review-1c4e683-20261022-e` returned **PASS for opt-in, attended scratch-clone use only**, with 25 adversarial probes, including the exact prior wrong-page attack and the mutation kill. This was NOT GitHub approval and did not authorize any autonomous/production Delete action. The reviewer identified two P2 repairs required before further live acceptance: (1) three Peekaboo screenshots were captured to the same filename without invalidating the old file, so a partial screenshot write failure could falsely reuse the earlier row fingerprint; (2) no direct CI test called `_row_visual_fingerprint`, leaving the screenshot-producing safety logic unprotected. A new PR revision requires each menu capture to remove the previous screenshot **before** Peekaboo and each crop to remove the previous output **before** sips. Successful tool status without a newly written output now refuses rather than trusting old bytes. New stdlib-only tests run the real fingerprint-producing function with a strictly validated fake sips command, cover valid PNG hash, actual menu screenshot recreation, stale screenshot/crop, denied unlink, missing output, malformed metadata, wrong scale, subprocess timeout and invalid PNG. Those tests also found and repaired Python `True == 1` acceptance: output scale now requires an exact integer type with value 1.

### Copy-link exact-target and visually distinct page admission

The accepted prior Fabric review `paper-pr1780-fingerprint-fresh-review-24b0416-20261022-f` returned **PASS for attended disposable scratch clones**, and verified both stale screenshot/crop P2 fixes with independent producer mutation tests. No automatic production safety approval was given.

A further source-only hardening revision requires BOTH first-party **Copy link** actions to overwrite independently written, operation-bound clipboard markers, not merely differ from whatever happened to be on the pasteboard. Both observed `https://app.paper.design/file/{fileId}/{pageId}` URLs are strictly parsed and must resolve to the exact immutable *clone file ID and approved deletion page ID* from the guarded plan. Before the third-menu Delete click, a new pre-dispatch clipboard check must confirm the *second* proven URL is still intact and parse it against the exact identifiers. A pasted or externally changed wrong-page URL refuses **without deleting**. This final clipboard check does **not** claim that the third menu itself provides a fresh Paper identity link.

Paper's visible left sidebar screenshot intentionally covers a narrow label width. Even two different full page names can render indistinguishably when truncated. A strict clone-only admission guard now refuses short, non-ASCII/bidi/control, or first-six-character case-insensitively ambiguous names among the pages present in the clone. The row fingerprints of the three menu observations and the two exact Copy link identities remain separate mandatory checks. Negative regressions prove no UI click for ambiguous visible prefixes and no destructive click on first-marker failure or clipboard target tampering before Delete. A successful receipt counts **two** fresh exact-link verifications and one final evidence-preservation check; it does **not** claim a provider-atomic target binding.

**Honest release scope:** This remains a non-atomic first-party GUI helper for attended **disposable clones only**. It is not a worker-facing MCP Delete tool, nor is it safe for an unattended production delete on files with collaborative editing/identical rendered page stripes. No `fileId/pageId`-atomic native Delete API exists in the reviewed catalog. Completing CI and independent review accepts at most that limited source candidate. Do not re-label screenshots or post-effect `EFFECT_UNKNOWN` as preventive guarantees.

**Residual, not hidden:** First-party Paper exposes no observed atomic `delete_page(fileId,pageId)` action through the reviewed catalog. Human/collaborator mutations between the final screenshot and UI click are not atomically preventable; matching visible prefixes or UI animation can lead to false matches or fail-closed refusals. The safe deployment boundary remains **scratch clones only with one selected UI writer and attended proof** until current-head independent review, hosted CI and a stronger atomic binding/operational release contract are accepted. This is not authorization to delete any source or preservation clone.

Run any future deletion only after separate operator approval, source review, and selected-session installation. Never start a second browser/tunnel/agent or use raw Paper endpoints to perform deletion. It does not grant deletion of MASTERMIND PAGES or its preservation copy, which has a known eight-node Commodities discrepancy. Any error/uncertain actuation retains its original carrier. The source is still an opt-in candidate; synthetic and real *scratch* success is not evidence that all Business plugin consumers have a published deletion action.
