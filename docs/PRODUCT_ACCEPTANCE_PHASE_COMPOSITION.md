# Product acceptance across requesting and receiving hosts

The requesting worker and the receiving principal exist at different points in
the same decision. A worker request must exist before the principal's incoming
App obligation can be acquired. Giving a requester the principal COMMIT owner
to read a receipt is therefore not a workable installed composition.

The receipt reader now uses the existing Runtime-issued request and qualified
ruling events without holding a principal owner. It rechecks the current exact
requester context, subject and independent review, complete retained proof and
unchanged original-intent declaration. A repeated selector returns the existing
qualified digest without another send, Relay read or event append. When no
qualified receipt exists, the original reconciliation-required state remains;
absence of a receipt does not establish whether an earlier send happened.

The actual receiving App factory supplies the same exact sealed Context reader.
After a successful product-accept RULING, its existing COMMIT owner qualifies the
original request selected by its principal reply binding. The retained worker
context has no send grant. A qualification failure preserves the original send
result and reports qualification pending; it must never trigger a replacement
RULING. Acquired binding resolution rechecks the actual receiving request and
current principal authority, including after asynchronous Relay reads and inside
the existing qualification transaction.

Receipt-only reading cannot qualify a new ruling, commit a principal message or
project product acceptance before the exact worker and root terminal returns.
The existing final-consumption checks remain with that same receipt decoder.

The tests use actual Runtime/event/COMMIT owners with explicit source and Relay
fixtures. The receiving-phase unit test substitutes only source acquisition and
the send, and the existing acquisition/service suites exercise their real source
and local transport composition. These checks do not prove an installed worker
grant, live account admission, actual principal judgment or product acceptance.

The separate request facet is private source preparation. Its closed selector
has a distinct MCP identity and schema, defaults off, and authenticates the exact
kernel peer/current harness grant. It uses the existing Company socket and
Runtime target projection; consultation/native-return grants cannot substitute.
If post-COMMIT qualification was unavailable, the requesting host can use its
explicitly selected current COO authority to recover only the original retained
principal reply. The existing deterministic reply key and COMMIT decoder select
that reply; the current principal generation, requester and source are rechecked.
Recovery permits only Relay reads and the existing qualification event. It never
constructs a send gateway or authorizes another COMMIT. Its local host and source
observations remain fixtures requiring installed qualification.

Installed SDK selection, capability profile and service composition still
require completion and qualification. The held Context CLI and actual sealed
source path remain prerequisites. No source package here authorizes installation,
enrollment, dispatch, deadline changes or replay of any old uncertain run.
