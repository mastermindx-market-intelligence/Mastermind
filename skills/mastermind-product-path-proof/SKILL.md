# Mastermind Product Path Proof

## Work inside the current assignment

Reuse the verified Mastermind source pin and applicable repository instructions; do
not restart full bootstrap for each observation. This method supplies no runtime,
tool grant, release approval or trade authority. Keep denied actions denied and
EFFECT_UNKNOWN on the original operation and carrier. Continue independent safe
work instead of widening access or retrying an uncertain effect. Use existing
Executive/Fabric, Agent OS, source, browser and deployment owners, not replacements.

## Define the acceptance slice

Name the persona, entry route, exact user action, expected outcome and return path.
Recover the existing acceptance contract and canonical design source. For customer
UI use the existing mastermind-design-system method when admitted; do not invent a
new token root or copy generated JSX as architecture. Paper remains design intent,
not production proof or another source of token authority.

Identify candidate revision, deployed revision where available, environment,
origin, authentication role, data freshness, viewport, theme and language. Keep a
local preview, staging and production distinct. Never access another browser
profile, session or credentials to make a failing route appear usable.

## Use the already authorized browser path

Inspect the exact approved browser/resource binding before interacting. A tool
catalog or an online host proves neither a browser grant nor successful login.
For Paper edits apply the current Paper workflow separately. If browser access is
missing, inspect source and prepared tests, but state visual/interaction proof is
unavailable; do not substitute generated screenshots or source assumptions.

## Exercise the journey and meaningful failures

1. Establish the starting state, then perform entry -> selection -> drill-down or
   edit -> save/action -> confirmation -> return where the contract requires them.
2. Verify the real consumer: persisted watchlist change, loaded dossier, chart
   selection or expected state transition. A click, request dispatch or toast alone
   does not prove persistence. Read back through the authorized owner.
3. Inspect actual before/after screenshot bytes. Check hierarchy, overflow,
   occlusion, alignment, legible axes/units, focus, target sizes and overlay escape.
   Record evidence locations and what was actually viewed.
4. Test keyboard and touch paths where applicable. Do not hide important evidence
   behind hover-only controls. Use non-color-only meaning and preserve the
   product's language-specific market-direction semantics.
5. Cover applicable dark/light, EN/ZH and desktop/mobile cells using the existing
   design contract, including 390px mobile when specified. Record untested cells
   rather than claiming complete coverage. Recompose mobile; do not squeeze or
   silently remove the decision and next action.
6. Exercise loading, empty, stale, partial, denied, error and corrected data where
   relevant. Use explicit fixtures only in an authorized test environment and
   label them. Unknown must not become zero; stale data must not appear live.
7. Collect bounded relevant console/network evidence with sensitive data removed.
   A successful HTTP response can still contain a product error. Do not suppress
   failures or restart unrelated services merely to obtain a clean screenshot.

Read [acceptance cases](references/cases.md) for concrete falsifiers.

## Return the observed result

Provide the exact revision/environment, task, state matrix, screenshots actually
inspected, interactions exercised, persistence readback, defects, and remaining
gates. Distinguish visual fidelity, functional correctness, accessibility testing
and production acceptance. Do not claim WCAG conformance, usability-study results,
performance gains or all-account availability from this bounded check. Route real
repairs through the assigned source and reverify the affected journey.
