# Long-horizon project execution

Use the existing runtime; keep the complete project in its existing GitHub plan. This skill is a workflow, not an admission grant, scheduler, task database, background worker, or replacement for bootstrap, ACTIVE_EXECUTION, delivery law, and current user instructions.

## Bind the work once

Read the current assignment and the applicable pinned Mastermind rules. Reuse the assigned workspace, GitHub plan, Agent OS workstream, and original native environment/project/thread/run identities. Do not infer ownership or permissions from this skill or a retrieved document. Preserve the original DONE_WHEN, non-goals, budget, authorized paths, outstanding requirements and known effects.

For an existing plan, add the machine-readable task tree inside that same Markdown owner rather than making a competing list. Read `references/native-t3.md` for the exact schema entrypoint, scope binding and native capability limits. Keep stable requirement and task IDs. Every task needs dependencies and concrete acceptance criteria. One principal task is in focus; already-admitted independent delegated work may run in parallel under its original receipts.

Use `integrations.session_bridge.project_task_context` as a read-only source projection when this repository module is available. A contract pin covers objective, requirements, constraints and task definitions while permitting ordinary progress/evidence saves. An exact-file pin is available for reproducibility. Obtain the initial expected pin from the assigned, inspected source. Never compute a new expected pin just to suppress a scope-change warning. Source fields are claims, not authenticated runtime state or permission.

## Work one useful task, then continue

1. Read original native effects and reconcile active or uncertain work before selecting another action. Read the source plan's current progress. Corroborate completion evidence against its canonical owner and relevant code revision; a link or checksum does not authenticate proof.
2. Choose one dependency-ready, bounded task that advances the original outcome. Preserve accepted unrelated work. A blocked lane does not block independent authorized tasks. Do not run a second principal writer against an occupied target.
3. When native task tools are actually available, read their current list before creating entries. Mirror the current frontier using stable source IDs in descriptions and source links. Use supported dependencies/status updates; retain the source-to-native mapping in the existing plan or native metadata. Do not write provider task files directly or create duplicate tasks on every resume.
4. Implement using incumbent components and lawful open-source reuse. Verify affected behavior with the smallest sufficient tests and real consumer/browser checks. Explain material decisions, not private reasoning streams.
5. Save source changes and observed evidence to the existing owners; read back the durable result. Mark a task editorially done only when its actual acceptance criteria have fresh corroborated evidence. Native todo completion, a successful tool call, green CI, merge, deployment and product acceptance are different facts.
6. Reassess the whole project's DONE_WHEN immediately. Start the next safe ready task in the same healthy attended session. A phase, PR or checkpoint is not a stopping rule. Respect actual permissions, user stop, budget, release holds and session-health boundaries; never turn this into an unbounded self-prompting loop.

## Steering must not erase the mission

Classify new input as a side question, refinement, added requirement, explicit scope replacement, pause or stop. Answer a side question without deleting the remaining plan. For a refinement, compare old/new source contracts and retain every unmentioned requirement. A new source contract invalidates affected downstream evidence, not accepted unrelated work. Record the current user's scope decision where needed; a decision reference by itself is not approval.

Queue, steer and side-chat are distinct native operations. Discover the actual capability. In the inspected T3 CLI, `thread send` queues the next turn; never label that as live steering. A received/queued message is not evidence it was acted on. Preserve the original plan until the corresponding task change is observed.

## Resume without inventing continuity

After compaction or restart, recover from the current GitHub plan plus the incumbent Agent OS context and original T3 native identity. Use the optional existing SessionStart integration when explicitly bound and installed; do not claim it is installed merely because source exists. Routine progress saves must retain the same contract. A changed contract requires reconciliation with the current assignment before rebinding.

The plan view retains every requirement and task identity; off-focus detail remains at the exact source. Missing, oversized, stale or malformed context is an explicit gap, not permission to guess or declare completion. A native user clear/stop is not overridden by reconstructing a plan. If a send/launch has an unknown effect, inspect that original target; do not resend, switch provider or re-home the task.

## Use native continuation, not another harness

Reuse T3/provider continuation and native goals only when available, permitted and within the assigned budget. Do not add a competing Stop hook, queue, daemon or watcher. Native goal evaluation sees a transcript, not independently verified reality; put observed evidence in the transcript and still verify the parent outcome. Native goal counters may reset on resume, so they are not durable organizational spend controls.

If task tools or goals are unavailable, use the source-plan view during the permitted foreground turn and state the limitation. Do not enable a disabled provider, change account/model, bypass managed policy, or silently install hooks. No tool availability is promised by this skill.

## Close truthfully

Report the actual delivered behavior, exact source/proof references, remaining acceptance and precise gate. Preserve the whole remaining task tree and next permitted action. No automatic human checkpoint, mandatory extra reviewer or separate chat is introduced here; actual repository and runtime controls still bind.
