# Continuity patterns and practical heuristics

These are original, provider-independent operating habits derived from documented behavior and the existing Mastermind owners. They are not claims about Claude or Grok's private prompts, an intelligence benchmark, or permission to keep running indefinitely.

## Keep three things distinct

The project contract defines the whole outcome. The current task defines the bounded action in focus. The native run identifies the actual effect and its result. A conversational reply, a checked todo item or a restored plan must not collapse these into a single “done” flag.

Prioritize a dependency-ready task that unlocks useful downstream work, but never displace an active principal writer or take over a live delegate merely because a ranking changes. Keep accepted unrelated work. If a source or implementation change affects a task, reverify that task and its downstream dependents; a changed implementation can invalidate proof even when the written requirement is unchanged.

Two consecutive attempts with the same task and hypothesis and no observed progress mean change the hypothesis, tactic or independent lane. Do not repeat an uncertain or denied effect. A different spelling, provider, account, queue or tool is not a legitimate recovery for that same refused action.

## Steering and interruption

A side question is not scope replacement. Explicit refinements and added requirements preserve unmentioned requirements and task identities. A replacement is a distinct user decision, not something inferred from a short new message. Pause/stop do not erase progress or authorize later automatic resume. `check_direction` validates an explicit classification; it does not pretend to understand or authenticate natural-language user intent.

Before any continuation, reconcile original native effects. A disconnected send can still have executed. One original run and its observed result are preferable to a second plausible-looking run. A blocked dependency holds that lane, not independent permitted work. User stop, pending native input, missing capability, unknown budget and exhausted budget take precedence over a keep-going instruction.

`long_horizon_guidance.advise` implements these priorities over bounded owner-supplied observations. Its result is advice with `execution_authority=false`, `native_action=NONE` and unauthenticated-observation labeling. It is not an admission engine, scheduler or proof oracle. Never pass model-authored observations off as canonical runtime facts.

## Long-lived bots: reuse the successful habit, not the entire conversation

Grok Bot's public documentation distinguishes persistent bot identity, selective memory and reusable skills/routines from a single conversation. It recommends testing a one-off task before saving a skill or routine. Adopt that sequence: demonstrate the actual workflow, capture the stable technique as a bounded skill, then use the existing authorized event/schedule owner. Do not infer that keeping all transcript text forever improves continuity.

Separate durable preferences from current project facts. Recheck time-sensitive facts, current code, original task state and pending results at their owners. Retain concise decisions and proof pointers rather than private reasoning streams. A reusable technique belongs in a skill; a project requirement belongs in the existing source plan; a run's state belongs in its runtime; credentials remain with the existing credential owner.

A wake should recover the same assignment and original effect before acting. It is not a new blank mission or permission to start another bot. Never add a Paperclip heartbeat alongside an existing Hermes/Executive schedule merely to obtain “always on” behavior. UI migration must preserve bot identity, profile-scoped memory, session lineage, stop controls, evidence and one dispatch owner.

## Bounded context

Full JSON inspection remains available. Native prompt delivery uses a frontier projection that keeps every requirement, every task ID/dependency/state, blockers, next actions and original delegated references, plus complete acceptance detail for the focused task. Off-focus acceptance detail stays at the exact source. The projection is bounded before delivery; it never silently removes a requirement to fit. A mandatory mission that still exceeds the delivery bound is an explicit context gap, not permission to guess.
