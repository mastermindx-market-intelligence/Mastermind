# Mastermind graph engineering

Free the principal to direct the product, plan ahead, resolve cross-domain decisions and accept the integrated result. Give meaningful delivery ownership to suborchestrators; give bounded execution to workers. Optimize accepted outcomes and total coordination cost, not agent count.

## Start with the existing mission

1. Recover the original objective, DONE_WHEN, current source, accepted work, live writers, unresolved effects and return destination. Reuse the existing task tree and checkpoint.
2. For governed Mastermind work, load protected `docs/sol_skills/INDEX.md` and applicable owners at one compatible SHA. Load `skills/mastermind-fabric-orchestration/SKILL.md` and only the assigned role. This skill adds working technique, not authority or a second procedure owner.
3. Inspect the actual delegation interface, ancestry and remaining grants before promising descendants. Match the environment using [T3](references/t3.md), [Hermes](references/hermes.md), or [Paperclip](references/paperclip.md). Read only the relevant reference.
4. For substantial multi-domain work, make a delegation decision before implementation. Prefer outcome-owning domain leads when they reduce principal context and coordination. Use direct execution for small work or a documented lower-overhead/access/critical-path exception.

## Build two relationships

Use **one accountable-parent tree** for responsibility and result return, and **a dependency DAG** for inputs and sequencing. A dependency does not create another boss. Preserve existing project/workstream/task/job identities; editorial node names are not Runtime IDs.

For each meaningful node, record its outcome, parent, required input revision, write scope, DONE_WHEN and integrating consumer. Add a dependency only when one result actually gates another. Keep dependency edges acyclic; represent rework as a bounded revision under the existing attempt/retry owner. Do not introduce a scheduler, task database, queue, registry, routing policy or graph execution engine.

Choose a useful shape from [graph patterns](references/graph-patterns.md): direct, pipeline, parallel work with a join, domain hierarchy, or staged investigation then execution. Combine shapes when needed. Default to the shallowest shape that gives the principal meaningful relief. Add a suborchestrator when it owns a separable domain, multiple workers or a difficult integration boundary; omit relay-only layers.

## Assign responsibility at the right level

| Function | Own | Return upward |
| --- | --- | --- |
| Principal | Product thesis, acceptance, priorities, architectural boundaries, cross-domain tradeoffs, critical path | Integrated outcome, evidence, material limitations |
| Domain suborchestrator | A complete domain outcome, decomposition, admissible child packets, local repair, integration and proof | Accepted domain result, dependency changes, reserved decisions |
| Nested suborchestrator | A substantial subdomain under the same root and narrower grant | Integrated subdomain result to its immediate parent |
| Worker | A bounded artifact, implementation, investigation or proof; ordinary local debugging | Exact artifacts, validation, effects and remaining gaps |

Delegate the result and its constraints. Let the receiving lead choose ordinary steps and repair within its grant. Do not require parent approval for every command. Keep source authorship and independently required review distinct; this skill creates no extra reviewer gate.

Workers and reviewers remain leaves unless the existing runtime explicitly admits a different coordinator/operator role. A role title, recursive prompt or skill installation cannot extend a child/depth limit. If descendant dispatch is unsupported, retain the logical decomposition and return ready packets to the admitted ancestor; that ancestor must use its real runtime parent identity. Do not fabricate ancestry or relaunch denied/uncertain work.

## Compile a compact commission

Use [commission.md](assets/commission.md) as an optional template. Include only fields needed for the task:

- Original mission and why this result matters; precise DONE_WHEN and required consumer proof.
- Existing root, actual parent, task/job/attempt when supplied, carrier and return destination. Do not invent missing runtime IDs.
- Exact source/input revisions, dependencies, accepted facts, uncertainties and relevant policy links.
- Owned paths or other write surfaces, one writer/integrator, non-goals, authority and reserved decisions.
- Existing budget/depth/concurrency/expiry constraints and whether descendant delegation is admitted.
- Expected artifact/evidence locations, compact result format, repair allowance and escalation conditions.

Send a brief plus source references, not the parent transcript or the entire organization history. Load files and domain references progressively. Keep raw logs and large outputs in their existing artifact owner. For investigations specify the question and falsifier, not a guessed conclusion.

## Admit the graph without multiplying resources

Use Executive/Fabric/Capacity and supplied harness interfaces for actual admission, placement, leases and accounting. Classify each child independently; topology or business importance does not make routine work frontier reasoning. Prefer qualified economical paid Fabric for bounded labor. Native children require a real reasoning/coordinator role under the applicable policy.

Every descendant inherits the intersection of its parent's authority, its own grant and current controls. Preserve the original root and true immediate parent. Count relevant descendants against the same conserved allowances; do not multiply a root budget per lead or reset limits with fresh identities. Reserve capacity for integration, required review and bounded repair before fan-out. Unknown capacity is not free capacity.

Start only independent ready work with compatible source custody and a supported result return. Use separate admitted workspaces or disjoint surfaces; serialize conflicting edits through one integrator. Agree shared interfaces before dependent builders diverge. Backpressure new dispatch when returned work exceeds the parents' ability to integrate it.

## Run the principal's control loop

1. Keep a small frontier: original DONE_WHEN, domain owners, critical path, accepted outcomes, decisions, blocked effects and next proof. Use [frontier.md](assets/frontier.md) inside the existing checkpoint, not a new store.
2. While leads execute, work on forward planning, product decisions, cross-domain interfaces, risk or returned integration. Do not duplicate their implementation to stay busy.
3. Consume material returns when useful. The immediate parent inspects decisive evidence and integrates its own descendants; the root receives a compact integrated summary.
4. Escalate only a reserved product/architecture decision, authority or budget gap, cross-domain conflict, invalidated acceptance, material failure or uncertain effect. Include a recommendation and impact. Keep routine debugging local.
5. After each accepted result, save/read back the material delta through the existing owner, reassess the original mission and begin the next safe phase in the same healthy session.

A useful upward update is: **outcome changed; evidence; remaining dependency; decision and recommendation if needed; next action and resource impact**. A normal update should fit in roughly 200–400 words; expand when the decision needs it. This is a communication target, not a platform or safety limit.

## Make joins and acceptance explicit

Name the join's required outputs, versions, compatibility checks and integrating owner. Distinguish required outputs from exploratory alternatives. A domain lead cannot close its outcome by forwarding unexamined child summaries. Verify the actual producer-to-consumer path and preserve unmet original obligations.

Use [result.md](assets/result.md) to return artifact identities, actual validation, known effects, unresolved facts and the next decision. Delivery, ACK, QUEUED, STARTED/RUNNING, exit, result, parent consumption, merge, installation and product acceptance are separate facts. Claim only observed facts. Static graph validity and green CI do not prove runtime admission or integrated acceptance.

## Recover without duplicate effects

Classify failures before acting: schema/configuration, capacity, transport, execution, acceptance, permission/security denial, or uncertain effect. Read the original request/attempt and target. A timeout or stale heartbeat does not establish termination. Preserve active writers, held operations and EFFECT_UNKNOWN on their original carriers.

An explicit permission/security denial ends that action; never replay it through another worker, provider, account or tool. Use existing bounded recovery only after authoritative reconciliation and actual permission. Two unchanged failures require a different hypothesis or independent lane, not another identical dispatch. Continue truly independent useful work when one lane blocks.

Before a lead stops, cancels, rotates or is superseded, account for descendants, partial artifacts and pending returns through existing owners. Save a compact continuation with exact references and DO_NOT_REDO; do not reconstruct private reasoning or clone full chat histories. A completed child does not automatically wake an idle parent. Use an actually supported return path and describe its limits honestly.

## Check whether delegation helped

Use existing receipts to assess accepted results, principal intervention, context loaded at the principal, rework, integration backlog, critical-path delay and observed cost coverage. Keep missing observations unknown. Do not claim measured time/token savings from the skill alone or build another telemetry store. Adjust hierarchy when a lead adds more relay work than it removes.

Finish only when the original assigned outcome is proven or the applicable ACTIVE_EXECUTION boundary is established. A plan, installed skill, queued worker or phase completion is not permission to abandon remaining safe work.
