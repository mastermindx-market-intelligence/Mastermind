# Choose and combine useful graph patterns

| Shape | Use when | Integration obligation |
| --- | --- | --- |
| Direct | One small result has clear inputs and proof | Commissioner consumes the result |
| Pipeline | Each stage transforms an accepted predecessor artifact | Bind each edge to an exact revision and acceptance condition |
| Parallel work and join | Independent domains can progress together | One integrator checks compatibility and the complete journey |
| Domain hierarchy | Several domains each contain meaningful parallel work | Each lead integrates descendants; principal adjudicates cross-domain effects |
| Investigation then execution | An unresolved decision prevents safe specification | Resolve uncertainty, freeze the decision, then admit implementation |

Use hierarchy for context isolation and responsibility, not a fixed ladder. A large mission can have principal → product/engineering leads → subdomain leads → workers, while a narrow repair uses principal → worker. Actual grants may permit fewer levels than the editorial plan.

## Example: an options research journey

The principal owns the original journey: identify an opportunity, understand its evidence, inspect entry/invalidation conditions, save it, and return later.

An engineering lead owns the joined data contract and persistence. It may commission bounded producer and consumer workers on disjoint paths. A product lead owns the workspace flow and states, with a component worker and interaction-proof worker when admitted. A validation lead owns point-in-time and uncertainty evidence, using distinct technical review only where required.

The engineering contract gates final UI integration, but a compatible fixture may permit earlier layout work. A fixture proves its own layer only. The UI lead returns integrated behavior evidence; the engineering lead returns exact source and contract results. The principal checks the whole saved-and-returned journey rather than every worker log.

Declare one shared-interface owner and a revision-change protocol. Invalidate only affected downstream results after a contract change. Keep unaffected accepted work. Do not make assurance a universal permission gate or allow conflicting writers merely because the graph is parallel.

## Review before dispatch

Check that each node has one accountable parent, an independent useful outcome, available inputs, explicit writer/return ownership and a checkable join. Check for dependency cycles, shared writes, unbounded descendants, root-budget multiplication, unsupported wake assumptions and missing integration capacity. Reuse an accepted validator if available; a held draft planner is not installed runtime capability.

## Recovery example

If a publisher times out while two leads are running, retain its exact operation and reconcile that target. The affected integration waits. Independent evidence analysis may continue. A new worker on another host must not republish to escape uncertainty. When the original outcome is known, its lawful owner decides whether the existing grant permits a materially changed attempt.
